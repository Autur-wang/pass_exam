Lesson 0003 · 第 2 章 操作系统组织

内核如何「手搓」第一个进程
—— init 从哪来,「鸡生蛋」的答案

🎯 对应使命:进入第 2 章。上一课你看到 shell 用 fork 造出新进程; 可 fork 必须先有一个进程才能复制。这一课回答 0002 结尾那个悬念—— 最开始那一个进程,没有父亲,它是谁造的? 答案在 kernel/main.c 与 kernel/proc.c 里。
🔁 先回忆(别往回翻 0002):新进程是靠谁产生的?……对,靠已有进程 fork 自己。 那 shell 是谁 fork 的?是 /init。那 /init 又是谁 fork 的?…… 再往上追,总得有第一个进程,而它无父可依——fork 到这里就断了链。今天补上这一环。
这节课你将能做到一件事: 讲清楚 1 号进程不是 fork 来的, 而是内核在开机末尾手工造出来的——它怎么分配、怎么被塞进一段代码、醒来后第一件事又为什么是 exec("/init")。

1 · 「鸡生蛋」问题:fork 造不出第一个进程

上一课的 fork 有个隐含前提:它复制的是「当前进程」。也就是说,fork 永远需要一个 已经存在的进程当模板。可开机的那一刻,一个用户进程都还没有——没有模板可复制。 这就是经典的「鸡生蛋」:第一个进程不可能由 fork 产生。

Unix 的解法很朴素,甚至有点作弊:既然没法「生」,那就让内核亲手「捏」一个出来。 内核不走 fork 那条路,而是直接分配一个空进程壳、往里面填一段极小的代码,再把它标成「可运行」丢给调度器。 这个开机时手工引导出第一个进程的过程,叫 bootstrapping(自举)。

📖 依据:xv6 book (rev3) 第 2 章 Operating system organization,"the first process" 一节。

2 · 看真东西:启动的最后一步是 userinit()

内核启动做的一长串初始化,都在 ../xv6-riscv-20230207/kernel/main.c 里。只看 0 号 CPU 这条主线:

13if(cpuid() == 0){
14  consoleinit();
..  // kinit / kvminit / procinit / trapinit … 一串子系统初始化
30  virtio_disk_init(); // 磁盘
31  userinit();      // ← first user process:手搓第一个进程
32  __sync_synchronize();
33  started = 1;
..}
44scheduler();        // 内核最后进入调度循环,永不返回

读法:所有硬件/内存/中断都准备好后,第 31 行 userinit() 造出第一个用户进程; 然后第 44 行 scheduler() 进入调度循环。调度器一挑中那个新进程,它就开始跑—— 内核从此不再直接「往下执行」,而是靠调度在各进程间切换。

🔎 本地对照:../xv6-riscv-20230207/kernel/main.c 第 13–44 行。

3 · 手搓现场:userinit() 逐行拆

第一个进程是怎么「捏」出来的?全在 kernel/proc.c 的 userinit()(第 232–255 行):

237  p = allocproc();            // 分配一个空进程壳（不是 fork!）
238  initproc = p;               // 记为全局的「init 进程」
242  uvmfirst(p->pagetable, initcode, sizeof(initcode));
243  p->sz = PGSIZE;             // ↑ 把 initcode[] 机器码拷进它的第一个用户页
246  p->trapframe->epc = 0;      // 用户程序从地址 0 开始执行
247  p->trapframe->sp = PGSIZE;  // 用户栈指针
249  safestrcpy(p->name, "initcode", sizeof(p->name));
250  p->cwd = namei("/");       // 当前目录设为根 /
252  p->state = RUNNABLE;        // ← 标成「可运行」,等调度器挑中

把这几步翻成人话,对照第 1 节「捏一个出来」的四个动作:

代码在干嘛为什么关键
allocproc()要一个空白进程结构凭空分配,没有父进程——这就是它和 fork 的根本区别
uvmfirst(…initcode…)把一段现成机器码拷进它的内存fork 是复制别人的内存;这里是内核直接喂给它一段代码
epc = 0设定「从用户地址 0 开始跑」因为 initcode 就被放在用户空间第 0 页的开头
state = RUNNABLE挂上「可运行」牌子它自己不会跑;要等 scheduler() 挑中才真正上 CPU

那 initcode 到底是什么?就在同一文件第 221 行,是一个写死的字节数组: 

221uchar initcode[] = {
222  0x17, 0x05, 0x00, 0x00, 0x13, 0x05, 0x45, 0x02,
...  // …一串十六进制…
228  0x00, 0x00, 0x00, 0x00
229};

这串十六进制不是乱码——它是一小段汇编编译出来的机器码,被硬编码进了内核。 注释(第 219–220 行)甚至写明了它「assembled from ../user/initcode.S」。 换句话说:第一个进程的全部代码,就是内核源码里躺着的这几十个字节。

🔎 本地对照:../xv6-riscv-20230207/kernel/proc.c 第 219–229 行(initcode[])、第 231–255 行(userinit)。

4 · 第一个进程醒来:唯一的事是 exec("/init")

那段机器码的源头 ../xv6-riscv-20230207/user/initcode.S 只有几行,做的事一目了然:

8start:
9  la a0, init          # a0 = "/init" 字符串地址
10  la a1, argv          # a1 = 参数数组
11  li a7, SYS_exec       # a7 = 系统调用号:exec
12  ecall                # ← 陷入内核,发起 exec("/init", argv)
21init:
22  .string "/init\0"

认出来了吗?第 11–12 行 li a7, SYS_exec + ecall,正是 0001 讲过的 系统调用发起方式——把调用号放进 a7,再 ecall 陷入内核。 所以第一个进程醒来后做的第一件(也几乎是唯一)事,就是 exec("/init"): 把自己整个替换成磁盘上的 /init 程序(还记得 0002 的 exec「成功不返回」吗?)。

开机 → start() 切到 supervisor 模式 → main() │ 一串子系统初始化（kinit / kvminit / procinit …） │ userinit() ← 内核「手搓」第一个进程 ┌─────────────┴─────────────┐ allocproc() 分配空壳 uvmfirst() 把 initcode[] （不是 fork！） 机器码拷进第 0 页 │ │ epc=0, sp=PGSIZE p->state = RUNNABLE └─────────────┬─────────────┘ scheduler() 挑中它 │ 它从用户地址 0 开始跑 initcode │ exec("/init") ← initcode 唯一的事 │ /init 再 fork 出 shell ── 回到 Lesson 0002 的世界

至此「鸡生蛋」闭环了:内核手工造出唯一的第一个进程 → 它 exec 成 /init → /init 用 fork 繁衍出 shell 及一切。 从第二个进程起,世界就完全交给了上一课的 fork/exec/wait。
