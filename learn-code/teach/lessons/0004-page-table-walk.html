Lesson 0004 · 第 3 章 页表 / 虚拟内存

为什么「地址 0 不打架」
—— 读懂 walk():地址翻译的心脏

🎯 对应使命:进入第 3 章。0003 结尾埋了个钩子—— userinit 把第一个进程装在虚拟地址 0,可系统里几十个进程都从地址 0 开始, 内存条只有一份,凭什么不互相踩踏?这一课回答它,并带你读懂 vm.c 里最核心的那个函数 walk。
🔁 先回忆(别往回翻 0003):userinit 里那句 uvmfirst(p->pagetable, …),把第一个进程的代码放到了哪个地址?……对,虚拟地址 0。 今天的主角,正是那个当时被我们跳过的参数——p->pagetable,进程的页表。
这节课你将能做到一件事: 打开 vm.c,读懂 walk() 那 19 行—— 讲清楚一个虚拟地址怎样被切成三段、如何逐级下钻三层页表,最后找到它对应的物理页。
🗺️ 贯穿全课的类比:小区门牌 vs 地球经纬度。 虚拟地址就像收件人写的「XX 小区 1 号楼 101 室」——好写好记,而且每个小区都能有「1 号楼 101」。 但内存条上的真实位置是全地球唯一的「经纬度」(物理地址)。 页表就是每个小区门口那本专属地址簿,负责把「1 号楼 101」翻译成真实经纬度。 于是不同小区(不同进程)都能有「1 号楼 101」却永不冲突——因为各查各的地址簿。 而 walk() 就是「查簿」这个动作:地址簿分三层(省册 → 市册 → 街道册),门牌里三段编号各查一层, 最后查出「那一行登记」——翻译就差最后一步拼接了(那一步 walk 不做,留给用它的人)。

1 · 为什么要有页表:让「地址 0 不打架」

先看 0003 里被跳过的那句(../xv6-riscv-20230207/kernel/vm.c 第 210–221 行的 uvmfirst): 

217  mem = kalloc();                         // 要一页真实物理内存
219  mappages(pagetable, 0, PGSIZE, (uint64)mem, PTE_W|PTE_R|PTE_X|PTE_U); // ← 映射到虚拟地址 0
220  memmove(mem, src, sz);              // 把 initcode 拷进这页

第 219 行第二个参数就是 0——把物理页 mem 映射到虚拟地址 0。 关键在:每个进程都有自己的一张页表(p->pagetable)。所以进程 A 的「虚拟地址 0」和进程 B 的「虚拟地址 0」, 经过各自不同的页表,会被翻译到两块不同的物理内存上。 它们不打架,不是因为代码里有什么 if 拦着,而是因为这个机制:同名门牌,各查各的地址簿。 这就是页表存在的头号理由——隔离。

(第 219 行末尾那个 PTE_U 标志表示「用户态可访问」——它是另一条隔离轴,内核页不带 U,用户碰了就出错;细节留到后续课。)

🔎 本地对照:../xv6-riscv-20230207/kernel/vm.c 第 210–221 行(uvmfirst)、kernel/riscv.h 第 341–345 行(PTE 标志位)。

2 · 一个虚拟地址长什么样:三段索引 + 一段偏移

要看懂翻译,先看懂被翻译的东西。vm.c 第 80–84 行的注释,直接画出了 RISC-V Sv39 的虚拟地址结构(Sv39 = RISC-V 这套 39 位虚拟地址分页方案的名字): 

80//   39..63 -- must be zero.
81//   30..38 -- 9 bits of level-2 index.   ← 第 1 段:查「省册」
82//   21..29 -- 9 bits of level-1 index.   ← 第 2 段:查「市册」
83//   12..20 -- 9 bits of level-0 index.   ← 第 3 段:查「街道册」
84//    0..11 -- 12 bits of byte offset.    ← 页内偏移:不翻译
什么是 PTE? PTE(Page Table Entry,页表项)= 页表这一页里的一格,8 字节, 存着「下一级页表(或最终数据页)的物理页号」外加几个标志位(如 PTE_V 有效位)。 一张页表正好是一页 = 4096 字节 = 512 个 PTE(riscv.h 第 331 行:pagetable_t 是指向 512 个 pte_t 的指针)。

为什么是「三段各 9 位 + 12 位偏移」?两个数字算一下就懂:

数字来自为什么
低 12 位
不翻译		PGSIZE=4096=212一页 4096 字节,低 12 位刚好表示「这一页里的第几个字节」。翻译只负责找到是哪一页,页内偏移原样保留
每段 9 位一页装 512=29 个 PTE9 位索引(0..511)刚好点到 512 个 PTE 里的一个,一段索引对应一级页表
共 3 段9×3 + 12 = 39三段 9 位管高 27 位 + 12 位偏移 = 39 位虚拟地址,正是 Sv39 的「39」

riscv.h 里那个 PX(level, va) 宏,就是「从 va 里抠出第 level 段那 9 位」的工具: 

335#define PGSIZE 4096   // bytes per page
336#define PGSHIFT 12    // bits of offset within a page
355#define PXMASK 0x1FF  // 9 个 1,用来只留最低 9 位
356#define PXSHIFT(level) (PGSHIFT+(9*(level)))   // level2→30, level1→21, level0→12
357#define PX(level, va) ((((uint64)(va)) >> PXSHIFT(level)) & PXMASK)

翻成人话:PX 把 va 右移到该级的位置,再和 0x1FF 做与运算,只留下那 9 位,得到这一级在页表里的下标。

🔎 本地对照:../xv6-riscv-20230207/kernel/vm.c 第 80–84 行、kernel/riscv.h 第 330–336、355–357 行。

3 · walk():软件版 MMU 的那 19 行

正常情况下,「切地址、逐级查表」是 CPU 里一个叫 MMU(Memory Management Unit,内存管理单元)的硬件自动做的。 而 walk() 是它的软件复刻——内核有时需要自己走一遍页表,就用 C 把 MMU 干的活写了出来。读懂这 19 行,你就读懂了地址翻译的心脏。

先建立「树」的画面: 三级页表是一棵树。前两级(level 2、level 1)的 PTE 指向下一级页表页(树枝); 最后一级(level 0)的 PTE 才指向真正的数据页(树叶)——所以它叫叶子 PTE。查表就是从树根往下走到某片叶子。 
85pte_t *
86walk(pagetable_t pagetable, uint64 va, int alloc)
87{
88  if(va >= MAXVA) panic("walk");   // 地址越界直接崩
89
91  for(int level = 2; level > 0; level--) {   // ← 只跑 level 2、1 两圈
92    pte_t *pte = &pagetable[PX(level, va)];  // 抠出本级 9 位索引,定位一个 PTE
93    if(*pte & PTE_V) {                     // 这一格有效?(指向下一级页表)
94      pagetable = (pagetable_t)PTE2PA(*pte); // 顺着它下探一层
95    } else {
96      // —— alloc=1 时在这里现建一页新页表 —— 本课跳过,留给 0005 ——
97      if(!alloc || (pagetable = (pde_t*)kalloc()) == 0) return 0;
99      *pte = PA2PTE(pagetable) | PTE_V;
100    }
101  }
102  return &pagetable[PX(0, va)];   // ← 第 3 段(level0)索引在这里才用上!
103}

逐句读:

行在干嘛
91for(level=2; level>0; level--) —— 只跑 两圈(level 2、level 1),下钻两级树枝
92&pagetable[PX(level,va)] —— 用本级 9 位索引,在当前页表页里定位一个 PTE。这就是「查地址簿这一层」的本体
94PTE2PA(*pte) —— 把 PTE 里存的物理页号还原成下一级页表的地址,顺指针下探一层
102循环结束后 pagetable 已指向最底层(level0)页表页;return &pagetable[PX(0,va)] 才用上第 3 段索引,取出叶子 PTE 的地址
⚠️ 最容易数错的地方: 虚拟地址明明有 三段索引,循环却只跑 两次。 别慌——三段 = 两次循环(level 2、1) + 一次 return(level 0)。第三段不是丢了,是在最后 return 那行用的。

还有个关键点常被忽略:walk 返回的是「叶子 PTE 的地址」这个指针,它并没有算出最终的物理地址。 「从 PTE 里读出物理页号、再拼上低 12 位偏移」是调用者的事。看 walkaddr(第 108–126 行)怎么接手: 

117  pte = walk(pagetable, va, 0);   // 复用 walk(alloc=0:只查不建),拿到叶子 PTE 指针
...  // (检查有效位 / 用户位 …)
124  pa = PTE2PA(*pte);            // ← 这一步才把 PTE 读成物理页基址
125  return pa;                     // (调用者再拼上低 12 位偏移,就是最终物理地址)

对回类比:walk 把你送到「街道册里的那一行登记」;从登记里读出「楼栋经纬度」(PTE2PA)、 再贴上「室号」(低 12 位),是 walkaddr 这类用它的人做的。分工清楚,才不会把两个函数的活记混。

虚拟地址 va（Sv39，39 位） ┌───────┬───────┬───────┬────────────┐ │ 段①9位│ 段②9位│ 段③9位│ 偏移 12 位 │ └───┬───┴───┬───┴───┬───┴─────┬──────┘ │ │ │ │ PX(2,va) PX(1,va) PX(0,va) └─ 不翻译，最后拼上去 │ │ │ ▼ ▼ ▼ [根页表]→[中间页表]→[叶子页表] 循环① 循环② return 那行 │ 取出「叶子 PTE 的地址」← walk() 到此为止 │ walkaddr: PTE2PA(*pte) 读出物理页基址 + 偏移 = 物理地址
