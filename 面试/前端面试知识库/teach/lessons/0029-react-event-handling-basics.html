React 怎么处理事件

这节课要回答一个很具体的问题:当你在 JSX 里写下 onClick={handleClick} 时,React 在背后做了什么与原生 addEventListener 不一样的事;以及鼠标、输入、表单、焦点、键盘这几类高频事件,分别该用哪个 handler、怎么给它起名字、要不要给它传参数。

开课前先回忆一下:第 21 课梳理"React 面试到底叠加了哪些新知识点"时,把"合成事件"列成了叠在原有五道关卡外壳上的 React 专属考点之一。再往前翻一步,回忆你自己写原生 JavaScript 时怎么给一个按钮绑定点击事件——大概是 element.addEventListener('click', ...) 这样一行代码。这节课要做的事,就是把这两条线接起来:React 里的 onClick={...} 和这行原生代码,到底是不是同一件事。

一、合成事件与事件委托:React 事件系统和原生 JS 有什么不一样

原生 JavaScript 里,给一个元素绑定点击事件通常是这样:

原生 JavaScript

document.getElementById('btn').addEventListener('click', (event) => {
  console.log('Clicked!');
});

React

<button onClick={() => console.log('Clicked!')}>点击我</button>

写法上看起来只是把监听器搬进了 JSX 属性里,但 React 在背后多做了两件事。第一,它把原生事件包了一层,变成一个叫 SyntheticEvent 的标准化对象,目的是在不同浏览器之间保持一致的行为,同时对性能做优化。第二,React 用的是事件委托——它不会给每一个写了 onClick 的元素单独挂一个监听器,而是把事件统一绑定在 React 应用的根节点上(不是 document 根节点,也不是逐个元素),再靠冒泡把动作分发给对应的处理函数。

用户点击/按键原生浏览器事件
→
冒泡到应用根节点不是逐元素绑定
→
包装成 SyntheticEvent跨浏览器一致 + 性能优化
→
分发给对应的 onClick你写的处理函数

这个 SyntheticEvent 会作为第一个参数传给你的处理函数,多数场景下可以把它当成原生浏览器 Event 对象来用;需要真正的原生事件时,可以通过 event.nativeEvent 拿到它:

function handleClick(event) {
  console.log(event); // React SyntheticEvent
  console.log(event.nativeEvent); // 原生浏览器事件
  console.log(event.target); // <button>...</button>
}

<button onClick={handleClick}>点击我</button>;

延伸阅读见 react.dev 的响应事件一文。

二、写事件处理程序:命名规范与传参方式

React 里的事件处理程序,说到底就是响应用户交互(点击、按键、表单提交、鼠标移动)的普通函数。手册里出现的例子——handleClick、handleSubmit、handleKeyPress——用的是同一套命名习惯:"handle" 加上事件动作,对应到 JSX 属性上的 onClick、onSubmit,一眼就能看出"谁触发、谁处理"这层对应关系。

更值得记住的是怎么把处理函数接到 JSX 属性上,这里有两种写法,取决于你要不要额外的参数:

// 不需要额外参数、只需要 event 对象本身:直接传函数引用
<button onClick={handleClick}>点击我</button>

// 需要在 event 里取具体字段、或者要塞进额外参数:包一层箭头函数
<input onChange={(event) => setValue(event.target.value)}>

第一种是把函数本身(不是函数调用的结果)交给 React,等事件真的发生时再由 React 去调用;第二种是用一个箭头函数包一层,在里面按需要访问 event 或者塞进别的参数。下面讲鼠标、输入、表单、焦点、键盘几类具体事件时,这两种写法会反复出现,先把这条判断标准记住,再看具体例子会更容易对上号。

三、鼠标事件:面试最常问的几个

鼠标事件处理程序接收 MouseEvent 参数,用户点击、悬停时触发。

事件什么时候触发面试出现频率
onClick元素被点击(鼠标按下 + 抬起)常用
onMouseEnter鼠标进入元素有时
onMouseLeave鼠标离开元素有时
onMouseOver鼠标进入元素或其子元素有时
onMouseOut鼠标离开元素或其子元素有时
onMouseDown鼠标按钮被按下很少,多数场景用 onClick
onMouseUp鼠标按钮被释放很少,多数场景用 onClick
onDoubleClick元素被双击很少

这份列表里最值得记住的一组对比是 onMouseEnter/onMouseLeave 和 onMouseOver/onMouseOut——前者不冒泡,后者会冒泡。如果被问到二者区别,答案就是这一条。另外,悬停样式(比如鼠标进入时变色)最好用 CSS 的 :hover 伪类去做,CSS 能完成的事没必要上 JavaScript。

四、输入事件:onChange 与 onInput 怎么选

输入事件处理程序接收 InputEvent 参数,可以加到 <input> 和 <textarea> 上:

function Foo() {
  const [value, setValue] = useState('');

  return (
    <input
      onChange={(event) => setValue(event.target.value)}
      value={value}
      placeholder="Type here"
    />
  );
}

这里有两个容易混的事件:onChange(值发生变化时触发)和 onInput(用户输入数据时触发,行为上类似 onChange,大多数场景直接用 onChange 代替就够)。真正需要记住的是它们和浏览器原生事件的对应关系不是字面意思那样直接——对 <input type="text"> 这类元素,浏览器原生的 'change' 事件通常只在控件失去焦点时才触发一次;但 React 的 onChange 故意做成了更像原生 'input' 事件的行为,每次按键都会触发。

特性onChange(React)原生 'input' 事件
每次按键都触发?是(React 特意这样设计)是
在 IME(中文/日文/韩文输入法)上触发?否,只在提交时触发一次是,每个字符都触发
适用于 contenteditable?否是

面试期间如果拿不准该用 onChange 还是 onInput,答案是:用 onChange。

五、表单事件、焦点事件与键盘事件:剩下三类速览

表单事件(onSubmit、onReset)只适用于 <form> 元素。onSubmit 接收 SubmitEvent 参数,只在表单内的提交按钮触发时才会触发;onReset 接收通用 Event 参数,对应重置按钮。由于大多数场景下你在写的是没有服务端配合的单页应用,通常需要在 onSubmit 里调用 event.preventDefault(),否则点击提交会触发整页刷新,把 React 应用打断:

function SimpleForm() {
  const [input, setInput] = useState('');

  function handleSubmit(event) {
    event.preventDefault(); // 阻止页面重新加载
    alert(`表单提交内容:${input}`);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={input}
        onChange={(e) => setInput(e.target.value)}
      />
      <button type="submit">提交</button>
    </form>
  );
}

焦点事件(onFocus、onBlur)适用于能接收焦点的元素,比如 <input>、<textarea>、<select>、<button>,参数是 FocusEvent。和悬停样式一样,焦点样式也优先用 CSS 的 :focus 伪类。给一个本来不可聚焦的元素(比如 <div>)加上 tabIndex,能让它也接收焦点、变得可点击,但这主要用在自定义设计系统组件上;面试期间大多数情况下按默认可聚焦的那批元素处理就够。

键盘事件(onKeyDown、onKeyUp,以及已经弃用的 onKeyPress)接收 KeyboardEvent 参数。onKeyDown 在按键被按下时触发,按住不放会持续触发;onKeyUp 在按键释放时触发,常用来检测"最终"输入完成。手册给的示例本来用的是已弃用的 onKeyPress,按最佳实践改成 onKeyDown 之后是这样:

function handleKeyDown(event) {
  if (event.key === 'Enter') {
    alert('Enter key pressed!');
  }
}

<input type="text" onKeyDown={handleKeyDown} />;

event.key、event.code 和已经弃用的 event.which/event.keyCode 看起来很像,面试只需要记住一条:用 event.key。除此之外,event.shiftKey、event.ctrlKey 这类修饰键状态也能从同一个 KeyboardEvent 上读到,完整属性列表见 MDN 上 KeyboardEvent 的实例属性。React 中处理键盘事件的几条最佳实践:优先用 onKeyDown 而不是已弃用的 onKeyPress;优先用 event.key 而不是已弃用的 event.which/event.keyCode;需要时调用 event.preventDefault()(比如阻止 Enter 提交表单);给不可聚焦的元素加 tabIndex 才能收到键盘事件;认真处理好键盘导航这类可访问性细节。多数面试场景其实不需要直接处理键盘事件——检测输入变化用 onChange/onInput 更直接,检测 Enter 提交表单用 <form> 的 onSubmit 更可靠。

六、关键定义

合成事件(SyntheticEvent)
React 对原生浏览器事件包一层之后得到的对象,统一了不同浏览器的行为差异,同时对性能做了优化;多数场景可以把它当作原生 Event 来用,还能通过 event.nativeEvent 拿到真正的原生浏览器事件。避免把"合成"理解成"React 自己发明了一整套跟浏览器无关的新事件"——它包着的核心还是原生事件,只是多套了一层统一的外壳。
事件委托
React 不会给每个写了 onClick 的元素单独挂一个监听器,而是把事件统一绑定在 React 应用的根节点上,靠事件冒泡把动作分发给对应的处理函数,借此换取性能。避免以为这需要你自己在父元素上手写一个大 if/else 去判断"到底是谁触发的"——分发这一步是 React 在框架层面做完的,你写的 onClick 依旧是挂在具体元素上的语法,写法上感觉不到委托的存在。

现实中怎么用。面试时被要求实现一个交互组件(下拉菜单、表单、评分组件),写每个事件处理函数之前先问自己两件事:这个 handler 要不要访问 event 里的具体字段或者带额外参数(决定是直接传引用还是包一层箭头函数),这个交互要不要考虑冒泡差异(比如悬停效果该用 onMouseEnter 还是 onMouseOver)。这两条问清楚,handler 的写法基本就不会跑偏。

一个容易踩的误区:把鼠标事件处理程序加到非交互元素上,或者用 <a href="#" onClick={...}> 模拟按钮。出于可访问性考虑,onClick 这类处理程序应该只加在 <button>、<a>、<input> 这样原生就能接收焦点和触发的交互元素上;加到 <div>、<span> 这类元素上,屏幕阅读器用户没法通过键盘或辅助工具触发这个交互。手册给的实际建议是:该用按钮的场景就直接用 <button onClick={...}>,配合 CSS 调整外观,而不是给一个看起来能点、实际不是交互元素的节点硬套一个 onClick。

今天就做的一件事:挑一个你最近写过的表单或按钮组件,把它的每个事件处理函数过一遍这节课的判断顺序——名字是不是"handle + 动作"这个模式、要不要额外参数(决定要不要包一层箭头函数)、如果是表单提交有没有调用 event.preventDefault()。三条对完,基本能揪出命名或传参上的小毛病。

带走这一条:React 用合成事件统一包了一层原生事件、又把监听器委托到应用根节点上,这解释了它为什么能跨浏览器一致又相对省性能;写处理函数时记住"handle + 动作"这套命名习惯,以及"要不要额外参数决定直接传引用还是包一层箭头函数"这条判断标准,鼠标/输入/表单/焦点/键盘该用哪个具体 handler,基本可以从"是否冒泡""要不要贴近原生语义"这两个角度推出来,不需要死记硬背整张事件列表。

七、自测题

Q1:关于 React 的事件委托机制,下面哪个说法最准确? (A) React 给每一个带 onClick 的 DOM 元素单独挂一个 addEventListener,写法和原生完全一样 (B) React 把事件统一绑定在应用的根节点上,依靠事件冒泡分发给对应的处理函数,而不是给每个元素单独挂监听器 (C) React 把所有事件都绑定在浏览器的 document 根节点上,这一点和绑定到应用根节点没有区别

正确答案是 (B)。React 用事件委托换性能,监听器绑在应用的根节点,靠冒泡分发给具体的处理函数。(A) 错在"和原生完全一样"——如果真是逐元素单独绑定,就不需要"委托"这个说法了,那正是 React 想省掉的开销;(C) 混淆了"应用根节点"和"document 根节点"这两个不同的位置,这节课强调的正是事件绑定在应用根节点,不是 document 根节点。

Q2:下面哪个关于 onChange 和 onInput 在 React 里的说法准确? (A) 面试中如果不确定该用哪个,优先选 onChange——它在 React 里被设计成更接近浏览器原生 input 事件的行为,每次按键都会触发 (B) React 的 onChange 和浏览器原生 change 事件完全一样,只在输入框失去焦点时才触发一次 (C) onInput 在 React 里已经被弃用,和已经弃用的 onKeyPress 属于同一类,不应该再使用

正确答案是 (A)。React 特意让 onChange 表现得像原生 input 事件,每次按键都触发,这正是这节课强调的关键差异点。(B) 错在混淆了"React 的 onChange"和"浏览器原生 change 事件"——原生 change 通常要失焦才触发,但 React 的 onChange 不是这样;(C) 是编造的说法,手册没有说 onInput 被弃用,只是建议大多数场景用 onChange 代替它,真正弃用的是 onKeyPress 这类按键事件,和 onInput 是两件不同的事。
