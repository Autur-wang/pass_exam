表单错误处理与校验策略

前面几课解决的是"表单的状态该怎么存"。这节课换一个问题:用户输入错了、或者提交之后后端拒绝了这次请求,页面该在什么时机、用什么方式让用户知道。源材料把这件事拆成了好几种可以叠着用的校验策略——这节课要理清它们分别拦截什么、什么时候该用哪一种,以及为什么"前端已经校验过了"从来不是后端可以省事的理由。

回忆一下上一课:面对地址、个人资料这类嵌套数据,建议是用一个对象干净地管理相关字段,复杂表单的最佳实践里还提到一句——"利用 React Hook Form 或 Formik 等表单库来简化验证和状态管理"。当时这句话只是列在最佳实践清单里,没有展开;这节课要具体拆开的,正是"简化验证"这半句到底指什么,以及在没有库的情况下,校验本身要解决的是哪几层问题。

一、验证要解决的问题:不是"对不对",是"什么时候查、谁来查"

源材料给验证策略这一节的开场很直接:处理错误和验证用户输入,是让 React 表单体验流畅的关键——验证确保用户在提交前输入正确的数据,从而防止无效条目、减少后端错误。这句话里藏着一条时间线:数据从用户打字开始,经过点击提交,再到后端收到请求,中间至少有三个可以拦截错误的时间点。这节课接下来按这条时间线,依次讲提交时校验、即时校验、服务端校验联动三种策略,最后再看它们在面试里合起来考什么。

二、提交时校验:最朴素、但离不开的一层

最基础的做法是用 useState 存一个 error,在 handleSubmit 里手动检查:字段是空的就 setError('Email is required') 并 return,通过校验就把 error 清空再继续提交流程。这个策略只在用户点击"提交"那一刻才检查,好处是简单、容易读懂,足以覆盖"必填项漏填"这类基本情况——但用户在输入框里打字的过程中,不会收到任何反馈,只有点了提交才知道错在哪。

浏览器自己也提供了一层等价的能力,而且完全不需要写 JS:给 <input> 加上 required、minLength、pattern 这几个原生属性,浏览器会在表单尝试提交时自己拦下不合规的输入。required 确保字段填了、minLength 限制长度、pattern 直接在 HTML 里写正则——三者的共同点是浏览器原生实现,不需要额外的 JavaScript 校验逻辑就能工作,性能上更好。这两种做法(useState 手动检查和 HTML5 原生属性)都属于"提交那一刻才拦截"的范畴,区别只是要不要自己写判断逻辑。

三、即时校验:让用户在打字过程中就知道错在哪

对邮箱、电话号码、密码这类结构化字段——格式本身是可以用规则描述的——正则表达式校验更合适。源材料给的例子是一个 validateEmail 函数,用 /^[^\s@]+@[^\s@]+\.[^\s@]+$/ 检查邮箱格式是否合法。这种基于规则的检查天然适合"边输入边提示":把同一个校验函数绑定到 onChange 而不是只在提交时调用一次,用户每敲一个字符就能重新判断一次格式对不对,不必等到点了提交才发现"邮箱少了个 @"。这正是源材料强调的一点——为用户提供实时反馈,而不是把所有反馈都拖到提交那一刻才给。

四、校验规则变多以后:交给库统一管理

手写的 if 判断在字段一多就会散得到处都是,这时候 React Hook Form 这类库的价值就出来了。它的核心机制是用 register 把校验规则(required、minLength 及对应的错误文案)直接挂在字段配置上,再通过 formState.errors 统一读取当前有哪些字段没通过。源材料点出的两个关键收益:第一,它靠 refs 而不是 state 追踪输入,大幅减少了重新渲染;第二,这套内置的错误收集机制,让大表单也能保持整洁,不用为每个字段单独维护一个 error 状态变量。上一课最佳实践清单里和 React Hook Form 并列提到的 Formik,在这节源材料里没有展开代码示例,但定位是同一类——用声明式的规则配置取代手写判断,而不是另一套完全不同的思路。

五、服务端校验联动:客户端校验管不到的那部分

即便前面几层都通过了,请求真正发到后端之后,还有一类错误只有服务端才知道——比如这个邮箱已经被别人注册过。源材料给的模式是:用 fetch 把数据发出去,try/catch 包住整个请求;如果 response.ok 为假,就 throw new Error(data.message),在 catch 里把这条错误消息塞进 setError 显示出来。这一层要解决的不是"用户体验",而是安全风险——源材料原话是"防止安全风险(例如,黑客绕过客户端验证)"。客户端的所有校验都跑在用户自己的浏览器里,理论上可以被绕过(比如直接拿接口地址发请求,不经过页面上的任何一个 input),所以无论前端做得多严密,服务端都要把同一批规则再检查一遍。

六、面试官通过这一节在考什么

源材料把面试关注点收在几句话里,合起来看是一份检查清单:简单表单里受控和非受控输入都说得过去;表单要包在 <form> 标签里,借助浏览器原生的提交事件;能用 HTML5 校验的地方尽量用,减少重新渲染、换来更好的性能;错误消息要写清楚,指导用户具体该怎么改,而不是只说"输入有误";仅有客户端校验是不够的,服务端校验是防安全漏洞必须补上的一环;如果题目允许用第三方库,React Hook Form 是很好的加分项,能同时兼顾功能和性能。面试官问"这个表单你会怎么做校验",实际在听的是你能不能把这几层分清楚,而不是背出某个 API 的参数名。

七、关键定义

表单校验策略
按"什么时候检查、检查什么、由谁来检查"划分出的一组做法——提交时用 state 或 HTML5 属性拦下明显错误,即时用正则给结构化字段实时反馈,服务端在请求到达之后再做一次不能被绕过的复核。避免把"选一种校验策略"当成互斥的单选题——多数真实表单是这几层叠着用,不是二选一。
服务端校验
请求提交之后,由后端对数据再检查一遍,并通过 API 响应把结果(通过或具体错误消息)告诉前端,是防止客户端校验被绕过的最后一道关卡。避免把"页面上已经写过校验逻辑"当成后端可以省掉这层检查的理由——两者防的是不同的风险,一个管体验,一个管安全。

现实中怎么用。一个普通的注册表单,三层可以这样搭:邮箱和密码输入框先挂 required、minLength 这类 HTML5 属性做最低成本的拦截;邮箱格式再用正则在 onChange 里即时提示,减少用户提交后才发现"格式不对"的来回;点击提交时用 state 或 React Hook Form 的 formState.errors 做一次统一检查,拦住明显没填的字段;真正提交后,像"用户名已被占用"这种只有后端才知道的错误,再通过 fetch 的返回结果显示出来。三层各管一段,不是选一层就够。

一个容易踩的误区:把"客户端校验都通过了"当成"这批数据一定合法"。客户端的所有校验——不管是手写的 if 判断、正则,还是 React Hook Form 的规则配置——都运行在用户自己的浏览器里,理论上可以被绕过,比如直接对接口发请求而不经过页面上的表单。源材料专门点出这一点是为了防止"黑客绕过客户端验证"这类安全风险,所以服务端必须自己再检查一遍,不能因为前端已经写了校验逻辑就假设数据是干净的。

今天就做的一件事:找一个你写过或练习过的表单,把它现在实际拥有的校验层写下来——有没有即时反馈?提交时拦截了哪些情况?后端返回的错误有没有显示给用户?如果三层里缺了一层,挑最容易补的那一层动手加上,而不是同时重写整个表单。

带走这一条:表单校验不是"选一种技术"的问题,是分层配合——即时校验优化打字时的体验,提交时校验拦下明显错误,服务端校验兜住安全底线;三层各自解决不同的问题,谁也替代不了谁。

自测题

Q1:关于"正则表达式校验"和"提交时的 state 校验",下面哪个说法最准确? (A) 两者本质上是同一种做法,正则表达式只是换了一种写法 (B) 正则表达式适合校验邮箱、电话这类结构化字段的格式,可以绑定到输入过程中提供实时反馈;state 校验通常只在提交那一刻检查,对"是否为空"这类简单规则不需要用正则也能表达 (C) 正则表达式只能写在服务端代码里,不能出现在浏览器端的 React 组件中

正确答案是 (B)。正则适合有固定格式的结构化字段,并且天然可以绑定到 onChange 做实时反馈;而基础的 state 校验通常只在 handleSubmit 里跑一次,查的多是"填了没填"这类不需要正则的简单规则。(A) 忽略了两者在触发时机和适用场景上的差异,不是同一件事换了个写法;(C) 是编造的限制——源材料给的 validateEmail 函数就是直接写在浏览器端的 React 组件里的。

Q2:为什么"仅有客户端校验"不足以保证数据安全?下面哪个说法最准确? (A) 因为用户可以绕过前端页面,直接向后端接口发起请求,跳过页面里写的所有校验逻辑,所以后端必须自己复核一遍 (B) 因为浏览器里运行 JavaScript 校验函数的速度比后端校验慢很多倍,拖慢了整体性能 (C) 因为 React 组件里的 state 一旦页面刷新就会重置,校验规则会跟着丢失

正确答案是 (A)。源材料把这一点说得很直接——服务端校验是为了"防止安全风险(例如,黑客绕过客户端验证)",客户端的检查完全可能被跳过。(B) 把"校验速度"和"校验能否被绕过"这两个不相关的问题混在一起,性能不是这里要解决的安全问题;(C) 提到的现象(state 刷新后重置)本身是真的,但这和"是否需要服务端复核"没有因果关系,也不是源材料给出的理由。

主推资源

本节多次提到的两个表单库,源材料把它们并列推荐为"简化验证和状态管理"的选择,建议直接去官网翻一下各自的校验配置怎么写:

  • React Hook Form —— 本节配了完整代码示例的表单库(Formik 这节只提到名字,没有配套代码),register + formState.errors 的用法可以在官网文档里找到更完整的版本。
  • Formik —— 源材料在复杂表单最佳实践里与 React Hook Form 并列提到的另一个表单库,定位类似,官网上有独立的校验方案说明。

有任何不清楚的,回到会话里问你的 AI 老师——可以让老师用 ELI5 讲清"为什么前端都校验过了,后端还要再查一遍",也可以让老师给你出一个具体表单场景,让你现场说出该怎么分层设计校验。
