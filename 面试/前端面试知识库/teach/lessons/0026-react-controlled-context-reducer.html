受控组件、Context、Reducer 怎么选

state 字段本身怎么组织,上一课已经讲过了。这一课往前走一步:当状态要跨出一个组件、被别的组件读到或改到时,你有三条常见的路可以走——把它做成受控组件交给父组件、放进 Context 让整棵子树共享、或者用 Reducer 把变化收敛成 action。这节课要回答的问题是:这三条路各自解决什么问题、面试官在设计题或白板题里怎么追问"你为什么选这个而不是另一个"。

回忆一下上一课:状态怎么构建,讲的是尽可能保持状态本地化、把相关状态组合成一个对象、用单个 status 字段避免矛盾状态、派生值而不是额外存一份冗余状态;重置状态,讲的是给组件的 key 属性换一个新值,强制 React 卸载重建。这些都是"一个组件内部,state 字段怎么设计"层面的问题。这节课不重复这些——它们已经解决了。这节课处理的是下一层问题:这份 state 该不该交给父组件控制、该不该放进 Context 让全树共享、该不该用 Reducer 集中处理变化,这是三个独立的决定,分别对应"谁控制"、"谁能读到"、"怎么变化"三条不同的轴。

受控 / 非受控谁控制这个组件先本地 state,需要协调再提升
Context谁能读到这份数据跨很多层共享,但别用于高频更新
Reducer状态怎么变化变化路径复杂、多来源才需要

一、受控组件与非受控组件:先问"谁在替它做决定"

源文件先提醒一句:"受控"和"非受控"这两个词不是严格的技术定义,而是一种理解组件如何跟父组件交互的方式。一个受控组件的行为完全由它的 props 决定,而不是由自己的本地 state 决定——父组件掌握完全的控制权;一个非受控组件在内部自己管理 state,独立于父组件,父组件没办法直接改动它的状态。

类型谁控制状态?优点缺点
受控父组件,通过 props灵活,容易跟其他组件协调需要更多 props / 配置
非受控组件自己,通过本地 state更容易用,所需 props 更少灵活性较低,更难协调

源文件特别点出一个容易搞混的地方:非受控组件的传统定义只针对表单 <input> 这类元素,争的是"状态存在 DOM 里还是由 React 控制";但现代定义把"非受控"的范围扩大到了任何组件——不限于表单输入。大多数组件也不是非黑即白的"严格受控"或"严格非受控",而是两者混合,一个推荐的做法是先从本地 state(非受控)起步,只有真的需要协调时才把状态往上提升。

源文件举的例子是手风琴(accordion):在营销页的 FAQ 区块里,每个手风琴条目自己管理"展开/折叠",非受控版本就够用,不需要父组件插手;但在仪表盘或详情页里,手风琴条目往往要根据用户在别处的操作联动展开或折叠,这时就需要把展开状态提升成受控的。同一种组件,该不该受控取决于"父组件到底需不需要插手",不是组件类型本身决定的。

二、上下文(Context):谁都能读到,但代价也不小

Context 用来管理需要被后代组件访问的全局或共享数据,不需要一层层手动往下传 props。它通常跟 state 配对,放在应用顶层,让主题、身份验证之类的应用级数据在整棵树里都能拿到。有一点必须记住:Provider 的 value 一旦变化,所有用了 useContext(...) 的后代组件都会重新渲染,不管它们实际关心的是不是变化的那一部分。

源文件列了五个 Context 的陷阱,这些陷阱合起来解释了为什么它是"更容易、但不一定是最佳"的共享数据方式:

  • 不可静态分析:props 是显式传给组件的,Context 是运行时才动态提供的,构建期没法轻易确认一个组件到底拿不拿到它需要的 Context,出问题往往要等应用跑起来才发现。
  • 可能导致不必要的重新渲染:Provider 的值一变,所有消费者都会重渲染,哪怕它们不关心变化的那部分——Provider 里放大对象或频繁更新时,这会变成性能问题。
  • 易加难删:加一个 Context 很方便,但项目大了以后想删掉或重构它会很麻烦,子组件可能悄悄依赖着它,静态分析工具也标不出这种依赖。
  • 不该用于频繁更新的状态:表单输入、动画、搜索框打字这类高频变化的状态不适合放进 Context——应该留在本地 useState / useReducer 里,只在必要时才更新 Context,减少不必要的渲染。
  • 别把太多数据塞进一个 Provider:大量不相关的数据堆在同一个 Provider 里,会放大"不必要重新渲染"的范围,也让状态更难管理——应该按关注点拆成多个 Provider(比如身份验证、主题、通知各自一个)。

源文件也给了一份典型用例清单,方便判断"这种数据是不是 Context 该管的":主题(深色模式等)、当前登录用户、语言与本地化、路由库内部的当前路由、通知/Toast 的显示与关闭、全局的模态框开关状态、跨界面同步的用户偏好设置,以及配合 useReducer 一起管理应用级的复杂状态。

三、Reducer:什么时候真正用得上

应用规模变大后,状态层面会出现三类麻烦:状态转换的方式成比例、甚至指数级增加;更新状态的触发点分散在很多地方(UI 各处、后台事件、命令面板等);本该一起变化的状态字段,在 UI 不同角落的处理逻辑却不一致。应对这类麻烦的一种方式,是把所有可能的变更合并成一组"操作(action)",再把"收到某个操作后 state 该怎么变"的逻辑统一放进一个函数里。

React 里的 reducer 就是这样一个函数:接收当前 state 和一个 action,依据这个 action 返回新的 state。它遵循 Redux 模式,通常配合 useReducer 使用——对 state 的所有改动都必须经过一个 action,不能直接改 state 本身。

const newState = reducer(currentState, action);

function reducer(state, action) {
  switch (action.type) {
    case 'INCREMENT':
      return { count: state.count + 1 };
    case 'DECREMENT':
      return { count: state.count - 1 };
    default:
      return state; // 操作未知,原样返回当前状态
  }
}

源文件点出三类真正用得上 reducer 的场景:复杂的多步骤表单(多个步骤或相关字段互相牵连,reducer 把提交、校验、步骤导航的逻辑集中到一处);状态驱动的 UI(模态框、通知、下拉菜单这类被多处触发、共享同一份状态的 UI 元素);需要明确转换的有限状态机(身份验证流程、多步向导这种状态数量有限但转换规则明确的流程)。它的好处包括:逻辑集中带来的可读性、可以在顶部加一行 console.log 打印每次 action 因此容易调试、纯函数意味着不依赖 UI 环境就能单独测试。源文件也提醒一句:reducer 本身不该有副作用,同样的输入必须返回同样的输出,而且要通过 Context 管理非本地状态时,useReducer 只是可用选项之一,还有 Redux、Zustand、Jotai 这类更成熟的替代品。

四、面试官怎么追问"该用哪个"

源文件专门有一节写"面试需要了解的内容",核心态度出乎意料地保守:因为面试里的 UI 编程题通常很小,状态大多能放在顶层,大多数子组件应该是无状态的、只作为 props 接收数据;子组件自己持有 state 的场景很少,基本只剩表单输入的临时状态,或者压根不需要在全应用范围共享的状态。基于这个前提,源文件给出两条直白的判断:

这份状态需要跨越两三层以上、被很多组件共享吗?
↓
不需要 —— prop 传递最多两三层
坚持 prop 传递,更简单,大概率不需要 Context
需要,但更新很频繁
照样别用 Context;留在本地 state,或者换专门的状态管理库
状态的变化方式会不会随功能增多成比例甚至指数增长(多来源、多步骤)?
↓
不会 —— 多数 UI 编程题就是这样
直接在事件处理函数里整合状态更新,不必上 useReducer
会 —— 典型例外是游戏逻辑
用 useReducer,把变化收敛成 action

换句话说,面试官问"你会用 Context 还是 Reducer"的时候,很多时候在测的不是你会不会写 useContext/useReducer 的语法——而是你敢不敢在一道很小的题目里,先给出"prop 传递 + useState 就够"这个更简单的答案,再说清楚"如果规模变成 XX 样,我会换成 Context 或 Reducer"。默认答案往往是不需要,例外才需要论证。

五、关键定义

受控组件(Controlled Component)
行为完全由 props 决定、不依赖自身本地 state 的组件,父组件因此掌握完全的控制权。避免把"受控"锁死在表单 <input> 上——那是较早的窄定义,现代定义已经扩展到任何"父组件通过 props 决定其行为"的组件,手风琴这类非表单组件同样可以是受控的。
上下文(Context)
让后代组件无需一层层手动传 props 就能读取共享数据的机制,通常跟 state 配对放在应用顶层。避免把它当成万能的跨组件传值方案随手就用——它对频繁更新的状态(表单输入、动画)不友好,Provider 值一变,所有消费者都会重渲染。
Reducer
接收当前 state 和一个 action、依据 action 返回新 state 的纯函数,遵循 Redux 模式,通常配合 useReducer 把状态转换逻辑收敛到一处。避免把"状态字段变多了"直接等同于"该上 reducer"——真正的判断标准是变化路径是否多来源、多步骤,大多数小型 UI 编程题并不需要它。

现实中怎么用。拿一个"设置面板"组件来说:先给每个设置项本地 state,面板自己管理(非受控);如果产品需求变成"顶部导航栏的一个开关也要能改这些设置",这份状态就该提升、变成受控,由更上层的组件通过 props 传下来。如果设置项本身要在整个应用的十几个页面里被读取(比如深色模式),再考虑放进 Context——但如果某一项是用户正在拖动的滑块(高频更新),就把它留在组件本地,不要塞进 Context。只有当"保存设置"这个动作会触发校验、错误提示、多步确认这类互相牵连的转换时,才值得为它单独写一个 reducer。

一个容易踩的误区:把 Context 或 Reducer 当成"状态变多了就该上"的默认选项。源文件的陷阱清单里明确写着 Context"不应用于频繁更新的状态",也明确写 reducer 的判断标准是"转换是否复杂、是否多来源",不是"state 字段数量"。很多人一看到组件里 useState 调用变多,第一反应是"该重构成 Context 了"或"该换 useReducer 了",却没有先问一句"这些状态真的要跨很多层共享吗"或"这些变化真的互相关联、需要收敛吗"——多数情况下答案是否定的,这时更简单的 prop 传递或普通 useState 才是更好的选择。

今天就做的一件事:找一个你项目里已经用了 Context 或 useReducer 的组件,对着这节课第四部分的两条判断标准自问一遍——这份状态真的跨越了两三层以上吗?这些变化真的有多个互相关联的来源吗?如果答案是否,想一想改回 prop 传递 + useState 会不会反而更简单、更容易维护。

带走这一条:受控组件、Context、Reducer 分别回答三个不同的问题——"谁控制它"、"谁能读到它"、"它怎么变化"。默认答案优先选最简单的那个:本地 state 起步、需要协调再提升为受控;prop 传递够用就别上 Context,上了也别塞进频繁更新的状态;state 字段多不等于该上 reducer,变化路径真的多来源、多步骤才需要它。

六、自测题

Q1:关于受控组件与非受控组件,下面哪个说法最准确? (A) 一个组件一旦被设计为受控组件,就永远不能再拥有任何自己的本地 state (B) 一个推荐的做法是先让组件从本地 state(非受控)起步,只有当父组件真的需要协调它时才把状态提升上去、变成受控 (C) 受控与非受控是严格的技术定义,一个组件必须完全属于其中一类,不存在中间状态

正确答案是 (B)。源文件明确写"一个好的做法是先从本地状态(非受控)开始,并在需要时提升状态"。(A) 把受控组件的定义极端化了——源文件说的是"大多数组件并非严格受控或非受控,它们通常混合使用两者",不是彻底禁止本地 state;(C) 把源文件的说法说反了,源文件开篇就点明"这些术语不是严格的技术定义",而是一种理解组件交互方式的方式。

Q2:面试时该怎么判断是否需要引入 Context 或 Reducer,下面哪个说法最符合源文件的态度? (A) 只要一个应用里的 state 数量变多了,就应该马上引入 useReducer 统一管理,不用管这些状态变化是否互相关联 (B) Context 适合放频繁更新的状态,比如表单输入或动画进度,因为它本来就是为高频更新设计的 (C) 大多数 UI 编程面试题规模很小,prop 传递通常不会深过两三层,默认可以不用 Context 也不用 Reducer,除非真的遇到多来源、多步骤的复杂状态转换

正确答案是 (C)。源文件"面试需要了解的内容"明确写"您可能不需要上下文"和"您可能不需要 reducer",判断标准是 prop 传递的深度和状态转换是否复杂,例外分别是更深的层级需求和游戏这类真正复杂的状态机。(A) 错在只看"state 数量变多"就决定上 reducer,源文件强调的是转换是否复杂、是否多来源,不是单纯数量;(B) 把陷阱说反了——源文件的陷阱清单里明确写 Context"不应用于频繁更新的状态",表单输入和动画恰恰是应该避免放进 Context 的典型例子。
