RADIO 框架是什么 + 需求探索怎么问

系统设计面试问题往往故意留白、故意模糊——这节课要回答两个问题:面试官期待你照着走的 RADIO 五步分别是什么、为什么值得用这套结构;以及走的第一步"需求探索",具体应该开口问哪几类问题,才不会一上来就答偏题。

上一课我们区分了面试官到底在评估什么——不只是盯着"你最后设计得对不对",更看你解决问题的过程。这节课往前走一步:如果面试官真的在看过程,那你听到题目之后的头几分钟,该做什么、说什么,才能体现出这个过程是扎实的,而不是上来就默写一套模板?想清楚这个问题,再往下看 RADIO 框架怎么具体回答它。

一、为什么系统设计题需要一套"框架"

前端系统设计面试题有一个共同特点:题目故意留出空白,故意含糊——面试官不会把题目出得像单元测试用例那样精确。如果没有一套顺序,很容易一上来就想着"这个页面该怎么实现",东讲一点西讲一点,面试官很难判断你是不是真的想清楚了。RADIO 就是用来解决这个问题的一套结构化步骤:先搞清楚 Requirements(需求),再定义高层的 Architecture(架构)和 Data Model(数据模型),然后定义组件之间的 Interfaces(接口),最后讨论 Optimizations(优化)与需要深入的领域。源文件里有句话值得记住:一个好的开始就是成功的一半——这五步的顺序本身,就是"好的开始"的具体做法。

还有一个小的措辞习惯:前端系统设计面试里,你被要求设计的"系统",往往其实是一个产品(比如新闻 feed、聊天界面),所以这门课接下来会跟着源文件的说法,把"系统"直接叫作"产品"。

二、RADIO 五个字母分别是什么

R · 需求探索 提问澄清,确定范围
→
A · 架构/高层设计 关键组件与关系(下一课)
→
D · 数据模型 核心实体与字段(下一课)
→
I · 接口定义 组件间 API(下一课)
→
O · 优化与深入 专题讨论(下一课)

五步各自要做的事,是这样分工的:

  • 需求探索:彻底了解问题,通过提出澄清问题确定范围。
  • 架构/高层设计:确定产品的关键组件,以及它们之间的相互关系。
  • 数据模型:描述核心实体及其数据——每个实体包含哪些字段、属于哪个组件。
  • 接口定义(API):定义组件之间的接口、每个 API 的功能、参数和响应。
  • 优化和深入研究:讨论构建产品时可能的优化机会,以及特别值得深入的领域。

这节课只精读第一步——需求探索。A/D/I/O 四步具体怎么做,会留到下一课,用"设计 Facebook"这个完整案例从头走一遍;这节课先把整张地图画清楚,知道自己现在站在哪一步。

三、需求探索:目标、心态与时间预算

目标:彻底了解问题,并通过提出有用的澄清问题确定范围。建议时长:不超过整场面试的 15%——剩下的大头时间要留给架构、数据模型、接口和优化这四步,所以这一步要问得快、问得准,不能没完没了地磨下去。

需求探索≤15%
其余四步合计A + D + I + O

为什么必须靠提问,不能凭经验直接开始设计?系统设计面试题本质上是开放式的,通常模糊,而且是故意没说清楚的——面试官想看的是你怎么把一个模糊的问题变成一个双方都认可的明确问题,而不是看你背了多少种架构方案。把面试官当成正在和你一起做新项目的项目经理,提问是为了确认"我们到底要解决什么问题、要建成什么样子"。源文件里有句话说得很直接:有些问题根本不需要任何工程就可以解决——如果连这一点都没问清楚,后面画的架构图再工整也是白搭。

还有一点容易被忽略:即使你之前被问过完全一样的题目,也不会有两次系统设计面试经历是相同的——不同面试官背景不同,关注的重点也不同。需求探索阶段的提问,同时也是在借机摸清楚"这位面试官这次最在意哪一块",好把接下来的时间往那个方向倾斜。

四、需求探索具体要问哪些问题

1. 这次该关注产品的哪些主要用例?

假设题目是"设计 Facebook"。Facebook 是一个巨大的平台,有新闻 feed、个人主页、好友、群组、故事等等——你该关注哪一部分?面试官心里其实有答案,但希望你通过提问找出来,而不是自己瞎猜。通常应该关注产品最独特、最能定义它的功能:对 Facebook 来说是新闻 feed、feed 的分页和发新帖;对 YouTube 来说是看视频本身的体验。反过来,如果没有澄清就自己认定"应该讲讲加好友的流程"然后讲了半天,好一点的面试官会把你引导回正题,但已经浪费了宝贵时间讨论一个不重要的话题。下一课会继续用"设计 Facebook"这道题,把需求探索之后的四步走完。

2. 什么是功能需求,什么是非功能需求?

类型定义举例
功能需求产品能正常运行的底线要求,缺了它核心流程就跑不动用户能刷到 feed、能发帖
非功能需求被视为对产品的改进,但不是"能不能用"的门槛——没有它产品依然能用,只是不够好加载够快、能撑住大数据量、体验流畅

获得这个答案有两种方式:优先主动列出你认为的需求,请面试官给反馈、达成一致(首选做法);或者直接问面试官,但大多数时候他们希望你自己定义,就算给了答案也不会太详细。至少,设计必须先满足功能需求,满足之后再继续讨论怎么满足非功能需求。

3. 哪些是要重点关注的核心功能,哪些是锦上添花的功能?

就算已经知道了功能需求,同一个大功能下面也可能藏着一堆小功能。还是拿"在 Facebook 发一条新帖"举例:除了常规的文字帖子,用户是否还要能上传照片、上传视频、创建投票、签到某个地点?应该先明确核心功能有哪些、把它们设计清楚,再去讨论这些额外的功能。

4. 还有哪些通用问题值得在开场问一遍?

  • 需要支持哪些设备/平台(桌面/平板电脑/移动设备)?
  • 是否需要离线支持?
  • 这个产品的主要用户是谁?
  • 有没有具体的性能要求?(性能要求通常属于非功能需求)

这份清单能给你一个不错的开场提问列表,但绝不是穷尽的——不同题目会要求你提出特定领域的问题,具体案例会在后续课程里继续展开。建议把双方商定下来的需求写在某个地方,这样整场面试都能回头对照,确保没有遗漏。

五、关键定义

RADIO 框架
前端系统设计面试的一套结构化答题步骤,依次是需求探索(R)、架构/高层设计(A)、数据模型(D)、接口定义(I)、优化与深入研究(O),把"设计一个产品"拆成五个可以顺着走的动作。避免把它当成必须掐着秒表机械走完、五步互不重叠的固定流程——面试官的追问、你自己的补充,常常会让讨论在几步之间来回,框架只是给你一条不容易走丢的主线,不是一份考试规定动作。
核心功能与锦上添花的功能
在已经确定要做的功能范围内,核心功能是缺了它这个流程就立不住的部分(比如发一条纯文字帖子),锦上添花的功能是可以先放一放、后面再补的部分(比如发投票、签到)。避免把这条分类和"功能需求 vs 非功能需求"当成同一件事——核心/锦上添花问的是"功能需求内部先做哪个",跟"这条要求是不是产品能用起来的底线"是两个不同的问题。

现实中怎么用。面试官说完题目的那一刻,别急着在白板上画框——先按上面几类问题过一遍:这题该关注哪个主要用例?哪些要求是功能需求、哪些是非功能需求?哪些功能是核心、哪些可以放到后面?问完面试官后,把双方商定的结论写在白板或文档的角落——不是为了好看,是因为后面讨论架构、数据模型时,你会不断想回头确认"我们刚才说的范围是不是这个",有份随时能看的清单,比全靠脑子记省心得多。

一个容易踩的误区:把"功能需求 vs 非功能需求"和"核心功能 vs 锦上添花的功能"当成同一条分类线。它们回答的是两个不同的问题——功能需求/非功能需求区分的是"这个要求是不是产品能不能用起来的底线"(比如"用户能发帖"是功能需求,"发帖响应要快"是非功能需求);核心功能/锦上添花功能区分的是"在已经确定要做的功能里,哪些必须优先设计、哪些可以先放一放"(比如发帖这件事本身是核心,但要不要支持发投票、签到,是可以往后放的锦上添花)。混着用,很容易在面试里把"这个我们先不做"和"这个不重要"说成一回事,让面试官误以为你没分清产品的底线在哪。

今天就做的一件事:挑一个你平时天天用的 App(朋友圈、B 站、外卖都行),假装面试官让你设计它的某个核心页面。花 10 分钟,只做需求探索这一步:写下你认为的主要用例是什么,列出 3 条功能需求和 3 条非功能需求,再挑出其中哪个功能是核心、哪个是锦上添花。不用画架构图,只练"提问和界定范围"这一件事。

带走这一条。RADIO 把系统设计面试拆成 R(需求探索)→A(架构)→D(数据模型)→I(接口)→O(优化)五步,今天精读的只是第一步:需求探索的核心动作不是"证明你会设计",而是"通过提问,和面试官对齐清楚要解决的到底是什么问题、做到什么程度"——这一步没走扎实,后面画的架构图再漂亮,也可能是在回答一个错的问题。

六、自测题

Q1:RADIO 框架里的 R 代表什么,这一步主要该做的事是什么? (A) Response,尽快把你心里已经想好的技术方案讲出来 (B) Requirements,通过提问澄清问题、确定这次要设计的范围 (C) Review,回顾你以前做过的类似系统设计项目

正确答案是 (B)。R 是 Requirements(需求探索),这一步的动作是提问,把模糊、开放式的题目澄清成一个双方都认可的范围。(A) 把这一步理解反了——一上来就抛方案,恰恰是需求探索阶段最容易踩的坑,面试官更想看到你先确认问题再动手设计;(C) 不是回顾过去做过的项目经历,而是澄清眼下这道题的边界,和"以前做过什么"没有关系。

Q2:关于"功能需求"和"非功能需求",下面哪个说法准确? (A) 功能需求是产品能不能正常运行的底线,非功能需求(比如性能、可扩展性)是在此基础上的改进,不是"能不能用"的门槛 (B) 非功能需求可以完全不用管,反正是锦上添花,面试里提都不用提 (C) 两者其实是同一回事,只是叫法不同,面试时不用刻意区分

正确答案是 (A)。功能需求决定产品能不能跑起来,非功能需求是在此基础上的加分项,但源文件明确说满足功能需求之后仍要继续讨论非功能需求,不是可以跳过的选项。(B) 把"非功能需求"和"锦上添花的功能"混成了一件事——这正是这节课点出的常见误区,非功能需求依然要讨论,只是顺序放在功能需求之后,不是不用提;(C) 忽略了两者回答的是完全不同的问题:一个问"能不能用",一个问"用得好不好",不能划等号。

七、主推资源

需求探索这一步本身不需要外部工具,但下一课一旦开始画架构框图,就会用到画图工具——建议现在先打开看一眼、熟悉一下操作,免得面试当天手忙脚乱找工具。源文件里提到的两个免费选项:

  • diagrams.net —— 免费在线绘图工具,常用来画系统设计的架构框图。
  • Excalidraw —— 另一个手绘风格的免费绘图工具,同样适合画组件框图和箭头关系。

有任何不清楚的,回到会话里问你的 AI 老师——可以让老师用 ELI5 讲清"为什么需求探索不能跳过、直接开始画架构图",也可以让老师现场出一道新的产品设计题,陪你练习一遍需求探索该怎么问。
