React 为什么长这样:发展历程

面试官偶尔会问"你了解 React 的历史吗",但更常见的情况是——他们不问,却假定你知道。当面试官说"你更习惯 Hooks 还是 class 组件"、或者让你在白板上选一个状态管理方案时,背后都藏着一条时间线:React 是怎么从"Facebook 内部一个解决渲染性能问题的小项目",演变成今天这个自带庞大生态系统的东西的。这节课就讲这条时间线,以及它分裂出来的生态各个分类——目的不是背年份,而是搞懂"为什么现在的 React 面试会问这些概念"。

上一课讲了 React 面试考什么、怎么准备。回忆一下:那节课里提到的考察范围,除了"写代码"之外,通常还包括对 React 生态和设计取舍的理解——比如"你用过哪些状态管理库""为什么选它而不是另一个"。这类问题问的不是死记硬背的知识点,而是你是否理解这些工具各自要解决什么问题。这节课要打的底,就是让你看懂这些工具从哪来、解决的是哪一代的什么问题。

一、为什么 React 能一直占主导地位

源文件开篇先回答了一个更根本的问题:为什么面试官会假定"你应该懂 React"?原因不是"React 语法简单",而是几个结构性因素叠在一起:

  • 企业背书:React 诞生于 Facebook,支撑着 Facebook 全部产品的界面,被全球主要公司采用于各种规模的应用。
  • 庞大社区:官方文档之外,还有无数教程、课程、开源项目在持续产出学习资源。
  • 庞大的开源生态:从状态管理库(Redux、Zustand、Recoil)到 UI 组件框架(Material UI、Chakra UI),生态本身在不断扩张。
  • 服务器端与全栈能力:借助 Next.js 和 React Server Components,React 已经不只是"前端框架",而是深入到了后端渲染链路里。
  • 持续演进但保持向后兼容:这一点决定了"旧知识不会立刻过期",但也意味着面试现场可能同时遇到还在用 class 组件的老代码库,和已经用上 Server Components 的新项目。

这五条不是并列的装饰性理由——它们合起来解释了"为什么 React 面试会考生态知识"这件事本身:一个技术如果只是"语法好用",不会催生出十几个细分品类的第三方库;正是因为 React 长期占主导、又持续演进,才会在状态管理、数据获取、路由、测试、动画等每个方向上,都长出好几个相互竞争的方案——而面试官假定你至少对着某个方向有过取舍经验。

二、一条时间线:React 怎么从"class 时代"走到今天

源文件按年份列了一条演变时间线,核心矛盾是:每一次架构或 API 上的大改动,都是为了解决上一代方式暴露出来的具体问题。按时间顺序梳理:

2011 · React 诞生 — Facebook 工程师在渲染新闻提要这类动态 UI 时遇到性能瓶颈,Jordan Walke 做出早期版本(代号 FaxJS)
↓
2013 · 在 JSConf US 开源 — JSX 混合 JS 与 HTML 一度被质疑,但 Virtual DOM 带来的性能优势很快说服了开发者
↓
2015 · Flux 与状态管理 — 大型应用的数据流变得难以预测,Facebook 用 Flux 强制单向数据流,直接启发了 Redux 的诞生
↓
2016 · 函数式组件 + Fiber 架构 — 函数式组件让逻辑更清晰;Fiber 重写了协调算法,为并发模式和 Suspense 铺路
↓
2018 · React Hooks(React 16.8) — 在此之前只能靠 class 组件管理状态和生命周期,Hooks 把开发风格转向函数式
↓
2020 · 并发模式与 Suspense(React 17) — React 可以给渲染工作排优先级,让应用感觉更灵敏;Suspense 让数据获取更容易表达
↓
2021 · React Forget 亮相 — 早期预览展示了一个编译器构想:自动生成等效于 useMemo/useCallback 的优化,减少手写记忆化的负担
↓
2022 · React 18 与服务器组件 — 自动批处理、新 hooks(useId、useTransition)、React Server Components 把部分渲染工作卸载到服务器
↓
2023 · react.dev 上线 — 官方文档站换代,支持内嵌可运行的编码练习
↓
2024 · React 19 — 进一步优化服务器组件与静态生成,Actions 简化状态更新,React Compiler 实验版发布(即 React Forget 的落地)

把这条时间线压缩成一句话:2018 年之前的核心矛盾是"状态和生命周期只能靠 class 管理",Hooks 解决了它;2018 年之后的核心矛盾变成"渲染工作怎么安排优先级、怎么卸载到服务器",并发模式、Server Components、Compiler 都是在回答这个新矛盾。面试里问"你怎么看 Hooks 相比 class 组件的优势",本质上问的就是你是否理解第一次转折解决了什么问题;问"你了解 Server Components 吗",问的是你是否跟上了第二次转折。

三、生态怎么分类:每个方向都在解决什么问题

源文件把 React 生态拆成八个方向。这里的关键不是记住每个库的名字,而是记住每个方向对应内置能力的哪个短板:

方向内置能力的短板代表方案
状态管理useState/useReducer/Context 够用,但大型应用的全局状态会变得难以追踪Redux、Zustand、Jotai
UI 组件(样式化)React 本身不提供任何组件外观MUI、Mantine、Ant Design
UI 组件(无头)样式化组件锁定了外观,团队想要行为和可访问性、但自己控制样式Headless UI、Radix UI、Base UI、React Aria、Ariakit
数据获取手写 fetch + useEffect 拿不到缓存、重试、分页这些能力TanStack Query、SWR、Apollo Client、Relay
表单验证表单状态、校验规则、错误展示都要手写,重复劳动多React Hook Form、Formik(已不再维护)
路由与元框架React 本身不带路由,也不解决服务端渲染Next.js、Remix / React Router、TanStack Start
测试与调试需要单元/集成/端到端测试,以及组件级调试手段Jest、Vitest、React Testing Library、Storybook、Cypress、React Developer Tools
打包器模块化代码(导入、JSX、CSS、图片)要转换成可上线的优化包Vite、Parcel、webpack(继承者 Turbopack)
动画与效果React 里手写动画一直被认为很难Motion(原 Framer Motion)、React Spring、GSAP

注意路由那一行里的一个细节:Remix 团队后来把 Remix 的功能合并进了 React Router v7——这不是随口一提的八卦,而是生态本身也在持续整合、不是永远细分下去的一个例子。面试官如果追问"Remix 和 React Router 现在是什么关系",答不上来会显得你的信息停留在旧版本。

四、关键定义

Fiber 架构
2016 年开始的一次对 React 核心协调算法的完全重写,目的是让渲染工作可以被拆分、打断、重新排优先级,为并发模式和 Suspense 打基础。避免把 Fiber 说成"一个新的 Hook 或新的 API"——它是引擎级的重写,开发者平时写代码基本感觉不到它的存在,但它是后面几年新特性的地基。
React Server Components(RSC)
一种可以运行在服务器、把渲染工作卸载到服务器端的组件形态,2022 年随 React 18 引入。避免把它和同一年引入的自动批处理、useId、useTransition 混为一谈——这几个是 React 18 里并列的不同新特性,RSC 特指"组件本身运行在服务器端"这一种形态,不是新 Hook 或调度机制。
React Compiler(原 React Forget)
2021 年以"React Forget"名字亮相、2024 年发布 beta 版的编译器,自动生成等效于 useMemo/useCallback 的优化,减少不必要的重新渲染。避免把它讲成"取代了 Hooks"——它优化的是记忆化这一层,组件依然用 useState、useEffect 这些 Hooks 写,编译器只是替你少写手动优化代码。

现实中怎么用。面试前不需要把八个生态方向的每个库都用过一遍,但至少对每个方向说出"它解决什么问题、我用过其中哪一个"——比如"数据获取这块我用 TanStack Query,因为它自带缓存和重试,不用自己在 useEffect 里手写"。这比空泛地说"我了解 React 生态"更有说服力,也是源文件里"目标是熟悉并获得每个类别中至少一项技术的经验"这句话的具体落地方式。

一个容易踩的误区:把发展历程当成一份年份记忆题。面试官几乎不会问"Hooks 是哪一年发布的",他们真正想确认的是你是否理解"为什么会有这次转变"——如果你能说清楚 class 组件在状态复用和逻辑拆分上的具体痛点,自然就答对了"为什么要有 Hooks";反过来死记年份,遇到追问"那 Hooks 解决了 class 组件的什么问题"就会卡壳。记时间线是为了记住因果链条,不是为了应付一道填空题。

今天就做的一件事:挑一个你实际项目里用过的库(哪怕只是 axios 而不是 TanStack Query),对着上面的生态分类表,写一句话说明"它属于哪个方向、解决了内置能力的什么短板、如果换成表格里同方向的另一个库会有什么取舍"。这个练习比抽象背诵八个分类名字更接近面试现场的真实提问方式。

带走这一条:React 的每一次大改动都是在回应上一代方式暴露出的具体问题——class 组件的状态复用问题催生了 Hooks,渲染优先级和服务端能力的缺口催生了并发模式和 Server Components;生态里的每个分类(状态管理、数据获取、路由……)也是同一个逻辑:内置能力有短板,才会长出第三方方案填补它。

五、自测题

Q1:关于 React Hooks(2018 年,React 16.8)出现的背景,下面哪个说法最准确? (A) Hooks 是为了取代 JSX,让开发者不再需要混写 JS 和 HTML (B) Hooks 是为了解决"此前只能依赖 class 组件管理状态和生命周期"这个限制,把开发风格转向函数式 (C) Hooks 是 Fiber 架构里新增的一个渲染优先级排序功能

正确答案是 (B)。源文件明确写"在 Hooks 出现之前,开发人员依赖类组件来管理状态和生命周期方法",Hooks 的引入正是为了打破这个限制。(A) 把 Hooks 和 JSX 搞混了——JSX 是 2013 年开源时就有的语法,与 Hooks 无关;(C) 把 Hooks 和 Fiber 架构混为一谈,Fiber 是协调算法的底层重写,Hooks 是开发者可见的 API 层特性,二者是不同层面的东西。

Q2:在源文件的生态分类里,"数据获取"这个方向要解决的核心问题是什么? (A) React 本身不带路由,应用无法在多个页面间跳转 (B) 手写 fetch 加 useEffect 拿不到缓存、重试、分页这些实用能力,需要专门的库来补上 (C) React 组件的状态在大型应用里难以追踪,需要集中式存储来管理

正确答案是 (B)。源文件说数据获取库"简化数据获取,其中包含缓存、重试和分页等有用功能",这正是手写 fetch/useEffect 缺失的部分。(A) 描述的是"路由与元框架"这个方向的问题,不是数据获取;(C) 描述的是"状态管理"方向的问题(对应 Redux 这类方案),同样答错了方向。

六、主推资源

  • react.dev —— React 官方文档与资源站,2023 年换代后内置可运行的编码练习,是理解当前 API 全貌最权威的起点。
  • React Fiber Architecture —— 对 2016 年那次协调算法重写的详细说明,想搞懂"为什么并发模式需要先重写引擎"可以从这里深入。
  • React Server Components 参考文档 —— 官方对 use server 与服务器组件模型的规范说明,回答"RSC 到底怎么工作"的一手材料。
  • React Compiler Beta 发布说明 —— 2021 年 React Forget 构想的落地版本,读这篇能补上时间线最后一格的细节。

有任何不清楚的,回到会话里问你的 AI 老师——可以让老师用 ELI5 讲清"Hooks 到底解决了 class 组件的什么麻烦",也可以让老师挑你实际用过的某个库,带你按这节课的分类表分析一遍取舍。
