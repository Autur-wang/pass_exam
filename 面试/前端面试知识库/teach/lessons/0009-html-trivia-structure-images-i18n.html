HTML 高频问答:文档结构、图片与多语言

这节课把 quiz题库 里 8 道 HTML/i18n 方向的高频问答题,按三组问题重新归类讲清楚:文档骨架怎么声明与摆放(DOCTYPE、HTML5 的能力清单、CSS/JS 标签该放哪、data- 属性该不该用),图片与渲染怎么又快又省(srcset、渐进式渲染的几种手法),以及一个页面要服务多语言用户时,设计和交付各自该注意什么。

先回忆一下上一课:CSS 高频问答那几节里,你已经练过"给一个现象倒推浏览器在做什么"的思路——比如响应式布局怎么适配不同屏幕、渲染引擎在兼容性上做了哪些取舍。这节课换到 HTML 这一侧,同样是给你一串真实高频问答题,但问题从"CSS 怎么画"变成"文档骨架、图片资源、多语言内容分别该怎么组织与交付"。带着同一个习惯往下读:先弄清楚"浏览器/服务器实际在做什么",再去记结论。

一、文档结构类:DOCTYPE、HTML5 构建块与标签摆放

DOCTYPE 在干什么

DOCTYPE 是 Document Type 的缩写,和 DTD(Document Type Definition)绑在一起。DTD 定义这类文档该怎么搭(比如 button 能不能包含 div),DOCTYPE 则声明"这份文档打算遵守哪份 DTD"。网页少不了这句声明——浏览器认出正确的 DOCTYPE 就会用 no-quirks 模式解析;认不出就退回 quirks 模式,排版行为会变得不可预期。HTML5 的标准写法就是 <!DOCTYPE html>。

要素说明
DOCTYPE声明"这份文档应该遵守哪个 HTML 规范版本"。
DTD定义这类文档具体怎么搭,DOCTYPE 声明的正是"我遵守哪份 DTD"。
no-quirks 模式浏览器识别出正确 DOCTYPE 后触发,按规范解析。
quirks 模式浏览器认不出 DOCTYPE 时的退路,排版行为不可预期。

HTML5 是一个开放 Web 平台:8 个构建块

把 HTML5 当成一整个平台而不是一门标记语言来看,它对外提供的能力可以归成下面 8 块:

构建块解决什么
语义HTML 标签本身描述内容是什么。
样式自定义 HTML 标签的外观。
连接性以新方式与服务器通信。
离线和存储让网页在客户端本地存数据,离线也能更有效地运行。
多媒体让视频、音频成为开放 Web 里的一等公民。
2D/3D 图形和效果提供更丰富的呈现方式。
性能和集成更高的速度优化,更好利用硬件。
设备访问支持各种输入输出设备。

CSS <link> 放 <head>,JS <script> 放 </body> 前

页面首次加载时,HTML 和 CSS 会同时被解析——HTML 建 DOM,CSS 建 CSSOM,两者都要就位才能画出视觉效果。把 CSS <link> 放进 <head>,是为了让样式表在浏览器准备渲染时已经加载好;放在文档底部会挡住渐进式渲染——有些浏览器会直接阻塞渲染,让用户卡在一片空白页上;另一些浏览器则会先显示未设置样式的内容,出现"闪一下"的 FOUC。<script> 标签则相反:它下载、执行的过程会挡住 HTML 解析,放在 </body> 前能让 HTML 先解析完、先显示给用户。

✗ script 堆进 head,没有 defer

<head>
  <link rel="stylesheet" href="style.css">
  <script src="app.js"></script>
</head>
<body>
  ...
</body>

✓ CSS 留在 head,script 挪到 body 末尾

<head>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  ...
  <script src="app.js"></script>
</body>

这条规则里,源材料点出的一个例外情况是:脚本里还留着 document.write() 时——不过这如今已经不是推荐写法了。另外要留意,把脚本挪到结尾会造成"空缓存下页面加载更快"的错觉:脚本确实不再挡文档剩余部分的下载,但脚本本身要等整份文档解析完才开始执行;如果一定要把 <script> 留在 <head> 里,加上 defer 属性能让浏览器提前发起下载请求,在缓存命中的场景下反而感觉加载更快。顺带一提,HTML5 规范里 <head> 和 <body> 标签本身是可选的,但这种省字节的写法还没被广泛采用,收益也有限。

data- 属性该用在哪

在 JS 框架流行之前,开发者常用 data- 属性直接在 DOM 里存点额外数据,不必去发明非标准属性。第三方库也这么用,比如 Bootstrap 用 data-bs-toggle/data-bs-target 让一个按钮触发页面别处的模态框(示例):

<button type="button" data-bs-toggle="modal" data-bs-target="#myModal">
  Launch modal
</button>

现在这种用法不太被鼓励——用户在浏览器"检查元素"里就能直接改数据属性,数据模型更适合放在 JS 环境里,靠虚拟 DOM 协调或双向绑定跟 DOM 保持同步。但有一个用法一直站得住脚:给端到端测试(Playwright、Puppeteer、Selenium)加一个选择器,比如 data-test-id="my-element",不用为了测试去污染本该服务其他用途的 class 或 id。

二、图片与渲染类:srcset 与渐进式渲染

srcset:同一张图,按屏幕宽度和密度挑版本

想根据用户设备的显示宽度给不同图片,就用 srcset——高密度屏幕给更清晰的图能提升体验,低端设备给更小的图能省流量、提性能。以 srcset="small.jpg 500w, medium.jpg 1000w, large.jpg 2000w" 为例,在 320px 设备宽度下:

候选宽度描述符320px 下的比值典型上选场景
small.jpg500w500/320 ≈ 1.56251x(普通)屏幕——比值最接近 1
medium.jpg1000w1000/320 ≈ 3.1252x(视网膜)屏幕——比值离 2 最近且不低于 2
large.jpg2000w2000/320 ≈ 6.25更高密度或更宽的设备

浏览器不是无条件挑最大的文件,而是拿设备的目标密度去找"比值够用、又最接近"的候选:1x 屏幕选 small.jpg,因为 1.5625 离 1 最近;2x 屏幕不会选 500w,因为 1.5625 小于 2,图会显得糊,于是选比值更接近 2 的 1000w。

渐进式渲染:让用户尽快看到东西

渐进式渲染是一组让网页尽快把内容摆到用户眼前的技术,在宽带普及前很流行,如今因为移动网络又多又不稳定,依然在用:

图片懒加载loading="lazy" 或用 JS 监听滚动位置
→
优先渲染首屏只带最少 CSS/内容/脚本,其余等 DOMContentLoaded/load 再补
→
异步 HTML 片段后端边生成边把片段刷给浏览器
→
框架时代的延伸渐进式水合 / 流式 SSR / 选择性水合

"异步 HTML 片段"这套手法的完整案例见这篇 eBay 工程博客;框架时代的三种延伸分别是渐进式水合、流式服务器端渲染、选择性水合,思路都是同一件事的不同实现:别等全部东西都准备好才给用户看。

三、多语言类(i18n):设计阶段与交付阶段

设计阶段要注意的事

维度要点
SEO 层面<html lang="..."> 声明语言;URL 里带区域设置(如 en_US、zh_CN);用 <link rel="alternate" hreflang="..."> 告诉搜索引擎同一内容还有其他语言版本;给不匹配的语言配一个 hreflang="x-default" 兜底页。
区域设置 ≠ 语言语言区域设置(locale)管的是数字、日期、货币怎么显示,按地区划分,不完全等同于国家边界。
同一语言,不同"版本"使用广泛的语言在不同地区可能有不同语法/拼写/字符,比如 en-US 和 en-GB、zh-CN 和 zh-TW,不能假设一种版本能代表整个语言。
预测但不要限制服务器可以用 Accept-Language 头加 IP 猜访问者的语言区域设置,但猜测不是万无一失的(比如用户开了 VPN),要留一个能轻松手动切换的入口。
文本长度差异同一句话在不同语言里长度不同,标题、标签、按钮这类短文本最容易被撑破布局;正文这类自由流动的文本受影响较小。
阅读方向希伯来语、阿拉伯语等是从右到左书写,布局和元素位置要能适配。
别拼接翻译字符串类似 "今天的日期是 " + date 的写法会在语序不同的语言里崩掉,应该用带参数替换的模板字符串。
日期/货币格式不同地区习惯不同,比如美式"月在前"和欧洲"日在前"。
别把文字做进图片图片里嵌文字不好翻译,每种语言都要单独出一张图,对设计师不是可持续的工作流程。
颜色的文化含义同一种颜色在不同语言/文化里被感知的方式不一样,配色要考虑这一点。

这部分设计原则的参考出处见区域设置和语言之间的差异。

交付阶段:把对的语言送到对的人面前

浏览器发请求时通常会在 Accept-Language 里带语言偏好;服务器可以据此返回对应语言的文档版本,并在 <html lang="..."> 里声明当前用的是哪种语言。要让搜索引擎知道同一内容还有别的语言版本,用带 rel="alternate" 和 hreflang="..." 的 <link> 逐一标注。渲染这份内容,常见两条路:

渲染方式怎么做
服务端渲染HTML 标记先留字符串占位符,服务端按语言从代码配置或翻译服务取内容,动态生成该语言版本的页面。
客户端渲染提取对应区域设置的字符串,和基于 JavaScript 的视图结合后再渲染出来。

这道题有一个前提要记住:讨论的是"同一页面只用一种语言一致地显示",不是"一页混排多语言"的场景。

四、关键定义

渐进式渲染(Progressive Rendering)
让浏览器尽快把内容摆到用户眼前的一组技术组合——图片懒加载、优先渲染首屏内容、异步 HTML 片段,以及框架时代的渐进式水合/流式 SSR/选择性水合都算在内。避免把它等同于"随便延迟加载点什么就算渐进式渲染";它的目标是尽快显示,不是尽量晚加载。
语言区域设置(locale)与语言
语言决定用什么词汇和语法,区域设置(locale)决定数字、日期、货币怎么显示,同一种语言在不同地区可能对应不同区域设置(如 en-US 和 en-GB)。避免把 lang="en" 当成"这页面已经适配好所有英语国家的格式";没标区域设置,日期和货币的展示规则仍然不确定。
DOCTYPE
声明文档遵守哪个 HTML 规范版本的标记,浏览器识别后进入 no-quirks 模式解析,识别不出则退回 quirks 模式。避免把它当成一句可删可留的历史遗留样板——少了它,浏览器排版行为会整体变得不可预期。

现实中怎么用。这几道题在真实工作里最常出现的场景,不是被面试官逐字追问定义,而是 code review 时被抓这些细节:图片组件是不是该加 srcset/loading="lazy"、多语言项目里字符串是不是被硬拼接了、<script> 标签堆在 <head> 里却没打 defer 导致首屏变慢。把这节课当成一份检查清单,比背定义更有用。

一个容易踩的误区:把"把 <script> 挪到 </body> 前"当成性能优化的万能解药。挪位置只解决了脚本会不会挡 HTML 解析这一件事;脚本里还留着 document.write(),或者其实更想让浏览器提前发起下载请求,答案是在 <head> 里加 defer,不是死记"脚本放最后"。同理,data- 属性也常被当成"存应用状态的地方"——它本来是给没有更合适属性时的兜底方案,以及给 E2E 测试当选择器用,不是数据模型的主战场。

今天就做的一件事:打开手头一个真实项目的入口 HTML,做两件事:①检查 <head> 里的 <script> 标签有没有 defer/async,或者是不是该挪到 </body> 前;②找一张响应式场景下的关键图片(比如首页 banner),看它有没有用 srcset 按宽度给出多个版本——没有的话,哪怕只是练习,也写一行加上。

带走这一条:这 8 道题拆开看是零散的 trivia,拼起来只有一条逻辑:让用户尽快看到东西(渐进式渲染、CSS/JS 标签摆放、srcset),同时让不同语言/地区的用户看到对的东西(lang、hreflang、Accept-Language、别拼接字符串)——记住这条主线,比死记 8 个孤立答案更抗遗忘。

五、自测题

Q1:srcset="small.jpg 500w, medium.jpg 1000w, large.jpg 2000w",在 320px 设备宽度下,如果客户端是视网膜屏(2x),浏览器倾向选择哪张图,为什么? (A) large.jpg,因为分辨率越高的屏幕就该选最大的图 (B) small.jpg,因为 500w 是资源列表里的第一个值 (C) medium.jpg,因为它的比值(3.125)是几个候选里最接近 2 且不低于 2 的,能保证视网膜屏不糊

正确答案是 (C)。浏览器是拿设备目标密度去找"比值够用、又最接近"的候选,不是无条件选最大文件——large.jpg 的比值 6.25 对 2x 来说是浪费,(A) 把"分辨率越高就选最大"当成规则,忽略了比值匹配的逻辑。(B) 错在 500w 对应比值 1.5625,低于 2,在视网膜屏上会显得模糊,这恰恰是 1x 场景该选的答案,不是 2x。

Q2:关于把 CSS <link> 放进 <head>、JS <script> 放在 </body> 前,下面哪个说法最准确? (A) 把 <script> 放在 <head> 里且不加任何属性,和放在 </body> 前效果完全一样,只是写法习惯不同 (B) 把 <script> 放在 </body> 前能让 HTML 先解析、先显示给用户,但脚本里若留着 document.write(),这个位置的收益会被打破,这也是该规则的一个例外情况 (C) CSS <link> 应该放在 <body> 末尾,这样才不会挡住页面的首次渲染

正确答案是 (B),这也是源材料明确点出的例外情况。(A) 错在把 <script> 放 <head> 且没有 defer/async 时会阻塞 HTML 解析,和放在 </body> 前的效果并不相同。(C) 正好说反了——CSS <link> 要放进 <head> 才能保证渐进式渲染、避免 FOUC,放到 <body> 末尾反而会挡住渐进式渲染,让用户先看到一片空白或未设置样式的内容。
