内建 Hooks 怎么考:useState/useEffect/useContext/useRef/useId

React Hooks 手册开篇就点名了五个"你可能需要在面试中用到"的内建 Hook:useState、useEffect、useContext、useRef、useId。这节课不讲"Hooks 是什么"这种概论,而是逐个拆开这五个 Hook——它们各自在解决什么问题、手册里明确标出的陷阱是什么、面试官最容易在哪一处发现你其实没搞懂。useEffect 单独占了手册最长的一段,这节课也花最多篇幅讲它。

上一课你已经区分过什么时候该用受控组件、什么时候该上 Context、什么时候干脆用 Reducer 收拢状态逻辑。先回忆一下:那节课里你说到 Context 比较适合共享哪一类状态?如果传给 Provider 的 value 恰好是一个对象或数组,你还记得直接把它每次渲染都重新塞进去,会带来什么后果吗?这节课会在 useContext 那一节把这个后果讲清楚——它其实和 useEffect 的一个经典陷阱是同一件事的两个变体。

一、五个 Hook 摆在桌面上,是在回答三条问题

手册原文把话说得很直接:"熟悉常见的 Hooks：useState、useEffect、useContext、useRef、useId,您可能需要在面试中使用其中的一些。"这五个不是同一层次上并列的知识点,而是分别在回答三条不同的问题——这个值要不要触发重渲染?要不要跨组件共享,而不是一路手写 props?要不要跨渲染保留下来,但又不影响 UI 本身?想清楚这三条,该挑哪个 Hook 基本没什么悬念;真正有难度的,是 useEffect 那一节的依赖数组。

useState组件私有状态
→
useEffect同步外部系统
→
useContext跨层级共享
→
useRef跨渲染可变引用
→
useId跨 SSR 唯一 ID

接下来按手册原文的顺序,一个一个拆开看。

二、useState:组件私有状态,别直接改

useState 让函数组件在自己的组件实例里记住状态,这份状态是隔离且私有的——如果你在两个不同的地方渲染同一个组件,每个实例各自拿到自己的一份状态,互不干扰。什么时候用它?当这个状态只属于当前组件、不打算共享给兄弟或父组件时。

const [state, setState] = useState(initialState);

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount((prevCount) => prevCount + 1)}>
      Count: {count}
    </button>
  );
}

initialState 是必需参数——如果传进去的是一个函数,React 会调用它来做延迟初始化。手册点名的第一个陷阱是直接改变状态对象,而不是走 setter:

❌ 直接改变状态

const [user, setUser] = useState({ name: 'Alice', age: 25 });
user.age = 26;
setUser(user); // 同一个对象引用,React 认为状态没变

✅ 传入新对象

setUser((prevUser) => ({ ...prevUser, age: 26 }));

第二个陷阱是在闭包里引用过时的值——如果新状态依赖旧状态,直接写 setCount(count + 1) 在间隔或异步函数里可能读到的已经是过期的 count;改成函数式版本 setCount((prevCount) => prevCount + 1) 能绕开这个问题,因为 React 会把最新的那份状态交给你,而不是让你自己手写的变量去猜。第三个陷阱手册说得也很干脆:如果一个值的变化根本不需要触发重渲染,别用 useState——去看下面 useRef 那一节。

在 react.dev 上进一步阅读:useState - React。

三、useEffect:同步外部系统的钩子,也是面试重灾区

useEffect 的定位很明确:它主要是用来把组件和外部系统同步的 Hook,而不是"生命周期钩子的万能替代品"。典型用法是获取数据、订阅事件、和 DOM 交互。

useEffect(effectFunction, dependencyArray);

第一个参数是必需的副作用函数,第二个参数——依赖数组——是可选的,但它决定了这个 effect 到底什么时候跑:

什么时候该跑这个 effect?依赖数组怎么写例子
每次渲染后都跑不传第二个参数useEffect(() => {...});
只在挂载时跑一次空数组 []useEffect(() => {...}, []);
依赖项变化时才跑写上具体依赖 [var1, var2]useEffect(() => {...}, [var1, var2]);
卸载或重跑前先清理effect 里 return 一个函数useEffect(() => { return () => {...}; }, []);

手册特别提醒:useEffect 在面试题里并不常见——面试题大多是自包含的,不太需要真的去同步一个外部系统,所以 GreatFrontEnd 官方题解里也没有太多 useEffect 的影子。如果你发现自己的解答里用上了它,先停下来想想是不是有别的选择,再对照官方题解看看能不能去掉。

手册点名的四个陷阱,前两个是文字描述、后两个各带一组代码。第一个是缺依赖导致陈旧闭包:

❌ 依赖项漏了

useEffect(() => {
  fetchData();
}, []); // 如果 fetchData 依赖某个 prop,这个空数组里就藏着一个陈旧闭包

✅ 补上真实依赖

useEffect(() => {
  fetchData(someProp);
}, [someProp]);

第二个陷阱是在 effect 内部更新状态,又没管好触发它重跑的依赖,导致效果一遍遍地把自己重新触发出一个无限循环——这也是为什么"依赖数组该写什么"从来不是随手填的小事。第三个陷阱是依赖数组里放了对象/数组,导致不必要的重跑:

❌ filteredTodos 每次渲染都是新数组

function TodoList({ todos }) {
  const [count, setCount] = useState(0);
  const [status, setStatus] = useState('in_progress');
  const filteredTodos = todos.filter((todo) => todo.status === status);

  useEffect(() => {
    console.log('filteredTodos 变了');
  }, [filteredTodos]);
  // 点"强制重新渲染"(只改了 count),
  // filteredTodos 引用也变了,effect 照样重跑
}

✅ 用 useMemo 稳定引用

function TodoList({ todos }) {
  const [count, setCount] = useState(0);
  const [status, setStatus] = useState('in_progress');
  const filteredTodos = useMemo(
    () => todos.filter((todo) => todo.status === status),
    [todos, status]
  );

  useEffect(() => {
    console.log('filteredTodos 变了');
  }, [filteredTodos]);
  // 引用只在 todos 或 status 真正变化时才变
}

第四个陷阱是没清理副作用,比如忘了清定时器、忘了取消订阅:

❌ 没有清理

useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);
}, []); // 组件卸载后,定时器还在跑

✅ 返回清理函数

useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);
  return () => clearInterval(interval);
}, []);

手册对 useEffect、useCallback、useMemo 的依赖数组给出的建议是:老老实实把依赖填对是当下的好习惯——更长远来看,React 编译器想做的是让开发者不必手写 useCallback/useMemo,但这是未来时,面试现场你仍然要能解释依赖数组本身的道理。手册也直言:useEffect 充满陷阱,即使经验丰富的工程师也常常用不对。如果你想真正吃透它,手册给出的阅读顺序是先看《与 Effects 同步》,再看《你可能不需要 Effect》,然后是《响应式 Effects 的生命周期》、《将事件与 Effects 分开》,最后是《删除 Effect 依赖项》——这五篇按顺序读完,比只看这节课的摘要扎实得多。

在 react.dev 上进一步阅读:useEffect - React。

四、useContext:跨层级共享,记得给对象值做记忆化

useContext 提供了一种不用一路手写 props 就能在组件之间共享状态的方式,适合主题、身份验证、用户设置这类全局状态。

const ThemeContext = createContext('light');

function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={theme}>
      <ThemedComponent />
    </ThemeContext.Provider>
  );
}

function ThemedComponent() {
  const theme = useContext(ThemeContext);
  return <div>主题：{theme}</div>;
}

React 19 起,Context 的 Provider 可以直接写成 <ThemeContext value={theme}>,不必再套一层 .Provider。不管哪种写法,行为都一样:当 Provider 收到一个不同的值,React 会自动重新渲染树里所有消费这个 context 的子组件——从这句话就能看出手册点名的第一个陷阱在哪:用对象或函数当 context 值却不做记忆化。假设 Provider 的 value 是一份过滤后的待办列表,而这份列表每次父组件渲染都会重新 filter 出一个新数组——即使内容没变,引用变了,树里所有读这个 context 的组件也会跟着重渲染。修法和 useEffect 那节的 filteredTodos 完全一样:用 useMemo 把这份计算结果的引用锁住,让它只在 todos 或 status 真正变化时才变。第二个陷阱是过度使用 useContext 去管理本该交给状态管理库的深层嵌套状态。

在 react.dev 上进一步阅读:useContext - React。

五、useRef:跨渲染保留,但改了不触发渲染

useRef 存的是一份在渲染之间保持不变的可变引用,典型用法有三种:引用组件实例专属的数据、存一份对 DOM 的引用、存放不影响 UI 的数据(比如定时器或 interval 的 ID)。关键区别在于——更改 ref 的值不会导致组件重新渲染。

function FocusInput() {
  const inputRef = useRef(null);
  return (
    <div>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current.focus()}>Focus Input</button>
    </div>
  );
}

手册点名的陷阱只有一个,但很容易在面试里现形:过度使用 useRef 去代替本该用 useState 管理的状态。判断标准回到第一节的那条问题——这个值的变化要不要在 UI 上体现出来?要,就该用 useState;只是需要在渲染之间"记住"一份东西,又不想因为它的变化多渲染一次,才轮到 useRef。

在 react.dev 上进一步阅读:useRef - React。

六、useId:生成跨 SSR 一致的唯一 ID,不是拿来当 key 用的

useId 是 React 18 引入的 Hook,用来给无障碍属性和表单元素生成唯一 ID,并且确保这份 ID 在组件树里是唯一的——即使是在服务器端渲染的场景下也一样。

function Form() {
  const id = useId();
  return (
    <div>
      <label htmlFor={id}>名称：</label>
      <input id={id} type="text" />
    </div>
  );
}

它主要用在三种场景:设计系统组件需要 aria-labelledby 之类的无障碍属性,但页面上可能同时存在这个组件的多个实例;服务端渲染的表单需要给输入框生成唯一 ID;想避免手写一个全局计数器或额外引入一个库来生成唯一 ID。手册点名的陷阱是两条:别把 useId 拿来当列表的 key——列表的 key 该用数据库 ID 这类稳定的值;useId 生成的是静态 ID,不是用来追踪动态状态的工具。

在 react.dev 上进一步阅读:useId - React。

七、关键定义

useEffect 依赖数组
useEffect 的第二个参数,决定 effect 什么时候重新执行:不传、传空数组、传一组变量,分别对应"每次渲染后都跑""只在挂载时跑一次""这些值变了才跑"三种不同时机。避免把它当成"随手塞一个 [] 让报错消失"的开关,却没想过数组里的对象或数组是不是每次渲染都在被重新创建,导致 effect 该跳过时没跳过、或者跑起来没个头。
setState 的函数式更新
把 setCount((prevCount) => prevCount + 1) 里的 prevCount 交给 React 去传,而不是自己手写的旧变量,用来避开事件处理器、定时器等场景里"读到的还是上一次渲染时的旧状态"的问题。避免图省事写成 setCount(count + 1),在异步或高频触发的场景下这一行读到的 count 可能已经过期。
Context 值的记忆化
传进 Provider 的 value 如果是对象或数组,要用 useMemo 稳定它的引用,让它只在真正的依赖变化时才变,避免树里所有消费该 context 的组件跟着一起重渲染。避免以为用了 Context 就自动只在必要时更新——记忆化这一步需要自己动手写,Context 本身不会包办。

现实中怎么用。写一道 UI 编程面试题时,把这五个 Hook 当成一张检查单来挑:这个值要不要触发重渲染、又只属于当前组件?选 useState。要跨组件共享、又不想一路传 props?选 useContext。要跨渲染保留、但不影响 UI(DOM 引用、定时器 ID)?选 useRef。要给无障碍属性生成跨 SSR 一致的唯一 ID?选 useId。至于 useEffect——先问自己这道题是不是真的需要连接一个外部系统,如果答案含糊,大概率可以不用它。

一个容易踩的误区:把 useEffect 当成万能的"生命周期钩子"来兜底所有副作用。依赖数组随手写、随手留空,或者把对象/数组直接扔进依赖数组却不做记忆化,这正是手册反复强调的"即使经验丰富的工程师也常踩"的坑。更隐蔽的一种是无限循环:在 effect 里更新状态,又没管好触发它重跑的依赖,于是这个 effect 一遍遍地把自己重新触发出来——这类 bug 往往不报错,只是页面莫名其妙地卡顿或疯狂刷新。

今天就做的一件事:找一个手头用到 useEffect 的组件,对着上面那张四行的依赖表逐条核对——这个 effect 到底属于"每次渲染后""仅挂载一次""依赖变化时"还是"需要清理"里的哪一类?如果答案含糊不清,大概率是这个 effect 本身该拆分,或者根本不需要它。

带走这一条:五个内建 Hook 背后其实只是三条分岔——这个值要不要触发重渲染、要不要跨组件共享、要不要跨渲染保留却不影响 UI。想清楚这三条,该选哪个 Hook 基本没有悬念;真正难的是 useEffect 的依赖数组,那需要单独小心对待。

自测题

Q1:一个 TodoList 组件里,filteredTodos 由 todos.filter(...) 在每次渲染时重新生成,useEffect 的依赖数组里写的正是 [filteredTodos]。点击一个只会改动无关状态 count 的"强制重新渲染"按钮,这个 effect 却又跑了一次。下面哪种做法能正确解决这个问题? (A) 把依赖数组改成空数组 [] (B) 用 useMemo 包一层 filteredTodos,依赖写 [todos, status] (C) 直接删掉这个 useEffect,把 console.log 写在组件渲染的地方

正确答案是 (B)。用 useMemo 记忆 filteredTodos 后,它的引用只在 todos 或 status 真正变化时才更新,"强制重新渲染"按钮改动的 count 不会波及它,effect 自然不会再多跑。(A) 把依赖清空会让这个 effect 变成"只在挂载时跑一次",以后 todos/status 真正变化时它也不会再运行,这是另一种错误,不是修好了原来的问题。(C) 把 console.log 挪到渲染阶段,意味着每次渲染(包括无关的 count 变化)都会打印一次,比原来更频繁,并没有解决"不必要触发"这件事。

Q2:一个纯 UI 组件需要显示"点击次数"给用户看,同时还要记一个只在清理定时器时用得到、不需要显示在界面上的 ID。下面哪种 Hook 搭配最合适? (A) 点击次数用 useState,定时器 ID 用 useRef (B) 两者都用 useState,因为组件里所有要"记住"的值都该交给 useState (C) 两者都用 useRef,因为 useRef 改值不触发重渲染,性能更好

正确答案是 (A)。点击次数要显示在 UI 上,变化必须触发重渲染,所以用 useState;定时器 ID 只在清理时用一次,变化不需要让界面重画,所以用 useRef——刚好对应"要不要触发重渲染"这条分岔。(B) 会让定时器 ID 的每次变化都白白多触发一次重渲染,这正是手册点名的"过度使用 useState"的反面陷阱之一。(C) 会让点击次数变了却不触发重渲染,界面上的数字永远停在初始值,用户点了按钮也看不到任何变化。
