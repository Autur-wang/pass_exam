前端系统设计题有哪几种类型

上一课确认了"前端系统设计面试"和后端系统设计面试的核心差异在于聚焦客户端。但光知道"要聊客户端"还不够——真正走进考场,题目会以两种完全不同的画风出现,而这两种画风该往哪个方向准备、该重点讲什么,几乎是两套不同的剧本。这节课只回答一个问题:前端系统设计题主要分哪几类,每一类你该往哪想。

先回忆一下:上一课你应该已经能说出前端系统设计面试和后端系统设计面试的一个具体差异——比如前端更关注客户端架构和组件接口,后端更关注分布式一致性/可用性的取舍。现在往前一步想一想:如果考官让你"设计一个下拉菜单组件",和让你"设计一个类似 Instagram 的照片分享应用",这两道题看起来都叫"前端系统设计",但你准备的思路真的应该一样吗?先给自己一个直觉答案,再往下看。

一、先分类:应用程序 vs UI 组件

前端系统设计问题主要有两种:(1) 应用程序和(2) UI 组件。之所以要先分清这两类,是因为它们要求你展开的"架构"根本不是同一个尺度的东西——一个是"整个产品怎么搭",一个是"一个组件内部怎么搭"。分错类,后面所有的讨论重点都会跑偏。

二、应用程序类:题目长什么样、该往哪想

设计一个应用程序,思路会很接近一般的软件工程系统设计面试——事实上两者非常相似。区别在于:你应该专注在客户端,讨论应用程序架构和客户端实现细节,而不是讨论分布式系统。今天很多网站本身就是交互丰富的应用程序,几乎能做到桌面软件能做的事——Gmail、Facebook、YouTube、ChatGPT、Google 日历都是这一类。它们的共同特征是:内容经常动态变化,页面切换通常不需要整页刷新,而是用 JavaScript 拉取下一页的远程数据、动态改内容和 URL。

因为 Web 应用是涉及多模块的复杂软件,软件工程课上学过的常见应用架构——MVC(模型-视图-控制器)、MVVM(模型-视图-视图模型)——同样适用于构建 Web 应用。React 是构建交互式 Web 应用最流行的库之一,很多 React 应用采用基于单向数据流的 Flux/Redux 架构。

不同应用有各自独特的关注点,重要的是专注在这个应用特有的部分,而不是把时间都花在"适用于所有题目"的通用内容上。推荐的展开顺序是:先设计高层架构、确定系统里的组件以及组件之间的 API,再深入到几个对这道题有趣/独特的领域,讲清楚怎么实现或优化它们。

三、UI 组件类:题目长什么样、该往哪想

现代前端开发里,用组件库搭应用很常见——jQuery UI、Bootstrap、Material UI、Chakra UI 都是你可能用过的。前端工程师应该有能力构建应用所需的各种 UI 组件。有些组件很容易搭(文本、按钮、徽章),有些则复杂得多(自动完成、下拉菜单、模态框)。大多数情况下,如果考官让你设计一个 UI 组件,它属于后一类。

推荐的展开顺序是:先确定组件的子组件(比如图片轮播里有图片、分页按钮、缩略图),定义组件对外的 API(该接受哪些 props/options),描述组件内部状态,以及子组件之间的接口(如果相关),再深入性能、可访问性、用户体验、安全性等方面的优化和考量。

你可能需要写一小段代码,通常是为了以下一个或多个目的:描述组件层级结构、描述组件状态的形状、解释组件内部某段不那么直白的逻辑。比如描述一个图片轮播的对外 API,可能就是这样一段 JSX:

<ImageCarousel
  images={...}
  onPrev={...}
  onNext={...}
  layout="horizontal">
  <ImageCarouselImage style={...} />
  <ImageThumbnail onClick={...} />
</ImageCarousel>

还有一点很容易被忘掉:你几乎肯定会被期望设计一种方式,让组件的使用者(其他开发者)能自定义这个组件的外观——这部分原始手册专门用一整节展开对比不同的自定义方案,这节课先记住"要留自定义接口"这条硬要求即可。

UI 组件类的常见题目:自动完成组件、下拉菜单组件、可嵌入的轮询小部件、图片轮播、模态框组件、富文本编辑器、带排序和分页的数据表、日期选择器、多选组件。

四、关键定义

应用程序类问题
要求设计一整个产品/应用的前端系统设计题,思路接近后端系统设计但聚焦客户端架构与实现,推荐先搭高层架构和组件间 API,再深入这道题特有的一两个领域。避免把它当成"随便哪个应用都用同一套万能答案套"——每个应用独特的关注点才是分数所在。
UI 组件类问题
要求设计单个组件(通常是自动完成、下拉菜单、模态框这类较复杂的组件)的前端系统设计题,推荐先拆子组件、定义对外 API 和内部状态,再深入性能/可访问性/安全等优化。避免把它当成"随手写个组件"的编码题——它考的是接口设计和状态设计,不是现场敲代码的速度。
自定义主题(可定制外观)
UI 组件类问题里几乎必答的一项要求:要设计出让组件使用者(其他开发者)能自定义外观的方式,而不是把样式写死。避免把它当成锦上添花的加分项——它是这类题目默认就该覆盖的基本盘。

现实中怎么用。拿到一道前端系统设计题的第一步,不是急着画架构图,而是先判断它落在哪一类:题目里出现的是一个完整产品名(照片分享 App、聊天应用),大概率是应用程序类,该往"高层架构 + 组件间 API + 这个产品独特的一两个难点"去想;题目里出现的是一个具体组件名(下拉菜单、图片轮播、日期选择器),大概率是 UI 组件类,该往"子组件拆分 + 对外 API + 内部状态 + 性能/可访问性优化"去想。分类判断错了,后面十几分钟的展开方向都会偏。

一个容易踩的误区:把"适用于所有题目"的通用内容当成重点讲。不管是应用程序类还是 UI 组件类,源材料反复强调的都是同一件事——要专注在这道题特有的部分,而不是把时间花在放到哪道题都能用的套话上。比如设计照片分享应用,如果只泛泛讲"要有前端要有后端要有数据库",却没深入"照片浏览怎么做无限滚动、照片上传怎么处理大文件分片",就是典型的把通用内容当重点讲;设计下拉菜单如果只说"这是个简单组件不用深挖",也是低估了它——大多数被问到的组件恰恰属于"看似简单、实际复杂"的那一类。

今天就做的一件事:从上面两份题目清单里(应用程序类或 UI 组件类)随手挑一道,比如"设计一个下拉菜单组件"或"设计一个照片分享应用",花 2 分钟先只做一件事——判断它属于哪一类,然后写下这一类对应的展开顺序(应用程序类:高层架构→组件间 API→独特难点;UI 组件类:子组件拆分→对外 API→内部状态→优化),不用真的把整道题答完,先确认自己能条件反射地套对结构。

带走这一条:前端系统设计题分两类——应用程序类(聚焦客户端架构与组件间 API,再深入这个产品独特的难点)和 UI 组件类(聚焦子组件拆分、对外 API、内部状态,再深入性能/可访问性等优化);拿到题目先分类,再套对应的展开顺序,而不是用同一套通用答案硬套所有题。

五、自测题

Q1:考官让你"设计一个类似 Netflix 的视频流应用",这道题应该往哪个方向展开? (A) 先搭高层架构、确定组件间 API,再深入视频播放器/视频流/推荐这些这道题特有的领域 (B) 先拆这个应用有哪些子组件,再定义它对外接受的 props (C) 先讨论分布式系统里的数据分片和一致性协议,因为这本质上是个系统设计题

正确答案是 (A)。这是一道应用程序类问题,推荐顺序是先高层架构和组件间 API,再深入这道题独特的领域(视频播放器、视频流、推荐视频)。(B) 是 UI 组件类问题的展开顺序,拆的是"子组件"和"props",用错了尺度;(C) 混淆了前端系统设计和后端系统设计的边界——前端系统设计应该聚焦客户端,不是讨论分布式一致性协议。

Q2:关于 UI 组件类问题(比如设计一个下拉菜单组件),下面哪个说法最准确? (A) 因为组件相对简单,通常不需要考虑让使用者自定义外观 (B) 大多数被问到的 UI 组件属于自动完成、下拉菜单、模态框这类较复杂的组件,而且几乎都要设计可定制外观的方式 (C) 只要能现场把组件的样式和交互写出来,不需要额外讨论对外 API 或内部状态设计

正确答案是 (B)。源材料明确说大多数情况下被问到的 UI 组件属于"较复杂"这一类,而且几乎都会被期望设计自定义外观的方式。(A) 恰恰说反了——自定义主题是这类题几乎必答的基本要求,不是可以跳过的选项;(C) 混淆了这是接口与状态设计题,而不是单纯考验现场编码速度,对外 API 和内部状态正是这类题的核心考点。

有任何不清楚的,回到会话里问你的 AI 老师——可以让老师用 ELI5 讲清"为什么下拉菜单这种看起来很小的组件,在前端系统设计面试里也算一道正经的系统设计题",也可以让老师帮你把手头正在准备的某道具体题目先分好类。
