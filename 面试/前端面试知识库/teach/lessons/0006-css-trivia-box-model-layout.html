CSS 高频问答 I:盒模型、定位与布局

这节课用 9 道 h5bp 经典 CSS trivia 题,拆解前端面试里被问得最频繁的一组底层机制:盒子怎么计算尺寸(box-sizing)、一个元素怎么脱离或留在文档流(position 与 float)、脱离文档流之后父元素要靠什么才能重新"看见"它(BFC)、重叠元素到底谁盖着谁(z-index 与堆叠上下文),以及 display 属性怎么决定一个元素长什么样。这几件事平时写代码可能全靠手感,但面试官一句"为什么"追问下去,手感是顶不住的。

上一课确认了前端面试里算法题该刷到什么程度——那一课练的是"写代码解决问题"的能力。这一课换一个完全不同的考察维度:面试官不会让你写代码,只是拿着一个 CSS 概念追问"这到底是什么、为什么这样设计"。开课前先诚实测一下自己:如果被追问"box-sizing: border-box 到底改变了 width 的计算方式",你能不能脱口而出具体公式,而不是含糊说一句"更好算"?再想想"position: relative 和 position: absolute 的核心区别是什么"——是不是也只答得出"一个流、一个不流"这种笼统说法?这两个问题答得越模糊,接下来这节课就越该放慢速度读。

一、盒模型与 box-sizing:两种算尺寸的方式

CSS 盒模型描述的是浏览器给每个元素生成的矩形框:一个内容区域,外面可以套着 padding、border、margin 三层。默认情况下(box-sizing: content-box),元素设置的 width/height 只描述内容区域本身,padding 和 border 是另外加到内容区域外面的,不计入 width/height 的数值。

.example {
  box-sizing: content-box; /* 默认值 */
  width: 100px;
  padding: 10px;
  border: 5px solid black;
}

按 content-box 的算法,这个元素在页面上实际占用的宽度是 130px(100 内容 + 10×2 padding + 5×2 border)——width 说的 100px 只是内容区域,padding 和 border 都要额外往外加。把 box-sizing 换成 border-box 之后,情况反过来:width、padding、border 一起凑够 100px 总宽,内容区域反而被压缩成 70px(100 − 10×2 − 5×2)。也就是说 border-box 下,元素在页面上占用的空间就是你写的那个 width 数字,不用再手动加 padding/border。

属性box-sizing: content-box(默认)box-sizing: border-box
content是是
padding否是
border否是
margin否否

这张表最后一行值得盯着看:不管选哪种 box-sizing,margin 都不参与 width/height 的计算。margin 只影响这个盒子在页面上占用的"外部空间",盒子本身的区域到 border 就截止,不会延伸进 margin 里。因为 border-box 把 padding、border 都算进总尺寸,更贴近设计师在网格里想象内容的直觉方式,所以 Bootstrap、Tailwind、Bulma 这类框架都会全局设 * { box-sizing: border-box; },让页面上所有元素默认用这种算法。

盒模型另外两条容易被问到、又和 box-sizing 完全无关的默认行为:边框不会和相邻元素的边框折叠,每个元素的边框各自独立渲染;垂直方向上相邻块级元素的 margin 会折叠——上面元素的下 margin 和下面元素的上 margin,只取较大的那个生效,但这只发生在垂直方向、只发生在块级元素之间,水平 margin 从不折叠。另外补充两个边界情况:table、figure、input 这类元素有自己的默认宽度,不会主动撑满父容器;span 是内联元素,没有默认宽度,同样不会撑满。延伸阅读见MDN 的盒模型入门和CSS-Tricks 对 box-sizing 的讲解。

二、定位:relative / fixed / absolute / sticky / static

"已定位元素"专指 position 计算值为 relative、absolute、fixed 或 sticky 的元素——这个定义后面讲 BFC 和 z-index 触发条件时还会反复用到,先记住它。

值行为
static默认值,元素照常随文档流排布;top/right/bottom/left/z-index 全部不生效。
relative位置相对自身做偏移,但不改变布局——原来该占的空间照样留着,就像它没被定位过一样。
absolute彻底脱离文档流,相对于最近的"已定位"祖先(没有的话就相对初始包含块)定位;它设的 margin 不会跟别的元素折叠,也不会挤占别的元素的位置。
fixed脱离文档流,相对视口固定一个位置,滚动页面时它不会跟着移动。
stickyrelative 和 fixed 的混合:没越过设定的阈值之前表现成 relative,越过阈值之后表现成 fixed。

三、float 与清除浮动

float 是一个 CSS 定位属性,但浮动元素依然属于文档流的一部分——这正是它和 position: absolute 的关键区别:absolute 元素被整个移出文档流,其它元素完全不会绕着它排布;float 元素没被移出文档流,其它内容(比如文字)会绕着它环绕排布。

float 带来一个经典坑:如果一个父元素只包含浮动的子元素,父元素的高度会直接塌缩成 0——浏览器算父元素高度时,压根没把浮动的子元素计算进去。"清除浮动"说白了就是想办法让父元素重新"看见"并包住这些浮动子元素,常见三种做法:

方法怎么做适用场景 / 注意
空 div<div style="clear:both;"></div>,放在浮动元素之后最直接,但每处需要清除浮动的地方都要手动插入一个空标签
Clearfix给父元素加一个 .clearfix 类,配合 ::after 伪元素在大型项目里当成通用工具类反复用,不用到处插空标签
overflow: auto / hidden直接给父元素设置 overflow父元素会顺带建立一个新的块格式化上下文(下一节讲),从而把浮动子元素包住;但如果子元素比父元素还高,overflow: hidden 可能把多出来的内容剪掉
.clearfix::after {
  content: ' ';
  visibility: hidden;
  display: block;
  height: 0;
  clear: both;
}

题外话:早期的 CSS 框架(比如 Bootstrap 2)曾经直接用 float 实现整套网格系统;今天有了 Flexbox 和 Grid,网格布局已经不再需要依赖 float。想看 clearfix 这个技巧完整的历史演变,可以读这篇 CSS-Tricks 的文章。

四、BFC:块格式化上下文,浮动塌陷问题的答案

上一节 overflow 那种清除浮动方法,其实是在借用一个更底层的机制:块格式化上下文(Block Formatting Context,简称 BFC)。BFC 是网页视觉渲染里的一块独立区域,块级盒子在其中按规则布局;满足下面任意一条,一个 HTML 盒子就会建立自己的 BFC:

  • float 的值不是 none。
  • position 的值既不是 static 也不是 relative。
  • display 是 table-cell、table-caption、inline-block、flex/inline-flex、grid/inline-grid 中的一种。
  • overflow 的值不是 visible。

留意第二条:relative 定位不会触发新的 BFC——这一条经常被记混。

BFC 内部,每个盒子的左外边缘都贴着包含块的左边缘(从右到左的排版则贴右边缘)。同一个 BFC 内相邻块级盒子之间的垂直 margin,依然会按前面说的规则折叠;但 BFC 会挡住这种折叠往外扩散,不会影响到 BFC 外部的元素,详细规则见MDN 的外边距折叠专题。

不建立新 BFC 会有什么后果?最典型的就是上一节的浮动塌陷——包含块不会自动包住浮动的子元素。这个坏处比 margin 折叠更隐蔽,因为整个盒子会用一种看起来莫名其妙的方式塌掉,不细查很难第一时间反应过来是 BFC 没建立。MDN 这一节专门讲了怎么用 BFC 让浮动内容和旁边内容一样高。

五、z-index 与堆叠上下文

z-index 控制重叠元素的垂直堆叠顺序,但它只对"已定位元素"生效——也就是第二节表格里 position 不是 static 的那几种(以及它们的后代,或者 flex 项目)。没有设置任何 z-index 时,元素按 DOM 出现顺序堆叠,同一层级里后出现的元素会盖在前面元素上面;而只要一个元素的 position 不是 static,它(连带它的子元素)就会始终盖在所有默认 static 定位的元素之上,不管 HTML 结构里谁先谁后。

真正容易踩坑的是堆叠上下文。堆叠上下文是一个自成一体的层叠单位:进入某个堆叠上下文内部之后,子元素的 z-index 只是相对这个上下文比大小,不是相对整个文档根元素比大小。等这个堆叠上下文内部全部排好序之后,浏览器会把它当成一个整体,拿去跟父级堆叠上下文里的其它层比排序。举个具体例子:如果元素 B 视觉上盖在元素 A 上面,而 C 是 A 的子元素,那么不管 C 的 z-index 设得比 B 高多少,C 也不可能显示在 B 之上——因为 C 的排序被限制在 A 这个堆叠上下文内部,翻不出 A 这层"盒子"。

除了 position + z-index 这对组合,opacity 小于 1、filter 不是 none、transform 不是 none 这几个属性也会各自触发一个新的堆叠上下文——具体哪些条件会创建堆叠上下文,MDN 列了一份很长的规则清单。

六、display 属性:block、inline、inline-block 怎么选

display 属性决定一个元素在布局里长什么样。常见取值:

值效果
none不渲染这个元素,子元素也全部一起消失,文档表现得就像它压根不存在。
block独占一整行(块方向,通常是水平方向)。
inline可以和别的内容并排放。
inline-block基本表现像 inline,但允许设置 width/height 等 block 才有的属性。
flex / grid变成块级 flex/grid 容器,可以用相应的布局模型摆放子元素。
table / table-row / table-cell分别表现得像 <table>/<tr>/<td>。
list-item表现得像 <li>,可以设置 list-style-type/list-style-position。

完整取值列表见MDN 的 display 文档。面试里被追问最多的,是 block、inline-block、inline 这三者的具体差别:

七、关键定义

盒模型(Box Model)
浏览器把每个元素渲染成内容、padding、border、margin 四层嵌套的矩形框;box-sizing 决定 width/height 只算内容(content-box),还是把 padding 和 border 也算进去(border-box)。避免以为 border-box 会把 margin 也纳入计算——不管哪种 box-sizing,margin 都从来不计入元素自身的 width/height。
BFC(块格式化上下文)
块级盒子在其中布局的一块独立视觉区域;float 非 none、position 为 absolute/fixed、特定 display 值或 overflow 非 visible 都会触发它,最实际的用途是让容器"包住"浮动的子元素。避免以为 position: relative 也能触发 BFC——按判定条件,只有 position 既不是 static 也不是 relative 才算。
堆叠上下文(Stacking Context)
一个自成一体的层叠单位,内部子元素的 z-index 只在这个上下文内部比大小,拿到上下文外部毫无意义。避免以为子元素设一个超大 z-index 就能盖过父级堆叠上下文之外的元素——只要父元素本身的堆叠顺序被排在别人下面,子元素再高的 z-index 也翻不出这层"盒子"。

现实中怎么用。写组件库或页面布局代码时,几乎默认会在全局 CSS 里设 * { box-sizing: border-box; },照着 Bootstrap/Tailwind/Bulma 的做法,让宽高心算不用再手动加 padding/border;遇到"父元素高度莫名塌陷"这种诡异现象,先怀疑是不是浮动子元素在作怪,加一个 overflow: hidden 或专门的 .clearfix 类触发 BFC,把它包住;做弹窗、下拉菜单一类悬浮 UI 时,如果 z-index 加到很大还是压不住别的元素,别急着继续往上加数字,先查它和目标元素是不是根本不在同一个堆叠上下文里。

一个容易踩的误区:以为 z-index 是全局的一把尺子,谁的数字大就一定盖住谁。它其实是分层比较的——一旦一个元素的祖先建立了自己的堆叠上下文,这个元素的 z-index 就被"锁"在了祖先内部,出了祖先这层"盒子"就不再算数。给一个深藏在某个堆叠上下文里的子元素设 z-index: 9999,如果它的祖先本身就排在别的元素下面,这个 9999 照样翻不上去——这正是很多人调 z-index 调到很大的数字还是没用的真正原因,该查的是祖先的堆叠顺序,不是继续加大子元素的数字。

今天就做的一件事:打开你之前写过的任意一个项目,搜一下全局 CSS 里有没有 * { box-sizing: border-box; }——如果没有,想清楚原因再决定要不要补上;再找一处用了 float 布局或者 overflow: hidden 清除浮动的地方,对着第四节 BFC 的四条触发条件,确认自己当时是真的理解它为什么生效,还是只是"蒙对了"。

带走这一条:这九道题背后其实就一件事——盒子怎么算尺寸(box-sizing)、怎么脱离或留在文档流(position/float)、脱离文档流之后怎么被父元素重新"看见"(BFC)、重叠时谁盖住谁(堆叠上下文),是四个各自独立又互相牵连的机制,分开记、想清楚各自的触发条件,别混在一起囫囵吞下去。

自测题

Q1:关于 box-sizing: border-box,下面哪个说法准确? (A) width 和 height 只包含内容区域,padding 和 border 需要另外加到总尺寸上 (B) width 和 height 包含内容、padding 和 border(但不包含 margin),所以设置的 width 就是元素在页面上实际占用的宽度 (C) width 和 height 包含内容、padding、border 和 margin 的总和

正确答案是 (B)。border-box 把 padding 和 border 都算进 width/height 里,所以写的 width 数字就是页面上实际占的宽度。(A) 描述的其实是默认的 content-box 行为,不是 border-box;(C) 错在把 margin 也算了进去——不管哪种 box-sizing,margin 从来不参与 width/height 的计算,它只影响盒子外部占用的空间。

Q2:元素 A 建立了自己的堆叠上下文,A 的子元素 C 的 z-index 设成了 9999;A 的兄弟元素 B 视觉上正好压在 A 上面。下面哪个说法符合堆叠上下文的规则? (A) 不管 C 的 z-index 设多大,只要 A 整体已经排在 B 下面,C 就不可能显示在 B 之上 (B) 只要把 C 的 z-index 设置得比 B 大,C 就会显示在 B 上面 (C) z-index 只在同一个 HTML 标签层级之间比较,和父子关系完全没关系

正确答案是 (A)。C 的 z-index 只在 A 这个堆叠上下文内部有意义,一旦 A 整体在父级堆叠顺序里排在 B 下面,C 再高的 z-index 也翻不出 A 这层"盒子"。(B) 正是最常见的误区——把局部比较误当成全局比较;(C) 说反了机制,z-index 的比较范围恰恰是由父子的堆叠上下文关系决定的,不是什么"同一层级"的说法,而且父子关系正是这道题成立的关键原因。
