受控/非受控表单 + 不同输入类型怎么处理

上一课讲的是事件已经触发之后,你能不能拦住它往哪走;这节课往前退一步,回到事件最常打交道的地方——表单输入框。同一个 <input>,它当前的值到底存在哪里、由谁说了算?这决定了你写的是受控组件还是非受控组件,也决定了 checkbox、radio、select 这些不同的输入类型,各自要盯哪个属性。这节课只讲这两件最基础的事,复杂表单状态和错误校验策略留给接下来两课。

开课前先回忆一下:0030 讲 preventDefault 时,举的例子正是一个 <form>——调用 event.preventDefault() 能拦住表单提交后的整页刷新。但那节课没细讲这个 <form> 里的 <input> 本身,它的值是怎么来的、用户打字时发生了什么。这节课把镜头拉回到这个问题:同一个输入框,值存在 React state 里和存在 DOM 自己手里,是两种完全不同的活法。

一、受控与非受控:值到底存在哪

React 里管理表单输入,分两种方式,区别就在"数据到底存在谁手里"。

在受控表单组件里,React 管理表单元素的状态:输入的 value 存进状态变量,再通过 onChange 处理程序更新。这是一个闭环——value 读的是 state,onChange 写回 state,下一次渲染又读到刚写回去的新值:

const [name, setName] = useState('');

<input
  type="text"
  value={name}
  onChange={(event) => setName(event.target.value)}
/>
stateReact 状态
→
value={state}渲染到 input
→
用户输入触发 onChange
→
setState(...)写回状态,回到最左边

在非受控表单组件里,表单元素的值由 DOM 自己管理,不经过 React state。要在提交时拿到这个值,源材料给了两种办法:用 FormData 直接从 event.target 建一个表单数据实例,配合 formData.get('name')(对应 input 上的 name 属性)读值;或者用 useRef() 拿到 input 节点的引用,通过 nameRef.current.value 直接读。

const nameRef = useRef();

function handleSubmit(event) {
  event.preventDefault();
  const formData = new FormData(event.target);
  console.log(formData.get('name'));   // 办法一:FormData
  console.log(nameRef.current.value);  // 办法二:ref
}

二、怎么选:一张对比表

源材料给了一张对比表,把两种方式的差异摊开:

特性受控表单非受控表单
存储状态的位置React 状态(useState)原生 DOM
性能需要在更新时重新渲染,大型表单可能吃力对简单用例更有效率
验证容易实现需要手动验证
表单重置容易(setState(''))需要 ref.current.value = '' 或触发 'reset' 事件
用例动态表单、验证、实时更新简单表单、文件上传或集成非 React 代码

落到判断标准上,源材料给了两条:需要动态验证、根据前面的输入切换其他字段是否显示、或者要管理嵌套表单状态时,用受控;表单很大、要跟非 React 代码集成、或者要在性能上抠细节时,用非受控。它还补了一句更偏实战的个人经验:面试里表单通常字段不多,受控和非受控都能用,但作者本人更偏向受控——因为面试官经常会追加"重置一下""输入时就校验"这类要求,受控组件接这些需求更顺手,不是说非受控不行,只是受控这条路遇到追问时改起来更省事。

三、五种输入类型,各自靠哪个属性接值

全部走受控方式,五种输入类型的差别,可以收进一张表:

输入类型关键元素关键值属性状态更新
文本输入<input>valuesetState(event.target.value)
复选框<input>checkedsetState(event.target.checked)
单选组<input>checkedsetState(event.target.value)
文本区域<textarea>valuesetState(event.target.value)
选择下拉菜单<select>valuesetState(event.target.value)

复选框表达的是一个布尔值:选中或未选中,这也是它和其它四种类型最关键的差别——它绑定的是 checked 而不是 value,onChange 里读的是 event.target.checked。

单选组要求多个 <input type="radio"> 共享同一个 name(比如 name="gender"),这样浏览器才知道它们是一组,同一时刻只能选中一个;每个 radio 的 checked 通过判断当前状态是否等于自己的 value(如 gender === 'male')来决定,onChange 统一把状态设成被点的那个 value。

文本区域有个和原生 HTML 不一样的地方——普通 HTML 里 <textarea> 的内容写在标签中间(子节点),但 React 里用 value 属性,和 <input> 保持同一套心智模型,不需要单独记一套写法。

选择下拉菜单把 value 绑在 <select> 本身上,<option> 只负责列出可选项,不需要在某个 <option> 上单独加 selected。

四、text 输入还能怎么细分

type 属性除了默认的 text,还有一批更专用的值,自带不同程度的内置验证:

type用途内置验证
text常规文本输入否
number数字文本输入是,仅允许数字;可配合 min/max 做更多限制
email电子邮件地址是,必须包含 @
password安全密码输入否,但输入内容会被遮蔽显示
search带清除按钮的搜索字段否
tel电话号码否;可配合 pattern 做额外校验
urlURL是,必须以 http:// 或 https:// 开头
datetime-local日期和时间选择是
color颜色选择器是

源材料给的取用建议很直接:通用字段用 text;只要数值和数字校验用 number;想蹭浏览器内置校验就用 email/url/tel;安全文本用 password;搜索优化字段用 search;要日期时间选择用 datetime-local;要选颜色用 color。挑对 type,很多校验工作浏览器已经先做了一遍,不用自己再写一次。

五、关键定义

受控表单组件(Controlled Form Component)
输入的值存进 React state,通过 value 属性渲染、onChange 处理程序更新,值的每一次变化都经过 React。避免把"受控"当成表单必须遵守的规则——它只是让 React 接管值的一种方式,字段不多的表单里,非受控往往同样能用,不存在必须二选一的强制标准。
非受控表单组件(Uncontrolled Form Component)
值全程留在 DOM 手里,不经过 React state;提交时通过 FormData 或 ref 读一次当下的值。避免以为非受控组件就拿不到输入值——只是拿值的时机变了,从"实时同步进 state"变成"提交那一刻才去读"。
单选组(Radio Group)
一组共享同一个 name 属性的 radio,靠这个共享的 name 让浏览器知道它们互斥,让用户在同一时刻只能选中其中一个;每个 radio 的 checked 通过和自身 value 比较当前状态值来判断。避免给同组 radio 各自起不同的 name——一旦 name 不同,浏览器就不再把它们视为同一组,用户就能同时选中多个。

现实中怎么用。面试现场遇到"写一个表单"类题目,先问自己一件事:这个表单要不要在打字过程中就做事(实时校验、字段联动、限制字数)?如果要,直接上受控,不用犹豫;如果只是收集几个字段、提交时读一次,非受控配 FormData 往往更省代码。定下受控之后,再照着上面的表格一个个对号:checkbox/radio 绑 checked,其余绑 value;radio 别忘了共享 name;textarea 别按 HTML 老习惯把文字写进标签中间。

三个最容易踩的坑。第一,把 checkbox 也按 text 输入的老套路绑成 value + event.target.value——checkbox 元素确实也有 value 属性,代码不会报错,但表示选中状态的那个布尔值永远收不到 true/false,该读的是 event.target.checked。第二,给多个 radio 各自起不同的 name,而不是让它们共享同一个 name——一旦 name 不一样,浏览器不再认为它们是同一组,用户能同时选中好几个,而不是"只能选一个"。第三,把 <textarea> 当成普通 HTML 用,把文字写进标签中间当子节点——React 里这样写不会生效,textarea 的值同样要走 value 属性,和 <input> 保持一致。

今天就做的一件事:搭一个包含 text/checkbox/radio/select 四种输入的小表单,每种都用受控方式接住,在页面上把当前 state 整个 JSON.stringify 打出来,切换每个输入观察哪个字段变了;然后故意把某个 radio 的 name 改错,看浏览器允许同时选中几个,亲眼确认"共享 name"这件事的作用,比记住这条规则本身更管用。

带走这一条:受控和非受控的差别,归根到底是"值存在 state 里还是 DOM 里";五种输入类型的差别,归根到底是"该盯 value 还是 checked、要不要共享 name"。面试现场遇到不熟悉的输入类型,先问自己这两句话,基本能推出该怎么写,不需要死记每种类型的代码。

六、自测题

Q1:关于受控表单组件和非受控表单组件,下面哪个说法最准确? (A) 受控表单组件的值由 DOM 自己管理,不经过 React state;非受控表单组件反过来,值必须存进 state 才能被 onChange 更新 (B) 受控表单组件把值存进 React state,通过 onChange 更新;非受控表单组件的值由 DOM 自己管理,提交时通过 ref 或 FormData 读取 (C) 两者在 React 内部的渲染机制上完全等价,选哪个只是命名习惯不同,不影响代码怎么写

正确答案是 (B)。受控组件的 value 读自 state、onChange 写回 state;非受控组件的值全程留在 DOM 手里,直到提交才通过 ref.current.value 或 FormData 读一次。(A) 把两者的定义整个说反了;(C) 忽略了两者在"谁维护值"上有具体机制差异——比如非受控组件要重置输入,不能靠 setState(''),得手动改 ref.current.value 或触发 reset 事件,不是纯粹的命名区别。

Q2:一个 <input type="checkbox"> 和一个 <input type="text">,在受控模式下分别应该绑定并通过 onChange 更新哪个属性? (A) 两者都绑 value,因为 React 里所有输入类型统一只认 value 作为受控依据 (B) checkbox 绑 value、通过 event.target.value 更新;text 绑 checked、通过 event.target.checked 更新——两者刚好用反过来的属性 (C) checkbox 绑 checked、通过 event.target.checked 更新;text 绑 value、通过 event.target.value 更新——两者用的不是同一个属性

正确答案是 (C)。checkbox 表达的是布尔值,靠 checked 属性和 event.target.checked 判断选中状态;text 表达的是字符串内容,靠 value 属性和 event.target.value 读取输入。(A) 忽略了 checkbox 这种布尔类型元素本身不是靠 value 判断选中与否,写成 value 代码不会报错,但状态收不到 true/false;(B) 把两者对应关系正好写反,text 输入该绑的是 value,不是 checked。
