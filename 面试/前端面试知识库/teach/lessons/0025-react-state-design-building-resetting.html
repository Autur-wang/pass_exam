状态怎么构建 + 何时重置

上一课讲的是"给定状态,UI 该长什么样"这套声明式心智模型;这节课往前问一句更具体的问题——那个"状态"本身该怎么设计?面试限定的 UI 编码题字段不多,但正因为字段少,state 分成几份、怎么分,反而是面试官一眼就能看出你功底的地方。这节课讲手册里构建状态的四条具体原则,以及另一件容易被忽略的事:什么时候"整体换新"比"逐个清空"更可靠。

先回忆一下上一课:声明式思考的第三步是"设计一个最小结构来表示状态",当时举的例子是别同时维护 tasks、completedTasks、incompleteTasks 三份数组,已完成任务应该从 tasks 派生出来,而不是单独存一份。这节课要把"怎么设计最小状态结构"这件事讲得更具体——手册给出的不只是"别重复存"这一条,还有另外三条同样具体的原则,以及配套的"该整体重置的时候该怎么做"。

一、为什么状态结构本身是一道设计题

状态是 React 应用的支柱,决定组件随时间的行为和渲染方式。和写死的静态数据不同,状态支持动态更新、用户交互和实时变化,不需要整页重新加载。结构良好的状态能提高代码可维护性、增强性能、减少不必要的重新渲染;结构糟糕的状态管理则容易导致出错的代码、运行变慢、行为不可预测。

创建一个有状态组件时,你要做两个决定:用几个状态变量,以及怎么组织它们的数据结构。次优的设计仍然能跑出一个功能正常的应用,但面试限定的时间和字段数量,让"structure 得好不好"这件事被放大了——手册给出四条具体、可以直接套用的原则。

二、构建状态的四条原则

1. 状态尽可能本地化

当某个状态只有一个组件在用,不要因为"以后可能要往上提"就提前把它放到父组件、再通过 props 一层层往下传。父组件的状态一变,所有依赖它的子组件都要跟着重新渲染;状态留在真正用到它的组件内部,变化时只需要重渲染这一小块。比如一个只在自己内部使用的计数按钮,count 就该待在按钮组件里,不必先提到 App 再传 count/setCount 两个 props 下去。

2. 把相关状态组合在一起

如果两个值本来就是共同描述"一件事",分开用两个 useState 管理会让更新变得麻烦、也容易漏改一个。

❌ x、y 分开管理

const [x, setX] = useState(0);
const [y, setY] = useState(0);

function handlePointerMove(e) {
  setX(e.clientX);
  setY(e.clientY);
}

✅ 合并成一个 point 对象

const [point, setPoint] = useState({ x: 0, y: 0 });

function handlePointerMove(e) {
  setPoint({ x: e.clientX, y: e.clientY });
}

x 和 y 共同定义的是同一个点,理应作为一个单元一起管理和更新。

3. 避免状态中可能出现的矛盾

一个更容易被忽略的信号是:几个各自独立的布尔状态,组合起来能拼出一种逻辑上根本不该存在的情况。

❌ 三个独立布尔值

const [isSubmitting, setIsSubmitting] = useState(false);
const [isSubmitted, setIsSubmitted] = useState(false);
const [isError, setIsError] = useState(false);

// 如果不小心写出:
// setIsSubmitting(true); setIsSubmitted(true);
// 组件就会同时"在提交"又"已提交"

✅ 合并成一个 status 字段

const [status, setStatus] = useState('idle');
// 'idle' | 'submitting' | 'success' | 'error'
// 任意时刻只可能处于其中一种取值

三个独立布尔值理论上能组合出 8 种状态,但表单实际只有 4 种合理阶段——多出来的组合就是"矛盾状态"的来源。用一个 status 字段替代之后,UI 一次只能处于一种状态,错误处理也更干净:请求失败时只需要把 status 设成 'error',不会有哪个布尔值忘了改回去、让 UI 同时显示"提交成功"和"提交失败"。

4. 派生状态而不是存储冗余值

如果一个值能从别的状态直接算出来,就不要专门为它开一个新的 useState——那样会多出一份需要手动保持同步的"事实来源"。

const [todos, setTodos] = useState(['任务 1', '任务 2']);

const count = todos.length; // 不需要单独存,也不需要 useEffect 去同步

手册里还给出其他几条构建状态的原则,比如避免状态中的重复和避免深度嵌套状态——按手册原文的说法,这几条和面试关系不大,这节课不展开,想深挖的话可以直接点链接去读原文。

三、重置状态:什么时候该整体换新,而不是逐项复原

重置状态最直接的办法,是把每个字段用 setter 设回它的初始值。但当状态字段有好几个时,手动挨个调用 setter 很容易漏掉某一个——这也是为什么前面"把相关状态组合在一起"、以及给每种可能的操作单独写一个函数会重要:字段合并得越干净,需要记住的 setter 就越少。

还有另一种更彻底的做法:改变要重置的组件的 key 属性。key 变化时,React 会认为这个位置上出现了一个"不同的元素",于是把旧实例整个卸载、再重新创建一个全新实例——不需要你一个个列出该清空哪些字段。key 不只在渲染列表时有用,单个组件上一样适用。

用户点击"重置表单"按钮
↓
setKey(prev => prev + 1) —— key 的值变了
↓
React 发现同一位置元素的 key 不一样了,判定这是"不同的元素"
↓
卸载旧的 Form 实例,重新创建一个全新实例——内部所有 state 回到初始值
function Form() {
  return (
    <form>
      <input type="text" placeholder="John Doe" />
      <button>提交</button>
    </form>
  );
}

function App() {
  const [key, setKey] = useState(0);

  return (
    <div>
      <Form key={key} />
      <button onClick={() => setKey((prev) => prev + 1)}>重置表单</button>
    </div>
  );
}

这里发生了两件事:改变 key 会强制 React 卸载并重新挂载 Form 组件;原生 <form> 元素本身有内置的重置方式(比如 formElement.reset()),但 key 这种做法适用于任何组件,不限于表单。更完整的讨论,在 react.dev 上有专门一篇讲保留和重置状态,这节课只挑了面试里最常被追问的"整体重置"这一种场景。

四、关键定义

派生状态(derived state)
能够从已有的 state 或 props 直接计算出来的值,不需要单独用 useState 存一份、也不需要额外的 useEffect 去同步它。避免把"读取方便"当理由,专门开一个 state 字段去缓存一个本来能算出来的值——那样反而多了一份要手动保持同步的"事实来源"。
矛盾状态(不可能状态)
几个各自独立的 state 字段组合在一起,能拼出一种逻辑上根本不该存在的情况,比如同时"在提交"又"已提交"。避免看到某个流程有三种以上互斥的阶段,还继续用几个独立布尔值分别表示——该考虑合并成一个 status 字段。
用 key 强制重挂载
给组件设置一个会变化的 key;key 一变,React 就把这个位置上的旧实例整个卸载、重新创建一个全新实例,内部所有 state 自然回到初始值。避免把"重置状态"直接等同于"逐个调用 setter 把每个字段设回初始值"——字段一多,很容易漏掉某一个。

现实中怎么用。面试限定的 UI 编码题字段通常不多,但正因为字段少,状态到底怎么分反而更容易被面试官一眼看穿。写状态之前先问自己三句话:这份数据是不是只有某个子组件专用,可以不往上提?哪几个字段其实描述的是"同一件事",该合成一个对象或一个 status?有没有哪个字段其实能从别的字段算出来,不需要单独存。想清楚这三句话,比写完代码之后再回头重构省事得多。

一个容易踩的误区:把"重置状态"想成必须逐个手动清空每个字段。字段一多,setName(''); setEmail(''); setAgree(false); 这种逐条重置的写法很容易漏掉某一个——表单看起来"重置"了,实际还留着某个字段的旧值。当需要重置的是一整棵子树,而不是一两个字段时,改变外层传给它的 key 往往比一条条数清楚该重置哪些字段更可靠。

今天就做的一件事:找一个你最近写过、字段有三个以上 useState 的组件,逐个检查:有没有哪两个字段其实描述的是同一件事(该合并)?有没有哪个字段其实能从别的字段算出来(该删掉,改成派生)?写下你发现的至少一处可以合并或删掉的字段。

带走这一条:好的状态结构不是"字段越细越安全",而是每一份事实只存一处、互斥的几种情况合并成一个字段;当需要的是"整体换新"而不是"逐项复原"时,改一次 key 比记住该调用哪几个 setter 更不容易出错。

五、自测题

Q1:关于"避免状态中可能出现的矛盾",下面哪个说法最准确? (A) 只要分别用 isSubmitting、isSubmitted、isError 三个独立的 useState,读写都很方便,不需要额外处理矛盾问题 (B) 把互斥的几种情况合并成一个 status 字段(比如 "idle"/"submitting"/"success"/"error"),让状态本身就排除掉不合法的组合 (C) 矛盾状态只是理论上的担心,实际渲染时 React 会自动忽略互相冲突的判断分支

正确答案是 (B)。表单例子里,如果新代码不小心同时执行了 setIsSubmitting(true) 和 setIsSubmitted(true),组件会同时"在提交"又"已提交",这种没有意义的组合正是三个独立布尔值带来的风险;合并成一个 status 字段之后,组件在任意时刻只能处于其中一种取值。(A) 低估了这种矛盾的真实后果——它不只是"不方便",而是会让 UI 呈现出逻辑上说不通的状态;(C) 不成立,React 不会对你写的判断条件做任何"自动排除冲突"的检查,该怎么渲染完全由你写的 JSX 条件决定,矛盾的分支该显示还是会显示。

Q2:关于用改变 key 属性来重置组件状态,下面哪个描述最准确? (A) key 变化时 React 会保留组件实例,只是清空它内部的 state 字段,效果和逐个调用 setter 完全一致 (B) key 只在渲染列表(map)时才有意义,给单个组件设置 key 不会产生任何效果 (C) key 变化时 React 会认为这是一个不同的元素,从而卸载旧实例并重新创建一个全新实例,内部 state 因此回到初始值

正确答案是 (C)。key 变化会让 React 判定"这是位置上的一个新元素",于是走卸载旧实例、创建新实例的路径,新实例的 state 从初始值重新开始,不需要手动列出该清空哪些字段。(A) 说反了机制——React 走的不是"保留实例、清空字段"这条路,而是彻底卸载重建,这也是它能保证不漏掉任何字段的原因;(B) 说错了适用范围——给单个组件设置 key、需要重置时改变这个值,正是手册里用来"对组件做完全重置"的通用手法,不是列表渲染的专属技巧。
