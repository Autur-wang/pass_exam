UI 面试自查清单怎么用

上一课讲的是组件 API 该怎么设计;这节要回答一个更底层的问题——综合面试手册专门整理了一份横跨十几个类别的自查清单,列出了改进 UI 编程/系统设计面试代码的具体提示。这节不逐条背这份清单,而是回答:它该在面试前用,还是面试中用?怎么用才不是死记硬背?

先回忆一下:0011 课讲过 UI 编程面试比纯算法编码面试多考一项权重更高的维度——"领域专业知识",也就是浏览器、HTML、CSS、可访问性这些前端专属知识;上一课接着往下讲的是组件 API 怎么设计,才能让外观可定制、还能支持国际化。这两节其实都只覆盖了"领域专业知识"里的一小块。现在把镜头拉远:如果把这项知识拆到底,面试官会从多少个不同角度检查你写的 UI 代码?先凭印象猜一个数字,再往下看这份清单给出的答案。

一、这份清单是什么、从哪来

这份清单出自综合面试手册的 user-interface-questions-cheatsheet 一文,原文开头就交代了定位:它是一份用来"改进你在前端面试中必须构建/设计的用户界面"的提示集合,同时适用于两个场景——用户界面编码面试(0011 课讲的正是这一场景)和前端系统设计面试。

换句话说,这份清单不是针对某一道具体题目(比如"实现一个手风琴组件")给出的解法,而是横跨"代码怎么组织""状态怎么设计""安全怎么处理"等十几个维度的通用提示——更适合把它当成一份体检报告的项目清单,而不是某一道题的参考答案。

二、十三个类别覆盖什么

数一数原文的分节,一共十三类,每一类背后都对应一个自查问题:

类别核心自查问题
一般问题有没有拆成里程碑?每完成一步有没有在浏览器里测?能不能用框架而不是死磕 Vanilla JS?
组件组织渲染代码和数据来源分开了吗(容器/表现模式)?组件能不能创建多个独立实例?
状态设计状态是不是已经最小化?基本状态和派生状态分清楚了吗?复杂交互要不要上 reducer?

HTML标签语义化吗?标题层级只有一个 <h1> 吗?表单的 label/for、type、原生校验用对了吗?
CSS/样式写的是朴素 CSS 吗?有没有命名约定?组件里是不是避免了 #id 选择器?
用户体验移动端能用吗?错误状态清楚吗?图片适配、乐观更新考虑了吗?
网络请求的 pending/success/error 三种状态都反映了吗?有没有防竞态、防重复提交?
可访问性只用键盘能操作吗?屏幕阅读器能用吗?颜色对比度、元素尺寸够吗?
边缘情况长字符串、空状态、列表项过多这几类情况,想过怎么处理吗?
性能节流防抖、缓存、按需加载、预取这几招,哪些用得上?
安全有没有把用户输入直接塞进 innerHTML?URL 参数编码、CSRF 防护想过了吗?
国际化标签文案能不能替换成别的语言?长字符串、从右到左的书写方向考虑了吗?

这十三类里,组件组织、状态设计接下来的组件 API 设计几节课会单独深挖。这节课的重点不是把每一类展开讲一遍,而是回答下一个更实际的问题:这份清单本身,该在什么时候拿出来用。

三、面试前怎么用:当自评表

备考阶段,这份清单最适合的用法和 0001 课讲的自评方法是一回事:不是把十三类全部刻意背下来,而是拿它当一份体检单,诚实标出"这一类我心里有底"还是"这一类我心里没数"。比如"一般"这一类里"拆里程碑、边写边测、优先用框架"这几条,本质是临场习惯,面试现场来不及现学,只能靠考前反复练习养成;"状态设计"里的 reducer 模式,如果之前没写过 useReducer,考前找一两道状态复杂的题练一遍,总好过面试现场第一次尝试。

四、面试中怎么用:当心智提醒,不是台词稿

到了面试现场,把十三类逐条对着念是不现实的——时间有限,面试官也不是在考你能不能背下清单。手册自己在"边缘情况"这一类里给出的建议,其实可以推广到整份清单:"在面试中,你可能没有足够的时间来处理代码中的所有边缘情况,但最好在面试中提及它们以获得加分。"这句话背后的逻辑,同样适用于其它类别——网络状态的竞态处理、国际化的从右到左布局,现场很可能真的没时间全部写出来,但主动说一句"这里我还没处理 XX,时间够的话我会怎么做",比什么都不说要好得多。这正好对应 0011 课讲的临场流程里"主动讲权衡"那一步。

五、关键定义

UI 面试自查清单(User Interface Questions Cheatsheet)
综合面试手册整理的一份横跨十三个类别的提示集合,用来改进 UI 编程面试和前端系统设计面试里要写的界面代码。避免把它当成评分表逐项打勾对答案——它更像一份体检项目清单,提醒你该往哪些方向检查,不是要求每一类都写出代码才算过关。
加分项口头提及(Mentioning for Bonus Points)
手册在"边缘情况"一节明确指出:面试时间有限,做不完所有边缘情况没关系,但主动口头提出来就能拿到加分。避免把"没时间做"当成"不用说"——不说出来,面试官只会看到你漏掉了这一块,而不是你注意到了但做了取舍。

现实中怎么用。把十三个类别摘成一页纸,考前对着它做一次诚实自评,标出薄弱类别针对性补;考中不需要带着清单看,写完基础功能后,依次扫一遍网络状态、可访问性、边缘情况这几个最容易被忘、也最容易靠一句话补分的类别,没时间实现的,照着"边缘情况"那一节的建议,口头说清楚就好。

一个容易踩的误区:把这份清单当成面试现场要逐条念出来的台词稿,或者反过来完全不看,凭感觉写代码。十三类一次性在脑子里过一遍不现实,机械地念条目也不会让面试官觉得你更专业——手册给的方法是"提及",不是"背诵":挑出几类高杠杆的,该实现就实现,实现不完就用一句话讲清楚权衡,这才是清单真正的用法。

今天就做的一件事:翻出一道你之前写过的 UI 编程题(哪怕是手风琴或标签页这类简单组件),对着上面的十三类表格,逐类问自己"这一类我漏了什么"。挑出 2~3 个明显没做到的,不用回去补代码,只需要口头讲清楚"这里我没处理 XX,如果时间允许我会怎么做"——这本身就是在练面试现场真正要用的能力。

带走这一条:这份十三类的自查清单不是用来背的——面试前拿它当自评表,诚实标出薄弱类别针对性练;面试中拿它当心智提醒,写完基础功能后扫一遍高杠杆的几类,没时间实现的部分用一句权衡说明口头补上,好过什么都不说。

六、自测题

Q1:关于这份 UI 面试自查清单该怎么用,下面哪个说法最准确? (A) 面试现场应该把十三个类别逐条念给面试官听,证明自己记得完整 (B) 清单更适合当备考阶段的自评工具、面试中的心智提醒,而不是逐条背诵或逐条打勾 (C) 这份清单只适用于前端系统设计面试,和现场编码面试无关

正确答案是 (B)。清单的作用是帮你定位薄弱环节、提醒自己该往哪几个方向检查,不是要求逐条背诵或逐条打勾对答案。(A) 把"提及"曲解成了"逐条念台词",面试现场时间有限,机械念条目也不会加分;(C) 忽略了原文开头就说明它同时适用于用户界面编码面试和前端系统设计面试两个场景,并不是只针对系统设计。

Q2:手册在"边缘情况"这一类里明确给了一条建议,这对面试中怎么用清单有什么启发? (A) 边缘情况必须在写代码前全部列出并逐一实现,否则整个方案不算完整 (B) 只要口头提到过"边缘情况"这个词,就不需要再处理任何常见错误 (C) 面试时间有限,处理不完所有边缘情况没关系,但主动口头提及能拿到加分,说明没写完的部分可以靠"说出来"补上一部分分数

正确答案是 (C)。手册原文承认面试时间有限,不要求全部实现完才算数,主动提及就能拿到加分。(A) 错在把"不要求全部实现"说反成了"必须全部实现";(B) 曲解了"提及"的含义——提及是对没做完部分的补充说明,不代表可以忽略手册里明确点出的、本该处理的常见情形(比如空状态、长字符串)。

七、主推资源

以下四条都是清单原文在对应类别里点名的资源,想往下深挖某一类时按这个顺序看:

  • Presentational and Container Pattern —— "组件组织"一类点名的容器/表现模式原始出处,拆分渲染代码和数据来源的具体做法。
  • React · Managing State —— "状态设计"一类推荐的文档,讲怎么设计和使用组件状态,思路不限于 React。
  • OWASP XSS Prevention Cheat Sheet —— "安全"一类点名的 XSS 防护参考。
  • web.dev · Learn Accessibility —— "可访问性"一类推荐的免费深入课程。

有任何不清楚的,回到会话里问你的 AI 老师——可以让老师用 ELI5 讲清"这份清单和逐条背知识点有什么不一样",也可以现场挑一道你写过的 UI 题,让老师陪你按十三类过一遍,练一练怎么口头讲清楚没做完的权衡。
