Agent 可靠性:误差累积、pass^k、反思与人机交接

这节课把「怎么让 agent 真的可靠」拆成五道面试常考的硬题:「为何 agent 在长任务上会崩,即便每步都很可能成功?」「怎么评估 agent,为什么平均准确率不够?」「planning-first 与 reactive(ReAct)有什么区别?」「反思/自我批评何时真有用?」「coding harness 靠什么可靠、agent 该怎么把活交给人?」(源:AI 工程师题库 Q71、Q64、Q66、Q67、Q73、Q74)。一句话预告:可靠性不住在模型里,住在你围着模型搭的那圈 harness 里。

上一课(0020)我们讲了 agent 的记忆与编排——用外置状态、compaction、子 agent 让它跨越单个上下文窗口活下来。那是「怎么让它跑得久」。先别往下看:一个能跑很久的 agent,如果每一步都有 95% 的把握,你觉得它跑完 20 步任务的整体成功率,大概是多少?凭直觉猜一个数。

一、误差累积:为何长任务会崩(Q71)

直觉陷阱在于:我们习惯把「每步 95% 可靠」当成「整体挺靠谱」。但多步任务里,误差是乘性叠加的,不是相加。要整件事成功,得每一步都成功——概率相乘,一路往下掉:

误差累积(compounding / multiplicative error)
$$P_{\text{success}} = p^{\,n}$$
$p$ 是单步可靠度,$n$ 是步数。每步 95%、跑 20 步:$P=0.95^{20}\approx 0.36$,整体成功率只剩约 36%。单步看着很稳,链条一长就塌。

而且现实比这条曲线更糟,因为失败并不「独立」——它级联:

  • 污染下游:一个早期的错误观察或坏工具结果(读错文件、误解一个报错)会被喂进上下文,毒害其后所有推理步。错误不是孤立扣分,而是往后传染。
  • context rot:随着上下文被越堆越多的旧工具输出、过时推理塞满,模型的连贯性会退化,后面的步反而更容易出错——步数越多,单步可靠度本身也在悄悄下滑。

所以核心结论:平均单步准确率会误导人。它掩盖了乘性衰减和级联。真正该测的是端到端任务成功率与下面要讲的 pass^k。缓解方向也顺势而出——用更少、更可靠的步骤,给每步加核验与恢复,做紧凑的上下文管理,并在高危处插人工检查点。

二、怎么评估 agent:pass^k 与轨迹(Q64)

评估 agent 不能只问「对没对」,要同时看两层:结果(outcome)+ 轨迹(trajectory)。

结果
任务完成了吗
最终产物对不对
轨迹
是否「合理地」达成
用对工具、参数有效、忠于工具输出、没有浪费步
一致性
换个种子还稳吗
pass^k 度量可预测性

为什么平均准确率不够?因为它把「稳定的 80%」和「时好时坏的 80%」混为一谈。生产环境要的是可预测,不是一个好看的均值——一个平均能用、却不可预测地失败的 agent,不能上线。量化「稳不稳」要用 pass^k:

pass^k(一致性度量)
让 agent 对同一任务做 $k$ 次独立尝试,全部成功才算这一题过。
它逼出的是最坏情况下的可靠度,而不是「碰运气至少中一次」。注意别和大家更熟的 pass@k(Codex 论文里那个:$k$ 次里至少一次成功)搞混——pass@k 量的是「能力上限」,pass^k 量的是「稳定下限」。上线看后者。

具体怎么落地评估?两件工具:

  • trace-based 评估:把每一步(prompt、工具调用、返回结果)都记下来,人或自动化去看轨迹在哪一步偏离了预期判断。你修不了看不见的东西。
  • LLM-as-judge:用一个模型按 rubric 给轨迹打分(工具选得对不对、参数合不合理、回答是否 grounding 在工具输出上),但必须对人工标注做校准——judge 本身也会错,不校准就是拿噪声当尺子。

三、planning-first 与 reactive 的区别(Q66)

两种架构对应两种「什么时候想」的哲学:

planning-first
(plan-and-execute)
先出完整计划,再执行,必要时重规划
reactive
(ReAct)
据最新观察,一步一步临场决
hybrid
(现实里最常见)
粗计划保方向 + 步级反应处理计划外

planning-first 先把整条路径想清楚再动手:给你结构、可以并行互不依赖的子任务、以及一份可审计的计划。适合任务形态可预知的场景(流程大致固定、需要事先审批一份计划)。代价是环境一旦跟计划不符,它会显得僵。

reactive(ReAct) 每一步都看着最新的观察再决定下一步:更能应变,适合环境难以预料的探索型任务。代价是它可能游走、绕圈、甚至陷入循环——没有一张全局地图兜底。

所以很多真实系统是混合的:用一个粗粒度计划保住大方向,同时保留步级反应来吸收计划外的意外。怎么选?沿两个轴判断——任务的可预测度有多高,以及你是更需要一份可审计的计划还是灵活应变。没有哪种「总是更好」。

四、反思/自我批评何时真有用(Q67)

反思(reflection / self-critique) 就是让 agent 回头批评自己的输出或轨迹,再据此修订。听起来总是好事,但它的价值高度依赖一个前提:有没有可对照的可验证信号。

agent 有没有客观的检查信号可对照?
(测试结果 / 验证器 / rubric / 工具报错)
有 →
反思真有用:第二遍能把批评锚定在证据上,真抓到错。限次数、用 eval 验证它确实提升。
没有 →
反思常帮倒忙:白烧 token,甚至把一个本来对的答案「说服」成错的。

落地三条纪律:① 只把反思用在批评能被证据锚定的地方(比如编码有测试、检索有验证器);② 限制修订次数,别让它无限自我怀疑;③ 用 eval 验证反思到底有没有真提升,而不是凭感觉觉得「多想想总没错」。

五、coding harness 与人机交接(Q73、Q74)

coding harness 是把模型包进一个循环:让它能读写文件、跑命令、执行测试、搜索代码库——每次改动 → 观察结果(编译错 / 测试失败) → 迭代,直到通过或触到步数上限。

关键洞见:可靠更多来自 harness,而不是模型。决定成败的是这些工程活——好的工具设计、把真实反馈(测试输出、类型错误)原样喂回去、让工作上下文聚焦在相关文件、以及给循环设上限。编码之所以特别适合 agent,正因为它天然带可验证信号(测试过没过),让上一节讲的反思能牢牢锚定在结果上。

人机交接(agent → 人)不该被当成「出错」,而应设计成一等路径。四件事:

  • 定触发:低置信、高价值/高风险的动作、没有权限执行的操作、反复失败——这些时刻主动停下交给人。
  • 打包上下文:交接时附上足够的信息,让人能快速接手,而不是从零重建现场。
  • 保可恢复:人补上输入后,能把结果喂回循环让 agent 继续,而不是整条流程重来。
  • 记录交接与结果:交接率本身就是「agent 在哪弱」的真信号——哪类任务总要人接手,那里就是下一轮该修 harness 的地方。

面试官会顺着往下追(高频链):

  • 「20 步、每步 95%,整体成功率多少?」——$0.95^{20}\approx 0.36$,乘性衰减;别答成「约 95%」或「相加」。
  • 「那为什么不直接堆一个更强的单步模型就好?」——边际收益递减,且失败会级联;更划算的是减步数、每步核验、加恢复与人工检查点。
  • 「怎么量化一个 agent稳不稳,而不是准不准?」——pass^k(k 次独立尝试全成),看一致性;平均准确率会掩盖不可预测的失败。
  • 「反思到底有没有用?」——有可验证信号(测试 / 验证器 / rubric)时有用,能锚定证据;没有信号时可能白烧 token 甚至把对的改错。
  • 「coding agent 为什么特别适合 agent 化?」——有可验证信号(测试通过与否),harness 能把反思锚定到真实结果上。
  • 「什么时候该交给人?交接怎么设计?」——低置信/高风险/无权限/反复失败触发;打包上下文、保可恢复、记录交接率。

易错点(绝对化措辞几乎都是坑):

  • 「每步 95% 所以整体也差不多稳」——错,是 $0.95^{n}$ 乘性衰减,20 步就掉到约 36%。
  • 「平均准确率高就能上线」——不对,高均值 + 不可预测的失败 ≠ 可靠;上线看 pass^k 这类一致性指标。
  • 「反思一定让答案更好」——不一定;没有可验证信号时,它可能把正确答案「说服」成错误答案,或纯粹浪费 token。
  • 「planning-first 总比 ReAct 好(或反过来)」——都不对;按任务可预测度、是否需要可审计计划来选,现实常用混合。
  • 「coding agent 可靠全靠模型强」——错,可靠更多来自 harness:工具设计、把真实反馈喂回、聚焦上下文、限循环。
  • 「上下文越长越能扛长任务」——不一定;context rot 与「信息埋在长上下文中间被忽略」会反噬(见 Lost in the Middle)。

自测 1:一个 agent 任务需要 20 步,每步独立成功率 95%。整体成功率最接近哪个?

A. 约 95%,单步很稳所以整体也稳错。误差是乘性叠加,不是「取单步」。
B. 约 75%,大概打个折凭感觉打折不对;实际衰减比直觉快得多。
C. 约 36%,因为 $0.95^{20}\approx 0.36$ ✅正确。乘性衰减 + 级联失败,长任务是 agent 的软肋。
D. 约 0%,20 步必然失败过头了;是显著下降到约三分之一,不是归零。

自测 2:关于「反思/自我批评」何时真有用,下列哪句最准确?

A. 反思总能提升质量,应该无条件多加几轮不对。没有可验证信号时它可能帮倒忙、把对的改错。
B. 当有可验证信号(测试/验证器/rubric/工具报错)可锚定批评时才真有用,并要限次数、用 eval 验证 ✅正确。反思的价值取决于批评能否锚定到客观证据。
C. 反思只对创意写作有用,对代码没用恰恰相反,编码有测试这种可验证信号,反而是反思最有效的场景之一。
D. 反思能替代端到端评估,有它就不必测 pass^k 了无关且错误;反思是生成侧手段,评估仍要独立做。

一手出处与深挖方向:

  • ReAct: Synergizing Reasoning and Acting in Language Models(Yao et al., 2022/2023)——reactive「推理 + 行动」交替的经典范式,本课 reactive 一侧的原型。
  • Reflexion(Shinn et al., 2023)与 Self-Refine(Madaan et al., 2023)——反思/自我批评的代表工作,注意它们的增益都依赖可对照的反馈信号。
  • Evaluating Large Language Models Trained on Code(Chen et al., 2021,Codex)——pass@k 指标的出处;本课的 pass^k(全成)是它面向可靠性的变体,方向相反,别混。
  • Lost in the Middle(Liu et al., 2023)——长上下文中间信息被忽略的实证,是「上下文越长越好」这一直觉的反例,呼应 context rot。
  • Anthropic 工程博客 Building Effective Agents 与 Writing Effective Tools for AI Agents——loop / 工具设计 / 何时用 workflow 而非 agent 的工程判断,coding harness 与交接设计的实践参考。

一句话记忆:误差乘性衰减($0.95^{20}\approx 36\%$)让长任务变脆;所以少而可靠的步 + 每步核验 + pass^k 测一致性;planning 保结构、reactive 保应变、现实用混合;反思只在能锚定可验证信号时有用;可靠性主要来自 harness,而把「交给人」设计成一等路径。
