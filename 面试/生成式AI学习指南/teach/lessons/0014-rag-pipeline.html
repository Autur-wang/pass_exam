RAG 基础管线:分块、dense/sparse/hybrid、reranker

上一课我们决定了「什么时候该用 RAG」;这节课把 RAG 这台机器拆开,一颗螺丝一颗螺丝地讲。一口气答清五道面试常问的实战题:「端到端讲一遍基础 RAG 管线」「怎么选分块策略」「dense/sparse/hybrid 检索的区别」「reranker 做什么、何时值得」「为什么带了检索上下文反而答得更差」(源:AI 工程师题库 Q33、Q34、Q35、Q36、Q37)。目标是让你能在白板上画出完整链路,并说清每一步都是一个可调的旋钮。

上一课的结论是:当知识频繁变动、可溯源、成本敏感时选 RAG,而不是把知识烤进权重里。RAG 的本质是「先查资料、再带着资料作答」。先别往下看:如果让你从零搭这套「查了再答」的系统,离线你需要提前准备什么?在线来了一个问题又要做哪几步?

一、端到端:RAG 是「离线建库 + 在线查答」两条线(Q33)

面试官让你「端到端讲一遍」,最忌只说「就是先检索再生成」。要把它拆成离线 (offline / indexing) 和在线 (online / query) 两条线,每条线逐步说清。

把上面两张图翻译成一段能背下来的话:

  • 离线:摄入文档 → 清洗并分块 → 每块算 embedding → 把向量连同元数据和原文一起存进向量索引。
  • 在线:把 query 嵌入到同一空间 → 检索 top-k 最近的块(生产里常是 dense 语义 + 关键词的 hybrid)→ 可选地 rerank 精排 → 把「query + 检索到的上下文 + 一条『只依据这些内容作答并给出引用』的指令」拼成 prompt → 交给模型生成。

再加两句就显出功底:一是护栏——检索不到相关内容就拒答,而不是硬编;二是评估要分层——检索阶段和生成阶段分别评,才能定位问题出在哪(这条正是本课最后一节的伏笔)。

为什么强调「每一步都是一个旋钮」
分块粒度、embedding 模型、top-k 大小、是否 hybrid、是否 rerank、prompt 里怎么组织上下文、拒答阈值——每一个都能独立调。面试官想听的不是「我搭了个 RAG」,而是「我知道系统里有哪些可调点,以及每个点调动了什么权衡」。

二、分块:在召回与精度之间走钢丝(Q34)

分块是最被低估、却最容易翻车的一步。核心是一个权衡:

块太大
相关内容被无关文字稀释
还浪费上下文预算
块太小
丢掉答题所需的语境
一句话孤零零检回也没用
甜区(sweet spot)
块大小匹配内容结构
与 embedding 模型

怎么选,记住这几条可操作的原则:

  • 优先结构感知切分:按章节、段落、语义边界切,而不是盲目定长切字符。一个完整的段落/小节,语义自洽,检回来就能用。
  • 加小重叠 (overlap):相邻块之间留一点重叠,防止答案正好卡在两块的边界上被劈成两半、两边都不完整。
  • 块大小匹配内容与 embedding 模型的甜区:不同 embedding 模型对输入长度的「舒适区」不同,块的粒度要和它对齐,也要和内容本身的密度对齐。
  • 保留元数据:来源、标题、章节等一并存下,既能在检索时做过滤,又能在回答时给出引用。

最后一步别省:在你的 eval 集上验证「答案所在的那一块,到底有没有被检回来」。分块策略的好坏,不是靠感觉,是靠这个命中率说话。

三、dense / sparse / hybrid:三种检索的分工(Q35)

「检索」不是只有一种做法。三种路线各有盲区,面试要能一句话点出各自擅长与失手的地方。

dense retrieval(稠密 / 向量检索)
把 query 和块都编码成向量,按语义相似度匹配。强项:能找到没有共同词但意思相关的段落(paraphrase、同义改写)。弱项:可能漏掉精确术语、代码、罕见的专有名词——这些恰恰要求字面对上。
sparse retrieval(稀疏 / 关键词,如 BM25)
按词面匹配打分。强项:精确术语、编号、专名命中稳,而且便宜、无需 GPU。弱项:对换一种说法(paraphrase)基本盲——同义不同词就抓不到。
hybrid(混合)
两条都跑,再把结果融合(常用 RRF,Reciprocal Rank Fusion 之类的排名融合)。语义召回 + 字面精确,互补盲区,生产中通常最优。代价是系统复杂度上升——所以要用 eval 证明它确实值这份复杂度。
dense
懂「意思」
怕精确术语/编码
sparse (BM25)
懂「字面」+便宜
怕换说法
hybrid
两者融合(RRF)
换来复杂度

注意措辞:hybrid 是「通常最优」,不是「永远最优」——它更复杂,得靠 eval 说话。

四、reranker:便宜地多召回,再精挑细选(Q36)

一阶段检索(向量 / BM25)追求的是快,用相对粗的相似度从海量块里捞出候选。reranker 是第二阶段的精排器。

reranker(重排器,常为 cross-encoder)
把每个候选块和 query 拼在一起联合打分,让模型直接读「这块能不能回答这个问题」。因为 query 和文档一起进模型交互,它比一阶段那种「query 和文档各自编码、再算相似度」精准得多。

它的标准用法是一个漂亮的两段式模式:

  • 什么时候值得:当一阶段结果「大致相关但排序很差」(该在前面的埋在后面),且生成质量明显受限于检索时,rerank 收益最大。
  • 代价:每次查询都要对一批候选逐个跑一遍模型,增加延迟和成本。所以不是默认全开,而是「证明有收益再加」。

五、为什么带了检索上下文,反而答得更差?(Q37)

这道题是面试的「照妖镜」——它测你有没有真正跑过 RAG,还是只会背管线。反直觉的事实:加了检索,不一定更好,坏检索常常比不检索还差。

原因很实在:

  • 不相关 / 冲突 / 低质的检索文本会分散甚至误导模型——它本来会答,读了错料反而被带偏。
  • 长噪声上下文降低推理:塞进一大堆半相关的内容,模型要在噪声里找信号,推理质量下降。
三条要背下来的启示
① 检索质量、上下文构造,和模型本身同等重要——RAG 的天花板往往卡在检索,不在生成。
② 「更多上下文 ≠ 更好」:top-k 不是越大越好,塞满窗口经常是负优化。
③ 必须单独评估检索阶段,才能看清「答得差」到底是检索捞错了、还是模型不会用——这正是第一节里「评估分层」那颗伏笔的落点。

面试官会顺着往下追(高频链):

  • 「端到端讲一遍」——先分离线/在线两条线,再补护栏(拒答)和分层评估;只说「检索+生成」会被认为没搭过。
  • 「分块怎么选?」——别答一个固定数字。答结构感知 + 小重叠 + 匹配 embedding 甜区 + 留元数据,最后用 eval 验命中率。
  • 「为什么要 hybrid,不能只 dense 吗?」——dense 漏精确术语/编码/罕见名,sparse 补字面;融合(RRF)覆盖彼此盲区。追问代价:复杂度,用 eval 证明。
  • 「reranker 和向量检索差在哪?」——cross-encoder 让 query 和文档联合打分,比各自编码再算相似度精准;模式是「多召回再精排」。
  • 「RAG 答错了,你怎么排查?」——先分层:检索阶段命中了吗?没命中是分块/检索的问题;命中了还错,是 prompt/上下文构造或模型的问题。
  • 「上下文放不放得下、放哪儿?」——牵出「Lost in the Middle」:关键内容埋在长上下文中段容易被忽略(进阶检索课细讲)。

易错点(绝对化措辞是扣分点):

  • 别说「hybrid 一定最好」——它是通常最优,代价是复杂度,得靠 eval 证明值得。
  • 别说「top-k 越大越准」——更多上下文常引入噪声反而降质量,坏检索比不检索还差。
  • 别说「有了 RAG 就不会答错」——检索质量和上下文构造与模型同等重要,RAG 只是把错误来源从「模型不知道」换成「检索给错了」。
  • 别说「reranker 必须全程开」——它增加每查询延迟/成本,只在「大致相关但排序差且生成受检索限」时收益最大。
  • 别把分块答成一个固定字符数——脱离内容结构和 embedding 模型谈块大小没有意义;要在 eval 上验「答案块是否被检回」。

自测 1:某 RAG 系统在处理精确产品编号(如「型号 X-7291」)的查询时经常漏检,但对「怎么退货」这类语义化问题表现良好。最可能的原因与修法是?

A. embedding 模型太小,换更大的模型即可换模型可能有帮助,但精确编码/术语的漏检是向量语义检索的结构性盲区,不是模型大小决定的。
B. 只用了 dense 检索,漏掉字面精确匹配;加入 sparse(BM25)做 hybrid ✅正确。dense 擅长语义、弱于精确术语/编码;混入关键词检索并融合(如 RRF)正好补这个盲区。
C. 分块太大导致编号被稀释,把块切得越小越好方向不对且绝对化。这里的病根是检索类型不匹配,不是块大小;而且块越小越会丢语境。
D. top-k 设太小,把 top-k 开到最大就能覆盖调大 k 会引入噪声、降低生成质量,且治标不治本——字面匹配的能力缺失靠加 k 补不回来。

自测 2:你给一个原本能正确回答的问题接上了 RAG,结果答得更差了。下列哪种解释与应对最站得住脚?

A. 一定是生成模型能力不足,换更强的模型绝对化了。问题很可能出在检索阶段而非模型;不先分层排查就换模型是浪费。
B. 检索到不相关/冲突/低质内容,把模型带偏;应单独评估检索阶段并收紧上下文 ✅正确。坏检索常比不检索还差,长噪声上下文降低推理;必须分层评估、控制上下文质量与数量。
C. 上下文给少了,把 top-k 调大、尽量塞满窗口恰恰相反。「更多上下文 ≠ 更好」,塞满窗口通常引入更多噪声、进一步降质。
D. RAG 不适合这类问题,应彻底关掉检索过度反应。该做的是修检索质量与上下文构造,而不是一遇问题就否定整条路线。

一手出处与深挖方向:

  • Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks(Lewis et al., 2020)——RAG 的原始论文,奠定「检索 + 生成」联合范式。
  • Lost in the Middle: How Language Models Use Long Contexts(Liu et al., 2023)——实证「更多上下文 ≠ 更好」:关键信息埋在长上下文中段容易被忽略,直接支撑本课第五节。
  • Reciprocal Rank Fusion(Cormack et al., 2009)——hybrid 检索里融合 dense 与 sparse 排名的经典方法(RRF)。
  • 下一步:进阶检索技术(第 0015 课)——查询改写、多路检索、上下文重排与压缩,把本课的「旋钮」调到更细。

一句话记忆:RAG = 离线「切块 + 嵌入 + 建索引」+ 在线「嵌 query → hybrid 检索 → 可选 rerank → 拼 prompt → 生成」;每步都是旋钮,而检索质量常常是天花板——更多上下文不等于更好。
