部署决策与可观测:model routing、self-host、fallback、监控

上一课把「延迟-吞吐-成本」的物理约束讲清了,这节课把它落到系统怎么搭。一口气答清五道真实生产工程题:「怎么为某一步选模型?」「什么时候该自托管开源权重、而不是用托管 API?」「模型调用失败/超时/限流时怎么安全 fallback?」「生产可观测长什么样、成本怎么按功能和用户归因?」「API 大幅降价时架构该怎么改?」(源:AI 工程师题库 Q101、Q110、Q111、Q103、Q109、Q108)。目标是让你答得像一个见过线上事故的人,而不是只会调 API 的人。

回忆上一课:同一个功能,选 GPT 级大模型还是小模型、开不开 reasoning、要不要 streaming,直接决定了延迟和每次调用的钱。先别往下看:如果一个多步流程里,有的步骤很简单(抽个字段)、有的步骤很难(多跳推理),你会用同一个模型跑完全部,还是分开处理?为什么?

一、Model routing:用「能过线的最便宜模型」(Q101)

直觉先行:不是所有请求都值得同一档算力。把一个复杂任务的每一步都丢给最强的推理模型,等于用出租车送外卖——能送到,但贵得离谱且慢。反过来,全用最便宜的小模型,尾部的难例就会翻车。routing 要做的,就是给每一步匹配刚好够用的能力。

Model routing(模型路由)
按任务难度与约束把每个请求/每个步骤,分派给一组模型里能过该步质量线的、最小最便宜最快的那个。只有当便宜模型过不了线时,才把这个「难例」升级(escalate)到强模型或 reasoning 模型。

落地成一个路由器:它可以是规则(按输入长度、任务类型、是否含代码、用户档位分流),也可以是轻量分类器(一个小模型/打分器先判难度)。这样常见的易路径走便宜通道省钱,只有尾部的难请求才付大模型的钱——成本花在刀刃上。

两个容易被忽略、但资深面试官会点的前提:

  • 用 eval 兜底:「便宜模型够用」不能靠感觉,要在你真正用它的那个环节上用评测集验证它确实过线。否则省下的钱会以质量事故的形式加倍还回来。
  • 路由是会过期的决策:模型在持续变便宜、变强。今天必须用大模型的步骤,几个月后小模型可能就够了。要定期重估路由表,而不是一次配置永久不动。

二、自托管 vs 托管 API:别凭意识形态(Q110)

这题最容易答歪成「开源=省钱=牛」。资深的答法是:托管 API 通常是默认赢家,直到某个具体驱动因素强到压过它。自托管开源权重只有在下面几类情况才真正合理:

数据 / 合规
数据驻留、零留存要求
根本不允许把数据送给 provider
规模经济
调用量大到按 token 的 API
比自己养硬件还贵
能力 / SLA
需要 API 没有的微调/专用模型
或共享端点给不了的延迟/可用性保证

但自托管的代价是真实且持续的,面试时把这些说全才显得你真做过:

  • GPU 容量:要拿得到、养得起、扛得住峰值的显卡。
  • 推理服务专长:批处理(batching)、KV cache 复用、自动扩缩容——这些不是装个开源权重就自动有的。
  • 持续维护:监控、升级、故障处理,是一支团队的长期投入,不是一次性成本。

所以正确的决策姿势是:用「总成本 + 需求」的具体比较来决定,而不是凭对开源/闭源的立场。还有一个常被忽视的中间选项——托管的开源权重端点(有人替你把开源模型跑成 API):它能给你开源模型的选择权,又免掉自己养 GPU 的重担,常常是「既要合规/选型自由、又不想自建机房」时的折中。

一句话决策框架
默认托管 API;当合规排除送数据、规模让 API 更贵、需要 API 没有的能力、或需要共享端点给不了的 SLA 之一强到主导时,才考虑自托管;并把「托管开源端点」作为中间档一起比。

三、安全 fallback:先设计「不快乐路径」(Q111)

心态转变是这题的灵魂:假设每一次模型调用都可能失败——会超时、会限流(rate limit)、会 5xx、会返回坏结构。新手先写成功路径再补异常;资深工程师先设计失败路径。

  • 瞬时错误:超时 + 重试 + 指数退避(exponential backoff)。别无脑重试——那会在 provider 已经过载时把它锤得更死。
  • 持续故障:断路器。当失败率飙高,快速「跳闸」不再打这个 provider,给它喘息、也让你的功能快速失败而不是一直挂着。
  • 降级行为(要提前定义):切到更小/替代模型、返回缓存过的答案、或诚实地告诉用户「稍后再试」。三选一,但必须是设计好的,不是崩了才现想。

两条红线(说反了直接扣分):

  • 绝不让一个 provider 的故障拖垮整个功能、或把用户请求挂住不返回。局部失败要被隔离。
  • 绝不静默返回坏的结构化输出。JSON 解析失败/字段缺失时要校验 + 回退,而不是把脏数据传给下游。

此外还要:记录每次失败及其对应的 fallback——这样你才能看清各 provider 的真实可靠性、据此调限额与超时。工程手法上用一层 provider 抽象(把「调哪个厂商/哪个模型」藏在统一接口后面),切换备用模型或备用厂商才便宜——这条同时也是下一节降价题的伏笔。

四、可观测 + 成本归因:别盲飞非确定性系统(Q103、Q109)

核心论点一句话:没有可观测,你就是在盲飞一个非确定性系统——同样的输入可能给出不同输出,出问题时你连「哪一步错了」都不知道。所以它必须从第一天就内建,不是上线后再补。

LLM 应用的端到端追踪(tracing)
对每一次请求记录整条链路:拼装出的 prompt / 上下文、检索命中了哪些块及其分数、每一次工具调用及其结果、模型输出、token 数、各阶段延迟、成本。有了追踪面板,就能把一条多步 agent 的完整轨迹摊开看,定位到底哪一步出错。

光有追踪还不够,可观测是三件事叠起来:

记录(为可审计)
完整存下每次请求的输入输出
出事能回溯、能复盘
抽样质检
抽样输出做持续评估
非确定系统靠采样看质量漂移
告警
对要紧指标漂移报警
幻觉信号、拒答率、延迟、成本、错误率

成本归因:把「一张月账单」变成可查询维度(Q109)

光看一张月度总账单,你永远不知道钱花在哪。做法是给每一次调用打上元数据:功能(feature)、用户/租户(tenant)、模型、缓存 vs 非缓存 token;并记录输入/输出 token 数。这样成本就从「一个数字」变成可查询的维度。

  • 能看清哪个功能、哪个重度用户在驱动开销;
  • 能抓到回归——比如「有人改了个 prompt,让 token 数悄悄翻倍」;
  • 能给每租户设预算 / 限流。

更进一步,资深答法会把开销绑到价值上:按 每次成功交互的成本 来追踪,而不是只看总花销。省了钱但成功率掉了,那不是省,是亏。

五、API 大幅降价:把模型选择当「定期重估」(Q108)

这题考的是架构随外部条件演化的意识。降价意味着:昨天为了省成本而做的妥协,今天可能不再必要。该重估的有两类:

  • 曾经为省钱拆给便宜模型、或用重度 prompt 工程硬把任务压进小模型的那些步骤——现在可能在同样预算内直接跑更强模型,效果更好且更简单;
  • 那些当初精巧的省钱脚手架(多级路由、复杂缓存、prompt 压缩),降价后可能从「净收益」变成「净负担」——维护它的复杂度超过了它省的钱,该拆就拆。

但别矫枉过正,两条平衡:

  • 别过早过度优化。与其押注某个模型价格,不如让架构保持灵活——provider 抽象 + routing 就绪,更便宜/更好的模型一到就能采纳(这就是第三节那层抽象的回报)。
  • 降价不等于成本自动下降。便宜 token 会招致更大规模的使用,总花销反而可能上涨——所以仍要盯着「每次交互成本」这个指标(回到第四节)。

一句话收束这整节的资深直觉:把模型选择、部署形态、路由策略,都当作「定期重估的决策」,而不是一次拍板的永久结论。五道题其实是同一件事的不同切面——生产系统是活的,你的架构也得是活的。

面试官会顺着往下追(高频链):

  • 「routing 器本身怎么实现?」——规则(长度/类型/档位)或轻量分类器;要点是用 eval 证明便宜档在实际用处过线,别只答「用大模型判难度」——那本身就贵。
  • 「什么时候必须自托管?」——数据合规排除送 provider、规模让 API 更贵、需要专用/微调模型、需要 SLA;并主动补一句成本(GPU、服务专长、维护)和「托管开源端点」这个中间档。
  • 「provider 挂了你的功能会怎样?」——考的是断路器 + 降级行为 + 隔离;错误答法是「加个 try/except 重试」就完事。
  • 「重试要注意什么?」——指数退避,别在 provider 过载时无脑重试把它锤死;配合断路器。
  • 「怎么知道是哪个功能在烧钱?」——每次调用打元数据(feature/tenant/model/cache),token 数入库,成本变可查询维度;按「每次成功交互成本」追。
  • 「一次 agent 请求中间某步错了,你怎么查?」——端到端 trace 面板摊开整条轨迹逐步看,这就是为什么可观测要从一开始内建。
  • 「主力模型降价一半,你改不改架构?」——重估被省钱妥协过的步骤 + 拆掉变成净负担的脚手架,但保持抽象灵活、继续盯每次交互成本;强调「模型选择是定期重估」。

易错点(绝对化措辞是扣分点):

  • 别说「开源自托管一定更省钱」——只有规模足够大时才可能;小规模下托管 API 通常更划算,还免掉运维。
  • 别说「所有请求都该用最强模型」或「所有请求都该用最便宜模型」——routing 的整个意义就是分而治之。
  • 别把 fallback 等同于「加个重试」。重试只解决瞬时错;持续故障要断路器,无结果要降级行为,坏输出要校验回退——四件事不是一件。
  • 别说「上线后再加监控也来得及」——非确定系统没有可观测就是盲飞,出事无法归因,应从一开始内建。
  • 别把「API 降价」直接等于「成本下降」——规模上涨可能吃掉降价红利,仍要按每次交互成本监控。

自测 1:一个多步流程里,大多数请求很简单、少数很难。下列哪种做法最符合 model routing 的思路?

A. 全部用最强的 reasoning 模型,保证质量最高成本和延迟都被拉爆——简单请求根本不需要这档算力。这正是 routing 要避免的浪费。
B. 默认走能过质量线的最便宜模型,只把便宜模型过不了线的难例升级到强模型 ✅正确。routing 就是「给每步匹配刚好够用的能力」,常见路径省钱、尾部难例才付大模型的钱,并用 eval 验证便宜档确实过线。
C. 全部用最便宜的小模型,省到极致尾部难例会翻车,省下的钱以质量事故的形式加倍还回来。
D. 随机分配模型以均衡负载routing 依据的是任务难度与约束,不是随机;随机分配和质量线无关。

自测 2:关于生产 LLM 应用的可观测与成本,哪句最准确?

A. 只要保存一张月度总账单,就能定位是哪个功能在烧钱总账单只是一个数字,无法归因。要给每次调用打 feature/tenant/model/cache 元数据,成本才成为可查询维度。
B. 可观测可以等系统稳定后再加,前期先跑起来要紧非确定系统没有可观测就是盲飞,出问题无法归因;应从第一天内建。
C. 端到端追踪每次请求(prompt/检索/工具/输出/token/各阶段延迟/成本)+ 按每次成功交互成本归因,是把非确定系统变得可诊断、可控成本的基础 ✅正确。追踪让多步轨迹可摊开定位错误,元数据让成本可查询,「每次成功交互成本」把开销绑到价值。
D. 只要模型输出正确,就不需要记录中间的检索和工具调用中间步骤正是多步系统出错的地方;不记录就无法在 agent 轨迹里定位哪一步失败。

一手出处与深挖方向(部署与可观测是工程实践,经典来源多在系统可靠性与 agent 工程侧):

  • Release It!(Michael T. Nygard)——稳定性模式的经典,超时、重试、断路器(Circuit Breaker)、隔离(Bulkhead)都出自这里,本课 fallback 一节的骨架。
  • "Circuit Breaker"(Martin Fowler, martinfowler.com)——断路器模式的权威短文,配合上一本读。
  • Site Reliability Engineering(Google SRE Book, O'Reilly)——可观测、SLO/错误预算、告警的一手参考,把「对要紧指标漂移告警」讲透。
  • OpenTelemetry 官方文档——分布式 tracing 的开放标准,端到端追踪落地时的实现基座。
  • "Building Effective Agents"(Anthropic 工程博客)——多步 agent 的工程取舍,含对可观测/轨迹追踪重要性的讨论。
  • 下一步:第 0027 课把「幻觉」这一要紧指标单独拆开——成因、评估与缓解,正是本课「对幻觉信号告警」背后要监控的东西。

一句话记忆:routing = 用能过线的最便宜模型、难例才升级;自托管只在合规/规模/能力/SLA 主导时才赢;fallback 先设计失败路径(退避重试+断路器+降级+校验);可观测 = 端到端追踪+抽样质检+告警,成本按 feature/tenant 归因、盯每次成功交互成本;降价把模型选择当定期重估、但保持架构灵活。
