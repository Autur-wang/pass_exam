上下文工程:context rot、lost-in-the-middle、compaction

上一课讲的是「怎么把一句 prompt 写好」;这一课把镜头拉远——决定放进上下文窗口的到底是哪些 token,以及它们怎么排。本节一次答清五道高频真题:「什么是 context engineering、为何常比措辞更重要?」「什么是 lost-in-the-middle、怎么规避?」「什么是 context rot、它如何改变长程 agent 的构建?」「什么是 context compaction、何时用?」「长对话里怎样管理历史而不爆预算?」(源:AI 工程师题库 Q17、Q20、Q23、Q24、Q25)。

第 0008 课我们打磨的是 prompt 里的措辞——few-shot、CoT、角色设定这些「怎么说」。先别往下看:如果一句话已经写得很清楚,但模型仍答错、答漏、答飘,你觉得问题更可能出在「话术」上,还是出在「你在这句话周围还塞了些什么」上?这个转念,就是从 prompt engineering 爬到 context engineering 的那一级台阶。

一、context engineering:把上下文窗口当预算经营

先说直觉。上下文窗口不是一个「越大越好、能塞就塞」的垃圾桶,而是一份稀缺、要主动经营的预算。模型在每一步只能看见窗口里的东西——窗口外的一切对它都不存在。所以真正决定回答质量的,往往不是你把话说得多漂亮,而是你让它看见了什么、没看见什么、以及按什么顺序看见。

这就是为什么这件事常常比措辞更重要:一句措辞完美的指令,如果被埋在几十段无关检索、陈旧工具输出、混乱历史之间,模型照样退化。上下文一旦臃肿、嘈杂、乱序,再好的话术也救不回来。领域里把能力分成三级台阶,层层包住:

Context engineering(上下文工程)
决定什么进入上下文窗口(指令、检索结果、工具返回、记忆、示例)、什么留在窗口外,以及怎么排序与格式化的工程实践。核心心法:把窗口当作要主动管理的稀缺预算,而不是能塞就塞的垃圾场。

在 agentic 系统里,这更是一条核心纪律:agent 每走一步都要重新拼装一次上下文——这一步真正需要哪几片信息,就只拼哪几片,而不是把历史全量拖过来。谁在管理这份预算,谁就决定了 agent 能不能撑住长任务。

二、lost-in-the-middle:模型偏爱首尾、冷落中间

假设你把 40 段检索 chunk 一股脑塞进窗口,以为「信息越多越保险」。研究给出的反直觉结论是:模型对上下文里开头和结尾的信息利用得最好,对正中间的信息利用得最差——哪怕正确答案就躺在中间某一段,它也很可能视而不见。

Lost in the middle(中段迷失)
当关键信息位于长上下文的中间位置时,模型的检索/利用能力显著下降,呈现「两端高、中间凹」的 U 形。所以「乱塞几十个 chunk」多半是浪费——真正相关的那一片,可能恰好被你埋在了模型最看不见的中段。

怎么在设计上规避?三条落地动作:

  • 少而精地检索:与其召回 40 段,不如召回真正相关的 5 段。宁缺毋滥。
  • 用 reranker 把最相关内容放到两端:排序后,让命中率最高的片段落在开头和结尾这两个「高利用区」。
  • 让总上下文保持紧凑:上下文越短,「中间」这个坏区就越窄,信息越不容易掉进去。

这也是那句面试金句「更多上下文 ≠ 更好答案」的一个根因:堆量不但不涨分,还会把好料稀释进中段迷失里。

三、context rot:长上下文不是免费升级

如果说 lost-in-the-middle 讲的是「位置」,context rot 讲的就是「长度」本身。

Context rot(上下文腐化)
来自 Chroma 的研究:随着输入变长,模型准确率会下降——即便相关事实全都在里面、窗口也远没塞满。换句话说,长上下文不是一次免费升级;窗口开到 200k 不等于你能把 200k 都填满还指望它照样聪明。(相关的姊妹现象是 context anxiety:模型逼近上限时会「赶工」、变毛躁。)

这一点直接改写了长程 agent(long-horizon agent)的构建方式。老思路是「窗口够大就把一切都塞进去」;context rot 把设计目标从「塞下一切」翻转成「让工作上下文保持小、相关、新鲜」。具体推向主动上下文管理:

  • 压缩/摘要旧的对话轮次,别让它们原文堆着;
  • 逐出(evict)陈旧的工具输出——上一步跑完的日志,下一步用不到就清掉;
  • 把子任务隔离到独立的上下文里跑,别让互不相干的任务互相污染;
  • 只检索这一步需要的那一片切片,而不是把整个知识库拖进来。

四、compaction 与长对话历史管理

把上面这些动作系统化,就得到两套面试常考的具体技术。先看压缩上下文的三种手法——注意它们代价不同,别混用:

Clear(清理)
删掉已完成的工具结果
安全、几乎无损
Compact(压缩)
把历史摘要成短文
有损,压缩 ≠ 保真
Offload(卸载)
把状态挪到文件/外部存储
要用时再拉回来
Context compaction(上下文压缩)
定期把累积的长上下文(多轮消息 + 冗长工具结果)换成一份短摘要,只保留决策、关键事实和未竟目标。它是「三手法」里的 compact,本质是有损压缩。

何时用?两类场景最典型:

  • 会耗尽窗口、或已经受 context rot 拖累的长程 agent 循环;
  • 旧细节不再影响下一步的多轮对话——早几十轮的寒暄,对当前决策早已无关。

它的风险很直接:摘要有损,可能把要紧细节一并丢掉。所以稳妥的做法是分层对待:

这套分层也正是长对话历史管理的答法。面试官问「一段很长的对话,历史怎么管才不爆预算?」——错误答案是「无限往后追加」。正确的运行策略是:

  • 保留最近几轮原文——它们最可能改变下一次回复;
  • 把更早的轮次摘要成「运行记忆」(running memory),用短文替代长历史;
  • 把持久事实(用户偏好、已定的决策)存进结构化记忆,按需再检索,而不是一直挂在窗口里;
  • 激进裁剪,并把最相关的近期内容放到末尾(呼应第二节:末尾是高利用区)。

一句话收口:目标是保住「会改变下一次回复」的信息,而不是字面上的全量历史。

面试官会顺着往下追(高频链):

  • 「context engineering 和 prompt engineering 差在哪?」——prompt 管「怎么说这一句」,context 管「窗口里放哪些 token、怎么排」;后者是更高一级台阶。
  • 「更大的窗口不就解决问题了吗?」——不。lost-in-the-middle(中段迷失)+ context rot(变长即掉分)说明大窗口不是免费升级,还是要主动管理。
  • 「lost-in-the-middle 具体怎么规避?」——少而精检索 + reranker 把最相关内容放两端 + 总上下文保持紧凑。
  • 「compaction 会不会丢信息?怎么办?」——会,它有损;所以近期轮次与关键 artifact 保留原文,其余摘要,持久事实存外部记忆可再检索。
  • 「clear、compact、offload 有什么区别?」——clear 删完成的工具结果(近乎无损);compact 摘要历史(有损);offload 把状态挪到外部存储(要用再拉回)。
  • 「这跟长程 agent 有什么关系?」——每步重新拼装上下文、逐出陈旧工具输出、隔离子任务、只取这一步要的切片——设计目标从『塞下一切』变成『保持工作上下文小、相关、新鲜』。

易错点(绝对化措辞几乎都是坑):

  • 别说「上下文越多越好」——lost-in-the-middle 与 context rot 都是它的反例。堆量会稀释信号、把好料埋进中段。
  • 别说「窗口够大就不用管理」——context rot 表明:窗口没满、事实齐全,准确率照样随长度下降。
  • 别把 compaction 说成「无损压缩」——它有损,"压缩 ≠ 保真"。要说清用「近期原文 + 其余摘要 + 外部记忆」来兜底。
  • 别把 clear / compact / offload 混为一谈——代价不同:clear 近乎无损、compact 有损、offload 靠外部存储换窗口空间。
  • 别答「历史一律全部保留」或「一律激进删掉」——正确姿态是分层:留会改变下一步的,压掉不会的。

自测 1:一位候选人说「我们的模型支持 200k 窗口,所以直接把所有检索结果和完整历史都塞进去最保险」。这句话最主要错在哪?

A. 200k 窗口在技术上根本装不下这么多内容装得下不是重点;问题是装满之后模型用不好。
B. lost-in-the-middle 与 context rot 说明:窗口没满、事实齐全,准确率也会随长度下降,关键信息还会掉进中段 ✅正确。大窗口不是免费升级,堆量既会触发中段迷失,也会引发上下文腐化。
C. 塞满窗口会永久改变模型权重,造成过拟合推理时的上下文不改变权重,与过拟合无关。
D. 只要 prompt 措辞写得足够好,塞多少都不影响恰恰相反——臃肿嘈杂的上下文会让再好的措辞也退化,这正是 context engineering 常比措辞更重要的原因。

自测 2:一个长程 agent 的对话已经积累了几十轮消息和大量冗长工具日志,窗口快撑满。关于 compaction,下列哪句最准确?

A. compaction 就是把整段历史无损地压缩,信息不会丢不对。compaction 是有损摘要,"压缩 ≠ 保真"。
B. 定期把累积历史换成保留决策/事实/未竟目标的短摘要,但近期轮次与关键 artifact 保留原文、持久事实存外部记忆 ✅正确。这样既省预算又降低丢失要紧细节的风险。
C. 只要开更大的窗口,就完全不需要 compaction大窗口有 context rot,长程循环仍需主动管理,compaction 依然有用。
D. compaction 和 clear 是一回事,都只是删掉已完成的工具结果不是。clear 删完成的工具结果(近乎无损),compact 摘要历史(有损),两者代价不同。
