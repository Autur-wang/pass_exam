内聚与耦合:高内聚、低耦合

"高内聚、低耦合"是每个人都会背的六个字,但面试真正想听的是:内聚衡量什么?耦合又衡量什么?它俩是不是一回事?这一节把这两个词拆到能当场举例、能说出级别、能连到 SOLID 的程度。

先想个画面:一个叫 FileUtility 的类,里面既能读写文件,又能存数据库,还能清缓存、解析 JSON。你打开它时第一反应是"这类好方便"还是"这类好乱"?再想:如果另一个类里写着 car.engine._temperature = 120 直接伸手改别人的内部字段,哪天 Engine 重构了会发生什么?把这两种"不舒服"的感觉记住,它们正好对应本节两个词。

一、直觉:一个看"里面",一个看"之间"

这两个词最容易被搅成一团,先用一句话把它们钉死在不同的位置上:

  • 内聚(Cohesion)看的是一个类内部——它的那些方法和数据彼此有多相关。相关性越高,这个类越"专一"。
  • 耦合(Coupling)看的是类之间——一个类对另一个类的依赖有多深、多脆。依赖越浅、越走正门,越"松"。

换个比喻:内聚像"一个部门里的人是不是都在干同一件事";耦合像"两个部门之间靠什么协作——是各自派代表走流程(松),还是你直接冲进我办公室翻我抽屉(紧)"。目标口号就一句:高内聚 + 低耦合。一个把"每个类只干一件事"做到位,一个把"类之间只走正门"做到位。

内聚 (Cohesion)
一个类内部方法与数据彼此相关的紧密程度。高内聚=类专注单一职责,更易理解、维护、更可靠;低内聚=类塞了多个常常互不相关的职责,难懂、难改。
耦合 (Coupling)
类 / 模块之间相互依赖的程度,直接影响灵活性、可维护性、可测试性。松耦合(loose)更受欢迎;紧耦合(tight)牵一发动全身。
它们是两个正交维度
内聚讲"里面",耦合讲"之间"。一个高不代表另一个就好——别混为一谈(见易错点)。

二、内聚:从"万能工具类"说起

低内聚长什么样?典型就是名字里带 Util / Manager / Helper 的"什么都能干"类:

# ❌ 低内聚:方法之间毫无关系,只是碰巧被塞进同一个类
class FileUtility:
    def read_file(self, path): ...          # 读文件
    def write_file(self, path, data): ...   # 写文件
    def save_to_database(self, record): ... # …还管数据库?
    def clear_cache(self): ...              # …还清缓存?
    def parse_json(self, text): ...         # …还解析 JSON?

病根:这个类有好几个"变化的理由"——数据库换驱动要改它,缓存策略变了要改它,JSON 格式调整还要改它。谁都得动它,谁动都可能误伤别人。改法是按职责拆开,让每个类都只围绕一件事:

# ✅ 高内聚:每个类只服务于单一、明确的任务
class FileReader:
    def read(self, path): ...
    def read_lines(self, path): ...

class FileWriter:
    def write(self, path, data): ...
    def append(self, path, data): ...

class JsonParser:
    def parse(self, text): ...

怎么提升内聚?两条手段:SRP(单一职责原则)——让每个类只有一个变化的理由;封装——把数据藏好,只通过一组彼此相关的方法暴露它。内聚不是"非高即低",它有一条从弱到强的七级谱,面试问"你知道内聚分几种吗"时就是考这张表:

级别(弱 → 强)方法凭什么被放在一起评价
① 偶然 Coincidental没有任何有意义的关系,纯属凑一块最差
② 逻辑 Logical按某种逻辑归类,但没有清晰主题(如"所有 IO 操作")差
③ 时间 Temporal按执行时机相关(如"启动时要做的所有初始化")偏弱
④ 过程 Procedural按一个特定的执行顺序组织在一起中
⑤ 通信 Communicational都操作同一组数据较好
⑥ 顺序 Sequential一个方法的输出正好是下一个的输入好
⑦ 功能 Functional所有方法协同服务于单一、明确的任务最理想

功能内聚是天花板,它恰好就是 SRP 在类内部的样子。记不住七个名字没关系,记住"越往下,方法之间的关系越本质、越指向同一个目的"这条趋势就够用。

三、耦合:从"伸手翻抽屉"说起

耦合最坏的样子,是一个类直接去读写另一个类的内部字段:

# ❌ 内容耦合(最强/最坏):Car 直接伸手改 Engine 的内部字段
class Engine:
    def __init__(self):
        self._temperature = 90        # 约定为内部状态

class Car:
    def __init__(self):
        self.engine = Engine()

    def is_overheating(self):
        # 直接读别人的私有实现细节 —— Engine 一重构,这里就碎
        return self.engine._temperature > 100

为什么坏?因为 Car 知道了 Engine 内部"温度存在一个叫 _temperature 的字段里"这个实现细节。哪天 Engine 改成用摄氏/华氏两个字段、或改名,Car 立刻跟着坏。松耦合的写法是:只走公开的"正门"接口,再把依赖注入进来:

# ✅ 消息耦合(最弱/最好):只通过公开方法通信,依赖被注入
class Engine:
    def __init__(self):
        self._temperature = 90

    def is_overheating(self):         # 稳定的公开接口
        return self._temperature > 100

class Car:
    def __init__(self, engine):       # 依赖注入:不自己 new,由外部传入
        self.engine = engine

    def check(self):
        # 只发一条"消息",不碰对方任何内部字段
        return self.engine.is_overheating()

现在 Engine 内部怎么存温度、用什么单位,Car 一概不知也不必知——只要 is_overheating() 这个约定不变,两边可以各自独立演化。耦合也有一条从强到弱的谱(强=坏,弱=好),这是面试的另一张必背表:

级别(强 → 弱)两个模块靠什么绑在一起评价
① 内容 Content一个模块直接访问 / 修改另一个的内部数据最坏
② 公共 Common多个模块共享同一份全局数据,改它牵连所有人差
③ 控制 Control一个模块靠传 flag 等控制信息,去左右另一个的内部流程偏弱
④ 外部 External靠外部因素(配置文件、数据 schema 等)关联中
⑤ 印记/数据 Stamp/Data共享一个数据结构,但只用到其中一部分(仍需知道结构)较好
⑥ 消息 Message只通过标准接口 / 方法调用 / 消息通信最好

顺带认一眼控制耦合的味道:调用方传个 mode 进来指挥被调方走哪条分支——被调方的逻辑其实被外面攥着。

# ⚠ 控制耦合:调用方用 flag 遥控被调方的内部分支
def process(data, mode):
    if mode == "csv":
        ...          # 走 CSV 分支
    elif mode == "json":
        ...          # 走 JSON 分支
# 更松的做法:拆成 process_csv / process_json,或传入一个策略对象(消息耦合)

四、为什么这两个词是"好设计"的总开关

把它俩放一起想:高内聚让每个类各司其职、边界清楚;低耦合让类与类之间只靠稳定接口协作。合起来的直接红利是——

  • 可维护:改动被关在一个高内聚的类里,不会顺着紧耦合的链条炸到全项目。
  • 可测试:松耦合的类能被单独拎出来测,依赖可以用 mock / 假对象替换(这正是依赖注入的价值)。
  • 可复用、可并行开发:边界清楚的模块能被搬到别处用,也能让多人各改各的、少踩彼此。

而降耦合的系统方法,恰好就是下一节的主角 SOLID。这里先建立映射(细节留到 0013 起讲):

原则怎么帮你降耦合 / 提内聚
SRP 单一职责职责单一 → 依赖更少 → 内聚更高、耦合更低
OCP 开闭靠接口 / 抽象来扩展,而不是改现有代码 → 减少紧耦合
LSP 里氏替换子类可无缝替换父类 → 模块只依赖抽象,独立于具体子类
ISP 接口隔离接口聚焦、拆小 → 不被迫依赖自己用不到的方法
DIP 依赖倒置依赖抽象而非具体实现 → 上层与下层解耦,更模块化

高频追问链(这一簇几乎连着问):

  • "内聚和耦合有什么区别?" → 内聚讲一个类内部方法/数据的相关性,耦合讲类之间的依赖程度。两个正交维度,目标是"高内聚 + 低耦合"。
  • "给个低内聚的例子。" → 名字带 Util/Manager/Helper 的万能类,如又读文件又写数据库又清缓存的 FileUtility——多个不相关职责挤一起。改法:SRP 拆开 + 封装。
  • "内容耦合和消息耦合差在哪?" → 内容耦合是直接读写别人的私有字段(最强/最坏);消息耦合只通过公开方法/接口通信(最弱/最好)。中间还有公共、控制、外部、印记等级别。
  • "低耦合是不是就是没有依赖?" → 不是。对象总要协作,零依赖不现实;低耦合是"依赖稳定的抽象接口"而不是"依赖对方的内部实现"。
  • "怎么降低耦合?" → 面向接口编程、依赖注入、遵循 SOLID(尤其 DIP/OCP)——都是把"依赖具体"换成"依赖抽象"。

头号坑:把内聚和耦合混为一谈,或以为"高内聚自动等于低耦合"。它们是两个正交维度。完全可能出现"一个类本身很内聚(只干一件事),却又紧耦合到另一个类的内部实现"——比如上面那个只负责判断过热、逻辑很专一的 Car.is_overheating(),却偏要去读 engine._temperature。内聚高不救耦合,耦合松也不保证内聚。答题时要能分别举例。

第二个坑:把"低耦合"理解成"零依赖"。对象存在的意义就是协作,依赖不可能也不该消灭。低耦合的准确含义是通过稳定的接口/抽象来依赖,而不是伸手进对方内部。把"消除依赖"当目标,只会写出一堆什么都不与谁合作、却又互相偷偷读全局变量的怪类。

第三个(经验性)提醒:Util/Manager/Helper 这类命名往往是低内聚的味道(并非绝对——确有职责聚焦的工具类)。看到它多问一句"这个类到底只干一件事吗"。

内聚 / 耦合是设计层面的概念,和语言无关——七级内聚、六级耦合的分类对 Java、C++、C# 同样成立。真正随语言变的,是"降耦合"手上有哪些工具:

语言降耦合的典型手段
Python鸭子类型 + 依赖注入;抽象靠 abc.ABC / typing.Protocol(结构化子类型),不强制显式接口
Java显式 interface + DI 容器(如 Spring),面向接口编程是主流范式
C++抽象基类(纯虚函数)或模板(编译期多态)来隔离具体实现
C#显式 interface + 内建 DI(Microsoft.Extensions.DependencyInjection)

一句话:概念全语言通用,Python 因为鸭子类型,降耦合时"不必先声明接口",更轻但也更靠约定。

合上讲义,做两件小事验证你真的分得清:

  • 把上面那个内容耦合版的 Car/Engine 亲手改成消息耦合版:给 Engine 加 is_overheating(),把 Engine 通过构造函数注入 Car。
  • 然后回答自己:改完之后,如果 Engine 把温度从摄氏换成华氏,Car 需要动吗?(不需要——这就是低耦合买到的东西。)
  • 再挑一个你写过的 XxxManager 类,列出它的所有方法,判断它落在七级内聚的哪一级,想想怎么拆能提到"功能内聚"。
自测 1:A 类的方法里直接写了 b._cache.clear()——伸手清了 B 对象的私有字段。这属于哪一种耦合?它在耦合谱里是最强还是最弱?

答案:内容耦合(Content coupling),最强、也最坏的一种。

A 依赖了 B 的内部实现细节("缓存存在一个叫 _cache 的字段里,而且它有 clear()")。B 只要重构这个内部结构,A 立刻崩。修法:给 B 加一个公开方法 clear_cache(),让 A 只发这条"消息"——就降到了最弱的消息耦合。

自测 2:有人说"我这个类内聚很高,所以耦合肯定也低"。这句话对吗?为什么?

不对。内聚和耦合是两个正交维度,一个好不蕴含另一个好。

反例:一个 PriceCalculator 类只做"算价格"这一件事(功能内聚,很高),但它在方法里直接读取了另一个 TaxService 对象的私有字段 _rate_table——这就是紧耦合(内容耦合)。它内聚高,却依然脆:TaxService 一改内部结构它就坏。所以两者要分别评估、分别优化。

自测 3(选择题):下面四种"方法为什么被放进同一个类"的理由,哪一种内聚最强?

选项:(A) 它们碰巧都比较短 (B) 它们都在对象初始化时被调用 (C) 一个方法的输出正好是下一个方法的输入 (D) 它们都属于"跟字符串有关的操作"

答案:(C) —— 顺序内聚(Sequential),在这四项里最强。

(A) 是偶然内聚(最弱),(B) 是时间内聚,(D) 是逻辑内聚。越往"所有方法协同完成同一个明确任务"靠拢,内聚越强;顺序内聚已经很接近理想的功能内聚了。

带走这一条:内聚看"类内部方法/数据有多相关"(越高越专一,顶点是功能内聚 ≈ SRP);耦合看"类之间依赖有多深/多脆"(越松越好,顶点是只走接口的消息耦合,最坏是伸手改内部的内容耦合)。它俩是正交维度,目标"高内聚 + 低耦合";而"低耦合"不是消灭依赖,是让依赖落在稳定接口上——把这套系统化的正是下一节的 SOLID。
