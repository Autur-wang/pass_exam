SOLID(三):接口隔离与依赖倒置

SOLID 收尾的 I 与 D 常被一起考,而且最容易背混:ISP 讲"接口别太胖",DIP 讲"依赖别太具体"。这一节把它们讲透,顺带拆掉那个几乎人人踩的坑——把 DIP 和 DI 当成同义词。

先想一个真实场景:你写了个 NotificationService,构造函数里直接 self.sender = EmailSender()。现在产品说"也要支持短信和 Slack",而且测试时不想真发邮件。你现在这个写法,改起来疼在哪?先在心里回答,再往下看。

一、ISP:不要强迫别人依赖用不到的方法

Interface Segregation Principle(接口隔离原则)一句话:客户端不该被迫依赖它用不到的方法。宁可要多个小而专的接口,也不要一个大而全的"胖接口"(fat interface)。

直觉类比:瑞士军刀什么都有,但你只想拧一颗螺丝时,得攥着开瓶器、剪刀、锯子一起使——多出来的功能不是免费的,它们是你必须"扛着"的重量。接口也一样:一个方法一旦写进接口,所有实现类都得对它负责,哪怕它根本用不上。

经典反例是一个胖 Worker 接口:

# ❌ 胖接口:work() 和 eat() 被塞进同一个接口
from abc import ABC, abstractmethod

class Worker(ABC):
    @abstractmethod
    def work(self): ...
    @abstractmethod
    def eat(self): ...

class HumanWorker(Worker):
    def work(self): print("写代码")
    def eat(self):  print("吃午饭")

class RobotWorker(Worker):
    def work(self): print("焊接")
    def eat(self):
        # 机器人不吃饭,却被接口逼着实现 eat()
        raise NotImplementedError("机器人不吃饭")   # ← 坏味道

RobotWorker 被迫实现一个它根本不需要的 eat(),只能抛异常或写个空实现。这就是"被迫依赖用不到的方法"——而且一旦有人真去调用它,程序在运行时才炸。ISP 的解法是按客户端的实际需要把接口拆开:

# ✅ 拆成小而专的接口,谁需要谁实现
class Workable(ABC):
    @abstractmethod
    def work(self): ...

class Eatable(ABC):
    @abstractmethod
    def eat(self): ...

class HumanWorker(Workable, Eatable):   # 人既能干活也能吃饭
    def work(self): print("写代码")
    def eat(self):  print("吃午饭")

class RobotWorker(Workable):            # 机器人只承诺它做得到的
    def work(self): print("焊接")

现在 RobotWorker 不再背负 eat(),契约诚实了。注意 ISP 是站在客户端(调用方)的视角看接口粒度:接口应该小到"用它的人不会被迫拖着废方法走"。

二、DIP:高层和低层都去依赖"抽象"

Dependency Inversion Principle(依赖倒置原则)有两句话:

  • 高层模块和低层模块都应依赖抽象,而不是高层直接依赖低层的具体实现。
  • 抽象不应依赖细节,细节应依赖抽象。

"倒置"倒的是什么?传统写法里,高层模块(业务逻辑)直接 new 一个低层的具体类,依赖方向是"高层 → 低层具体"。DIP 在中间插一层抽象接口,让两端都指向它——低层实现反过来去"实现"这个抽象。于是那条从高层伸向低层的箭头被掰了回来,这就是"倒置"。

回到开场那个疼点。反例是高层把低层"焊死"在自己体内:

# ❌ 高层直接依赖低层具体类
class EmailSender:
    def send(self, msg): print(f"Email: {msg}")

class NotificationService:
    def __init__(self):
        self.sender = EmailSender()   # 硬编码依赖:想换 SMS/Slack 就得改这一行
    def notify(self, msg):
        self.sender.send(msg)

问题不止"改代码":测试 NotificationService 时你被迫真的去发邮件,因为它自己 new 了发送器,你插不进手。DIP 的解法是让高层只认一个抽象 MessageSender,具体实现从外部传进来:

from typing import Protocol

class MessageSender(Protocol):              # 抽象:只规定"能 send"
    def send(self, msg: str) -> None: ...

class EmailSender:                         # 注意:不必显式继承 MessageSender
    def send(self, msg: str) -> None: print(f"Email: {msg}")

class SlackSender:
    def send(self, msg: str) -> None: print(f"Slack: {msg}")

class NotificationService:
    def __init__(self, sender: MessageSender):   # 依赖抽象,实现从外部注入
        self.sender = sender
    def notify(self, msg: str) -> None:
        self.sender.send(msg)

# 组装:由调用方决定用哪个实现
NotificationService(EmailSender()).notify("hi")
NotificationService(SlackSender()).notify("hi")   # 换实现,Service 一行不改

现在换实现、加实现,NotificationService 都不用动;测试也变简单了——注入一个假实现即可,根本不碰真网络:

# 测试:注入 FakeSender,断言"发了什么",不真的发送
class FakeSender:
    def __init__(self): self.sent = []
    def send(self, msg: str) -> None: self.sent.append(msg)

fake = FakeSender()
NotificationService(fake).notify("test")
assert fake.sent == ["test"]              # ✅ 可测、快、无副作用

三、DI:落地 DIP 的常用手段

上面那句"实现从外部传进来",名字就叫 Dependency Injection(依赖注入,DI):不在对象内部自己 new 依赖,而是让外界把依赖递进来。最常见的是构造器注入(像上面那样从 __init__ 传),此外还有方法注入(当参数传给某个方法)和属性注入(实例化后赋给某个属性)。

DI 是把 DIP 从"原则"变成"代码"的常用手段之一。它属于一个更大的概念——IoC(Inversion of Control,控制反转):本来"该由谁创建依赖"的控制权在对象自己手里,现在被反转交给了外部(调用方或框架)。DI 是 IoC 的一种实现形式。

ISP · 接口隔离原则
不应强迫类依赖它用不到的方法;宁可多个小而专的接口,也不要一个胖接口。视角在客户端。
DIP · 依赖倒置原则
高层与低层都依赖抽象,而非具体实现;抽象不依赖细节,细节依赖抽象。它倒置了"高层直接依赖低层具体类"的方向。
DI · 依赖注入
把对象所需的依赖从外部传入(构造器 / 方法 / 属性注入),而非内部自己 new。是落地 DIP 的常用手段。
IoC · 控制反转
"谁来创建/装配依赖"的控制权从对象自身反转给外部。DI 是 IoC 的一种实现。

高频追问链(ISP/DIP 常被连环问):

  • "DIP 和 DI 是一回事吗?" → 不是。DIP 是原则(依赖抽象),DI 是手段(从外部传入依赖)。你可以遵守 DIP 却用别的方式注入,也可能用了 DI 但依赖的仍是具体类(那就没真做到 DIP)。这是本节头号考点,见易错点。
  • "为什么叫'倒置'?到底倒了什么?" → 传统上依赖方向是"高层 → 低层具体类";插入抽象后两端都指向抽象、低层反过来实现抽象,那条箭头被掰回来了。
  • "ISP 和 SRP(单一职责)有什么区别?" → SRP 关注类只有一个变化原因(内聚);ISP 关注接口的粒度、以及客户端只依赖它需要的部分。角度不同,但常常一起把大东西拆小。
  • "Python 没有 interface 关键字,怎么做 ISP/DIP?" → 用 abc.ABC、typing.Protocol,或干脆鸭子类型。见跨语言对照与易错点。
  • "一定要上 IoC 容器 / DI 框架吗?" → 不必。IoC 是大概念,DI 是其一种;很多场景手动在入口处构造并注入就够了。

坑一:把 DIP 和 DI 当同义词。它们不在一个层面。DIP 是"依赖抽象"的设计原则;DI 是"从外部把依赖递进来"的具体手段。判断题:一个类用构造器注入了依赖,但注入进来的类型标注是具体的 EmailSender 而非抽象 MessageSender——它用了 DI,却没遵守 DIP。反过来也成立。面试时把这层区分讲清,立刻显出功底。

坑二:以为 Python 要"面向抽象"就必须写 ABC。不一定。Python 的鸭子类型 + typing.Protocol(结构化子类型)同样满足 DIP:上面的 EmailSender / SlackSender 没有显式继承 MessageSender,只要"长得像"(有对应签名的 send)就被接受。别把 Java 式"必须 implements 接口"的思维硬套到 Python 上。当然,想要更强的显式约束或抽象基类默认逻辑时,用 ABC 也完全可以——两条路都行。

"这门语言怎么落地 DIP?"是跨语言必问题:

语言抽象怎么表达注入怎么做典型依赖
Pythontyping.Protocol / abc.ABC / 鸭子类型构造器注入,入口处手动装配通常不需要重型 DI 容器
Javainterface多用 DI 框架自动装配常配 Spring 等 IoC 容器
C#interface构造器注入 + 内置容器常配 .NET 内置 DI

一句话:Java/C# 常靠 interface + DI 框架来落地 DIP;Python 靠构造器注入 + Protocol/鸭子类型,多数情况下不用请出重型容器。原则相同,手段更轻。

合上讲义,自己写一个小报表模块,把 DIP 走一遍:

  • 定义抽象 DataSource(用 Protocol 或 ABC 均可),约定一个 fetch() 返回一组记录。
  • 写两个实现:CsvSource 和 ApiSource(内容随便造)。
  • 高层 ReportBuilder(source: DataSource) 用构造器注入拿到数据源,build() 里只调用 source.fetch(),绝不自己 new 任何具体源。
  • 写个 FakeSource 注入进去做测试,断言 build() 的结果——全程不碰真文件或真网络。

写完自问:如果哪天要加 DbSource,你需要改 ReportBuilder 吗?(答案应该是"不需要"——这正是 DIP 给你的礼物。)

自测 1:下面这段代码遵守 DIP 吗?class OrderService: 的 __init__(self, mailer: SmtpMailer) 用构造器把 SmtpMailer 传了进来。

答案:用了 DI,但没有真正遵守 DIP。

它确实做了依赖注入(从外部传入 mailer),但注入的类型是具体类 SmtpMailer,高层 OrderService 依然被钉死在一个具体实现上。想满足 DIP,应把参数类型改成抽象(如 Mailer 的 Protocol/ABC),让 SmtpMailer、FakeMailer 等都能替换进来。这正说明:DI ≠ DIP——有注入的形式,不代表依赖了抽象。

自测 2:一个 MultiFunctionPrinter 接口同时声明了 print()、scan()、fax(),结果一台只会打印的老式打印机类被迫给 scan()/fax() 写空实现或抛异常。这违反了哪条原则?怎么改?

违反 ISP(接口隔离原则)。它是个胖接口,强迫实现类依赖它用不到的方法。

改法:按客户端需要拆成 Printer、Scanner、Fax 三个小接口。多功能一体机同时实现三个,老式打印机只实现 Printer。这样没有谁再被迫背负废方法,契约变诚实。

带走这一条:ISP 让接口小到"用它的人不被迫拖着废方法走";DIP 让高层与低层都依赖抽象、把"高层→低层具体"的箭头倒过来。而 DIP 是原则、DI 是手段、IoC 是更大的概念——三者别混。Python 里,构造器注入 + Protocol/鸭子类型就能轻量落地,不必套 Java 式接口或重型容器。
