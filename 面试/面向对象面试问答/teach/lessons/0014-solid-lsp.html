SOLID(二):里氏替换原则

SOLID 的 L:子类必须能顶替父类而不出事。这一节用"正方形不是矩形"这个最经典的反例,教你一眼看穿——"这个继承到底该不该存在"。

先想一个场景:你有个函数 render(shape),里面调用 shape.area(),早就写好、测试也过了。某天同事加了一个 Square(Rectangle) 子类,一行父类代码都没动。为什么这个看起来人畜无害的继承,可能让那段老代码突然算错结果、甚至崩溃?先在心里给个答案,再往下看。

一、直觉:替补上场,不能偷偷改比赛规则

里氏替换原则(Liskov Substitution Principle,LSP)说的是一件很朴素的事:凡是用父类对象的地方,都应该能换成任意一个子类对象,而程序照样正确运行。子类是父类的"替补队员"——替补上场天经地义,但它不能上场后偷偷改掉比赛规则(比如把"可以自由跑动"改成"只能站着")。一旦替补的行为超出了原队员的约定,依赖这套约定写的代码就会翻车。

注意关键词是"替换"而不是"继承"。语言允许你 class Square(Rectangle),编译/运行都不报错;但"语法上继承成立"和"行为上能安全替换"是两码事。LSP 关心的正是后者——它是判断"这个继承该不该存在"的试金石。

里氏替换原则 (Liskov Substitution Principle, LSP)
若 S 是 T 的子类型,那么程序里所有用 T 对象的地方,都能用 S 对象替换而不破坏正确性。
换句话说:子类要能"透明顶替"父类。落到重写方法上,子类必须守住父类的"契约" ↓
① 前置条件不能加强 (preconditions)
子类不能要求"更多"。父类 withdraw 接受任意正数,子类却要求金额 ≥ 100——老代码传 50 就崩。
② 后置条件不能减弱 (postconditions)
子类不能保证"更少"。父类保证返回已排序的列表,子类返回乱序的——调用方依赖的承诺没了。
③ 不变式必须保持 (invariants)
父类对象始终为真的规则,子类不能打破。矩形的不变式:宽和高可以各自独立设置。
④ 不抛父类没声明的异常
子类重写不能凭空冒出新异常类型(把父类保证能成功的调用改成抛错)。

二、经典翻车现场:正方形 is-a 矩形

先写一个规规矩矩的矩形。它的隐含契约是:宽和高互相独立,改一个不影响另一个。

class Rectangle:
    def __init__(self, width, height):
        self._width = width
        self._height = height

    def set_width(self, w):
        self._width = w              # 只改宽,不碰高

    def set_height(self, h):
        self._height = h             # 只改高,不碰宽

    def area(self):
        return self._width * self._height


class Square(Rectangle):            # "语言上" Square is-a Rectangle,合法
    # 正方形宽高必须相等,于是重写两个 setter,埋下地雷
    def set_width(self, w):
        self._width = w
        self._height = w            # 副作用:偷偷把高也改了

    def set_height(self, h):
        self._width = h            # 副作用:偷偷把宽也改了
        self._height = h

现在写一段只依赖"矩形契约"的通用代码。它不认识 Square,只知道"这是个矩形,宽高独立"——所以它有充分理由相信:设宽为 5、设高为 4,面积就该是 20。

def stretch_and_check(rect: Rectangle) -> None:
    rect.set_width(5)
    rect.set_height(4)
    # 对"矩形"这个抽象,调用方理所当然地认为:5 * 4 == 20
    assert rect.area() == 20, f"期望面积 20,实际 {rect.area()}"

stretch_and_check(Rectangle(0, 0))   # ✅ 通过:5 * 4 = 20
stretch_and_check(Square(0, 0))      # ❌ AssertionError:set_height(4) 把宽也改成 4 → 面积 16

这就是 LSP 违约的现场:把父类对象换成子类对象,一段本来正确的代码开始出错。诊断一下——Square 破坏了矩形的不变式(宽高独立),等价于"偷偷加强了前置条件"(你不能自由设宽而不动高)。数学上正方形确实是矩形;但在"可变对象"的世界里,Square 不是 Rectangle 的合法替补。

三、另一个经典反例:企鹅是鸟,却不会飞

如果父类 Bird 承诺"所有鸟都能 fly()",企鹅就成了反例——它只能这样交差:

class Bird:
    def fly(self):
        print("flap flap, up we go")

class Penguin(Bird):
    def fly(self):
        raise NotImplementedError("企鹅不会飞")   # ← 违反 LSP 的典型信号

任何写 for bird in birds: bird.fly() 的代码,遇到企鹅就炸(抛了父类没声明的异常,违反契约第 4 条)。请把两个违约信号刻进脑子:

  • 子类重写方法里出现 raise NotImplementedError / pass 空实现——说明这个方法根本不该在父类里。
  • 调用方必须先 isinstance(x, Penguin) 判断具体子类才能正确工作——说明子类无法"透明替换",抽象漏了。

高频追问链(LSP 是 SOLID 里最爱考的一条):

  • "LSP 里的 L 是谁?" → Barbara Liskov,1987 年 OOPSLA 主题演讲提出这个替换思想(1994 年与 Jeannette Wing 形式化为"行为子类型"),后被 Robert C. Martin(Uncle Bob)收进 SOLID 五原则。
  • "契约层面,子类到底不能做什么?" → 四条:前置条件不加强、后置条件不减弱、不变式保持、不抛父类没声明的异常。(进阶:参数可以更宽松=逆变,返回可以更具体=协变。)
  • "数学上正方形明明是矩形,代码里为什么不行?" → 数学是不可变的静态分类;代码里 Rectangle 的隐含契约是"宽高可独立设置",Square 破坏了它。is-a 讲的是分类,LSP 讲的是可替换的行为——两者可以背离。
  • "看到子类方法体里 raise NotImplementedError 意味着什么?" → 强烈的 LSP 违反信号,层级设计错了,该重构。
  • "LSP 和多态(polymorphism)是什么关系?" → 多态是机制(用父类引用调子类);LSP 是让这个机制安全的前提。没有 LSP,多态就会在运行时给你惊喜。

头号翻车点:把"is-a 在语言里成立"当成"满足 LSP"。class Square(Rectangle) 编译通过、跑得起来,但一替换就崩。语言的继承关系不能自动保证可替换性——LSP 是设计契约,类型系统检查不出来,得靠你自己问一句"子类能无条件顶替父类吗"。

第二个坑:以为"抛异常就一定违反 LSP"——这话太绝对。抛父类已声明的异常是允许的;违反的是凭空抛出父类没声明的新异常,或把父类保证成功的调用改成失败。别把话说死,面试时讲清这个边界更显功底。

四、怎么修?——重新设计层级,而不是打补丁

有人想给 Square.set_height 加校验、或直接抛异常"拦住"——但那只是把崩溃换个地方,契约照样被破坏。正解是动层级:

from abc import ABC, abstractmethod

# 修法 A:让 Square 和 Rectangle 平级,都继承"不可变、只承诺 area()"的 Shape
class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Rectangle(Shape):
    def __init__(self, w, h):
        self._w, self._h = w, h
    def area(self) -> float:
        return self._w * self._h

class Square(Shape):               # 不再是 Rectangle 的子类,地雷消失
    def __init__(self, side):
        self._side = side
    def area(self) -> float:
        return self._side ** 2


# 修法 B(企鹅):把"会飞"从"是鸟"里拆出去
class Bird:                        # 所有鸟的共性:eat / lay_egg……不含 fly
    def eat(self): ...

class FlyingBird(Bird):
    def fly(self): ...

class Penguin(Bird):              # 直接继承 Bird,天生不背"会飞"的契约
    def swim(self): ...

三条通用修法,任选其一或组合:① 重新设计层级(把冲突的能力拆到不同分支,如 Shape / FlyingBird);② 改用组合(把"可变宽高""飞行能力"做成一个部件持有,而非继承来);③ 把破坏不变式的东西从抽象里拆掉(Shape 干脆不承诺"可独立改宽高")。

LSP 与语言无关——任何支持继承 + 多态的语言(Python / Java / C++ / C#)都受它约束。区别在于"违约的气味"长什么样。静态类型语言里,违反 LSP 常表现为"向下转型(downcast)+ 类型判断":因为不能透明替换,只好在调用方掰开看具体类型。

语言违反 LSP 的典型"气味"
Python子类里 raise NotImplementedError / 空实现;调用方 isinstance(x, Sub) 分支
Javainstanceof + 向下转型 ((FlyingBird)b).fly();抛 UnsupportedOperationException
C++dynamic_cast<FlyingBird*>(p) 后判空再调用
C#if (x is Square sq) 模式匹配后才敢调方法;NotSupportedException

一句话:编译器帮不了你——LSP 是行为契约,类型系统只查"类型对不对",查不了"行为守不守约"。

合上讲义,亲手复现一次"违约 → 修复":

  • 写出上面的 Bird / Penguin 违约版,再写一个通用函数 make_them_fly(birds) 遍历调用 fly(),喂进一只企鹅,亲眼看它抛 NotImplementedError。
  • 把层级重构成 Bird → FlyingBird / Penguin(Bird),让 make_them_fly 只接受 FlyingBird 列表。

写完自测:重构后,make_them_fly 里还需要写 isinstance 判断吗?(不需要——不再需要掰开看类型,正是"修好了"的标志。)

自测 1:以下哪种情况最能说明一个继承违反了 LSP?

答案:一段只依赖父类契约的代码,把父类对象换成子类对象后,产生了错误结果或抛出意外异常(如 Square 让"面积 == 20"的断言失败)。这正是"不可替换"的定义。

干扰项:"子类新增了父类没有的方法"——那是正常的扩展,完全不违反 LSP;LSP 管的是"重写后能不能顶替父类",不管"多加了什么"。

自测 2:为了让 Square 和 Rectangle 共存又不违反 LSP,最好的办法是?

答案:别让 Square 继承 Rectangle。把两者都设计成不可变 Shape 的平级子类(各自实现 area()),或干脆不继承、用组合。

为什么不是"在 Square.set_height 里加校验/抛异常"?因为那只是把崩溃换个地方:抛出父类没声明的异常本身就违反契约第 4 条,调用方依旧无法安全替换。LSP 问题几乎都是设计问题,要动层级,不是打补丁。

带走这一条:LSP = 子类必须能无条件顶替父类。要判断一个继承该不该存在,就问一句——"任何用父类的地方,换成这个子类还对吗?" 答不出干脆的"对",就别继承:改组合,或拆层级。看到子类里 raise NotImplementedError、或调用方靠 isinstance 分类,基本就是 LSP 在报警。
