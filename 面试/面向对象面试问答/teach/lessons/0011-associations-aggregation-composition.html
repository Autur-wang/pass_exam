关联、聚合与组合:has-a 关系

"has-a"不是一句话就能打发的。它其实有三档强度:关联 < 聚合 < 组合。这一节把三者钉在同一条"耦合强度轴"上,让你知道分水岭到底是什么——以及为什么把所有 has-a 都叫"组合"会被面试官抓包。

先想三个"has-a":你的手机 has-a 电池、一家公司 has-a 员工、一篇文章 has-a 段落。它们真的是同一种关系吗?换个问法:哪个"部分"能被单独拆出来、放到另一个"整体"里继续用?哪个一旦"整体"没了、"部分"就失去了存在的意义?先在心里分好类,再往下看。

一、直觉:同样是"拥有",生死不一样

对象很少孤立存在。一个对象常常用到另一个对象,或者由另一些对象构成。这类"对象之间的连线"统称关联(Association)。但"关联"太粗了——就像说"这两个人有关系",没说是同事、亲人还是路人。OOP 把 has-a 关系按捆得有多紧细分成两档:

  • 聚合(Aggregation):典型的"has-a"。整体拥有/包含部分,但部分是独立的个体——它可以先于整体存在、可以被多个整体共享、也可以在整体消失后继续活着。
    比喻:公司 has 员工。公司倒闭了,员工还在,还能去别家。
  • 组合(Composition):更强的聚合。部分不能脱离整体独立存在——整体一旦销毁,部分也随之消亡。
    比喻:人 has 心脏。人没了,那颗"作为这个人一部分"的心脏也就不成其为这个人的心脏了。

把它们排到一条线上,你就得到了这节课的骨架——一条从"擦肩而过"到"生死与共"的耦合强度轴:

依赖 Dependency临时用到
(方法参数)
→
关联 Association长期持有
A 用到 B
→
聚合 Aggregation整体-部分
部分可独立/共享
→
组合 Composition整体-部分
部分随整体消亡

耦合强度:左弱 → 右强。越往右,"部分"的命运越被"整体"绑定。

关联 (Association)
对象之间"有一条线"的最一般说法:A 用到 B、或 A 与 B 相互引用。聚合和组合都是关联的特例。
聚合 (Aggregation) —— "has-a"
整体拥有部分的整体-部分关系,但部分能独立存在、可被共享。整体只是"持有一个引用",不负责部分的生死。
组合 (Composition) —— 更强的聚合
同样是整体-部分,但部分的生命周期依赖整体:整体创建它、整体销毁时它也一起消失,通常也不被别的整体共享。
依赖 (Dependency) —— 最弱
只是临时用到,用完即弃(例如把 B 作为方法参数传进来、方法里用一下就丢),不作为长期持有的成员字段。

二、分水岭:不是"感觉多紧",而是"能否独立存在"

初学者最容易犯的错,是凭"感觉"判断:"这个关系很重要,应该是组合吧?"——错。聚合与组合的分界线是一个客观问题:

部分能不能脱离整体独立存在、或被别的整体共享?
能 → 聚合;不能 → 组合。

用经典的"大学"例子把这条线走一遍:

  • 大学 has 系 → 组合。系是大学内部设立的,随大学撤销而消失——一个"系"脱离了它所属的大学,就不再是那个系了。整体销毁,部分随之销毁。
  • 系 has 教授 → 聚合。教授是独立的人,可以从计算机系转去数学系,也可以同时挂在两个系(共享),系解散了教授照样存在。部分独立于整体。

看到没?同一个"大学-系-教授"链条里,上一层是组合,下一层是聚合。决定它的不是关系"重不重要",而是"部分的生命线是否被整体攥在手里"。

四、代码:组合"自己造",聚合"外面给"

在 Python 里,组合和聚合都是"持有引用",语法上没有关键字区分。真正的区别落在一个设计问题上:这个"部分"是谁创建的、谁负责它的生死?

组合:整体在 __init__ 里亲手创建部分,部分不从外面来,也不交给外面——生命周期绑定在一起。

# ✅ 组合(Composition):House 亲手造 Room,二者生死与共
class Room:
    def __init__(self, name: str):
        self.name = name

class House:
    def __init__(self):
        # 部分由整体在内部创建,不接收外部传入,也不外泄
        self.rooms = [Room("客厅"), Room("卧室")]

h = House()
print(h.rooms[0].name)   # 客厅
del h                    # House 不再被引用 → 它内部的 Room 也没有别的引用,一起被回收
# 你无法把某个 Room 单独"拿出来"塞进另一栋房子 —— 它本就是这栋房子的一部分

聚合:部分从外部传进来,在整体出生之前就已经存在,整体只是"借用/持有"它的引用。

# ✅ 聚合(Aggregation):Department 只是持有外部已存在的 Professor
class Professor:
    def __init__(self, name: str):
        self.name = name

class Department:
    def __init__(self, professors: list):
        # 部分由外部注入,早已独立存在;系只持有引用,不管它的生死
        self.professors = professors

alice = Professor("Alice")          # 教授先独立存在
bob = Professor("Bob")

cs = Department([alice, bob])        # 系"拥有"这些已存在的教授
del cs                              # 系解散了……
print(alice.name)                   # Alice —— 教授照样活着,还能转去别的系
math = Department([alice])           # 甚至被另一个系共享

一句话记住这段代码:组合是"我生的孩子"(Room 在 House 内部 new 出来),聚合是"我雇的人"(Professor 从门外走进来)。孩子随家庭聚散,雇员来去自由。

高频追问链(关系题几乎必考):

  • "聚合和组合到底怎么区分?" → 看部分能否脱离整体独立存在 / 被共享。能→聚合,不能→组合。别答"组合更紧"这种没边界的话。
  • "为什么不把所有 has-a 都叫组合?" → 因为记号、语义、生命周期都不同。UML 里空心菱形≠实心菱形;把聚合说成组合,等于承诺了一个你并不打算维护的"生死绑定"契约。
  • "has-a 和 is-a 有什么区别?" → 两套正交关系。has-a 是"拥有/包含"(关联/聚合/组合),is-a 是"属于某类型"(继承)。"组合优于继承"说的正是:能用 has-a 表达时,别硬凑 is-a(详见上一节)。
  • "UML 里这几种关系怎么画?" → 关联=实线;聚合=空心菱形(整体端);组合=实心菱形(整体端);继承=空心三角(父类端);依赖=虚线箭头。
  • "依赖和关联的区别?" → 依赖是临时用到(方法参数、局部变量),关联是长期持有(成员字段)。字段 vs 参数,是最实用的判别法。

翻车点一:把所有 has-a 都叫"组合"。这是最常见的不精确。"组合"是有生命周期承诺的强关系;大多数日常的"拥有"其实是聚合(部分能独立存在)。分水岭是"能否独立存在",不是"我觉得它俩关系铁不铁"。

翻车点二:菱形画反端。菱形永远在整体/容器那一端,不是部分那一端。记"大鱼吃小鱼"——菱形是大嘴,长在吞并方(整体)。

翻车点三:以为 Python 能在语言层面保证"整体销毁,部分随之销毁"。不能。Python 里对象都是引用,由 GC(引用计数 + 循环回收)管理;del h 只是去掉一个引用,只有当再没有任何引用指向那个 Room 时它才会被回收。所以 Python(和 Java)里,组合与聚合更多是一种设计意图/约定,而不是语法强制。真正能在语言层面体现"部分随整体确定性销毁"的,是 C++ 的值成员(见下)。别把这点说死。

"这几种关系在不同语言里怎么落地?"——重点在谁管部分的生命周期:

语言组合(Composition)聚合(Aggregation)部分的生命周期由谁管
Python整体内部创建、不外泄引用外部注入、可共享引用GC(引用计数 + 循环回收),无确定性析构;组合/聚合靠设计约定
Java内部 new、不泄漏引用传入外部对象引用JVM GC,同样无确定性析构;靠设计表达语义
C++值成员 / unique_ptr<Part>(独占)裸指针 / shared_ptr<Part> 指向外部对象值成员随整体析构而确定性销毁——C++ 能在语言层面体现组合的生命周期

一句话:Python/Java 里组合是"承诺",C++ 里组合可以是"契约"(值成员/独占指针把生死写进了析构语义)。

合上讲义,自己写两个类,用"谁创建部分"来区分组合与聚合:

  • Engine 与 Car:Car 在 __init__ 里自己创建 Engine(组合)。想一想:你能把这台 Engine 单独拆下来装到别的车上吗?按你的设计,不该能。
  • Garage(cars):车从外部传入(聚合)。同一辆 Car 今天停这个车库、明天停那个,车库拆了车还在。

自测:哪个类里的"部分"是从参数进来的?哪个是内部 new 出来的?——这一个问题就能判定组合还是聚合。

自测 1:"大学 has 系"和"系 has 教授",分别是聚合还是组合?为什么?

大学 has 系 = 组合。系是大学内部设立的,随大学撤销而消失,不能脱离所属大学独立存在。整体销毁 → 部分随之销毁。

系 has 教授 = 聚合。教授是独立的人,可以从一个系转到另一个系、甚至同时挂在两个系(共享),系解散后教授照样存在。部分独立于整体。

关键:判据不是"关系重不重要",而是"部分能否脱离整体独立存在 / 被共享"。同一条链上,层与层的关系可以不同。

自测 2:一个方法 def render(self, printer): 接收一个 printer 参数,在方法内部调用一下 printer.print(...) 就结束,并不把它存成 self 的字段。这属于关联、聚合、组合,还是依赖?

依赖(Dependency),耦合最弱的一档。

printer 只是临时用一下、用完即弃,没有被作为成员字段长期持有。判别法:存进 self(字段)= 关联/聚合/组合;只在方法里用一下(参数/局部变量)= 依赖。如果换成 self.printer = printer 长期持有,才升级为关联/聚合。

自测 3(判断):"组合比聚合更紧,所以只要两个对象关系很重要,就该用组合。"这句话对吗?

不对。"重要"是主观的,不是判据。组合的真正含义是部分的生命周期依赖整体、通常不被共享。如果那个"部分"其实可以独立存在或被别处复用,你却建成组合(比如内部 new 死、不允许外部替换),就会得到一个僵硬、难测试、难复用的设计。先问"部分能不能独立活",再决定档位,而不是凭感情用事。

带走这一条:has-a 有三档强度——关联 < 聚合 < 组合。分水岭是客观的:部分能否脱离整体独立存在 / 被共享(能→聚合,不能→组合)。UML 里菱形画在整体端(空心=聚合,实心=组合)。别把所有 has-a 都叫组合;也别忘了 has-a(拥有)与 is-a(继承)是两套正交关系。
