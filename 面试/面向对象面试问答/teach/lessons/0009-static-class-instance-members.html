实例、类与静态成员:方法与变量,到底"归谁所有"

同一个类里,有的方法带 self、有的带 cls、有的两个都不带;有的变量每个对象各一份、有的全体共享一份。这一节把"归属"这条主线理清:一段代码里的每个成员,它到底挂在实例上、还是挂在类上。

先想一段代码:class Dog: tricks = [],然后 d1 = Dog(); d2 = Dog(); d1.tricks.append("坐下")。现在打印 d2.tricks 会输出什么?是空列表,还是 ['坐下']?先给个答案再往下看——这一题几乎是本节全部要点的缩影。

一、直觉:成员挂在"个体"上,还是挂在"物种"上?

把类想成一个物种(Dog),把实例想成一条具体的狗(旺财、来福)。有些属性属于个体——旺财叫"旺财"、来福叫"来福",这是实例变量,每条狗各存一份。有些属性属于整个物种——"全世界一共有几条狗",这个数不该记在某一条狗身上,而应记在"物种"这个层级,所有狗共享同一个计数,这就是类变量。

方法也一样分层。实例方法操作某条具体的狗(旺财现在几岁);类方法操作整个物种的账本(总数是多少),或者充当"造一条狗"的命名工厂;静态方法则既不碰具体的狗、也不碰物种账本,它只是一个逻辑上归这个类管、顺手放进类命名空间的普通函数(比如"检查一个名字合不合法")。

为什么要分这么细?因为面试官想看的不是你会不会写 @staticmethod,而是你能不能判断一个行为的"归属层级"——放错层级会直接埋 bug(比如把共享计数写进实例、把该独立的列表写成共享),这正是下面易错点的核心。

实例方法 (instance method)
第一个参数是 self,通过它读写实例状态。最常见的一种,占你写的方法九成以上。
类方法 (@classmethod)
第一个参数是 cls(指向类本身)。用来读写类级状态,或做命名构造器(返回 cls(...))。
静态方法 (@staticmethod)
既无 self 也无 cls。就是一个逻辑上属于该类、被放进类命名空间的普通函数,不访问实例或类的状态。
实例变量 (instance variable)
self.x = ... 定义,存在每个对象各自的 __dict__ 里,各存一份。
类变量 (class variable)
直接写在类体里(count = 0),存在类对象上,所有实例共享同一份。

二、一段代码看全五种成员

用一个 Counter 类把上面五个概念一次演示完:类变量统计实例总数、类方法读总数、静态方法做一个与任何实例都无关的工具函数。

class Counter:
    count = 0                          # 类变量:所有实例共享一份

    def __init__(self, name):
        self.name = name               # 实例变量:每个对象各一份
        Counter.count += 1             # 改类级状态:用类名限定,不用 self(见易错点)

    def describe(self):                # 实例方法:第一参数 self,读实例状态
        return f"我是 {self.name}"

    @classmethod
    def total(cls):                    # 类方法:第一参数 cls,读类级状态
        return cls.count

    @classmethod
    def anonymous(cls):                # 命名构造器:返回 cls(...),继承友好
        return cls("匿名")

    @staticmethod
    def is_valid_name(name):           # 静态方法:无 self/cls,纯工具函数
        return isinstance(name, str) and len(name) > 0

现在看它们的存储差异——这是理解"归属"的关键证据:

a = Counter("旺财")
b = Counter("来福")

print(a.name, b.name)        # 旺财 来福 —— 实例变量各存一份
print(Counter.total())       # 2       —— 类方法读到的是共享计数

print(a.__dict__)            # {'name': '旺财'} —— 实例只存自己的实例变量
print(b.__dict__)            # {'name': '来福'} —— count 根本不在这里
print(Counter.count)         # 2       —— count 挂在类对象上,被两个实例共享

print(Counter.is_valid_name(""))   # False —— 工具函数,不需要任何实例

注意 a.__dict__ 里没有 count。当你写 a.count 时,Python 先在实例 __dict__ 里找,没找到就沿着类(以及 MRO)往上找——于是读到了类变量。这套"实例优先、类兜底"的查找规则,正是下面第 2 条易错点的根源。

高频追问链(问了方法种类,追问几乎必来):

  • "@classmethod 和 @staticmethod 到底怎么选?" → 需要访问或返回类(读类级状态、写命名构造器、希望子类调用时拿到子类)就用 classmethod;完全不碰类也不碰实例、只是逻辑上归这个类的工具函数,就用 staticmethod。判据是"这段逻辑需不需要 cls"。
  • "类变量和实例变量在内存里怎么存?" → 类变量存在类对象上(所有实例共享);实例变量存在各自的 self.__dict__ 里。读属性时先查实例、再沿类查找(实例优先)。
  • "为什么计数要写 Counter.count += 1,不能写 self.count += 1?" → self.count += 1 会被展开成 self.count = self.count + 1:右边读到类变量(比如 2),左边却在实例上新建一个 count 属性(值 3),类变量原地不动。结果每个实例各记各的,共享计数失效。要改共享状态得用 Counter.count(或 type(self).count)。
  • "静态方法和直接写在类外面的普通函数有啥区别?" → 功能上几乎没区别;区别在命名空间归属与可发现性——它逻辑上属于这个类,通过 Counter.is_valid_name 调用,读代码的人一眼知道它和谁相关。所以要不要用 staticmethod,更多是组织代码的取舍。

易错点 ①:可变类变量的共享陷阱(本节开场那题的答案)。写 class Dog: tricks = [] 时,这个 list 是类变量,所有实例共享同一个对象。d1.tricks.append("坐下") 是在原地修改那唯一的一份,于是 d2.tricks 也变成 ['坐下']。想让每个实例各有一份独立列表,必须在 __init__ 里写 self.tricks = []——每次构造都新建一个。类变量适合放不可变的、真正共享的东西(常量、计数器),别放会被逐个实例修改的可变容器。

易错点 ②:实例属性遮蔽(shadow)类属性。c.x = 5 是赋值,它总是在实例上新建/覆盖属性,遮住同名的类变量;但它不会改动类变量本身。所以 c.x 读到 5(实例优先),C.x 仍是原值。这正是上面 self.count += 1 出 bug 的机制:自增里的赋值把你带进了"新建实例属性"这条岔路。读用类兜底、写只落实例——记住这条不对称。

易错点 ③:classmethod / staticmethod 选错。常见错误是"反正不用 self 就都写成 staticmethod"。可一旦你要写命名构造器(如 from_json),就必须用 classmethod:因为子类调用 Sub.from_json(...) 时 cls 会是 Sub,返回的是正确的子类实例;写死成 staticmethod 里 return Base(...) 就丢了这个继承友好性。

"这套东西在别的语言长什么样?"——Java 对照(面试常拿来考你对概念本质的理解):

概念PythonJava
类级变量(全体共享)类体里 count = 0static 字段
归属类、不碰实例/类状态的方法@staticmethodstatic 方法(无 this)
带类上下文(拿得到/返得回类)的方法@classmethod(参数 cls)无直接等价物
实例方法第一参数 self普通方法(隐式 this)

一句话:Python 的 @staticmethod 大致对应 Java 的 static 方法,类变量对应 Java 的 static 字段;但 Python 多出 @classmethod(带 cls)这一层,Java 没有直接等价物——想在 Java 里拿到"当前实际的类"通常得靠反射或传参绕。这多出来的一层,正是 Python 命名构造器优雅又继承友好的原因。

合上讲义,给一个 User 类补齐三种成员:

  • 类变量 registry = [] 的想法先忍住——想想易错点①,注册表该放类级还是实例级?(答案:全站唯一的注册表确实是共享的,放类级合理;但要小心别在里面塞可变的每实例数据。)
  • 实例变量 self.name;类变量 _count = 0,每次 __init__ 用 User._count += 1 递增。
  • @classmethod how_many(cls) 返回 cls._count;@classmethod from_email(cls, email) 取 @ 前缀当 name、返回 cls(...)(命名构造器)。
  • @staticmethod is_valid_email(s):检查含 @,不碰任何实例。

写完自测:故意写一次 self._count += 1 替换掉 User._count += 1,再 print(User.how_many()),看计数是不是"坏"了——亲手复现易错点②的 bug,比背十遍都记得牢。

自测 1:class Dog: tricks = [] 后,d1 = Dog(); d2 = Dog(); d1.tricks.append("坐下"); print(d2.tricks) 输出什么?为什么?怎么改才能各自独立?

输出 ['坐下']。 tricks 是类变量,两个实例共享同一个 list 对象;d1.tricks.append(...) 原地修改了那唯一一份,所以 d2 也看得到。

改法:在 __init__ 里写 self.tricks = [],让每次构造都新建一个独立列表。
补一个细节:如果写的是 d1.tricks = ["坐下"](赋值而非 append),那是在 d1 上新建实例属性、遮蔽类变量,d2.tricks 反而不受影响——因为赋值只落实例。共享陷阱只在"原地修改可变对象"时发作。

自测 2(选择题):你要给 Shape 加一个从字典构造对象的方法 from_dict(data),并且希望 Circle.from_dict(...) 能返回 Circle 实例。应该用哪一种?A) 实例方法 B) @staticmethod 里 return Shape(...) C) @classmethod 里 return cls(...) D) 类外的普通函数

答案:C。 命名构造器要写成 @classmethod,用 cls 来构造:子类调用 Circle.from_dict(...) 时 cls 就是 Circle,返回正确的子类实例——这就是 classmethod 的"继承友好"。

为什么其它不行:B 把类写死成 Shape,子类拿不到自己的类型,丢了继承友好;A 需要先有实例才能调用,而"构造"恰恰发生在还没有实例的时候,自相矛盾;D 脱离了类命名空间,可发现性差,也同样拿不到 cls。

带走这一条:先问"这个成员归谁"——归实例就用 self(实例方法 / self.x),归类就用 cls 或类名(@classmethod / 类体里的类变量),两者都不归、只是逻辑归属就用 @staticmethod。两条铁律配套记:可变类变量全体共享(要独立请进 __init__),而属性读用类兜底、写只落实例——想改共享状态必须走类名,别走 self。
