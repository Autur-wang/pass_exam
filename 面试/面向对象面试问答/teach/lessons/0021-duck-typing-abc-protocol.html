鸭子类型、ABC 与 Protocol

"Python 里怎么定义接口?"这是一道能瞬间分层的题。只会答"用 interface"的人当场出局;能讲清鸭子类型 / ABC / Protocol 这三条路以及各自的取舍,才算真懂 Python 的多态。这一节就把这三条路一次讲透。

先回忆两件事:第一,0005 讲"抽象类 vs 接口"时,接口的本质是什么?(一份"你必须能做这些操作"的契约。)第二,你要写一个函数 dump(x),它想调用 x.read()。你会先检查"x 是不是 File 类型"再调用,还是根本不管类型、直接调?先给个答案,再往下看——这正是三条路的分岔口。

一、直觉:走起来像鸭子,就当它是鸭子

有句老话:"如果它走起来像鸭子、叫起来像鸭子,那它就是鸭子。"(If it walks like a duck and quacks like a duck, it is a duck.)这就是鸭子类型(Duck Typing)——判断一个对象"能不能当某种东西用",不看它的类型标签,只看它有没有那个能力。

放到代码里:一个函数要 x.read(),它不问 x 是不是 File,只要 x 身上有个能调用的 read(),就当文件用。这是 Python 默认的多态方式——同一个函数,喂进毫无继承关系的不同对象,只要它们"能做这个操作",就都跑得通。

Python 表达"接口 / 多态"其实有三条路,它们回答的是同一个问题的不同版本——"怎么算'是'这种类型":

① 运行时 · 结构
鸭子类型
有这个方法就行,不问出身
② 名义 · 要继承
ABC
显式继承/注册才算"是"
③ 静态 · 结构
Protocol
形状对得上就算,事后契约
鸭子类型 (Duck Typing)
不检查对象类型,只依赖它是否具备所需的方法 / 属性。是 Python 默认的多态方式,判定发生在运行时。
EAFP vs LBYL
EAFP(Easier to Ask Forgiveness than Permission,请求原谅比请求许可容易):先动手,出错用 try/except 兜底。LBYL(Look Before You Leap,三思而后行):先用 if/hasattr 检查,再动手。Python 社区惯例偏向 EAFP,它和鸭子类型是天生一对。
抽象基类 ABC (Abstract Base Class)
abc.ABC + @abstractmethod。名义子类型(nominal):必须显式继承(或用 register() 注册)才被认作"是"这个类型;有未实现的抽象方法就不能实例化;可配合 isinstance 检查。
Protocol (typing.Protocol)
结构子类型(structural),也叫"静态鸭子类型"。只要一个类具备 Protocol 声明的方法 / 属性,类型检查器就认它符合,无需显式继承——一种事后追认、非侵入的契约。

二、鸭子类型:默认多态,配 EAFP

看它有多"不问出身":

# 鸭子类型:dump 只关心"你有没有 read()",不关心你是谁
def dump(source):
    return source.read()

class RealFile:
    def read(self): return "来自磁盘"

class MemoryBuffer:
    def read(self): return "来自内存"

print(dump(RealFile()))       # OK
print(dump(MemoryBuffer()))   # OK —— 两个类毫无继承关系,却都能当"可读物"用

那"要不要先检查类型"呢?这就引出两种风格。鸭子类型天然搭配 EAFP——别先验身份,直接用,不行再兜底:

# LBYL:先看后跳 —— 先检查再动手(有竞态风险:检查完到使用前状态可能变)
if hasattr(source, "read"):
    data = source.read()
else:
    data = None

# EAFP:先做,错了原谅 —— Python 更偏这种,也更契合鸭子类型
try:
    data = source.read()
except AttributeError:
    data = None

为什么 Python 偏爱 EAFP?因为鸭子类型的世界里,"能做某操作"的对象千奇百怪,你很难用一串 if 把所有合法情况都枚举干净;直接尝试、按异常兜底,代码更短、也避免了"检查"和"使用"之间的竞态窗口。

三、ABC vs Protocol:名义 vs 结构

鸭子类型很灵活,但有个代价(后面易错点细说):契约只存在于程序员脑子里,写错要到运行时才炸。于是 Python 给了两个"把契约写下来"的工具,分别代表两种哲学——

from abc import ABC, abstractmethod
from typing import Protocol

# ① ABC:名义子类型 —— 必须"报出身",显式继承才算数
class CloseableABC(ABC):
    @abstractmethod
    def close(self) -> None: ...

class Door(CloseableABC):            # 必须写出这层继承
    def close(self) -> None:
        print("门关上了")

# 有抽象方法没实现,就连实例都造不出来:
# class Broken(CloseableABC): ...    # 忘了实现 close
# Broken()   -> TypeError: Can't instantiate abstract class Broken ...

# ② Protocol:结构子类型 —— 不用继承,"形状"对得上就算
class Closeable(Protocol):
    def close(self) -> None: ...

class Valve:                         # 注意:没有继承 Closeable
    def close(self) -> None:
        print("阀门关闭")

def shut(x: Closeable) -> None:
    x.close()

shut(Valve())    # 静态类型检查器(如 mypy)认可:Valve 结构上满足 Closeable

两者的分水岭就一句话:ABC 问"你继承了吗"(名义),Protocol 问"你长得对吗"(结构)。ABC 是侵入式的——你得在定义类时就写上继承,契约是"事先声明"的;Protocol 是非侵入式的——契约可以在别处、甚至在你无法修改的第三方类之后追认,只要它碰巧有 close(),就自动符合。

补一个准确细节:Protocol 默认只在静态检查时生效(给 mypy / Pyright 看)。若想在运行时用 isinstance(obj, Closeable),要给 Protocol 加 @runtime_checkable 装饰器;而且这种运行时检查只核对方法名是否存在,不核对参数签名。ABC 则天生支持 isinstance。

高频追问链(这一簇几乎是 Python OOP 的必考区):

  • "Python 里怎么定义接口?" → 先纠正前提:Python 没有 interface 关键字。有三条路:鸭子类型(运行时结构)、ABC(名义、要继承)、Protocol(静态结构、不用继承)。
  • "ABC 和 Protocol 有什么区别?"(进阶分水岭) → 名义 vs 结构;ABC 要显式继承、Protocol 不用;ABC 侵入式(定义时声明)、Protocol 非侵入式(可事后追认第三方类)。
  • "什么是 EAFP?为什么 Python 偏爱它?" → 先做后兜底 vs 先检查后做;EAFP 代码更短、避免检查—使用之间的竞态,也更契合鸭子类型的"不问出身"。
  • "鸭子类型有什么缺点?怎么补?" → 契约不显式,错误延迟到运行时才暴露;补法:类型注解 + Protocol + 静态检查器,灵活与安全兼得。
  • "abc 的 register() 是干嘛的?" → 把一个不继承 ABC 的类注册成它的"虚拟子类",让 isinstance 返回 True——但它不会继承 ABC 里的任何实现,也不强制它实现抽象方法。

翻车点一:回答"Python 用 interface 关键字定义接口"。Python 根本没有这个关键字。这是把 Java/C# 的肌肉记忆套到 Python 上,面试官一听就知道你没写过 Python 的接口。

翻车点二:把 ABC 和 Protocol 说反或说混。记死:ABC = 名义 = 要继承(不继承就不算);Protocol = 结构 = 不用继承(有对的方法就算)。这条区别是区分"背过"和"用过"的进阶考点。

翻车点三:忽视鸭子类型的代价。它把类型错误推迟到运行时——喂进一个没有 read() 的对象,程序跑到那一行才 AttributeError,而不是编码时就报错。别把"灵活"讲成没有代价;正确的收尾是:用类型注解 + Protocol + 静态检查器(mypy/Pyright),既保留鸭子类型的灵活,又把错误提前到检查阶段。

翻车点四(易被反问):"Protocol 能不能用 isinstance?"——默认不能,要加 @runtime_checkable,且它只查方法名、不查签名。拿不准就如实说这一层限制,别拍胸脯保证。

"这门语言怎么表达接口 / 多态?"是必问的跨语言题。核心轴是名义(要显式声明) vs 结构(形状对就行):

语言接口机制名义 or 结构要不要显式声明"我实现了它"
Java / C#显式 interface + implements名义(nominal)要——必须写出 implements X 才算
Go接口隐式满足(有对应方法即自动满足)结构(structural)不要——像 Python 的 Protocol
Python鸭子类型 / ABC / Protocol三者兼有看你选哪条路:ABC 要;Protocol、鸭子类型不要

一句话记忆:Java/C# 要你"报出身"(名义),Go 只看你"长什么样"(结构),Python 三种都给你——鸭子类型是运行时结构,Protocol 是静态结构,ABC 是名义。

合上讲义,自己写一遍——用两条路各实现一次同一个契约"可迭代地关闭资源":

  • 先用 Protocol 定义 Closeable(有一个 close(self) -> None),再写一个不继承它的类 TempFile,只要有 close() 就应被 def cleanup(x: Closeable) 接受。用 mypy 跑一遍看是否通过。
  • 再用 ABC 定义 CloseableABC(@abstractmethod def close),故意写一个忘了实现 close 的子类,尝试实例化它——观察抛出的 TypeError,体会"名义 + 强制实现"的手感。
  • 自测:把一个没有 close() 的对象传进 cleanup()。鸭子类型下它会在哪一刻报错?(运行到 x.close() 那一行时。)这正说明为什么要加静态检查。
自测 1:你有一个第三方库的类 ThirdPartyLogger,它自带 close() 方法,但你无法修改它的源码去加继承。你想让类型检查器认可它"是可关闭的"。用 ABC 还是 Protocol?为什么?

答案:用 Protocol。

ABC 是名义子类型,要求目标类显式继承(或你手动 register())——但你改不了第三方源码,继承这条路走不通。Protocol 是结构子类型、非侵入式:你只需在自己这边定义 class Closeable(Protocol): def close(self) -> None: ...,由于 ThirdPartyLogger 碰巧有 close(),它就自动满足 Closeable,无需碰它一行代码。这正是 Protocol"事后追认、非侵入"的杀手级场景。

自测 2:下面说法哪个最准确?"在 Python 里,鸭子类型相比 Protocol 的关键差异是……"

答案:鸭子类型的检查发生在运行时(错了才炸),Protocol 让同样的"结构契约"能在编写时被静态检查器提前发现。

两者都是结构式的——都只看"有没有那个方法",都不要求继承。区别在什么时候校验:鸭子类型是纯运行时,喂错对象要跑到那一行才 AttributeError;Protocol 把这份契约写成类型注解,mypy/Pyright 能在你运行之前就报错。所以常见的正确收尾是:"Protocol = 给鸭子类型加了一层静态安全网",而不是"Protocol 取代了鸭子类型"。

常见错误答案:"鸭子类型要继承、Protocol 不要"——错,鸭子类型恰恰也不要继承。要继承的是 ABC。

带走这一条:Python 没有 interface 关键字,它用三条路表达接口——鸭子类型(运行时结构,配 EAFP,灵活但错误延迟到运行时)、ABC(名义,要显式继承,可强制实现 + isinstance)、Protocol(静态结构,不用继承,可事后追认第三方类)。想兼得灵活与安全:类型注解 + Protocol + 静态检查器。
