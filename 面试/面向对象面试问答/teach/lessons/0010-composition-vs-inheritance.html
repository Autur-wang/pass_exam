组合 vs 继承 vs mixin:三种复用手段,以及为什么"组合优于继承"

"你怎么在两个类之间复用代码?"——这个问题背后有三个答案:继承、组合、mixin。会背三个定义只是及格;能当场判断"这里到底该用哪个",才是加分项。这一节把三者摆在一起讲透,并说清那条著名准则的分寸。

先想一个具体场景:你有个 Car 类需要"启动引擎"的能力,又有个 Boat 类也要"启动引擎"。你有两个直觉选项:让 Car、Boat 都继承一个 Engine 类,或者让它们各自"持有"一个 Engine 对象。哪种更合理?为什么?先给自己一个答案,再往下看。

一、直觉:三个问句,对应三种关系

继承、组合、mixin 表面上都在做同一件事——让一个类用上另一处写好的代码。区别不在"能不能复用",而在你在描述一种什么关系。三者各自对应一个你能大声说出口的句子:

继承 Inheritance
is-a
Car is a Vehicle
组合 Composition
has-a
Car has an Engine
Mixin
can-do
Helicopter can fly
  • 继承(is-a):子类就是父类的一种。Car 本质上是一种 Vehicle,所以它天然拥有 Vehicle 的一切。你在建立分类学上的从属关系。
  • 组合(has-a):一个对象拥有另一个对象作为零件。Car 里面装了一台 Engine,但 Car 不"是"Engine。你在用小积木拼大积木。
  • Mixin(can-do / kind-of-a):一个只提供某种能力的类,被混进来给别人加技能。直升机不"是"鸟,但它"能飞得像鸟"——飞行是一种可以被到处混入的横向能力,而不是一条纵向的血统。
继承 (Inheritance)
子类继承父类的属性与行为,表达 "is-a" 关系。
优点:直接复用、关系直观;缺点:容易堆出复杂层级、过度泛化。
组合 (Composition)
通过把更简单的对象作为成员持有来搭建复杂对象,表达 "has-a" 关系。
优点:模块化、组件可替换;缺点:前期要多想一点设计、可能多写些委托样板。
Mixin
一个只提供方法、不作为独立实体存在的类,把某种能力"混入"其它不相关的类,表达 "can-do-this"。
优点:跨越继承树复用代码、避免深继承;缺点:方法来源不直观、多个 mixin 可能命名冲突。

二、三种写法,同一件事:给 Car 一个"启动"能力

① 继承 —— Car is a Vehicle

class Vehicle:
    def __init__(self, brand):
        self.brand = brand

    def start(self):
        print(f"{self.brand} 启动")

class Car(Vehicle):          # Car is-a Vehicle:子类"就是"一种父类
    def honk(self):
        print("Beep!")

c = Car("Toyota")
c.start()   # 继承来的行为,一行没写就有了
c.honk()    # 自己新增的行为

继承最爽的地方:Car 一个字没写就白得了 start()。但代价是——Car 和 Vehicle 被焊死在一条继承链上。父类改一处,所有子类跟着受影响;层级一深,你就得在脑子里同时装下整条链才能读懂一个方法。

② 组合 —— Car has an Engine

class Engine:
    def start(self):
        print("引擎点火")

class Car:                   # Car has-a Engine:Car 不"是"引擎,而是"装了"一台
    def __init__(self):
        self.engine = Engine()      # 持有一个 Engine 实例(组合)

    def start(self):
        self.engine.start()         # 把动作委托(delegate)给内部组件
        print("车子出发")

c = Car()
c.start()

注意 Car.start() 里那句 self.engine.start()——这叫委托(delegation):自己不干,交给持有的零件干。好处是Engine 随时能换成 ElectricMotor,只要它也有 start(),Car 内部改一行、外部零改动。Car 依赖的是"一个能 start 的东西",而不是某个具体父类。这就是组合更松耦合的原因。

③ Mixin —— 谁混入,谁就 can-do

import json

class JSONSerializableMixin:
    """只提供行为、自己不独立存在。混入谁,谁就获得 to_json() 这个能力。"""
    def to_json(self):
        return json.dumps(self.__dict__)

class User(JSONSerializableMixin):       # User can-do: to_json
    def __init__(self, name):
        self.name = name

class Product(JSONSerializableMixin):    # Product 与 User 毫无血缘,却也 can-do
    def __init__(self, price):
        self.price = price

print(User("Ann").to_json())     # {"name": "Ann"}
print(Product(9.9).to_json())    # {"price": 9.9}

关键看点:User 和 Product 没有任何共同的 is-a 关系——一个是人,一个是商品,硬给它们造一个共同父类会很别扭。但它们都需要"能序列化成 JSON"这项横向能力。mixin 就是干这个的:不建立血缘,只发能力。你还能给一个类混入多个:class User(JSONSerializableMixin, ComparableMixin):,每个 mixin 负责一簇技能。

高频追问链(这一簇几乎必被问,答对区分度很高):

  • "'组合优于继承'这句话出自哪里、到底在说什么?" → 出自 GoF《Design Patterns》(1994) 的设计原则 "Favor object composition over class inheritance",Joshua Bloch《Effective Java》也专列一条。它不是说"永远别用继承",而是说:当你只是想复用代码时,默认先考虑组合;只有存在真正的 is-a 关系时才用继承。
  • "那什么时候该用继承?" → 当 "X is a Y" 说得通并且满足里氏替换原则(LSP):任何用到 Y 的地方都能塞一个 X 进去而不出错。说不通 is-a,却为了省代码去继承,就是反模式(见易错点)。
  • "Python 的 mixin 靠什么实现?super() 在 mixin 里指向谁?" → Python 用多继承实现 mixin(把 mixin 类列进基类列表)。而 super() 走的是 MRO(方法解析顺序),它指向的是 MRO 里的"下一个",未必是直接父类——在多继承下可能是一个兄弟 mixin。这是协作式多继承的关键,也是新手常踩的点。
  • "组合的缺点是什么?" → 要多写委托代码(转发方法),前期得先想清楚拆成哪些组件。换来的是灵活和可测试性,大多数情况值得。

头号反模式:"为了复用代码而继承"。 看到父类里有个现成方法很好用,就随手 class A(B) 把它继承过来——哪怕 A 根本不"是"一种 B。后果是:① 强耦合,A 被绑死在 B 的实现上;② 脆弱基类问题(fragile base class),B 改动可能悄悄弄坏 A;③ A 被迫继承了 B 里它用不到甚至不该有的一堆方法。判断法则一句话:能说通 "X is a Y" 才继承;"X has a Y" 用组合;"X can do Z" 用 mixin。

mixin 的两个坑:① 方法来源不透明——对象上冒出个 to_json(),读代码的人得翻遍所有基类才知道它从哪来;② 命名冲突——两个 mixin 都定义了 save(),谁生效由 MRO 决定,容易踩雷。所以 mixin 类应当小而专一,名字最好带 Mixin 后缀,一眼看出它不是主血统。

"横向复用能力(mixin)"在各语言里名字不同,机制大同小异——但"优先组合"这条准则跨语言一致:

语言实现 mixin / 横向复用的机制
Python多继承(把 mixin 类列进基类列表,靠 MRO 协作)
Rubymodule + include
Java接口 + default 方法(Java 8+)近似 mixin
Scalatrait
C++多继承

不管语法叫什么,核心思想都一样:纵向血统(继承)要克制,横向能力(mixin)要专一,拼装(组合)是默认选项。

三、三选一决策树:把法则变成动作

你想让 A 用上 B 里的代码。先问:A 和 B 到底是什么关系?
↓
"A is a B" 说得通
继承:class A(B)
"A has a B" 更自然
组合:A 内部持有 B 实例并委托
"A can do Z"(一种能力)
Mixin:混入提供该能力的小类

拿不准时,默认走组合——这正是"组合优于继承"的实操含义:继承是"除非确有 is-a,否则不轻易动用"的选项,因为组合更灵活、更模块化、更好维护。

合上讲义,自己实现一次三选一:

  • 写一个 LoggerMixin,提供一个 log(msg) 方法(打印带类名前缀的日志);把它混入两个互不相关的类(比如 Order 和 EmailSender),验证两者都能 log(...)。
  • 再写一个 Stack,内部组合一个 list(self._items = []),只暴露 push / pop / peek。
  • 自问:第二题为什么不写成 class Stack(list)?(提示:那样会把 insert、__setitem__ 等一堆能破坏"后进先出"约束的方法全暴露出去——Stack 并不"是"一个通用 list。)
自测 1:一个团队里,Order、User、Report 三个毫无关联的类都需要"写审计日志"的能力。有人提议:建一个 Auditable 基类放 log(),让三者都继承它。这样做好不好?更合适的是什么?

不好。 "写日志"是一种横向能力(can-do),不是一条分类学血统——说 "Order is an Auditable" 相当勉强,而且一旦 Order 已经有别的父类,单继承语言就卡住了。硬造一个共同父类,是"为复用而继承"的典型反模式。

更合适:用 mixin。 写一个 AuditLogMixin 只提供 log(),混入需要的类即可(Python 里 class Order(AuditLogMixin):)。它不建立血缘、可被任意组合、也不占用"唯一父类"的名额。

自测 2:下面哪种说法最准确?"组合优于继承(Composition over Inheritance)"这条准则的意思是……

答案:当目标只是复用代码时,默认优先选组合;继承留给真正成立的 "is-a" 关系。

常见的错误理解是"永远不要用继承""继承是坏东西"。这太绝对了——继承在表达真实的 is-a 层级(如 Car(Vehicle))且满足里氏替换时完全恰当。这条准则针对的是把继承当纯代码复用工具的滥用:那会带来强耦合和脆弱基类。它出自 GoF《Design Patterns》,是一条"默认倾向",不是一刀切禁令。

带走这一条:三种复用对应三句话——is-a 用继承、has-a 用组合、can-do 用 mixin。"为省代码而继承"是反模式(强耦合 + 脆弱基类);拿不准就走组合,这就是"组合优于继承"的实操含义。它是一条有分寸的默认倾向,不是"禁用继承"。
