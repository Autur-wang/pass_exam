封装:信息隐藏、访问控制与 Python 的"伪私有"

封装是四大支柱里最容易"背得出定义、答不透追问"的一个。这一节的目标:让你既能一句话讲清它是什么,又能当场用 Python 演示"为什么 Python 根本没有真正的私有"。

开始前先想一个场景:你写了个 Account 类,里面有个 balance 属性谁都能直接 a.balance = -9999。这会带来什么问题?如果要"不让外面乱改",你会怎么做?先在心里给个答案,再往下看。

一、直觉:药瓶的儿童安全盖

封装(Encapsulation)就是给对象的内部状态加一个"儿童安全盖"。药瓶里的药(数据)不是不让你吃,而是必须通过一个受控的开盖动作(方法)才能拿到——这个动作可以顺手检查"你是不是拧对了方向""剂量对不对"。

换成代码的话:对象把数据和操作数据的方法捆在一起(bundling),把内部状态藏起来(information hiding),只留几个公开方法当"开盖口"(access control)。外面的代码想读、想改,都得走这几个口——于是你就有了插入校验、约束、日志的机会。

封装 (Encapsulation)
把数据与操作它的方法捆进一个单元,隐藏内部状态,只通过受控接口暴露。
它由三件事组成,缺一不可 ↓
① 捆绑 (Bundling)
数据 + 方法住在同一个类里。
② 信息隐藏 (Information Hiding)
内部状态与实现细节对外不可见。
③ 受控访问 (Access Control)
只能通过公开方法(getter/setter/property)读写,方法里可以加约束。

二、为什么要封装?——从一个会出事的类说起

先看没有封装的版本,问题一眼可见:

# ❌ 裸奔:任何人都能把 fuel 改成非法值
class Car:
    def __init__(self):
        self.fuel = 100      # 公开属性

c = Car()
c.fuel = 120                 # 超过满油?没人拦
c.fuel = -50                 # 负油量?也没人拦

这里的病根是:数据的合法性规则(0–100)散落在类外面,没人负责守门。项目一大,谁都可能写出把它改坏的一行。封装的解法是把"守门"这件事收回类内部:

# ✅ 封装:fuel 变"私有",读写都走受控通道
class Car:
    def __init__(self):
        self._fuel = 100          # 前缀下划线:约定为"内部使用"

    @property
    def fuel(self):               # getter:读
        return self._fuel

    @fuel.setter
    def fuel(self, value):        # setter:写时校验,把非法值挡在门外
        if 0 <= value <= 100:
            self._fuel = value
        else:
            raise ValueError("油量必须在 0–100 之间")

    def drive(self):
        if self._fuel > 0:
            self._fuel -= 1
            print("Vroom!")
        else:
            print("没油了!")

c = Car()
c.fuel = 80        # 走 setter,合法,通过
print(c.fuel)      # 走 getter → 80
c.fuel = 120       # 走 setter → ValueError,被挡下

关键收益有三条(这也正是源题给的答案):

  • 安全性:受控访问把"数据被改坏"的风险收敛到一处。
  • 简单性:外面只看到 c.fuel 这个简单接口,不必知道内部怎么存。
  • 灵活性:哪天你想把 _fuel 换成"百分比 × 油箱容量"来存,只要 getter/setter 内部改,外部一行都不用动——这叫松耦合。

高频追问链(封装几乎必被问):

  • "封装和抽象有什么区别?" → 封装是把细节藏起来(how),抽象是只暴露必要的功能(what)。封装关注"数据安全边界",抽象关注"接口简洁"。两者常配合,但不是一回事。
  • "Python 有 private 吗?" → 这是送分题也是坑,见下面「跨语言对照」和「易错点」。
  • "@property 是干嘛的?" → 把 getter/setter 伪装成属性访问,让调用方写 c.fuel 而不是 c.get_fuel(),既保留校验能力又保持 Python 式简洁。
  • "getter/setter 是不是越多越好?" → 不是,见易错点。

三、Python 的"私有"到底是什么?

Java/C++ 用关键字 private 从编译器层面强制阻止外部访问。Python 没有这种关键字,它用两级约定:

  • _single(单下划线):纯君子协定——"这是内部的,请别碰",但语言不拦你。
  • __double(双下划线):触发 name mangling(名称改写)——解释器把 __x 在类内改写成 _ClassName__x。看起来访问不到,其实只是换了个名字。
class Account:
    def __init__(self):
        self.__balance = 100          # 被改写为 _Account__balance

a = Account()
print(a.__balance)                    # ❌ AttributeError
print(a._Account__balance)            # ✅ 100 —— "私有"照样能访问!

最经典的翻车点:说"Python 用 __ 实现私有"。准确说法是:Python 没有真正的私有,__ 触发的是 name mangling,目的是避免子类意外覆盖父类的同名属性,不是安全边界——a._Account__balance 照样能读能写。面试时把这点讲清,立刻和"只会背定义"的人拉开差距。

另一个坑:getter/setter 泛滥反模式。如果一个 setter 只是 self._x = value 什么都不做,那它相当于把属性重新变公开,只是绕了个弯——徒增样板。Python 的建议是:先直接用公开属性,等真的需要校验/计算时再用 @property 无痛升级(接口不变)。别一上来就给每个字段配一对空 getter/setter(那是 Java 的历史包袱,不是 Python 风格)。

"这门语言怎么做封装 / 私有?"是跨语言必问题,记住这张对照表:

语言私有机制是否强制getter/setter 惯用法
Python_x 约定 / __x name mangling否(君子协定)@property
Javaprivate/protected/public(默认 package-private)是(编译器强制)显式 getX()/setX()
C++private/protected/public是(编译器强制)显式方法
C#private 等修饰符是语言级 Properties({ get; set; })

一句话总结:Java/C++/C# 的私有是"墙",Python 的私有是"礼貌"。

合上讲义,自己写一个 BankAccount:

  • 余额 _balance 内部持有,初始为 0;外部只能读不能直接写(只给 @property getter,不给 setter)。
  • deposit(amount):金额必须 > 0,否则 raise ValueError。
  • withdraw(amount):不能超过余额,否则 raise ValueError。

写完自测:a._balance = -999 能不能得逞?(能——因为是单下划线约定。想想这说明了什么。)

自测 1:下面哪种说法最准确?"在 Python 里,给属性名加双下划线前缀 __x 的作用是……"

答案:触发 name mangling(改写成 _ClassName__x),主要为避免子类命名冲突;它不是安全的私有边界。

常见错误答案是"让属性变成真正私有、外部无法访问"。反例:obj._ClassName__x 照样能访问。Python 层面没有语言强制的私有。

自测 2:一个团队新人给每个字段都配了一对 get_x()/set_x(),setter 里只有一行 self._x = value。这有什么问题?更 Pythonic 的做法是?

问题:空 setter 等于把私有属性重新变公开,只是多绕一层——纯样板,没有增加任何保护或功能,反而让调用方从 obj.x 变成 obj.set_x(...),更啰嗦。

更 Pythonic:先直接用公开属性 self.x;等真的需要校验或计算时,再用 @property 把它升级成受控访问——调用方代码一行都不用改。这正是"封装带来灵活性"的体现:接口稳定,实现可换。

带走这一条:封装 = 捆绑 + 信息隐藏 + 受控访问,目的是把"数据合法性"的守门责任收回类内部。Python 用约定(_/__)而非强制来做"私有",__ 是 name mangling 不是安全墙;受控访问在 Python 里靠 @property 无痛实现,别用空 getter/setter 堆样板。
