SOLID(一):单一职责与开闭原则

SOLID 是面试里"讲得出缩写、答不透理由"的重灾区。这一节只啃前两条——SRP 和 OCP,目标是让你既能一句话说清,又能当场用 Python 演示"为什么加需求时不该去改旧代码"。

先想一个你大概率写过的场景:一个 AreaCalculator,里面一串 if shape.type == "circle": ... elif shape.type == "rectangle": ...。产品说"再加一种三角形",你会怎么改?这一改,你要动的是新代码还是那段已经测过、上线过的旧代码?先在心里记下答案,再往下看。

一、先认全家福:SOLID 是哪五个字母

SOLID 是五条面向对象设计原则的首字母缩写,由 Robert C. Martin(Uncle Bob)整理提出,"SOLID"这个记忆缩写据传由 Michael Feathers 归纳。它们不是语法,而是一组让设计更易维护、易扩展、抗腐化的经验法则——目的都是同一个:让代码在需求不断变化时,不至于越改越烂。

本节讲 S 和 O。这两条常被合在一起考,因为它们回答的是同一个问题的两面:SRP 决定"把代码切成几块、按什么切",OCP 决定"块与块之间怎么连,才能加功能不动老代码"。

二、SRP:一个类只该有"一个变化的理由"

直觉类比:一把瑞士军刀什么都能干,听起来很强,但真要拧一颗大螺丝、切一块牛排时,它样样都别扭——而且你想换掉起子那一部分,只能整把扔掉。SRP 说的就是:别造瑞士军刀式的"上帝类"(God class),让每个类只干一件"会因同一个原因而变"的事。

注意关键词不是"只做一件事",而是"只有一个变化的理由"。Uncle Bob 后来把这句话说得更精确:一个模块应该只对一类使用者(actor)负责。换句话说,判断职责的尺子是"谁会来提需求让它改",不是"它有几个方法"。

# ❌ 上帝类:一个 Report 扛了三个「变化的理由」
class Report:
    def calculate(self):   ...   # ① 业务规则变(财务同事提需求)→ 要改
    def to_html(self):     ...   # ② 展示格式变(前端/设计提需求)→ 要改
    def save_to_db(self):  ...   # ③ 存储方式变(DBA/运维提需求)→ 要改

三个方法背后是三拨不同的人、三个独立变化的方向。它们挤在一个类里,改任何一个都可能碰坏另外两个(还得重跑全部测试)。按"变化的理由"切开:

# ✅ 每个类只对一类使用者负责
class Report:              # 只管「内容/业务计算」
    def calculate(self):   ...

class ReportFormatter:    # 只管「展示格式」
    def to_html(self, report):   ...

class ReportRepository:   # 只管「持久化」
    def save(self, report):      ...

现在"改格式"只碰 ReportFormatter,和业务计算、存储互不牵连——这正是 上一节说的高内聚、低耦合在"类"这个粒度上的落地。

SRP · 单一职责原则 (Single Responsibility Principle)
一个类应该只有一个变化的理由——只对一类使用者(actor)负责。切分依据是"会因什么原因而改变",不是方法数量。
OCP · 开闭原则 (Open–Closed Principle)
软件实体应对扩展开放、对修改关闭:加新功能靠"加新代码"(新增子类 / 实现接口 / 换新策略),而不是回去改那段已经测过、跑稳了的旧代码。

三、OCP:加功能靠"加代码",不靠"改代码"

回到开场那段 if-elif。每加一种形状,你都得回去改同一段计算逻辑——这就是违反 OCP的典型味道:一段稳定的旧代码,被反复撬开。

# ❌ 违反 OCP:每加一种形状,都要回来撬开这段 if-elif 长链
class AreaCalculator:
    def area(self, shape):
        if shape.type == "circle":
            return 3.14159 * shape.radius ** 2
        elif shape.type == "rectangle":
            return shape.width * shape.height
        # 加 triangle?又得回来动这里,还得重测整段……

OCP 的经典手法:用多态代替 switch / if type == ...。让"每种形状怎么算面积"这件会变的事,分散到各自的类里;计算器只依赖一个稳定的抽象。Python 里用 abc.ABC + @abstractmethod 定义这个抽象:

from abc import ABC, abstractmethod

class Shape(ABC):                       # 稳定的抽象:凡形状必会算面积
    @abstractmethod
    def area(self) -> float:
        ...

class Circle(Shape):
    def __init__(self, radius: float):
        self.radius = radius
    def area(self) -> float:
        return 3.14159 * self.radius ** 2

class Rectangle(Shape):
    def __init__(self, width: float, height: float):
        self.width, self.height = width, height
    def area(self) -> float:
        return self.width * self.height

class AreaCalculator:                   # 只依赖 Shape 抽象,永不需要改
    def total(self, shapes: list[Shape]) -> float:
        return sum(s.area() for s in shapes)

现在需求来了——加三角形。看看你要动多少行:

class Triangle(Shape):                  # ✅ 只「新增」一个类
    def __init__(self, base: float, height: float):
        self.base, self.height = base, height
    def area(self) -> float:
        return 0.5 * self.base * self.height

# AreaCalculator 一行都不用改,已上线的旧逻辑一个字节都不碰。

这就是"对扩展开放(可以随便加新 Shape)、对修改关闭(计算器这段稳定代码不再被撬)"。SRP 与 OCP 在这里咬合:因为先把"每种形状怎么算"按职责拆到了各自的类(SRP),才可能让计算器只依赖抽象、加功能不改它(OCP)。

高频追问链(SRP/OCP 常被连着追问):

  • "SRP 里的'职责'到底怎么界定?两个方法算一个职责还是两个?" → 尺子是变化的原因 / 使用者(actor):会被同一拨人、因同一个原因一起改动的,归一个职责;不是数方法个数。
  • "OCP 说'对修改关闭',那是不是永远不能改代码?" → 不是。它关闭的是"为了加新行为而去撬稳定的旧逻辑";修 bug、改抽象本身当然要动代码。关键是把"变化"引到扩展点上,而不是核心链路上。
  • "怎么用代码实现 OCP?" → 把会变的部分抽象成基类 / 接口 / 策略,用多态分派代替 if type == 长链——新增行为 = 新增一个实现类。
  • "SRP 和'高内聚'是一回事吗?" → SRP 可看作功能内聚在类粒度上的表达(接 0012);内聚描述"一块代码内部有多聚焦",SRP 给出一条切分它的具体判据。

坑一:把"职责"理解成"方法数量"。一个类有十个方法,只要它们都为同一个原因而变,那仍是单一职责;反过来,一个类只有两个方法,若一个随业务规则变、一个随存储方式变,它就违反了 SRP。判据永远是变化的来源,不是行数或方法数。

坑二:为了 OCP 过度抽象(YAGNI)。在还只有一种情况时,就预先架起一堆基类、接口、策略工厂,美其名曰"为将来扩展"——这是典型的过度设计,徒增复杂度还没人用。务实的节奏是:等第二种变化真的出现、看清了变化点在哪,再抽象("发现重复,再消除重复")。OCP 是应对已出现的变化方向,不是给想象中的需求预留脚手架。

SOLID 是语言无关的设计思想,但落地要靠各语言的抽象机制。同一条 OCP,换语言只是换"怎么声明那个稳定抽象":

语言提供稳定抽象的机制多态分派方式
Pythonabc.ABC + @abstractmethod;或 typing.Protocol鸭子类型 + 方法覆盖(有 area() 就能用,不必显式继承)
Javainterface / abstract classimplements + 覆盖,运行时动态分派
C#interface / abstract 类实现接口 + override
C++含纯虚函数的抽象基类(virtual f() = 0;)虚函数表(vtable)动态分派

一句话:思想一致,只是 Java/C#/C++ 靠显式接口 + 继承,Python 还可以靠 Protocol / 鸭子类型"结构化地"满足同一个抽象。

合上讲义,把开场那段 if-elif 折扣计算器重写成 OCP 版:

  • 定义抽象 DiscountPolicy(ABC),只有一个抽象方法 apply(price: float) -> float。
  • 实现三个策略:NoDiscount(原价)、PercentOff(打 n 折)、Coupon(减固定额)。
  • 写一个 checkout(price, policy),它只依赖 DiscountPolicy,不出现任何 if isinstance(...)。
  • 自测:新增一个"满减"策略 ThresholdOff,你需要改动 checkout 吗?(答案应是"不需要"——若需要,说明抽象没做对。)
自测 1:下面哪一种改动违反了开闭原则(OCP)?

答案:B。

  • A. 新增一个 Hexagon(Shape) 类来支持六边形 —— 纯扩展,不动旧代码,符合 OCP。
  • B. 为了支持六边形,回到 AreaCalculator.area() 里再加一个 elif shape.type == "hexagon" —— 撬开了稳定的旧逻辑,正是 OCP 要消除的味道。
  • C. 发现 Circle.area() 把 π 写错了,回去修正这个 bug —— 这是修 bug,不是"为加新行为而改",不算违反 OCP。

要点:OCP 反对的是"为了加新类型 / 新行为而反复修改同一段分发逻辑",不是反对一切代码改动。

自测 2:一个 UserService 类里有 validate_password()、send_welcome_email()、log_signup_metric() 三个方法。它违反 SRP 了吗?为什么?

大概率违反了——但理由不是"它有三个方法",而是这三件事分别会因不同的原因、被不同的人改动:

  • validate_password —— 安全策略变(安全团队)。
  • send_welcome_email —— 邮件文案/渠道变(市场/运营)。
  • log_signup_metric —— 埋点口径变(数据团队)。

三个变化理由 = 三个职责。更好的切法是拆成 PasswordValidator / EmailSender / MetricLogger,由 UserService 编排它们。判据始终是"几个独立的变化来源",不是方法计数。

带走这一条:SRP 告诉你"按变化的理由把代码切块"(一个类只对一类使用者负责),OCP 告诉你"块之间用抽象 + 多态连接,让加功能=加新类、而非撬旧代码"。两者一体两面;但别为想象中的需求过度抽象——看见第二种变化,再抽象。
