相等与哈希:__eq__ 与 __hash__ 契约

"自定义相等"是面试里最容易踩坑的一簇:很多人只重写了 __eq__,结果对象放进 set 就报错。这一节把 __eq__ 和 __hash__ 的成对契约讲透,让你既写得对,也答得清"为什么"。

还记得 0006 里 is 和 == 的区别吗?is 比的是身份(是不是同一个对象),== 比的是相等。可是——你自己写的类,默认的 == 其实就等价于 is。为什么?如果你想让两个 x、y 都相同的 Point 判为相等,又该动哪个方法?先在心里答一遍,再往下看。

一、直觉:两张一模一样的名片

桌上放着两张印着相同姓名、相同电话的名片。它们是"同一张"吗?不是——它们是两个物理对象(is 为假)。但它们"内容相等"吗?是——因为你关心的字段都一样(== 应为真)。

Python 默认只懂前一种判断:对你自定义的类,a == b 会退化成"a 和 b 是不是同一个对象",也就是和 is 一个意思。想让它懂"内容相等",你得亲手告诉它哪些字段算数——这就是重写 __eq__。

可这里埋着一个连锁反应:一旦你改了"什么叫相等",哈希也必须跟着改。因为 set 和 dict 靠哈希把对象分桶存放,而哈希和相等之间有一条硬契约。Python 为了逼你别忘,干脆在你只改 __eq__ 时,把哈希功能直接关掉。

二、默认相等,就是身份相等

所有类默认从 object 继承一套 __eq__ 和 __hash__:前者按身份(id)比较,后者按 id 计算。所以两个"内容一样"的实例,默认既不相等、哈希也不同:

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

a = Point(1, 2)
b = Point(1, 2)
print(a == b)      # False —— 默认 __eq__ 比身份,等价于 a is b
print(hash(a) == hash(b))   # 几乎必为 False —— 默认哈希基于 id

此时对象是可哈希的(能进 set、能当 key),只是"相等"的语义还停留在身份层面。要升级到"内容相等",就重写 __eq__。

三、重写 __eq__ 的隐藏代价:__hash__ 被设为 None

这是本节最高频的坑。规则是:如果一个类重写了 __eq__ 却没有同时定义 __hash__,Python 会把这个类的 __hash__ 设为 None,于是它的实例变得 unhashable——不能进 set,不能当 dict 的 key。

# ❌ 只重写了 __eq__,忘了 __hash__
class BadPoint:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)
    # 没有定义 __hash__ !

print(BadPoint.__hash__ is None)   # True —— Python 悄悄把它关掉了
p = BadPoint(1, 2)
{p}          # TypeError: unhashable type: 'BadPoint'
{p: "A"}     # 同样报错:不能当 dict 的 key

正确姿势是成对定义,并且让两者用同一组字段:

# ✅ __eq__ 与 __hash__ 都基于同一个 (x, y) 元组,逻辑一致
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented      # 类型不匹配就交还给对方,别硬判 False
        return (self.x, self.y) == (other.x, other.y)

    def __hash__(self):
        return hash((self.x, self.y))  # 复用内置元组的哈希,省心又正确

a, b = Point(1, 2), Point(1, 2)
print(a == b)               # True —— 内容相等
print(hash(a) == hash(b))   # True —— 相等对象哈希必相等(契约!)
print(len({a, b}))          # 1 —— set 认为它们是"同一个",去重成功

如果对象本就该"不可变 + 值语义",最省事的写法是 @dataclass(frozen=True),它会自动为你生成一致的 __eq__ 和 __hash__:

from dataclasses import dataclass

@dataclass(frozen=True)           # frozen=True 让实例不可变
class Point:
    x: int
    y: int
    # __init__ / __repr__ / __eq__ / __hash__ 全部自动生成,且相互一致

a, b = Point(1, 2), Point(1, 2)
print(a == b, hash(a) == hash(b))   # True True

小心一个默认值:普通 @dataclass(即 frozen=False)只生成 __eq__,并把 __hash__ 设为 None——和你手写只写 __eq__ 是一个下场。要可哈希,就得 frozen=True(或显式 eq=False 保留继承来的身份哈希)。

哈希契约(Hash Contract)· 三条铁律
违反任何一条,set/dict 就会给你"查不到明明存进去的键"这类灵异 bug ↓
① 相等 ⟹ 哈希相等
若 a == b,则必须 hash(a) == hash(b)。反过来不要求:哈希相等不代表相等(允许哈希冲突,容器会再用 == 复核)。
② 成对定义
重写 __eq__ 就要一并给出 __hash__,且二者基于同一组字段,逻辑一致。
③ 生命周期内哈希不变
一个对象只要还在被当作 key/成员,它的哈希就不能变。所以哈希应基于不可变字段——用作 key 的对象通常应当不可变。

高频追问链(这一簇几乎必被连环追问):

  • "为什么我定义了 __eq__ 之后,对象就不能放进 set 了?" → 因为 Python 把该类的 __hash__ 自动设成了 None,逼你要么一并定义 __hash__,要么明确承认它不该被哈希。
  • "相等的对象哈希一定相等吗?反过来呢?" → 正向必须成立(契约①);反向不成立——哈希相等只是"可能相等",容器还会用 == 再确认一次,这就是哈希冲突的正常处理。
  • "为什么用作 dict key 的对象最好是不可变的?" → 因为哈希在生命周期内不能变(契约③);可变对象一旦改了参与哈希的字段,就会在容器里"丢失"。见下面易错点的现场演示。
  • "@dataclass 默认会生成 __hash__ 吗?" → 不会。默认 eq=True, frozen=False 会把 __hash__ 设为 None;加 frozen=True 才生成哈希。
  • "__eq__ 里为什么返回 NotImplemented 而不是 False?" → 让 Python 有机会去问对方的 __eq__(反射比较),比直接判 False 更正确、更可扩展。

坑一:只重写 __eq__、忘了 __hash__。这是最高频的一题。后果不是"哈希用默认的",而是对象直接变 unhashable——放进 set 或当 dict key 立刻 TypeError。记牢:改相等,就成对改哈希。

坑二:拿"可变对象"当 dict key,之后又改了它。看现场:

# 假设 Point 是"可变的 + 基于 (x,y) 哈希"(反面教材)
p = Point(1, 2)
d = {p: "A"}
p.x = 99             # 改了参与哈希的字段 → 哈希变了!
print(d[p])          # KeyError! 键还躺在旧哈希对应的桶里,新哈希找不到它

这正是"哈希在生命周期内必须不变"被违反的样子。frozen=True 从根上堵住它——你根本改不了 p.x。

坑三:__eq__ 与 __hash__ 用了不同字段(逻辑不一致)。比如相等只看 x、哈希却算 (x, y),会造出"两个相等的对象哈希不同"的怪物,直接违反契约①,set 去重失败、dict 时灵时不灵。两者必须咬合同一组字段。

这条契约不是 Python 独有的,而是所有"用哈希表做集合/字典"的语言共有的经典陷阱题——Java 尤其爱考:

语言相等方法哈希方法契约要点
Python__eq____hash__成对重写;相等 ⟹ 哈希相等;只写 __eq__ → 实例 unhashable
Javaequals()hashCode()必须成对重写;a.equals(b) ⟹ a.hashCode()==b.hashCode(),否则 HashMap/HashSet 出错
C#Equals()GetHashCode()同构契约;重写 Equals 就应重写 GetHashCode

一句话记牢:"改了相等,就必须改哈希"是跨语言通用的铁律。Java 里若只重写 equals() 而不改 hashCode(),对象照样能编译能运行,但放进 HashSet 会"存得进、找不着"——比 Python 直接抛 TypeError 还阴险,因为它是静默出错。

合上讲义,自己写一个 Money 值对象(表示"金额 + 币种"):

  • 字段 amount(整数,单位分)与 currency(字符串,如 "CNY")。
  • 两个 Money 当且仅当 amount 和 currency 都相同才 ==。
  • 正确实现 __hash__,让它能进 set、能当 dict key。
  • 自测:len({Money(100,"CNY"), Money(100,"CNY")}) 应为 1;Money(100,"CNY") == Money(100,"USD") 应为 False。

写完再想一个问题:你会不会给 amount 加一个 setter 允许改金额?若允许,它还适合当 dict key 吗?(提示:契约③。)最省事的收尾——把它整个换成 @dataclass(frozen=True),对比你手写的版本。

自测 1:一个类只重写了 __eq__,没有定义 __hash__。下面哪种说法最准确?

答案:该类的实例变成 unhashable——放进 set 或当作 dict 的 key 会抛 TypeError。

常见错误答案是"哈希会退回用默认(基于 id)的实现"。恰恰相反:Python 检测到你重写了 __eq__ 却没给 __hash__,会主动把该类的 __hash__ 设为 None。这么设计是为了阻止你造出"两个相等的对象哈希却不同"的破契约对象——它宁可让你早早撞上 TypeError,也不放你埋下 set/dict 的隐性 bug。

自测 2:判断对错——"如果 hash(a) == hash(b),那么 a == b 一定成立。"

错。契约只要求单向:a == b ⟹ hash(a) == hash(b)。反方向不成立——不同的对象完全可能撞上相同的哈希值,这叫哈希冲突,是被允许且必然会发生的(哈希把无穷多的对象映射到有限的整数区间)。所以容器拿哈希只是"快速定位到桶",桶内还会用 == 逐一复核。正因如此,__hash__ 可以偶尔"偷懒"返回粗糙的值(顶多降低性能),但 __eq__ 必须精确。

带走这一条:改了"相等"就必须成对改"哈希",且二者基于同一组字段——相等的对象哈希必相等(反之不要求,允许冲突),可哈希对象的哈希在生命周期内不能变(所以 key 通常应不可变)。Python 里只写 __eq__ 会让实例 unhashable;想省事就用 @dataclass(frozen=True) 自动生成一致的一对。这条契约在 Java 的 equals()/hashCode() 上完全同构。
