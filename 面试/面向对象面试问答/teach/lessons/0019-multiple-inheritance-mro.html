多重继承与 MRO:diamond 问题

"D 同时继承 B 和 C,B、C 又都继承 A,那调 D 的方法时按什么顺序查?A 的 __init__ 会被调几次?"——这是 Python 多继承的招牌追问。答对它的关键只有一句:super() 调的不是父类,而是 MRO 里的下一个类。

先回忆:上一节你用过 super().__init__()。现在换个场景——如果一个类有两个父类,super() 到底指向谁?如果两个父类又共享同一个"祖父",那个祖父的构造函数会不会被执行两遍?先给自己一个答案,再往下看。

一、问题:菱形继承(diamond)

Python 允许一个类同时继承多个父类。这带来一个经典的歧义结构——菱形继承(diamond inheritance):

D(B, C),而 B(A)、C(A)。当你在 D 的实例上调一个方法,而 B 和 C 都定义了它——先用谁的?更棘手的是构造:天真地"每个类都调自己父类的构造",A 会被 B 走一遍、被 C 又走一遍,顶端 A 被初始化两次。这就是 diamond 问题的两副面孔:查找歧义与重复初始化。

二、Python 的解法:MRO + C3 线性化

Python 不靠"运气",而是在类被创建时,用 C3 线性化算法把这张菱形网压平成一条确定、无歧义的线性查找顺序——这条顺序就叫 MRO(Method Resolution Order,方法解析顺序)。查方法、查属性,都严格沿这条线从前往后找,第一个命中的就用。

你可以直接把它打印出来:

class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass

print([cls.__name__ for cls in D.__mro__])
# ['D', 'B', 'C', 'A', 'object']

D.mro()          # 等价的方法形式,返回同样的列表

读作:D → B → C → A → object。注意两点直觉:①子类永远排在父类前面;②A 只出现一次,被挪到了 B、C 之后——C3 保证"公共祖先在所有子类之后才出现",这正是它能避免重复的结构基础。

MRO (Method Resolution Order)
一个类查找方法/属性时遵循的线性顺序。用 Cls.__mro__(元组)或 Cls.mro()(方法)查看。
C3 线性化 (C3 Linearization)
Python(2.3 起,新式类)计算 MRO 的算法。它保证三条性质:子类先于父类、父类的相对顺序被保留、以及单调性(子类的 MRO 与父类的 MRO 不矛盾)。
协作式多重继承 (Cooperative Multiple Inheritance)
每个类的方法都用 super() 把调用"传给 MRO 的下一位",并用统一签名(常配 **kwargs)协作,使整条链每个类恰好执行一次。

三、核心洞察:super() 不是"父类",是"MRO 里的下一个"

这是本节最重要、也最反直觉的一句。很多人以为 super() 就是"我的父类"。在单继承下这么理解恰好不出错;可一旦进入 diamond,它会露馅——因为 super() 的真正语义是:沿着当前实例的 MRO,跳到"当前类"的下一个类。

看这个协作式的菱形。留意 B.__init__ 里的 super()——它跳到的不是 A(B 的父类),而是 C(B 在 MRO 里的"兄弟"):

class A:
    def __init__(self, **kwargs):
        print("A.__init__")
        super().__init__(**kwargs)   # A 也调 super():链的终点是 object

class B(A):
    def __init__(self, **kwargs):
        print("B.__init__")
        super().__init__(**kwargs)   # 在 D 的实例里,这一步跳到 C 而非 A!

class C(A):
    def __init__(self, **kwargs):
        print("C.__init__")
        super().__init__(**kwargs)   # 这一步才跳到 A

class D(B, C):
    def __init__(self, **kwargs):
        print("D.__init__")
        super().__init__(**kwargs)

D()
# 输出:
# D.__init__
# B.__init__
# C.__init__
# A.__init__        ← 只出现一次!

为什么 A 只跑一次?因为调用严格沿 MRO D → B → C → A → object 逐个前进,每个类的 super() 只把接力棒交给"下一位"。B 的下一位是 C(不是 A),等走到 C,它的下一位才是 A。整条链是一次性的直线接力,没有任何类被走两遍。这就是"协作式"的含义:大家都遵守同一条线,谁也不越级硬调。

对比一下"天真写法"——不用 super(),而是把父类名硬编码进去。这恰恰重现了 diamond 的经典 bug:

class A:
    def __init__(self):
        print("A.__init__")

class B(A):
    def __init__(self):
        print("B.__init__")
        A.__init__(self)      # 硬编码:直接点名 A

class C(A):
    def __init__(self):
        print("C.__init__")
        A.__init__(self)      # 硬编码:又直接点名 A

class D(B, C):
    def __init__(self):
        print("D.__init__")
        B.__init__(self)      # 手动分别调两个父类
        C.__init__(self)

D()
# 输出:
# D.__init__
# B.__init__
# A.__init__        ← A 第一次
# C.__init__
# A.__init__        ← A 第二次!顶端被初始化了两遍

同样的菱形,A.__init__ 被执行了两次。如果 A 的构造里有"计数 +1""打开一个连接""追加一个 handler"这类带副作用的动作,这就是实打实的 bug。super() + 协作签名,把"调几次"这件事交给 MRO 统一裁决,而不是散落在每个类里靠人手拼。

四、mixin:多继承最正当的用途

多继承常被劝退,但它有一个被广泛认可的正当用法:mixin。mixin 是一个"只提供某项能力、自己不独立成对象"的小类(比如 SerializableMixin、LoggerMixin),你把它放进继承列表来"混入"一项能力。它正是靠多继承落地的,而 MRO 决定 mixin 方法相对于主类方法的优先级:

class LoggerMixin:
    def save(self, **kwargs):
        print(f"[log] saving {self!r}")
        super().save(**kwargs)      # 关键:mixin 也 super(),把动作接力给 MRO 下一位

class Model:
    def save(self, **kwargs):
        print("Model.save: 写入数据库")

class User(LoggerMixin, Model):     # mixin 放前面 → 它的 save 先执行
    pass

User().save()
# [log] saving <__main__.User object ...>
# Model.save: 写入数据库

把 LoggerMixin 放在 Model 前面,MRO 就是 User → LoggerMixin → Model → object,于是 save 先记日志再落库。调换继承列表的顺序,优先级随之改变——这就是"MRO 决定 mixin 优先级"的具体含义。

高频追问链(多继承一旦被问,基本按这个梯度深挖):

  • "super() 到底调的是谁?" → 不是父类,是当前实例 MRO 里、当前类的下一个类。在 diamond 里 B 的 super() 可能指向"兄弟" C。这是本节的题眼。
  • "diamond 里 A 的 __init__ 被调几次?怎么保证一次?" → 只要整条链都用 super() 且签名协作(常用 **kwargs 透传),C3 保证 A 在 MRO 中只出现一次,故恰好执行一次;若有类硬编码 A.__init__(self) 就会重复。
  • "MRO 怎么算出来的?能讲讲 C3 吗?" → C3 线性化:合并各父类的 MRO,遵守"子类先于父类、父类相对顺序保留、单调性"三条;结果可用 __mro__ / mro() 验证。不必手算,但要能说清它保证"确定且无歧义"。
  • "mixin 和多继承什么关系?" → mixin 靠多继承落地(放进继承列表),MRO 决定它的方法优先级;这是多继承被认可的主流用法。
  • (进阶)"C3 会不会算不出来?" → 会。当继承结构自相矛盾(比如两个父类对同一对基类要求了相反顺序),C3 无法给出一致顺序,直接抛 TypeError,拒绝创建这个类。

易错点 ①:把 super() 说成"调用父类"。这是最常见的翻车。准确说法:super() 返回一个代理,它按当前实例的 MRO 把调用转发给当前类的下一个类——在多继承里可能是"兄弟"而非"父亲"。把这句讲对,面试官立刻知道你真懂协作式继承,而不是背了个 super().__init__() 模板。

易错点 ②:多继承里方法/属性冲突,不理解 MRO 就会 debug 到崩溃。两个父类有同名方法时,用哪个完全由 MRO 顺序决定(继承列表里靠前的、且满足 C3 的那个先命中)。遇到"我明明改了 C 的方法怎么没生效"这类灵异 bug,第一件事就是 print(Cls.mro()) 看真实顺序。

易错点 ③:以为 Python 总能给出一个 MRO。不是。C3 在不一致的继承结构下会直接 TypeError(报 "Cannot create a consistent method resolution order")。它宁可拒绝建类,也不给你一个自相矛盾的顺序——这是特性,不是缺陷:

class X: pass
class Y: pass
class A(X, Y): pass
class B(Y, X): pass       # 注意:A 要求 X 在 Y 前,B 要求 Y 在 X 前
class C(A, B): pass       # TypeError: Cannot create a consistent MRO ...

"多重继承 / diamond 你们语言怎么处理?"——三种语言,三种哲学:

语言多继承?diamond 怎么办
Python支持(类可多继承)MRO + C3 线性化:压成一条确定顺序;配 super() 协作,公共祖先只跑一次
C++支持真正的多继承默认会复制多份基类子对象;用虚继承(class B : virtual public A)让共享基类只保留一份
Java类禁止多继承,只能多实现 interface从根上回避 diamond;但 Java 8 的 default 方法带来自己的冲突规则——两个接口给出同名 default 方法时,子类必须显式覆盖,否则编译报错

一句话:C++ 让你自己用 virtual 声明"要不要共享基类";Java 干脆禁止类多继承、把问题挡在门外;Python 用 MRO 算法把它变成一条确定的线。

不看上文,自己动手验证 MRO:

  • 照第三节写出协作式的 A/B/C/D(每个 __init__ 都 print 自己的名字 + super().__init__(**kwargs)),先预测再运行 D(),核对 A.__init__ 是不是只出现一次。
  • 打印 [c.__name__ for c in D.__mro__],确认顺序是 D → B → C → A → object。
  • 把 B、C 里的 super().__init__(**kwargs) 改成硬编码 A.__init__(self),再跑一遍,观察 A 被调了几次——亲手复现那个 bug。
  • 加分:写一个 LoggerMixin,分别用 class User(LoggerMixin, Model) 和 class User(Model, LoggerMixin) 试,看日志出现在落库前还是后,理解"MRO 决定 mixin 优先级"。
自测 1:给定协作式的 D(B, C)、B(A)、C(A),D() 里 B.__init__ 的 super().__init__() 会跳到哪个类?

答案:跳到 C,而不是 A。

D 实例的 MRO 是 D → B → C → A → object。super() 的语义是"当前类在当前实例 MRO 里的下一个",B 的下一个是 C。这正是"super() 不等于父类"的活例——尽管 B 的父类写的是 A,在 D 的实例里它却先接力给"兄弟" C。等走到 C,C 的下一个才是 A,于是 A 只被执行一次。

自测 2:一个团队里,菱形结构中 A.__init__ 打开了一个网络连接。有人反馈"连接被打开了两次"。最可能的原因是什么?怎么修?

最可能的原因:链上有类没有用 super(),而是硬编码点名调了父类构造(如 B 和 C 各自写了 A.__init__(self))。这样 A 被 B 走一遍、被 C 又走一遍,共享祖先被初始化两次。

修法:把整条链改成协作式——每个 __init__ 都用 super().__init__(**kwargs) 接力,并让签名互相兼容(用 **kwargs 透传)。这样调用严格沿 MRO 走直线,C3 保证 A 在 MRO 中只出现一次,连接就只开一次。诊断时先 print(Cls.mro()) 确认顺序,再检查每个类是不是都规矩地 super()。

带走这一条:Python 用 MRO(由 C3 线性化算出的一条确定顺序)消解 diamond 歧义;super() 调的是MRO 里的下一个类,不是父类。只要整条链协作式地 super() + **kwargs 透传,公共祖先恰好执行一次;谁硬编码点名父类,谁就会把祖先调重复。查顺序就 Cls.mro(),遇诡异冲突先看它。
