行为型模式:策略、观察者、模板方法

创建型管"怎么造对象",结构型管"怎么拼对象",行为型则管一件更活的事:对象之间怎么分工、怎么通信。这一节只讲透三个高频到几乎必问的:策略(Strategy)、观察者(Observer)、模板方法(Template Method)。

先想一个真实场景:你有一个 checkout() 结账函数,里面一大坨 if kind == "vip" ... elif kind == "staff" ...,每加一种折扣就得回来改这个函数一次。你会怎么重构它,让"加折扣"不再需要动 checkout?先在心里给答案,再往下看——你多半已经会写策略模式了,只是没给它起名字。

一、直觉:行为型模式在解决什么

把设计模式按 GoF 的分法想成三箱工具:创建型关心"对象如何被创建",结构型关心"对象如何组合成更大的结构",行为型关心"对象之间如何分配职责、如何互相通信"。行为型的核心矛盾几乎都是同一个:把"会变的那部分行为"从"稳定的那部分流程"里抽出来,让变化能独立发生,而不牵动调用方。

模板方法 Template Method
父类定义算法骨架(固定的步骤顺序),把其中某些步骤延迟到子类实现。一句话:骨架在父类,细节在子类。

二、策略:把 if/elif 变成可插拔的算法

先看那个"会长胖"的版本。它的病根不在于用了 if,而在于:每多一种折扣,就得回来修改这个已经能跑的函数——违反开闭原则(OCP:对扩展开放,对修改关闭)。

# ❌ 未用策略:一坨 if/elif,加一种折扣就改一次这个函数
def checkout(total, kind):
    if kind == "normal":
        return total
    elif kind == "vip":
        return total * 0.8
    elif kind == "staff":
        return total * 0.5
    # 加"黑五折扣"?又得回来改这里 —— 违反 OCP

策略模式的解法:把每个分支提取成一个独立算法,调用方只负责"选一个策略传进去"。在 Python 里,因为函数是一等对象(可以像值一样传递),策略常常直接退化成"传一个函数":

# ✅ Python 式策略:每个算法就是一个函数,运行时传进去
def normal(total): return total
def vip(total):    return total * 0.8
def staff(total):  return total * 0.5

def checkout(total, discount):   # discount 就是"策略":一个可调用对象
    return discount(total)

checkout(100, vip)     # 80.0
checkout(100, staff)   # 50.0
# 加"黑五 5 折"?再定义一个函数,checkout 一行都不用改 —— 这就是 OCP

但面试官往往想看你懂经典(GoF)策略长什么样——即"策略接口 + 若干具体策略 + 持有策略的 Context":

from abc import ABC, abstractmethod

class Discount(ABC):              # 策略接口:统一签名
    @abstractmethod
    def apply(self, total): ...

class Vip(Discount):             # 具体策略
    def apply(self, total): return total * 0.8

class Staff(Discount):
    def apply(self, total): return total * 0.5

class Checkout:                  # Context:持有一个策略,可运行时替换
    def __init__(self, strategy):
        self._strategy = strategy
    def set_strategy(self, strategy):
        self._strategy = strategy      # 运行时换算法,Context 不用改
    def pay(self, amount):
        return self._strategy.apply(amount)

c = Checkout(Vip())
c.pay(100)              # 80.0
c.set_strategy(Staff())
c.pay(100)              # 50.0

两版是同一个思想的两种落地:函数版轻,类版在"策略自己也需要状态/配置"时更合适。共同点是——加算法 = 加策略,不改调用方。

三、观察者:状态一变,自动广播

观察者解决的是"一处变、多处要跟着反应"的耦合问题。反面教材是让 subject 亲自去调用每一个关心它的对象——那样 subject 就得硬编码它的所有下游,新增一个下游又得改 subject。观察者把关系倒过来:下游主动注册,subject 只管在变化时挨个通知,并不关心它们是谁。

class Subject:                    # 被观察者
    def __init__(self):
        self._observers = []      # 注册表:一对多的"多"
    def register(self, obs):
        self._observers.append(obs)
    def unregister(self, obs):    # 退订!不给退订就是内存泄漏隐患(见易错点)
        self._observers.remove(obs)
    def notify(self, event):
        for obs in self._observers:   # 挨个通知,不关心是谁
            obs.update(event)

class EmailAlert:                 # 观察者:只需实现约定好的 update
    def update(self, event):
        print(f"发邮件:{event}")

class Logger:
    def update(self, event):
        print(f"记日志:{event}")

s = Subject()
s.register(EmailAlert())
s.register(Logger())
s.notify("库存告罄")     # 两个观察者都被自动通知,新增下游不改 Subject

这套"注册 / 通知"结构你其实天天在用:GUI 的按钮点击回调、前端框架的响应式更新、消息通知——底层都是观察者的血脉。

四、模板方法:骨架在父类,细节在子类

当一批流程"大步骤完全一样、只有个别小步骤不同"时,模板方法让父类把步骤顺序(骨架)固定下来,只把变化的步骤留成抽象方法交给子类填。子类无法改动骨架,只能填空——这既是约束,也是保证。

from abc import ABC, abstractmethod

class Report(ABC):
    def generate(self):          # ← 模板方法:骨架 + 固定步骤顺序,子类别覆盖
        self.load()
        body = self.render()     # 变化的一步,延迟到子类
        self.save(body)

    def load(self):              # 公共步骤,父类实现
        print("读数据")
    def save(self, body):
        print(f"落盘:{body}")

    @abstractmethod
    def render(self): ...        # 抽象步骤,交给子类填空

class HtmlReport(Report):
    def render(self): return "<h1>报表</h1>"

class CsvReport(Report):
    def render(self): return "a,b,c"

HtmlReport().generate()   # 骨架(load→render→save)在父类,render 细节在子类

注意模板方法和策略解决的问题高度相似——都是"固定流程 + 可变的一步"。区别在实现手段,这正是最爱考的对比:

模板方法靠继承
·
子类填空编译期定制
vs
策略靠组合
·
注入对象运行时替换

模板方法用继承(子类通过覆盖钩子来定制,一旦定下就是编译期/类定义期的事);策略用组合(把算法作为对象注入,能在运行时随时换)。这条对比直接呼应"组合优于继承"那一节:需要运行时灵活切换、或一个对象要在多种算法间来回换,优先策略;流程骨架天然稳定、只想让子类补几个洞,模板方法更省事。

高频追问链(这三个模式几乎绑定出现):

  • "策略和模板方法都能定制算法,区别是什么?" → 策略用组合(运行时可换),模板方法用继承(子类填空、骨架固定)。这是最经典的一问,能把"组合 vs 继承"顺势带出来就是加分。
  • "观察者和发布-订阅(pub/sub)是一回事吗?" → 理念相近但不等同。经典观察者里 subject 直接持有 observer 列表、亲自通知;pub/sub 通常多一个中间 broker/事件总线,发布者与订阅者互不知道对方存在,更解耦(代价是多一层间接)。
  • "策略怎么体现开闭原则(OCP)?" → 加新算法 = 新增一个策略类/函数,调用方(Context)一行不改,即"对扩展开放、对修改关闭"。
  • "在 Python 里策略还需要建一堆类吗?" → 通常不必——函数是一等对象,传函数即可;但要能同时讲清经典类版长什么样(见易错点)。
  • "观察者会不会有内存问题?" → 会,观察者不退订就一直被 subject 持有(见易错点)。

① "策略模式=一定要建接口+一堆策略类"——这是把 Java 习惯搬到 Python。Python 的一等函数让策略常常退化成"传一个函数",硬造一堆只有一个方法的类反而是过度设计。但反过来别走极端:面试时要能同时说清"经典 GoF 类版"和"Python 函数版",只会一种会被追到底。

② 模板方法 vs 策略别混为一谈。核心差异是继承 vs 组合:模板方法把可变步骤绑在子类里(定制发生在类定义期),策略把算法作为对象注入(能运行时替换)。答题时点出这条,并顺带一句"这正是组合优于继承的体现"。

③ 观察者的退订与内存泄漏。subject 的注册表默认是强引用:观察者只要没 unregister,就会被 subject 一直持有、无法被垃圾回收——在长生命周期的 subject 上尤其危险。务必提供退订接口;若希望"观察者被回收时自动掉线",可用 weakref(弱引用)存注册表来缓解。

行为型里"把一段行为当参数传"(策略、命令等)在不同语言里的成本差很多——这也是"为什么 Python 的策略这么轻"的根因:

传一个"行为"写法样板量
Python直接传函数(一等对象),或传任意可调用对象几乎为零
Java 8 之前只能用匿名内部类包一个方法传进去大(一坨样板)
Java 8+lambda / 方法引用(配合函数式接口)小,已大幅简化
C++函数指针 / std::function / lambda中等

一句话:语言越把"函数当值",策略/命令这类"行为参数化"模式就越轻。Python 天生如此,所以经典策略在这里常常"瘦"成一个函数参数。

合上讲义,自己写一遍,把三个模式各摸一次:

  • 策略:写一个 sort_by(items, key_fn),把"按什么排序"作为函数策略传进去;再写一个"按价格 / 按名字"两种策略验证。(想想:这跟 Python 内置 sorted(..., key=...) 是不是同一个套路?)
  • 观察者:给上面的 Subject 补一个 unregister 的自测——注册两个观察者,退订一个,再 notify,确认只剩一个被通知。
  • 模板方法:写一个 Beverage 基类,模板方法 prepare() 固定"烧水→冲泡→倒杯→加料"四步,把"冲泡"和"加料"留给 Coffee / Tea 子类填。
自测 1:开头那个 checkout() 里一大坨 if kind == ... 的折扣分支,用哪个模式重构最贴切?为什么它顺带满足了开闭原则?

答案:策略模式(Strategy)。把每个折扣分支提取成一个独立算法(Python 里一个函数即可,或经典的一个策略类),checkout 只接收并调用传进来的策略。

为什么满足 OCP:加一种新折扣 = 新增一个策略,而不需要回去修改已经能跑的 checkout——对扩展开放、对修改关闭。原来的 if/elif 版本恰恰相反,每加一种都要改动老代码,风险随分支增长。

自测 2:两个场景——(A) 一个排序控件要让用户随时在"按价格/按销量/按评分"之间切换;(B) 一套报表生成流程,读数据和落盘完全一样,只有"渲染格式"因类型而异。各该用策略还是模板方法?判断依据是什么?

(A) 用策略。关键词是"随时切换"——需要运行时替换算法,这是组合(注入策略对象/函数)的强项;用继承的话没法在运行中把一个对象从"按价格"换成"按评分"。

(B) 用模板方法。流程骨架(读数据→渲染→落盘)天然稳定,只想让不同报表类型各自填"渲染"这一步,用继承让子类覆盖抽象步骤最省事。

判断依据一句话:要不要"运行时换"?要 → 策略(组合);只是"不同子类各定制固定的几步" → 模板方法(继承)。

带走这一条:行为型模式管"对象间如何分工与通信"。策略=可互换算法、靠组合、运行时替换、消灭 if/elif 并满足 OCP;观察者=一对多、subject 状态变则自动通知 observers(记得留退订、防内存泄漏);模板方法=骨架在父类、细节在子类、靠继承。策略 vs 模板方法的分水岭,就是组合 vs 继承 / 运行时 vs 编译期。
