抽象:抽象类 vs 接口

四大支柱里最容易"和封装混着答"的一个。这一节把抽象讲透,再把它的两种落地技术——抽象类与接口——摆到一张对照表和一棵决策树上,让你被追问"什么时候用哪个"时能当场给出理由。

先想一个日常场景:你按下遥控器的"开机"键,电视亮了。你不知道里面有多少块电路板、信号怎么解码——你只需要知道"有一个开机键,按下就开机"。这个"只暴露能做什么、藏起怎么做"的思路,就是抽象。那问题来了:如果你要设计一套"所有电器都必须有开机键"的规矩,你会怎么用代码表达"必须有,但各自怎么实现我不管"?先给个答案,再往下看。

一、直觉:抽象是"只给你需要的那一层"

抽象(Abstraction)= 聚焦本质特征,隐藏不必要的细节,在"高层概念"和"具体实现"之间划一条清晰的界线。你开车时面对的是方向盘、油门、刹车(高层概念),而不是燃烧室的喷油正时(实现细节)。这条界线让你能用简单的方式使唤复杂的东西。

它带来三个直接好处,也正是源题给的答案:促进复用(高层接口稳定,底层可换)、可维护(改实现不影响用它的人)、安全(不必要的细节根本不暴露,也就无从被误用)。

那"抽象"和上一簇的"封装"到底差在哪?这是几乎必被追问的一题,先在这里钉死:

抽象 (Abstraction)
只对外暴露必要的功能(what:能做什么),隐藏其余细节。关注"接口该长什么样"。
封装 (Encapsulation)
把数据和实现细节包起来、控制访问(how:怎么做的)。关注"数据的安全边界"。
一句话区分
抽象是设计层面"只给必要的";封装是实现层面"把细节藏起来"。二者常配合——你先决定暴露哪个接口(抽象),再把背后的状态锁好(封装)。

二、两种落地技术:抽象类 与 接口

源题问"有哪些抽象技术",标准答案给的是两条:抽象类(abstract class)和接口(interface)。它们都是"定义一个不完整的蓝本,逼后来者补全",区别在于"补多少、给不给默认实现"。

技术一
抽象类
不能自己实例化
技术二
接口
只有契约,没有实现
共同点
留白
强制子类补全

抽象类:一个不能被自身实例化的类,专门当别人的基础。它可以有两种方法——

  • 抽象方法:只声明、没有实现,把活留给子类;
  • 具体方法:有真正的代码,提供默认行为,子类可直接复用,也可覆盖。

它还能有构造器和实例状态。适用场景一句话:"有些方法有默认行为可被覆盖,有些必须由子类自己实现"——既想给点公共实现,又想强制留几个坑。

接口:一份类必须遵守的契约 / 蓝图。与抽象类不同,经典意义上的接口没有任何实现细节,只声明方法和属性的签名。它保证"实现类一定具备这组方法"(各自怎么实现可以不同),规定的是"必须能做什么"而不是"怎么做"。适用场景:让多个彼此不相关的类都遵守同一份契约、都提供相同的一组方法。

抽象方法 (abstract method)
只有签名、没有方法体,由子类必须提供实现。
契约 (contract)
接口承诺的"任何实现类都保证提供这些方法";调用方只依赖契约,不依赖具体是谁实现的。
Python 的现实
Python 没有 interface 关键字。表达抽象类用 abc.ABC + @abstractmethod;想表达"纯接口"有三条路:让 ABC 全是抽象方法、用 typing.Protocol(结构子类型,0021 详讲)、或直接靠鸭子类型。

三、Python 代码:用 abc 造一个抽象类

Python 里"抽象类"靠标准库 abc(Abstract Base Class)实现:继承 ABC,再给要强制的方法挂 @abstractmethod。看这个 Vehicle——它有一个抽象方法 start(逼子类实现)和一个具体方法 stop(给默认实现):

from abc import ABC, abstractmethod

class Vehicle(ABC):                      # 继承 ABC → 本类不能被实例化
    def __init__(self, name):
        self.name = name                 # 抽象类可以有构造器和状态

    @abstractmethod
    def start(self) -> None:             # 抽象方法:只声明、无实现,留给子类
        ...

    def stop(self) -> None:              # 具体方法:提供默认实现,子类可直接复用
        print(f"{self.name} 已停车")

class Car(Vehicle):
    def start(self) -> None:             # 必须实现,否则 Car 也是抽象的、无法实例化
        print(f"{self.name} 点火,引擎启动")

c = Car("小蓝")
c.start()        # 小蓝 点火,引擎启动 —— 用子类自己的实现
c.stop()         # 小蓝 已停车     —— 复用父类的默认实现

# v = Vehicle("x")   # ❌ TypeError: Can't instantiate abstract class Vehicle
#                    #    with abstract method start

三个要点从这段代码里读出来:①继承 ABC 后,直接 Vehicle(...) 会在实例化那一刻抛 TypeError;②Car 只有把 start 补上,才"够格"被实例化——漏一个抽象方法,它自己也还是抽象类;③stop 证明抽象类可以有具体实现和构造器,这正是它区别于经典接口的地方。

那"纯接口"在 Python 里长什么样?就是把 ABC 写成全是抽象方法、不给任何实现:

class Startable(ABC):        # 当"接口"用:只有契约,没有实现
    @abstractmethod
    def start(self) -> None: ...

    @abstractmethod
    def stop(self) -> None: ...
# 任何 class X(Startable) 都必须同时实现 start 和 stop,否则无法实例化

(另一条更"Python 味"的路是 typing.Protocol——它靠"结构对不对得上"判断,连显式继承都不需要,留到 0021 专讲。)

高频追问链(抽象几乎必问,而且爱往"vs 封装 / vs 接口"上引):

  • "抽象和封装有什么区别?" → 抽象是只暴露必要的功能(what),封装是把实现细节藏起来(how)。抽象在设计层,封装在实现层,常一起用但不是一回事。
  • "抽象类和接口怎么选?" → 需要在子类间共享部分实现或状态 → 抽象类;只需定义契约、且实现类彼此不相关、或一个类要同时满足多份"接口" → 接口。见下面的决策树。
  • "Python 里怎么表达接口?" → 没有 interface 关键字;用全抽象的 abc.ABC、或 typing.Protocol、或鸭子类型。这题是区分"背过定义"和"真写过 Python"的分水岭。
  • "抽象类能被实例化吗?为什么不能?" → 不能。因为它有没实现的抽象方法,实例化了也没法正常工作;abc 在实例化时就替你拦下,把"漏实现"从运行时的隐蔽 bug 变成明确的 TypeError。

坑一:说"抽象类不能有任何实现"。错——抽象类可以有构造器、实例状态和具体方法(上面的 __init__ 和 stop 就是)。它只是不能被直接实例化而已。经典意义的接口才是"没有实现细节"。

坑二:把"接口没有实现"当成永恒真理。这个界限正在变模糊——Java 8+ 的接口允许 default 方法(带实现),C# 8+ 也有默认接口方法。所以"接口一定没实现"只对经典/早期版本成立。面试时主动点出这段演变,比死背定义更能加分——但记得给它加上"经典意义上""Java 8 之前"这样的限定词。

坑三:以为"忘了实现抽象方法"会在定义类时就报错。不会。Python 是在你实例化那个类时才抛 TypeError——类定义本身不报错。所以漏实现可能潜伏到第一次 X() 被调用。

"你这门语言怎么区分抽象类和接口?"是跨语言必问题,记住这张对照表:

语言抽象类接口 / 纯契约
Pythonabc.ABC + @abstractmethod,可含具体方法与状态无关键字:全抽象的 ABC / typing.Protocol / 鸭子类型
Javaabstract class,可有实现与字段;类只能单继承interface:Java 8 前纯契约、之后可有 default/static 方法;可多实现
C++含纯虚函数(virtual … = 0)的类;支持多继承没有独立 interface,用全是纯虚函数的类当接口
C#abstract classinterface,C# 8+ 起也允许默认接口方法

记忆锚:抽象类是"半成品基类"(可带实现),接口是"纯契约"(经典上无实现);而"接口能不能带实现"这条线,近十年被 Java 8 / C# 8 悄悄改写了。

四、决策树:到底选抽象类还是接口?

要在多个类之间共享一部分实现或状态吗?
▼
需要共享实现 / 状态
抽象类
给公共部分写默认实现,把差异部分留成抽象方法。
例:各种 Vehicle 都用同一套 stop(),只有 start() 各不相同。
只需定义契约
实现类彼此不相关,或一个类要同时满足多份契约?
▼
接口
只声明"必须能做什么",不管怎么做。
例:Serializable、Comparable 这类横跨无关类的能力。

一句话口诀:要复用实现 → 抽象类;只要立规矩 → 接口。在 Java 里还有一条硬约束帮你决策——类只能单继承(一个抽象类),但能实现多个接口;需要"多重身份"时,接口是唯一出路。

合上讲义,用 abc 自己写一个 Shape 抽象类:

  • 抽象方法 area(self) -> float:没有默认实现,逼子类算面积。
  • 具体方法 describe(self):打印 f"这个图形面积是 {self.area()}"——注意它调用了抽象方法,这就是"模板方法"雏形。
  • 写两个子类 Circle(radius) 和 Rectangle(w, h),各自实现 area。

写完自测两件事:①直接 Shape() 会发生什么?②如果 Circle 忘了实现 area,报错发生在"定义 Circle 时"还是"Circle(1) 时"?

自测 1:下面这段代码运行到哪一行、抛出什么? 
from abc import ABC, abstractmethod

class Report(ABC):
    @abstractmethod
    def render(self): ...

r = Report()      # ← 这一行

答案:运行到 r = Report() 抛 TypeError(Can't instantiate abstract class Report with abstract method render)。

关键点:类定义本身不报错,报错发生在实例化那一刻。因为 Report 还有未实现的抽象方法 render,abc 拦下了实例化。要能创建对象,必须先有一个把 render 实现掉的子类。

自测 2:你要设计一组"可支付"的东西——信用卡、微信、Apple Pay,它们彼此毫无继承关系,但都必须提供 pay(amount)。你会用抽象类还是接口?为什么?

答案:接口(在 Python 里就是全抽象的 abc.ABC 或 typing.Protocol)。

理由:①这些类彼此不相关,没有可共享的实现或状态,用抽象类去当公共基类是硬凑一个不存在的"is-a"关系;②你要的只是一份契约——"任何支付方式都保证有 pay";③如果某个类还要同时满足别的能力(比如既能 pay 又能 refund),接口可以多实现,抽象类(在 Java 那种单继承语言里)做不到。反过来,如果它们能共享一大段公共下单流程,那才该考虑抽象类。

带走这一条:抽象 = 只暴露必要功能(what)、隐藏细节;它的两种技术——抽象类(能带默认实现和状态、不能自己实例化,适合"共享一部分实现")与接口(经典上只有契约、没有实现,适合"给不相关的类立同一份规矩")。选择口诀:要复用实现选抽象类,只要立规矩选接口。Python 没有 interface 关键字,统一用 abc.ABC / typing.Protocol / 鸭子类型来表达。
