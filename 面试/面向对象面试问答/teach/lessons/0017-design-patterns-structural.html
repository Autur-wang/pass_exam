结构型模式:适配器、装饰器、代理

创建型管"对象怎么造出来",结构型管"对象怎么拼成更大的结构"。这一节吃透三个高频:Adapter(转接口)、Decorator(加职责)、Proxy(控访问)——顺带拆穿那个最爱考的坑:Python 的 @decorator 和 GoF 的装饰器模式,根本不是一回事。

先想一个真实场景:你手上有个第三方旧类,方法叫 print_document(text),你不能改它的源码;可你整套系统的其他打印器都统一用 render(content)。你会怎么让这个旧类"混进"你的系统,而不去动它一行代码?先给个思路,再往下看。

一、直觉:结构型模式在解决什么

GoF 把二十三个模式分成三类。创建型关心"对象如何被创建"(工厂、单例…);结构型关心"如何把类和对象组合成更大的结构,同时保持结构灵活、可扩展";行为型关心"对象之间如何分工与通信"。

结构型的共同套路是"包装 + 委托":一个外层对象持有(或指向)一个内层对象,对外提供某种接口,把真正的活儿转交给内层去做。三个高频模式,区别只在于包装的目的不同:

目的:改接口
Adapter
把 A 接口转成 B 接口
目的:加职责
Decorator
接口不变,叠加行为
目的:控访问
Proxy
替身/占位符

三个都"包着一个对象",但意图天差地别——这也正是面试官最爱借它们互相比较来考你的地方。先各个击破。

结构型模式 (Structural Patterns)
关注类与对象如何组合成更大的结构,让结构在可扩展的同时保持灵活。核心手法是"包装一个对象,再把调用委托给它"。
① 适配器 Adapter
把一个类的接口转换成客户端期望的另一个接口,让原本不兼容的类能协作。关键词:转接(接口 A → 接口 B)。
② 装饰器 Decorator
在不改原类、不靠继承爆炸的前提下,运行时动态给对象叠加职责(层层包裹)。关键词:增强(接口不变,行为变多)。
③ 代理 Proxy
给对象提供一个替身/占位符,以控制对它的访问。常见变体:虚代理(延迟创建昂贵对象)、保护代理(权限控制)、远程代理(代表远端对象)。关键词:把关(接口不变,访问受控)。

二、适配器 Adapter:让不兼容的接口握手

回到开场那个旧打印器。适配器的思路是:另写一个类,对外实现你系统要的新接口,对内持有那个旧对象,把新方法的调用"转接"到旧方法上。旧类一行不动,系统也不必知道底下是个老古董。

# —— 适配器 Adapter:把旧接口"转接"成客户端期望的新接口 ——

# 旧类:接口是 print_document(text),我们不能改它(第三方 / 遗留代码)
class LegacyPrinter:
    def print_document(self, text):
        print(f"[Legacy] {text}")

# 客户端只认这个新接口:render(content)
class ModernPrinter:
    def render(self, content):
        raise NotImplementedError

# 适配器:实现新接口,内部持有旧对象,把 render 转接到 print_document
class PrinterAdapter(ModernPrinter):
    def __init__(self, legacy):
        self._legacy = legacy                    # 包裹被适配对象(Adaptee)

    def render(self, content):
        self._legacy.print_document(content)     # 转接:新接口 → 旧方法

# 客户端只跟 render 打交道,完全不知道底下是旧类
def client(printer):
    printer.render("Hello, patterns!")

client(PrinterAdapter(LegacyPrinter()))          # [Legacy] Hello, patterns!

这里演示的是对象适配器(用组合:持有被适配对象)。还有一种类适配器用多继承来实现——Python 支持多继承,可以写,但对象适配器更常用、更松耦合,面试首选讲组合版。适配器的一句话本质:"包装 + 转接",改的是接口的形状,不改功能。

三、装饰器 Decorator:层层包裹地加料

经典例子:一杯咖啡,可以加奶、加糖、加双份浓缩……每种加料都改变描述和价格。如果用继承来穷举组合(CoffeeWithMilk、CoffeeWithMilkAndSugar…),类会组合爆炸。装饰器的解法:每个加料是一个"装饰器",它实现和咖啡相同的接口,同时包裹一杯"里面的饮料",在其基础上叠加自己的价格和描述。包裹可以层层嵌套,运行时随意组合。

# —— GoF 装饰器 Decorator:运行时层层包裹,叠加职责,保持同一接口 ——
from abc import ABC, abstractmethod

class Beverage(ABC):                    # 共同接口(Component)
    @abstractmethod
    def cost(self): ...
    @abstractmethod
    def description(self): ...

class Coffee(Beverage):                 # 被装饰的核心对象(ConcreteComponent)
    def cost(self):
        return 10.0
    def description(self):
        return "Coffee"

class CondimentDecorator(Beverage):     # 装饰器基类:持有一个 Beverage
    def __init__(self, beverage):
        self._beverage = beverage       # 关键:包裹一个"同接口"的对象

class Milk(CondimentDecorator):
    def cost(self):
        return self._beverage.cost() + 2.0             # 在被包裹对象基础上叠加
    def description(self):
        return self._beverage.description() + " + Milk"

class Sugar(CondimentDecorator):
    def cost(self):
        return self._beverage.cost() + 1.0
    def description(self):
        return self._beverage.description() + " + Sugar"

drink = Sugar(Milk(Coffee()))           # 层层包裹:Coffee 外套 Milk,再套 Sugar
print(drink.description())              # Coffee + Milk + Sugar
print(drink.cost())                     # 13.0

注意 Sugar、Milk、Coffee 对外接口完全一样(都有 cost()/description()),所以谁包谁都行,客户端拿到 drink 也不用关心它裹了几层。这就是装饰器的威力:接口不变,职责可叠加,组合在运行时决定。

对比:Python 的 @decorator 语法糖

下面这个才是 Python 语言级的 @decorator——它是一颗语法糖,在函数/类定义时就地把它替换成"被包装过的版本":

# —— Python 的 @decorator:语法糖,定义时应用,装饰的是"函数/类"本身 ——
import functools

def timing(func):
    @functools.wraps(func)                 # 保留原函数的 __name__ 等元信息
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@timing                    # 等价于:add = timing(add) —— 在 def 完成的那一刻立即应用
def add(a, b):
    return a + b

add(1, 2)                  # 打印 "calling add",然后返回 3

两段代码理念相通(都是"包裹一层来增强"),但不是同一个东西——这正是下面易错点要讲清的分界。

四、代理 Proxy:给对象派个替身把关

代理和装饰器长得很像(都实现相同接口、都持有目标对象),但它的意图是控制访问而不是增强功能。最常考的是虚代理:一个对象创建起来很贵(比如从磁盘加载大图),就先给个便宜的替身占位,等真正用到时才创建真身(懒加载)。

# —— 代理 Proxy(虚代理):延迟创建昂贵对象,接口与真身一致 ——
class HeavyImage:
    def __init__(self, filename):
        self._filename = filename
        self._load()                          # 一构造就加载,很贵
    def _load(self):
        print(f"loading {self._filename} from disk...")
    def display(self):
        print(f"showing {self._filename}")

class ImageProxy:
    def __init__(self, filename):
        self._filename = filename
        self._real = None                     # 先不加载,只记住文件名
    def display(self):
        if self._real is None:                # 第一次真正用到时,才创建真身
            self._real = HeavyImage(self._filename)
        self._real.display()

img = ImageProxy("huge.png")                  # 此刻不加载,几乎零成本
# ...页面滚动到这张图时才:
img.display()                                 # 首次调用才 loading... 再 showing

把 if self._real is None 换成"检查当前用户有没有权限",就成了保护代理;把真身换成"网络另一端的对象、内部帮你收发请求",就成了远程代理。变体不同,骨架一样:替身实现相同接口,在转发调用前后插入"访问控制"。

高频追问链(结构型的坑几乎都藏在"三者互相比较"里):

  • "适配器和装饰器都包裹一个对象,区别是什么?" → 适配器改接口(A 接口转成 B 接口,为了让不兼容的东西能协作);装饰器不改接口(进出都是同一个接口),只是叠加职责。一个换形状,一个加内容。
  • "代理和装饰器接口都一样、都持有目标,怎么区分?" → 看意图:代理是控制访问(可能延迟创建、拦截、限权,甚至不让你碰真身),通常自己掌管目标的生命周期;装饰器是增强功能,目标一般由客户端从外部组装好再传进来,而且装饰器天生鼓励层层叠加。
  • "Python 的 @decorator 就是 GoF 装饰器模式吗?" → 不是同一个层次的东西,见下方易错点——这是本节头号考点。
  • "什么时候用虚代理?" → 目标对象创建/加载昂贵、又未必真会用到时(大图、大文件、重连接),用替身做懒加载省资源。
  • "举个标准库里真实的装饰器模式例子?" → Java 的 java.io:new BufferedReader(new FileReader(f))——BufferedReader 包裹一个 Reader,加了缓冲,接口还是 Reader。这是 GoF 装饰器的教科书级实例。

头号翻车点:把 Python 的 @decorator 语法直接等同于 GoF 的装饰器模式。它们相关但不是一回事:

  • 联系:理念相通——都是"包裹一层来增强/改变原来的东西"。
  • 区别(要能一口气说清):Python 的 @ 是语言语法糖,装饰的是函数或类,在定义时(import 那一刻)就应用,本质是 f = deco(f);GoF Decorator 是一种对象结构设计模式,包裹的是运行时的对象实例,在运行时动态组装、还能层层叠加,靠"实现同接口 + 持有被包裹对象"来搭。一个是语法层的便利写法,一个是对象层的结构安排。

第二个坑:适配器 vs 装饰器分不清。记死这句:适配器改接口(换形状),装饰器加职责但保持接口(加内容)。如果包裹后对外的方法名/签名变了,是适配器;如果对外还是同一套接口、只是行为增强了,是装饰器。

为什么这个坑几乎只在 Python 面试里出现?因为只有 Python 把 @decorator 做进了语言语法,名字又恰好撞上 GoF 的 Decorator。别的语言没这颗糖,想实现 GoF 装饰器只能老老实实"实现同接口 + 持有对象 + 委托":

语言有无 @decorator 语法糖实现 GoF 装饰器模式的方式
Python有(@,装饰函数/类,定义时应用)既能用 @,也能像本节那样用类:实现同接口 + 持有对象
Java无手写:implements 同接口 + 持有字段委托(标准库实例:BufferedReader 包 Reader)
C++无手写:继承抽象基类 + 持有指针/引用,转发调用
C#无(有 [Attribute],但那是元数据标注,语义不同)手写委托同接口对象

提醒:Java 的注解 @Override、C# 的 [Serializable] 虽然也用 @/[],但它们是元数据/编译提示,和"运行时包裹对象增强行为"更不搭边,别混为一谈。

合上讲义,挑一个自己写一遍,检验是否真懂:

  • 适配器:有个旧类 CelsiusSensor.get_celsius() 只返回摄氏度;你的系统要 read_fahrenheit()。写一个 FahrenheitAdapter,持有旧传感器,转接并换算。
  • 装饰器:把本节的咖啡例子扩展一个 DoubleShot(加 3.0 元),验证 DoubleShot(Milk(Coffee())) 的价格和描述都对。
  • 代理:给 HeavyImage 的代理再加一层"保护":display() 前检查 self._user == "admin",否则打印"无权限",不创建真身。

自问一句:你的"装饰器"改变对外方法名了吗?(不该改——改了就变成适配器了。)

自测 1:面试官问"Python 的 @staticmethod、你写的 @timing 这类 @decorator,是不是 GoF 里的装饰器模式?"——最准确的回答是?

答案:不是同一个东西,但理念相通。Python 的 @decorator 是语言语法糖,装饰的是函数/类、在定义时应用,本质 f = deco(f);GoF Decorator 是对象结构设计模式,在运行时包裹对象实例、可层层叠加、靠"同接口 + 持有对象"搭成。二者都体现"包裹增强"的思想,但一个在语法层、一个在对象结构层。

只答"是"或只答"完全无关"都会被扣分——要点在于同时说清联系(包裹增强)和区别(语法糖 vs 对象结构模式、定义时 vs 运行时)。

自测 2:下面三个包装类,分别最可能是适配器、装饰器还是代理?
(a) 实现新接口 render(),内部调旧对象的 print_document();
(b) 和目标同接口,display() 里先判断权限、无权就不转发;
(c) 和目标同接口,cost() 返回 inner.cost() + 2.0。

(a) 适配器——对外接口(render)和被包裹对象的接口(print_document)不同,做的是"转接",典型适配器。

(b) 代理——接口不变,包裹的目的是控制访问(权限把关),典型保护代理。

(c) 装饰器——接口不变,在被包裹对象的结果上叠加职责(加价),典型装饰器。

判别口诀:接口变没变?变了 → 适配器;没变再看意图:加功能 → 装饰器,控访问 → 代理。

带走这一条:结构型模式都是"包装 + 委托",区别只在意图——Adapter 改接口(换形状)、Decorator 加职责且接口不变(加内容)、Proxy 控访问(把关)。判别先问"对外接口变没变",再看"目的是加功能还是控访问"。最后守住那条红线:Python 的 @decorator 是语法糖(定义时装饰函数/类),GoF Decorator 是运行时包裹对象的结构模式——理念相通,层次不同。
