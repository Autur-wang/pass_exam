设计模式总览与创建型模式

这一节先给你一张"设计模式全景地图"(三大类各是什么、为什么这么分),再把创建型里最高频的三个——单例、工厂、建造者——讲到能当场用 Python 写出来、也能回答"这在 Python 里是不是根本不需要"。

先想两个具体需求:①你要让"配置对象"在整个程序里只有一份,任何模块拿到的都是同一个;②你想在不改调用代码的前提下,根据字符串 "circle" / "square" 造出不同的图形对象。这两件事你会怎么写?先在心里给个方案——它们各自对应一个经典的创建型模式。

一、什么是设计模式?先破一个误解

设计模式(Design Pattern)不是库,不是能 import 的代码,也不是框架。它是针对反复出现的设计问题的、可复用的通用解法——是前人踩坑后沉淀下来的"套路名字"。你和同事说"这里用个工厂",对方立刻知道你要干什么,这就是模式最大的价值:它是工程师之间的共享词汇。

但请把这句话刻进脑子里,它是本节的总原则,也是面试区分"读过书"和"用过"的分水岭:

模式是"识别出问题后套用"的经验,不是"为用而用"的目标。先有反复出现的问题,才有对应的模式;没有那个问题却硬套模式,只会平白增加复杂度(over-engineering)。面试里如果你张口就是"我会用单例+工厂+观察者",却说不出各自解决什么痛点,反而是减分项。

二、GoF 的三大分类:一张地图

1994 年四位作者(俗称 GoF,Gang of Four)在《Design Patterns》里总结了 23 个模式,并按"这个模式主要在操心什么"分成三类。记住这个分类维度,比记住 23 个名字更重要:

Creational
创建型
怎么造对象
单例/工厂/建造者 → 本节
Structural
结构型
怎么组合对象与类
适配器/装饰器/代理 → 0017
Behavioral
行为型
对象间怎么协作分工
观察者/策略/迭代器 → 0018

三类的区别用一句话拎清:创建型关心"对象从哪来"、结构型关心"对象怎么拼在一起"、行为型关心"对象之间怎么通信与分责"。本节只讲创建型里最高频的三个。

创建型模式 (Creational Pattern)
把对象的创建过程本身封装/抽象出来,让代码不必到处硬写 SomeClass(...),从而降低"使用方"和"具体类"之间的耦合。
① 单例 Singleton
保证一个类全局只有一个实例,并提供一个全局访问点。
② 工厂 Factory
把"造哪个具体类"的决定封装起来,调用方只面向抽象,不必知道具体类名。
③ 建造者 Builder
分步构造一个复杂对象(尤其是可选参数很多时),把"怎么拼"和"最终产物"分开。

三、单例 Singleton:全局只此一份

动机很实在:有些资源在整个程序里逻辑上就该只有一份——全局配置、日志器、连接池。如果每处都 new 一个,状态就散了、也浪费。单例要解决的就是"保证唯一 + 提供统一入口"。

在 Java/C++ 里,标准做法是"私有构造器 + 一个 static 实例 + 一个 getInstance() 静态方法"。但在 Python 里,最地道的单例根本不用写类技巧——模块本身就是单例。

# ── 法一:模块级对象(最 Pythonic)────────────────
# 文件 config.py
class _Config:
    def __init__(self):
        self.debug = False

# 一个模块首次被 import 后会缓存在 sys.modules,
# 之后再 import 拿到的是同一个模块对象,所以下面这个
# config 天然全局唯一——不需要任何"单例代码"。
config = _Config()

# 别处使用:
#   from config import config
#   config.debug = True     # 谁改都是改同一个对象

如果面试官坚持要"类级别的单例写法"(常见于把 Java 习惯带过来的题目),可以重写 __new__。多线程环境下要加锁,保证并发时也只造一次:

# ── 法二:重写 __new__ + 加锁 ────────────────────
import threading

class Logger:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        # __new__ 负责"造实例";我们拦截它,只在第一次真正创建
        with cls._lock:                       # 加锁:多线程下只造一次
            if cls._instance is None:
                cls._instance = super().__new__(cls)
        return cls._instance

a = Logger()
b = Logger()
print(a is b)      # True —— 永远是同一个实例

坑一:别硬搬 Java 的"双重检查锁(DCL)"。Java 里 DCL 是为绕开锁开销的经典写法,但在 Python 中,90% 的场景直接用模块级对象就够了,又简单又线程安全(模块首次导入本身受 import 锁保护)。上来就手写 DCL,往往是"把陌生语言的习惯生搬过来"。

坑二:__new__ 单例里 __init__ 每次调用都会重跑。调用 Logger() 时,只要 __new__ 返回的是本类实例,Python 就会紧接着调用 __init__。也就是说即便实例是同一个,__init__ 里的初始化仍会被反复执行,可能把状态覆盖掉。要么把初始化逻辑也做幂等,要么干脆用模块级方案回避这个问题。

高频追问链(单例几乎必被追一句"它是不是反模式"):

  • "单例是不是反模式?" → 它的争议在于:单例本质是全局状态。全局状态会隐藏依赖(函数签名里看不出它偷偷用了这个单例)、难做单元测试(测试间状态互相污染,还很难替换成 mock)。所以很多人视其为反模式,建议慎用。真要用,优先留给"确实天然唯一、且无状态或状态只读"的资源。
  • "那不用单例,全局唯一的东西怎么办?" → 常见替代是依赖注入:把需要的对象当参数传进去,而不是让代码自己去全局取。这样依赖显式、也好测试。
  • "Python 里写单例有几种方式?" → 模块级对象(首选)、重写 __new__、用元类(metaclass)统一拦截创建、或用一个返回缓存实例的装饰器/函数。

四、工厂 Factory:把"造哪个"藏起来

动机:当"用一个对象"和"决定造哪个具体类"这两件事纠缠在一起时,调用方就被绑死在具体类上了。工厂的思路是——把创建逻辑收进一个地方,调用方只说"我要一个形状",不关心是 Circle 还是 Square。这正好呼应 SOLID 里的 OCP(对扩展开放)和 DIP(面向抽象编程)。

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class Circle(Shape):
    def __init__(self, r):
        self.r = r
    def area(self) -> float:
        return 3.14159 * self.r ** 2

class Square(Shape):
    def __init__(self, side):
        self.side = side
    def area(self) -> float:
        return self.side ** 2

def shape_factory(kind: str, *args) -> Shape:
    """简单工厂:调用方只说'要什么',不碰具体类的构造。"""
    registry = {"circle": Circle, "square": Square}
    if kind not in registry:
        raise ValueError(f"未知形状:{kind}")
    return registry[kind](*args)

# 调用方:不 import Circle,也不写 Circle(2)
s = shape_factory("circle", 2)
print(s.area())        # 面向 Shape 抽象,拿到什么具体类无所谓

好处:哪天要新增 Triangle,只改工厂内部的 registry(甚至做成注册表自动登记),所有调用方一行都不用动。这就是"把易变的创建决策收敛到一处"。

坑三:上面这个 shape_factory 叫"简单工厂",它其实不是 GoF 23 个模式之一——它是一种常见编程惯用法(idiom),可以看作工厂方法的退化版。GoF 正式收录的是"工厂方法(Factory Method)"和"抽象工厂(Abstract Factory)"。面试时把这层说清,能显出你读得细。

坑四:工厂方法 vs 抽象工厂,别混。记一句话:工厂方法造"一个"产品,抽象工厂造"一族"产品。见下表。

工厂方法 Factory Method抽象工厂 Abstract Factory
造什么一类产品的一个对象一族相关/配套的产品
形式一个(可被子类覆盖的)创建方法,由子类决定实例化哪个类一个接口,里面有多个创建方法,分别造这族里的各件产品
例子create_button() 返回一个按钮"Windows 主题工厂"同时造配套的按钮 + 复选框 + 滚动条;换成"Mac 主题工厂"则造对应的一整套

五、建造者 Builder:告别"望远镜式构造器"

动机:当一个对象有很多可选参数时,构造器会膨胀成一长串——这就是"望远镜式构造器(telescoping constructor)":

# ❌ 望远镜:参数一多就没法读,调用处全是 None 占位
class Pizza:
    def __init__(self, size, cheese=False, mushroom=False,
                 bacon=False, onion=False, olives=False):
        ...

p = Pizza("L", True, False, True, False, True)   # 每个 True/False 是啥?

建造者把"分步设置"和"最终产出"拆开,让构造过程可读、可选、可复用。Python 里常用链式调用来实现:

# ✅ 建造者:一步一步说清楚要什么,最后 build()
class PizzaBuilder:
    def __init__(self, size):
        self.size = size
        self.toppings = []
    def add(self, topping):
        self.toppings.append(topping)
        return self               # 返回自身 → 支持链式
    def build(self):
        return f"{self.size} 披萨,配料:{self.toppings}"

p = (PizzaBuilder("L")
     .add("cheese")
     .add("bacon")
     .build())                    # 读起来就像一句话

什么时候用建造者?判据很简单:可选参数多、或构造需要分步/校验时。参数就两三个、且都必填,直接用普通构造器即可,别为用而用(呼应本节总原则)。

GoF 模式诞生于 C++/Smalltalk 那个"类型静态、函数不是一等公民"的世界。到了 Python,因为有一等函数、鸭子类型、模块天生单例,不少创建型模式被大幅简化,甚至"退化到看不见":

模式GoF 原生形态(C++/Java)Python 里的退化形态
Singleton私有构造器 + static 实例 + getInstance()直接用模块级对象(模块天生单例)
Factory专门的工厂类/工厂方法层级一个返回对象的普通函数(函数是一等公民)
Strategy(行为型,顺带一提)定义策略接口 + 多个实现类直接把函数当参数传进去

面试可以点出这一层:"很多 GoF 模式是在补静态语言的能力短板;Python 的动态特性让其中一部分退化成一行代码。"这句话能显出你理解的是"模式背后的问题",而不是把模式当教条。

合上讲义,自己写两段:

  • 单例:写一个 Counter,用重写 __new__ 的方式让它全局唯一;再验证 Counter() is Counter() 为 True。然后故意在 __init__ 里 self.n = 0,想想为什么"每次调用 Counter() 计数都被清零"——这就是坑二。
  • 工厂:给 shape_factory 加一个 Triangle,只允许你改工厂内部,不许改任何调用处——体会"新增不改旧代码"(OCP)。
自测 1:下面关于"在 Python 里实现单例"的说法,哪一个最准确?

答案:最地道、最简单的单例是直接用模块级对象,因为模块首次 import 后会被缓存、天然全局唯一;__new__/元类只是"当需要类级写法时"的备选。

常见错误答案:"Python 单例必须用双重检查锁"。反例:模块级对象根本不需要锁,且模块导入本身受保护。DCL 是从 Java 搬来的习惯,在 Python 大多数场景里是过度设计。

自测 2:同事说"我们的 UI 要同时支持深色和浅色两套皮肤,每套皮肤都有配套的按钮、输入框、滚动条,要能整套切换。"该用工厂方法还是抽象工厂?为什么?

答案:抽象工厂。

关键词是"配套的一整族产品、要整套切换"。抽象工厂正是用来创建"一族相关对象"的:一个 DarkThemeFactory 负责造深色的按钮+输入框+滚动条,一个 LightThemeFactory 造对应的浅色全套,切皮肤=换工厂,整族一致。工厂方法只解决"造一个产品该实例化哪个类",覆盖不了"一族产品保持配套"这个诉求。

带走这一条:设计模式是"识别出反复出现的问题后才套用"的共享词汇,不是为用而用的目标;GoF 把它们分成创建型(怎么造)、结构型(怎么拼)、行为型(怎么协作)。创建型三高频:单例(全局唯一——但它是全局状态,慎用;Python 首选模块级)、工厂(把"造哪个具体类"藏起来,解耦创建与使用)、建造者(可选参数多时分步构造,避免望远镜式构造器)。别忘了:Python 的动态特性让不少模式退化成一个函数或一个模块。
