RAG 全流程与「为什么要 RAG」

大模型有两个先天缺陷:它不知道训练截止之后的事,也不知道你公司内网里的事,而且一旦不知道,它还会一本正经地编。RAG(Retrieval-Augmented Generation,检索增强生成)就是给模型外挂一个可随时更新、可溯源的「资料库」,让它先查再答。这节课把整条链路一次性走通——从一份 PDF 到一句带出处的回答,中间每一步会出什么问题——这几乎是所有 RAG 面试的开场必答题。

上一课(DPO / GRPO / GSPO)讲的是对齐:让模型「更会说话、更听话」。但对齐改变不了一个事实——模型的知识被冻结在训练那一刻。先别往下看:如果老板要求模型准确回答「我们公司上周五发布的报销新规」,你会去重新训练模型,还是有更划算的办法?

一、为什么要 RAG:四个动机 + 一个成本账

把 RAG 想成开卷考试。闭卷(纯参数记忆)靠死记硬背,记错了就瞎编;开卷是带着资料进考场,答题前先翻到对应那一页,照着写。RAG 解决的正是「让模型在答题前翻到对的那一页」。它主要治四种病:

知识时效
参数知识冻结在训练截止日
外挂库随时增删,不必重训
私域知识
内网文档、产品手册模型没见过
放进检索库即可被引用
降幻觉 + 可溯源
不知道就爱编、无法追责
答案挂上原文出处,可核对

第四个动机是成本,也是面试高频对比点。当目标是「让模型掌握一批会频繁变动的事实」时:

  • 微调(改参数):知识每变一次就要重新准备数据、重新训练、重新评测、重新部署;而且往模型里「灌事实」还容易带来遗忘和新的幻觉。
  • RAG(改上下文):知识变了,只需更新检索库里的文档,模型权重一动不动。改一条规章 = 改一个文件。

所以经验法则是:「教模型新知识」优先 RAG,「教模型新行为/新风格/新格式」才考虑微调。两者边界这节先点到,细讲留到第 0031 课。

二、基础链路:一份 PDF 是怎么变成一句带出处的回答的

整条链路分成两个时段。离线(建库,只做一次或定期做)把文档灌进向量库;在线(每次提问)把问题变成检索、再拼进 prompt 交给模型。

逐环节说明,以及每一步最容易翻车的地方(面试官爱顺着链路一路追问):

环节做什么典型问题(出错点)
解析 / 清洗从 PDF/HTML 抽出干净文本,记录文件名、页码、来源、日期等元数据表格 / 多栏 / 扫描件抽错,导航栏噪声混入
分块 Chunking把长文切成检索单位(chunk)切太碎丢上下文,切太大稀释语义、还挤爆窗口
向量化 Embedding每块编码成一个稠密向量Embedding 模型与领域/语言不匹配,相似≠相关
建索引用 ANN 结构(HNSW / IVF / PQ)存向量,支持近似最近邻查询召回率 vs 速度/内存的取舍没调好
检索召回把问题也编码,取 Top-K 最相近的块只用向量,漏掉靠关键词/专有名词才能命中的块
重排 Rerank用更强的 Cross-Encoder 对候选精排,选出最相关的少数几块不做重排,粗排噪声直接进 prompt
生成把问题 + 命中片段填进 prompt 模板,让模型据此作答并给出处上下文太长被「中间遗忘」,或模型无视资料仍旧编

一句话记住整条链:解析 → 分块 → 向量化 → 建索引 → 检索 → 重排 → 拼 prompt → 生成。面试让你「讲讲 RAG 流程」,把这八步 + 每步的坑说清楚,基本就稳了。

三、五个可优化阶段:知道每一步能怎么调

朴素 RAG 效果往往不够,优化空间集中在五个阶段。这一节只给地图,后面几课逐个深挖(分块/向量库见 0022,检索与重排见后续课)。

① 解析与预处理
把原始文档变成干净文本,并保留元数据(文件名、日期、来源、页码、作者)。元数据不是摆设——检索时可以按它做过滤(「只在 2026 年的文档里找」),生成时可以用它给出处。清洗则是去掉导航菜单、乱码、统一标点与 Unicode。
② 分块策略(Chunking)
决定「检索的最小单位」有多大、边界切在哪。常见几档:固定大小(按 Token 数均分,常留 10%–20% 重叠维持连贯)、基于句子(用 NLP 工具找句界)、递归字符分块(按段落→换行→空格层层退让,LangChain 默认基线)、语义分块(相邻句子 Embedding 相似度低于阈值就切,主题一致但算得慢)、基于结构(顺着 Markdown/HTML 标题层级切)。工程上常见做法是先用递归字符分块打底,再按语义相似度决定要不要在某处断开。
③ 向量化与索引
选 Embedding 模型 + 选 ANN 索引类型。近似最近邻的三大家:IVF(倒排文件,粗筛桶+桶内细搜,配强过滤稳)、HNSW(分层可导航小世界图,召回率高)、PQ(乘积量化,压向量、省内存)。选型看约束:要强过滤走 IVF 系;要极致召回走 HNSW;内存/成本敏感走 PQ 系(如 IVF_PQ)。
④ 查询理解与增强
用户的原始问题往往不适合直接检索。三招:查询改写(把口语化/有指代的问题改清楚)、预设答案检索(先让模型草拟一个假想答案,再拿它去检索,常比原问题更贴近文档措辞)、查询分解(把复杂的多跳(Multi-Hop)问题拆成若干子问题,分别检索再合成——这正是 RAG 回答「A 的老板的生日是哪天」这类需要两步查证问题的标准解法)。
⑤ 混合检索与重排
不要只靠一种检索。稠密(向量,懂语义、抗同义改写)和稀疏(BM25 关键词,擅长专有名词、代码、精确匹配)各有盲区,并行跑再融合。融合后用 Cross-Encoder 做重排精选。下一节详解这一步的两个核心公式。

四、把「混合检索」讲到公式级

面试问「检索有哪些?BM25 是什么?」时,你要能区分两条路并写出关键式子。

稀疏检索:BM25

BM25 是词袋打分的代表,不看语义、只看「查询词在文档里出现得够不够、够不够稀有、文档是不是靠长度作弊」。总分是各查询词得分之和:

$$\text{BM25}(D,Q)=\sum_{i=1}^{n}\text{IDF}(q_i)\cdot\frac{f(q_i,D)\,(k_1+1)}{f(q_i,D)+k_1\!\left(1-b+b\cdot\dfrac{|D|}{\text{avgdl}}\right)}$$

$f(q_i,D)$ 是词 $q_i$ 在文档 $D$ 的词频,$|D|$ 是文档长度,$\text{avgdl}$ 是平均文档长度。

三个设计各治一个问题:

  • IDF(逆文档频率)——衡量区分度。稀有词权重高,「的/是」这种到处都有的词权重低: $$\text{IDF}(q_i)=\log\frac{N-n(q_i)+0.5}{n(q_i)+0.5}$$ 其中 $N$ 是文档总数,$n(q_i)$ 是含 $q_i$ 的文档数。
  • 词频饱和——一个词从出现 1 次到 2 次,相关性提升很大;从 20 次到 21 次几乎无差别。参数 $k_1$ 控制饱和速度(常取 $1.2\sim2.0$)。
  • 长度归一化——长文档偶然命中查询词的概率天然更高,用 $|D|/\text{avgdl}$ 惩罚它。参数 $b$ 控制强度:$b=0$ 不惩罚,$b=1$ 完全归一化,常取 $0.5\sim0.75$。

结果融合:RRF(Reciprocal Rank Fusion)

向量和 BM25 各返回一个排序榜单,分数量纲还不一样,不能直接相加。RRF 干脆只看名次不看原始分:一篇文档在某个榜单里排第 $r$ 名,就贡献 $\tfrac{1}{k+r}$,把它在所有榜单的贡献加起来:

$$\text{RRF}(d)=\sum_{r\in R}\frac{1}{k+\operatorname{rank}_r(d)}$$

$R$ 是所有检索路的榜单集合,$\operatorname{rank}_r(d)$ 是文档 $d$ 在第 $r$ 路里的名次,$k$ 是一个小平滑常数(常用 60)。

直觉:被多路一致地排在前面的文档,得分累加后自然冒头;只在一路里靠前的文档得分偏低。这就是为什么源材料里 doc_B(两路都靠前)融合后排第一,而各只在一路命中的 doc_A/C/D/E 排在后面。除了 RRF,也可用线性加权 $\text{score}=\alpha\cdot\text{vec}+(1-\alpha)\cdot\text{kw}$,但那要求两路分数先归一化,调 $\alpha$ 更麻烦。

把在线链路写成一段最小可读的伪代码,感受数据怎么流:

def rag_answer(question, index, llm, top_k=50, top_n=5):
    # ① 查询理解:改写 / 分解(此处从简)
    q = rewrite(question)

    # ② 混合检索:两路并行,各取 top_k
    dense_hits  = index.vector_search(embed(q), k=top_k)   # 稠密:懂语义
    sparse_hits = index.bm25_search(q,        k=top_k)     # 稀疏:抓关键词

    # ③ 融合:RRF 只看名次
    fused = rrf_fuse([dense_hits, sparse_hits], k=60)

    # ④ 重排:Cross-Encoder 精排,选最相关的 top_n 块
    ctx = rerank(q, fused)[:top_n]

    # ⑤ 拼 prompt:把命中片段 + 出处塞进模板,让模型据此作答
    prompt = build_prompt(question, ctx)
    return llm.generate(prompt)   # 回答里带 ctx 的来源,可溯源

注意:检索粗排取几十上百条(高召回),重排后只留几条进 prompt(高精度)。召回负责「别漏」,重排负责「别脏」。

面试官会怎么问:

  • 「完整讲一遍 RAG 链路。」——按解析→分块→向量化→建索引→检索→重排→拼 prompt→生成八步走,每步带一句「这步会出什么问题」,别只背名词。
  • 「为什么用 RAG 而不是微调?」——要改知识/事实且频繁变动 → RAG(更新库即可、可溯源、便宜);要改行为/风格/格式 → 微调。(细节第 0031 课)
  • 「RAG 有哪些优化阶段?」——五阶段:解析预处理 / 分块 / 向量化索引 / 查询理解增强 / 混合检索重排,能各举一两个具体手段。
  • 「检索有哪些?BM25 是什么?」——稀疏(BM25:IDF + 词频饱和 + 长度归一化)vs 稠密(向量语义);实际用混合检索 + RRF 融合 + 重排。
  • 「多跳问题怎么做?」——查询分解:拆成子问题逐一检索,再把中间结果拼起来合成最终答案。

易错点:

  • 把 RAG 当成「万能治幻觉」。它降幻觉靠的是「给了对的资料」;检索错了,模型照样会顺着错资料编——垃圾进,垃圾出。
  • 只用向量检索。向量擅长语义、却常在专有名词、编号、代码、罕见词上失手,这些恰是 BM25 的强项,所以要混合。
  • 把「向量相似」等同于「与问题相关」。相似度高的块未必答得了问题,这正是要单独做一步 Rerank 的原因。
  • chunk 越大越好 / 越小越好——都不对。太大稀释语义还挤占窗口,太小丢上下文;要按文档结构和问题粒度权衡(第 0022 课)。
  • RRF 用原始分相加。RRF 的精髓是只用名次,正因为两路分数量纲不可比;要相加原始分得先归一化(那是线性加权那一路)。

自测 1:某问答系统要能准确回答「本公司上周新发布的报销规定」,且规定几乎每月更新。下面哪种方案最合适?

A. 每次规定更新就用新规定重新微调模型知识频繁变动却用微调,意味着反复重训、评测、部署,成本高且易引入遗忘/幻觉,不划算。
B. 把最新规定文档放进检索库,用 RAG 让模型检索后作答 ✅正确。知识频繁变动时,更新检索库即可(改一条规章=改一个文件),模型权重不动,还能给出处溯源。
C. 把规定写进系统提示词,永久固定在 prompt 里规定每月变、且未来会越来越多,硬塞进 prompt 会不断膨胀且难维护,不如放进可检索的库。
D. 扩大模型参数量,让它「记住」更多规定参数量与「知道你公司内网私域知识」无关,模型没见过就是没见过,更大也记不住未训练过的内容。

自测 2:关于混合检索里用 RRF 融合向量检索和 BM25 的结果,下列说法正确的是?

A. RRF 把两路的原始相似度分数直接相加得到总分恰恰不是。两路分数量纲不同不可直接相加,直接加原始分是「线性加权」那条路(还需先归一化)。
B. RRF 只对向量检索有效,BM25 不能参与融合错。RRF 是与检索方式无关的排名融合,任何能给出排序榜单的检索路都能参与。
C. RRF 依据文档在各路榜单中的名次计算贡献 $\tfrac{1}{k+\text{rank}}$ 再求和,被多路一致排在前面的文档更容易胜出 ✅正确。只看名次不看原始分,躲开量纲不可比的问题;多路共识的文档得分累加后自然冒头。
D. RRF 要求两路检索必须返回完全相同的候选集合错。各路榜单可以不同,某文档只在一路出现时,它仅从那一路获得一份贡献,分数自然偏低。

这节课的一手出处与深挖方向:

  • Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks(Lewis et al., 2020)——RAG 这一术语与范式的原始论文。
  • Dense Passage Retrieval for Open-Domain QA(Karpukhin et al., 2020)——稠密向量检索(双塔 Embedding)的代表工作。
  • The Probabilistic Relevance Framework: BM25 and Beyond(Robertson & Zaragoza, 2009)——BM25 打分函数的系统性来源,本课 IDF / 词频饱和 / 长度归一化即出自此。
  • Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods(Cormack et al., 2009)——RRF 的原始论文。
  • Efficient and Robust ANN Search using HNSW Graphs(Malkov & Yashunin)——HNSW 索引来源,理解向量库为什么快。
