推理部署:vLLM / SGLang / PagedAttention 与显存估算

模型训好、量化完,真正上线要回答的是另一类问题:一张卡能扛多少并发?延迟卡在哪?为什么同样的模型换个推理框架吞吐能翻几倍?这节课把推理服务的核心指标、vLLM 的看家本领 PagedAttention、以及面试必被追问的「显存怎么估」一次讲透。面试里这是「工程落地」段位的分水岭题。

上节课(量化)我们把权重从 FP16 压到 INT8/INT4,省的是模型权重那部分显存。但推理时显存的另一大头是随着对话越来越长而不断膨胀的 KV Cache。先别往下看,试着回忆:自回归生成时,每吐一个新 token 都要重算前面所有 token 的 K、V 吗?如果不重算,那些 K、V 存在哪、占多大?

一、先立指标:你在优化什么?

没有指标就没有优化。推理服务通常盯三个量,而且它们互相拉扯——这正是面试官想看你懂不懂权衡的地方。

吞吐 Throughput
单位时间处理的 token 数
看运营成本:每 token 多少钱
TTFT
Time To First Token
看首字响应:用户等多久看到第一个字
TPOT
Time Per Output Token
看吐字流畅度:后续每个字多快

生成过程天然分两段,两段的瓶颈完全不同,这是理解一切推理优化的前提:

  • Prefill(预填充)阶段:把整段 prompt 一次性喂进去,所有 token 可以并行计算——这是计算密集(compute-bound)的,GPU 算力吃满。TTFT 主要由这一段决定。
  • Decode(解码)阶段:一个一个往外吐 token,每步只算一个新 token,却要读取整份 KV Cache——这是访存密集(memory-bound)的,GPU 算力大量闲置,瓶颈在显存带宽。TPOT 由这一段决定。

并发(concurrency)则是把很多请求塞在一起同时服务。提高并发能摊薄 decode 阶段的算力浪费、抬高吞吐,但会挤占显存、可能拉长单请求延迟。吞吐与延迟通常此消彼长——面试答「都要最好」是外行。

二、KV Cache:省了算力,却吃光显存

自回归生成靠 KV Cache 避免重复计算:已经算过的 token,它们的 Key 和 Value 存下来,新 token 只需算自己的 Q 去和缓存里的 K、V 做注意力。代价是显存——缓存随序列长度线性增长,而且每条并发请求都有自己的一份。

单条请求的 KV Cache 大小可以直接估:

$$\text{KV bytes} = 2 \times L \times n_{\text{kv}} \times d_h \times s \times b_{\text{p}}$$

$2$ 是 K 和 V 各一份;$L$ 层数;$n_{\text{kv}}$ 是 KV 头数(用了 GQA/MQA 会远小于注意力头数);$d_h$ 每头维度;$s$ 序列长度;$b_{\text{p}}$ 每个数的字节数(FP16 为 $2$)。乘上 batch 就是总量。

关键结论:KV Cache 正比于序列长度 × 并发数。这就是为什么「长上下文 + 高并发」是显存杀手,也是为什么 GQA(第 0004 课的多头变体)和量化 KV Cache 能救命——它们直接砍 $n_{\text{kv}}$ 或 $b_{\text{p}}$。

三、PagedAttention:把 KV Cache 当操作系统的内存来管

问题来了:传统实现会给每条请求预留一整块连续显存,按「可能的最大长度」分配。但请求实际生成多长事先不知道——按最大长度留,大部分是浪费(内部碎片);留得不够又要挪。不同请求长短不一,连续块之间还夹着用不上的空隙(外部碎片)。结果是显存利用率很低,能同时跑的请求数被硬生生压下来。

vLLM 的 PagedAttention 借用了操作系统虚拟内存分页的思想来解决:把 KV Cache 切成固定大小的 block(vLLM 默认一个 block 存 16 个 token 的 KV),这些 block 在物理显存里不必连续,靠一张「块表(block table)」把逻辑上连续的 token 序列映射到分散的物理块。

这样带来两个直接收益:

  • 几乎消除碎片:按需一块一块分配,只有最后一个块可能没填满,浪费上限就是「小于一个 block」的量,显存利用率大幅提升。
  • 能装更多并发:省下的显存直接变成更多 KV Cache 空间,同一张卡能同时服务更多请求 → 吞吐上去了。

额外好处:block 可以共享。多个请求若有相同前缀(比如同一个 System Prompt),它们的前缀 block 可以指向同一份物理内存,再配合 copy-on-write——这就引出了 prefix caching。

四、Continuous Batching:别让先跑完的请求干等

传统「静态批处理(static batching)」把一批请求凑齐一起发,必须等批里最慢那条生成完才能整批返回、再收下一批。可请求生成长度差异极大,短的早早算完却被锁在批里空转,GPU 利用率被拖垮。

vLLM 的 continuous batching(连续/动态批处理,也叫 in-flight batching)把调度粒度从「一整批」降到「一步(iteration)」:每生成一步就检查一次,谁生成完了立刻踢出去返回、腾出的位置马上塞进排队的新请求。GPU 始终被填满,不用等最慢的那条。这是 vLLM 高吞吐的另一半功劳,和 PagedAttention 是绝配——后者提供了灵活分配显存的能力,前者才能灵活地换进换出请求。

五、Prefix Caching 与 SGLang 的 RadixAttention

Prefix caching(前缀缓存):很多场景下不同请求共享同一段开头——固定的 System Prompt(角色设定、工具定义)、few-shot 示例、多轮对话里不变的历史。这段前缀的 KV 只需算一次,后续命中缓存直接复用,不必重算。收益直接落在 TTFT 上:prefill 少算了一大截,首字更快。vLLM 开 enable_prefix_caching=True 即可。

SGLang 把前缀复用做到更极致:它的 RadixAttention 用一棵 radix tree(基数树/前缀树)来组织所有请求的 KV Cache,自动发现并复用任意请求之间的公共前缀——不只是「同一个 System Prompt」,而是树上任何一条共享路径。对多轮对话、树状搜索、大量共享上下文的 Agent 场景收益尤其明显。一句话记:vLLM 以 PagedAttention 管显存见长,SGLang 以 RadixAttention 做前缀复用见长(两者能力也在互相借鉴,别背成「谁只会什么」)。

六、推理显存估算:面试高频计算题

「部署这个模型要多大显存?」几乎必问。拆成三块,逐块估:

组成怎么估随什么增长
模型权重参数量 × 每参数字节数模型大小、量化精度
KV Cache见上式 $2 L\, n_{\text{kv}} d_h\, s\, b_{\text{p}}$ × 并发序列长度 × 并发数
激活 / 中间结果 + 框架开销较小但非零(临时张量、CUDA context、碎片余量)batch、实现细节

权重那块最好算——每参数字节数由精度决定:

$$\text{权重显存} \approx P \times b_{\text{p}}, \qquad b_{\text{p}} = \begin{cases} 2 & \text{FP16 / BF16} \\ 1 & \text{INT8} \\ 0.5 & \text{INT4} \end{cases}$$

$P$ 是参数量。所以 FP16 下「参数量(以 B 为单位)× 2」就是权重显存(GB)的粗估:7B ≈ 14GB,72B ≈ 144GB。

多卡时用 Tensor Parallelism(TP)把权重切到多张卡:$\text{每卡权重} \approx (P \times b_{\text{p}}) / N_{\text{gpu}}$。例如 72B FP16 共约 144GB,切到 8 卡每卡约 18GB,剩下的显存留给 KV Cache 装并发和长文本。注意这是粗估:实际还要扣掉激活、框架开销,并给碎片留余量——所以 vLLM 用 gpu_memory_utilization(默认 0.9 量级)显式控制占用比例,把剩余空间稳稳留给 KV block,避免运行中 OOM。

PagedAttention
vLLM 的 KV Cache 管理机制:仿照 OS 虚拟内存分页,把 KV Cache 切成固定大小、物理上不连续的 block,用块表映射。消除显存碎片、支持前缀块共享,从而在同一显存下装下更多并发。
Continuous Batching
以「每生成一步」为粒度动态调度:请求一完成立即返回并让新请求补位,GPU 不必等整批最慢的请求,显著提升吞吐与利用率。
Prefix Caching / RadixAttention
共享前缀的 KV 只算一次、后续复用。SGLang 用 radix tree 组织 KV,自动复用任意请求间的公共前缀,主要降低 TTFT。
TTFT / TPOT
TTFT 是首个 token 的延迟(由 prefill 主导);TPOT 是后续每个 token 的平均间隔(由 decode 主导)。

用 vLLM 起一个兼容 OpenAI 接口的服务(单卡量化 + 多卡 TP 两种形态),这是最常见的部署骨架:

# 单卡:AWQ 量化模型,显式控制显存占用与最大长度
python -m vllm.entrypoints.openai.api_server \
    --model /path/to/Model-AWQ \
    --quantization awq \
    --dtype half \
    --max-model-len 16384 \
    --gpu-memory-utilization 0.9 \
    --enable-prefix-caching \
    --port 8000

# 多卡:Tensor Parallel 切到 N 张卡(多机再叠 Ray)
python -m vllm.entrypoints.openai.api_server \
    --model /path/to/Model \
    --tensor-parallel-size 8 \
    --distributed-executor-backend ray \
    --host 0.0.0.0 --port 8000

多机时先起 Ray 集群(head 节点 ray start --head,worker 节点 ray start --address=<head-ip>:6379),vLLM 会自动检测集群并分发分片。坑:多机 TP 对节点间网络极敏感,没有 InfiniBand 而走普通以太网,跨机通信会把延迟拖高。

面试官会怎么问:

  • 「vLLM 为什么快?」——两根支柱:PagedAttention 消除 KV Cache 碎片、装下更多并发;continuous batching 让 GPU 不等最慢请求。别只答「它优化了」。
  • 「PagedAttention 到底解决了什么问题?」——传统连续预留 KV Cache 导致内外部碎片、显存利用率低;分页化按需分配,几乎零碎片,还能共享前缀块。
  • 「部署 X B 模型要多大显存?」——分三块:权重(参数×字节)+ KV Cache(正比序列长×并发)+ 激活/开销;多卡用 TP 摊权重。
  • 「prefill 和 decode 哪个是 compute-bound、哪个 memory-bound?」——prefill 计算密集(定 TTFT),decode 访存密集(定 TPOT)。
  • 「SGLang 和 vLLM 区别?」——都做高吞吐推理;SGLang 以 RadixAttention 前缀树复用见长,vLLM 以 PagedAttention 显存管理见长。

易错点:

  • 把吞吐和延迟当成能同时拉满——它们通常此消彼长,加大并发抬吞吐往往牺牲单请求延迟。
  • 估显存只算权重、忘了 KV Cache。长上下文 + 高并发时 KV Cache 可能比权重还大,而且是它先把你 OOM。
  • 把 PagedAttention 和 continuous batching 混为一谈:前者管「KV Cache 怎么放」,后者管「请求怎么调度」,是两件事。
  • 以为 prefix caching 能降吞吐上限——它主要省的是 prefill 重算,收益落在 TTFT;对不共享前缀的请求没用。
  • gpu_memory_utilization 设太高(逼近 1.0)反而危险,没给激活和碎片留余量会运行中 OOM。

自测 1:PagedAttention 借鉴操作系统的分页思想,最核心解决的是什么问题?

A. 让模型权重占用更少显存权重靠量化(第 0028 课)去压,PagedAttention 管的是 KV Cache 不是权重。
B. 把 KV Cache 切成不连续的固定块、消除显存碎片,从而装下更多并发 ✅正确。分页化让 KV Cache 按需分配、物理不连续,几乎消除内外部碎片,省出的显存变成更多并发能力。
C. 加快单个矩阵乘法的计算速度它改变的是显存布局与分配,不是矩阵乘的算力。
D. 减少模型的层数以降低延迟与模型结构无关,不改层数。

自测 2:一个 Agent 服务,每个请求都带一段很长且完全相同的 System Prompt(工具定义+角色设定),你最该开启下面哪项来降低 TTFT?

A. 提高 tensor_parallel_sizeTP 是把权重切到多卡、解决单卡放不下,并不专门复用相同前缀。
B. 调低 gpu_memory_utilization那只会减少可用 KV 空间、降低并发,和复用相同前缀无关。
C. 开启 prefix caching,让相同前缀的 KV 只算一次后续复用 ✅正确。固定 System Prompt 是天然共享前缀,缓存命中后省掉这段 prefill 重算,直接降 TTFT。
D. 关闭 continuous batching关掉它只会降吞吐、让 GPU 空等,毫无帮助。
