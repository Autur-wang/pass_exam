大模型效果评估:指标与「让业务相信」

模型跑起来了,微调也做了,RAG 也接上了——然后老板问你一句:「它到底好不好?好多少?你怎么知道?」这节课不教花哨模型,专治这个「怎么知道」。它是大模型工程面试里最能拉开差距的一环:会调模型的人很多,能把效果说清楚、量出来、让业务信的人很少。

上节课(推理与服务)我们让模型跑得又快又稳:吞吐、延迟、显存都能用数字量化,压测一跑一目了然。先别往下看,试着回忆:「延迟 200ms」这种指标为什么好量?换成「这个回答写得好不好」,你还能一秒钟给出一个数字吗?差别到底在哪?

一、为什么评估「难」:开放生成没有标准答案

传统机器学习的评估是舒服的:图片分类,标签要么猫要么狗,预测对不对一目了然,准确率一算就完事。大模型的麻烦在于——它的主战场是开放生成。

「帮我写一封请假邮件」有几百种同样得体的写法;「总结这篇文章」的好摘要不止一个。没有唯一正确答案,你就没法用「等于/不等于标准答案」来打分。这就是评估之难的根:任务越开放,「对错」越退化成「好坏」,而「好坏」是连续的、主观的、依赖场景的。

但注意别走极端——不是所有大模型任务都开放。评估的第一步永远是把任务分类,因为不同类型能用的指标完全不同:

二、封闭任务:准确率 / 精确率 / 召回 / F1

如果你的大模型是拿来做分类或抽取的——判断评论是不是负面、从合同里抽出金额、识别工单属于哪个部门——那恭喜,你回到了经典机器学习的地盘,指标都是现成的、可信的、无争议的。

以二分类为例,把预测和真实交叉一下得到四类结果:真正例 TP、假正例 FP、真负例 TN、假负例 FN。四个基础指标:

准确率(Accuracy)
$$\text{Accuracy}=\frac{TP+TN}{TP+TN+FP+FN}$$
预测对的占全部。样本类别严重不均衡时会骗人:99% 都是负例,模型全猜负也有 99% 准确率,却毫无用处。
精确率(Precision)与召回率(Recall)
$$\text{Precision}=\frac{TP}{TP+FP}\qquad \text{Recall}=\frac{TP}{TP+FN}$$
精确率:「我说是正例的,有多少真是」——关心别误报。召回率:「真正的正例,我抓到了多少」——关心别漏报。两者常此消彼长。
F1 分数
$$F_1=2\cdot\frac{\text{Precision}\cdot\text{Recall}}{\text{Precision}+\text{Recall}}$$
精确率与召回率的调和平均。为什么用调和平均而不是算术平均?因为它对「短板」敏感——只要有一个特别低,$F_1$ 就被拉下去,逼你两个都不能太差。

什么时候看谁?这取决于犯哪种错更贵:

场景更怕的错优先看
垃圾内容拦截(宁可漏拦,别误伤正常用户)误报 FP精确率
疾病筛查 / 风险预警(宁可多查,别漏掉真患者)漏报 FN召回率
类别不均衡、两种错都要管都怕F1

面试追问「为什么不看准确率」,标准答案就是这张表里的「类别不均衡」+「两种错代价不同」。

三、生成任务:BLEU / ROUGE 的局限、人评、LLM-as-judge

到了摘要、翻译、对话这类生成任务,「等于标准答案」失效了。历史上人们发明了基于 n-gram 重叠的自动指标来近似:

BLEU
看生成文本与参考答案的 n-gram 精确率为主(生成里的词组,有多少出现在参考里),常用于机器翻译。
ROUGE
看 n-gram 召回率为主(参考答案里的词组,生成里覆盖了多少),常用于摘要。ROUGE-L 用最长公共子序列。

它们的价值是便宜、可自动、可复现,适合训练中快速回归对比。但局限也很硬,面试必须能说清:

  • 只看表面词重叠,不懂语义:换个同义说法、调个语序,意思一模一样,分数却可能暴跌。
  • 依赖参考答案的质量和数量:开放任务本就多解,单一参考答案会把其它同样好的答案判低。
  • 和人类判断的相关性有限:分数高不代表读起来好,尤其是长文本、对话、创作。

所以业界评开放生成,主要靠另外两条路:

人工评测
人来打分 / 两两对比
最贵、最慢、最可信
LLM-as-judge
用强模型当裁判打分
较便宜、可规模化
自动指标
BLEU / ROUGE 等
最便宜、只近似

人评:黄金标准,但要设计好

人评是最终裁判。常见两种形式:打分制(按维度给 1–5 分,如流畅度、事实正确性、有用性)和两两对比(A 和 B 哪个更好)。对比通常比打绝对分更可靠——人对「谁更好」的判断,比「这个值几分」稳定。关键是要有清晰的评分标准(rubric)、多人标注、算标注者一致性,否则打出来的分噪声大到没意义。

LLM-as-judge:用模型评模型

人评贵又慢,于是有了「让一个强模型来当裁判」:把问题、待评答案(甚至参考答案)喂给裁判模型,让它按 rubric 打分或做两两对比。它的好处是快、可规模化、成本远低于人评,和人类判断的一致性在很多场景下可用。但它有已知偏差,面试爱考:

  • 位置偏差:两两对比时,倾向于偏好放在前面(或后面)的那个——缓解办法是交换位置各评一次。
  • 长度 / 措辞偏差:容易偏好更长、更啰嗦或辞藻华丽的答案,哪怕内容没更好。
  • 自我偏好:裁判模型可能更偏爱和自己风格相近的输出。

务实的做法是组合拳:LLM-as-judge 跑全量做粗筛和监控,再抽样人审校准裁判本身可不可信。别把裁判模型的分当成绝对真理。

四、RAG 的评估:检索和生成要分开量

RAG(检索增强生成)是面试高频,它的评估有个专门的门道:问题可能出在检索,也可能出在生成,必须拆开看,否则你只知道「答得不好」,却不知道该修检索还是修 prompt。

检索段——本质是个信息检索问题,指标复用经典 IR:

  • 命中率 / Recall@k:前 $k$ 篇里有没有(有多少)真正相关的文档。检索的天花板——相关内容根本没召回来,后面生成再强也救不回。
  • 还可看 Precision@k(召回的前 $k$ 篇里有多少真相关)、以及考虑排序位置的指标(相关文档是否排在前面)。

生成段——在「给定召回文档」的前提下评答案质量,两个核心维度:

忠实度 / 事实一致性(Faithfulness / Groundedness)
答案里的每个说法,是否都能在召回的文档里找到依据。这是 RAG 的命门——直接对应「有没有幻觉、有没有瞎编」。答案再流畅,只要凭空捏造就是不合格。
答案相关度(Answer Relevance)
答案是否切题、真正回应了用户的问题,而不是答非所问或答一堆无关的正确废话。

拆开评的价值在于可定位:忠实度低 → 查 prompt 有没有强约束「只依据给定资料」、或生成模型能力不足;命中率低 → 修切分策略、embedding、检索召回。这套「分段归因」的思路,就是面试想听你说出来的东西。

五、业务落地:怎么「让业务相信」

这是本课的题眼,也是区分「调参工程师」和「能负责一条业务线的人」的地方。技术指标再漂亮,业务不信也白搭。让业务相信,靠三件事:

1. 把效果对齐到业务 KPI,而不是只报技术分

业务方听不懂也不关心 ROUGE、F1。他们关心的是他们的指标:客服机器人 → 人工转接率下降多少、会话解决率;搜索/推荐 → 点击率、留存;内容生成 → 采纳率、编辑修改量。你的工作是建立技术指标到业务指标的桥:先定义一个可量化、和业务目标挂钩的北极星指标,再证明模型能推动它。

2. A/B 测试:用对照给出因果证据

「上线后 KPI 涨了」不能证明是模型的功劳——可能是节假日、可能是别的改动。A/B 测试把用户随机分到对照组(旧方案)和实验组(新模型),同期对比,才能把效果归因到模型本身。这是让业务相信最硬的证据链:随机分组 + 同期对比 + 统计显著。上线前的离线评测只是「入场券」,线上 A/B 才是「判决书」。

3. 可解释 + 抽样人审:给信任兜底

数字之外,还要让业务看得见、敢负责:

  • 可解释:RAG 场景给出答案的引用来源,让业务能核对「这话是从哪篇文档来的」,信任度立刻不一样。
  • 抽样人审:定期抽一批真实线上样本,人工过一遍,既是质量兜底,也是给业务的「眼见为实」。
  • 盯 badcase 和长尾:平均分好看不代表没有灾难性错误。业务往往被一个恶性 badcase 吓退,主动暴露和治理 badcase 比只报平均分更能建立信任。

面试官会怎么问:

  • 「你微调 / 做了 RAG,效果怎么评判?」——极高频。先分任务类型,封闭任务报 P/R/F1,开放生成靠人评 + LLM-as-judge,RAG 拆检索(命中率)和生成(忠实度/相关度),最后落到线上 A/B 和业务 KPI。答出「分层评估」就赢了。
  • 「怎么向业务证明你的模型有用?」——对齐业务 KPI + A/B 对照给因果 + 引用来源可解释 + 抽样人审。别只报技术分。
  • 「BLEU/ROUGE 高就一定好吗?为什么大家还要人评?」——n-gram 重叠只看表面、不懂语义、和人类判断相关性有限;开放任务多解,单参考答案会误判。
  • 「LLM-as-judge 靠谱吗?有什么坑?」——快且可规模化,但有位置偏差、长度偏差、自我偏好;要交换位置、配 rubric、抽样人审校准。
  • 「RAG 答错了,你怎么定位是检索的锅还是生成的锅?」——分段评:先看检索命中率,再看生成忠实度,归因到具体环节。

易错点:

  • 类别不均衡时只报准确率——全猜多数类也能刷出高分,必须看 P/R/F1。
  • 把 BLEU/ROUGE 分数当成质量真值汇报给业务——它只是训练中的快速代理指标,不等于「用户觉得好」。
  • RAG 评估把检索和生成混在一起只报一个总分,答错了无从下手修。
  • 只做离线评测就宣称有效,不做线上 A/B——离线好不等于线上有业务收益。
  • 无脑信 LLM-as-judge 的绝对分而不做人审校准——它有系统性偏差,分数只在相对比较时更可靠。
  • 只报平均分,不看 badcase 和长尾——平均好看,一个恶性 case 就能让业务不敢上线。

自测 1:某风控模型识别欺诈交易,欺诈样本只占全部的 0.5%。下面哪个说法最合理?

A. 用准确率评估最合适,因为它综合了所有情况恰恰相反。0.5% 的正例下,模型全猜「非欺诈」就有 99.5% 准确率,却一笔欺诈都没抓到,准确率在这里严重误导。
B. 类别极度不均衡,应重点看召回率(别漏抓欺诈)并结合 F1,而非准确率 ✅正确。漏掉欺诈(FN)代价高,优先保召回;同时用 F1 平衡误报,准确率在极不均衡时会骗人。
C. 只看精确率就够了,别的都不用只看精确率会纵容漏报——模型只在最有把握时才报欺诈,大量真欺诈被放过,风控失效。
D. 用 BLEU 分数评估分类效果BLEU 是评生成文本 n-gram 重叠的,和分类任务不搭。

自测 2:你的 RAG 客服系统被投诉「有时一本正经地编造不存在的政策」。要针对性地量化和定位这个问题,最该看哪个指标?

A. 检索的 Recall@k命中率衡量的是「相关文档有没有被召回」,是检索段的指标;编造问题主要发生在生成段,即使文档召回对了,模型也可能不依据它瞎编。
B. 生成答案的忠实度 / 事实一致性(Faithfulness)✅正确。「编造不存在的政策」就是答案脱离了召回文档的依据,正是忠实度/事实一致性要量化的东西,直接对应幻觉。
C. 生成文本的 ROUGE 分数ROUGE 看和参考答案的 n-gram 重叠,既不针对「是否依据召回文档」,也抓不住语义层面的编造。
D. 推理延迟 P99延迟是性能指标,和「内容是否捏造」无关。

这节课的一手出处与深挖方向:

  • BLEU: a Method for Automatic Evaluation of Machine Translation(Papineni et al., 2002)——n-gram 精确率自动评测的原始论文。
  • ROUGE: A Package for Automatic Evaluation of Summaries(Lin, 2004)——摘要评测的经典指标。
  • Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena(Zheng et al., 2023)——系统研究用强模型当裁判的可行性与位置/长度等偏差,LLM-as-judge 的重要参考。
  • 想动手做 RAG 分段评估(忠实度/相关度/命中率),可深挖 RAGAS 等评估框架的指标定义与实现思路。
  • 下一步:效果不达标时,到底该微调还是上 RAG、各自要什么数据(第 0031 课)。

一句话记忆:先分任务(封闭用 P/R/F1、开放靠人评+LLM-judge、RAG 拆检索命中率与生成忠实度),再用对齐业务 KPI 的 A/B + 引用来源 + 抽样人审「让业务相信」。
