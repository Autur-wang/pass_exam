分块、Embedding 与向量库

RAG 效果的天花板,常常不在那个大模型,而在检索之前——文档怎么切、切完用什么模型编码成向量、向量又存进什么库、建什么索引。这三件事(Chunking → Embedding → Vector DB)决定了「含答案的那段话」到底能不能被召回。这节课把索引侧从头拆开,并落到面试最爱追的三问:chunk 大小怎么定、向量库怎么选、embedding 准不准怎么测。

上节课我们把 RAG 整条管线走通了:检索 → 拼进 prompt → 生成。留了个扣子——如果「检索」这一步永远拿不到含答案的那段文字,后面的 LLM 再强也是无米之炊。先别往下看,想一想:在「检索」发生之前,还有哪些更早的环节能悄悄决定它的上限?

一、索引侧的三级流水线

RAG 分两侧。离线索引侧把知识库灌进向量库;在线检索侧拿用户问题去查。二者共用同一个 embedding 模型和同一套向量空间——这是它们能对上话的前提。

三级里任何一级出问题,后面都救不回来:切错了,答案被劈成两半;编码模型选错,语义根本对不齐;索引参数太激进,该召回的漏掉了。逐级看。

二、分块:太大太小都是坑

为什么不能整篇文档当一块?因为检索的最小单位就是 chunk——你召回的是整块,也是拿整块去算一个向量。块的粒度,直接决定了「一个向量要概括多少信息」和「塞进上下文的东西有多干净」。

块太大
一个向量要概括好几个主题,语义被平均稀释;命中后塞进 prompt 的无关内容多,浪费上下文、还引噪声
块适中
一块 = 一个相对完整的语义单元;向量表达聚焦,召回精准,喂给 LLM 的上下文干净
块太小
上下文被切碎,一个完整答案可能横跨两块;块数暴涨,索引与存储成本上升

常见的四类切法(从粗到细)

策略怎么切优 / 劣
固定大小 + 重叠
(Fixed-Size + Overlap)		按字符/词/Token 数均匀切(如 ~500 Token),相邻块保留 10%–20% 重叠简单快;但易在句中、段中硬切,语义割裂。适合日志、代码这类结构混乱的数据
按句 / 递归字符
(Recursive)		先按段落,不够再按换行、句子、空格逐层退让,尽量在自然边界断开兼顾长度上限与自然边界,通用性强,是常用基线
语义分块
(Semantic)		算相邻句子 embedding 的余弦相似度,低于阈值处判定「话题变了」再切块内主题高度一致;但要额外算一遍 embedding,成本高。适合主题跳跃明显的文档
按结构
(Structure-aware)		顺着 Markdown/HTML/PDF 的标题、章节、表格等原生结构切保留层次信息,可把「所属章节标题」作为元数据带上;依赖文档本身结构规整

工程上一个稳妥的顺序:先用递归字符分块做基线,再在此之上叠语义判断——即在相邻切点处比较前后句的相似度,低于阈值才真正断块。重叠(overlap)的作用是让跨边界的上下文在两块里都出现一次,降低「答案正好被切在缝上」的概率;但重叠不是越大越好,冗余会推高存储和后续拼接的 token 成本。

三、Embedding:把文本压成一个可比较的向量

Embedding 模型把一段文本映射成定长稠密向量 $\mathbf{v}\in\mathbb{R}^{d}$,使得语义相近的文本,向量也相近。检索时最常用的「近」是余弦相似度:

余弦相似度(Cosine Similarity)
$$\cos(\mathbf{u},\mathbf{v})=\frac{\mathbf{u}\cdot\mathbf{v}}{\lVert\mathbf{u}\rVert\,\lVert\mathbf{v}\rVert}$$
只看两个向量的方向夹角,不受模长影响,取值 $[-1,1]$。多数句向量模型正是按余弦目标训练的,所以检索时也该用余弦。

一个关键工程细节:如果先把向量做 L2 归一化($\lVert\mathbf{v}\rVert=1$),那么

$$\cos(\mathbf{u},\mathbf{v})=\mathbf{u}\cdot\mathbf{v}\quad(\text{当}\ \lVert\mathbf{u}\rVert=\lVert\mathbf{v}\rVert=1)$$

归一化之后,余弦就退化成内积——而内积有高度优化的矩阵乘实现,更快。所以很多向量库把「余弦度量」实现为「归一化 + 内积」。

选型看什么

  • 语言与领域:中文场景优先选中文/多语训练充分的模型(如 BGE 系列);跨语言检索要选多语模型。
  • 维度 $d$:维度越高表达力通常越强,但存储与检索开销也越大(每个向量 $d$ 个 float)。是精度与成本的权衡,不是越高越好。
  • 最大输入长度:必须能覆盖你的 chunk 长度,否则超出部分被截断,尾部信息丢失。这也反过来约束了 chunk 上限。
  • 对称 vs 非对称检索:query 通常短、doc 通常长,分布不同。BGE 这类模型对 query 侧要求加一段任务指令前缀(instruction),query 和 passage 分别编码——忘了加指令会掉点。

四、向量库:库、库、库,定位差很多

面试常见的坑是把它们当成同一类东西。其实横跨了「一个库函数」到「一套分布式数据库」到「托管云服务」。看清定位再谈选型:

系统定位典型场景
Faiss相似度搜索库(C++/Python),不是完整数据库;持久化、分布式、元数据过滤这些要自己在外面补把 ANN 能力嵌进自己的服务;研究、大规模离线检索
Milvus面向生产的分布式向量数据库,支持多种索引类型、数据分区与容错、内存+持久化结合大规模、多模态检索,需要横向扩展与运维能力的生产系统
Chroma轻量、开发者友好,可嵌入/本地运行,API 简单快速原型、中小规模、面向 LLM 应用的本地开发
Pinecone闭源托管 SaaS,免运维,按用量付费不想自己维护基础设施、要快速上线的团队
LanceDB嵌入式、类似 SQLite,基于 Lance 列式存储;数据版本管理、零拷贝更新桌面/边缘、数据隐私要求高、需要本地跑的场景

选型的第一刀不是比 QPS,而是问需求:要不要独立部署与横向扩展(Milvus)?想彻底免运维(Pinecone)?只是本地原型(Chroma / LanceDB)?还是只要一个能塞进现有服务的 ANN 内核(Faiss)?规模、运维成本、元数据过滤和更新频率,通常比单纯的检索速度更早地决定答案。

五、索引类型:为什么要「近似」

暴力法(Flat)是把 query 和库里每一个向量都算一遍距离,结果精确,但在千万级向量上太慢。所以生产上用近似最近邻(ANN):牺牲一点点召回,换回巨大的速度。三种主流思路:

索引一句话原理取舍
IVF
倒排文件		先把向量聚成若干簇(k-means 出中心点),查询时只搜最近的 nprobe 个簇——粗筛 + 细搜nprobe 越大越准越慢;对「先按元数据强过滤再搜」的场景友好
HNSW
分层小世界图		把向量连成多层可导航图,从稀疏的高层入口逐层下沉贪心逼近最近邻召回高、查询快;代价是构建慢、内存占用大
PQ
乘积量化		把高维向量切成子段,各子段用码本量化压缩,大幅省内存(常与 IVF 组合成 IVF-PQ)内存友好;量化有损,精度略降,常用于超大规模

粗略的决策直觉:要极致召回且内存够 → HNSW;要强过滤 / 稳定粗筛 → IVF 系列;内存 / 成本敏感 → 叠 PQ 压缩。注意这些是「典型倾向」,具体还要看数据规模和实测。

六、怎么量化「准不准」

面试问 embedding 或检索质量,你不能只说「感觉还行」。要能报出可量化的指标。检索最核心的是召回率 Recall@k:

Recall@k
$$\text{Recall@}k=\frac{\lvert\,\text{top-}k\ \text{命中的相关块}\,\rvert}{\lvert\,\text{全部相关块}\,\rvert}$$
在一批标好「哪些块是相关的」的评测集上,看检索返回的前 $k$ 个里,盖住了多少应该被召回的块。RAG 里 Recall 常比 Precision 更受关注——只要含答案的块进了 top-k,后面的重排和 LLM 还有机会;漏掉了就彻底没机会。

此外常配合看排序质量,如 MRR(第一个相关结果排名倒数的均值)、nDCG(带位置折扣的增益)。评估 embedding 模型本身,则可以看它在公开基准(如 MTEB,涵盖检索、聚类、重排等多类任务)上的表现,再在自己业务数据上小规模标注一批 query→相关块,复算 Recall@k——公开榜单只是起点,业务分布才是终审。

def chunk_text(text, size=500, overlap=80):
    # 定长切分 + 相邻块重叠,维持跨边界的上下文连续性
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start += size - overlap        # 回退 overlap,产生重叠
    return chunks

import numpy as np
def l2_normalize(x):
    return x / (np.linalg.norm(x, axis=-1, keepdims=True) + 1e-9)

# 归一化后,余弦相似度 == 内积,可用一次矩阵乘批量打分
q    = l2_normalize(embed(["中央处理器的作用是什么"]))   # [1, d] query 向量
docs = l2_normalize(embed(chunk_list))                    # [N, d] 文档块向量
scores = docs @ q.T                                       # [N, 1] 内积即余弦
top_k  = scores.squeeze().argsort()[::-1][:5]             # 取 top-5

把「量化召回」也写成代码——这是你回答「怎么测」时最有说服力的东西:

def recall_at_k(retrieved_ids, gold_ids, k):
    # retrieved_ids: 检索返回的块 id(按相关度降序)
    # gold_ids:      人工标注的相关块 id 集合
    hit = len(set(retrieved_ids[:k]) & set(gold_ids))
    return hit / len(gold_ids)          # 命中的相关块 / 全部相关块

# 在整个评测集上取平均,得到该配置(某分块 + 某 embedding + 某索引)的 Recall@k
avg = sum(recall_at_k(r, g, k=5) for r, g in eval_set) / len(eval_set)

面试官会怎么问:

  • 「chunk 大小怎么定?」——没有万能值。先说权衡(太大稀释语义+引噪声,太小切碎上下文+涨成本),再说方法:受 embedding 最大长度约束,用递归/语义分块 + 适度 overlap 做基线,最后用 Recall@k 在业务数据上调,而不是拍脑袋。
  • 「向量库怎么选?」——先分清定位(Faiss 是库不是库=数据库;Milvus 分布式;Chroma/LanceDB 轻量本地;Pinecone 托管),再按规模、运维、元数据过滤、更新频率来挑,别一上来比 QPS。
  • 「embedding 准不准怎么测?」——公开基准(如 MTEB)看通用能力,自己标注 query→相关块算 Recall@k / MRR / nDCG 看业务能力;强调业务分布优先。
  • 「为什么用余弦而不是欧氏距离?」——句向量多按余弦目标训练,只看方向不看模长;归一化后余弦等于内积,还能用高度优化的矩阵乘。
  • 「IVF 和 HNSW 区别?」——IVF 聚簇粗筛+细搜、靠 nprobe 调速度/召回、利于强过滤;HNSW 图结构、召回高查询快但内存大构建慢。

易错点:

  • 把 Faiss 当成完整数据库——它是相似度搜索库,持久化、分布式、元数据过滤要自己补;别在面试里说「用 Faiss 存业务数据并做条件过滤」。
  • 模型按余弦训练,检索却用未归一化向量的内积排序:排序会被模长干扰,偏离余弦语义。要么先归一化,要么明确用库的 cosine 度量。
  • 索引侧和检索侧用了不同的 embedding 模型/版本——向量空间对不齐,检索结果全乱。二者必须严格一致。
  • 用 BGE 这类模型时忘了给 query 加指令前缀、或对 query 和 passage 用了不该用的处理,会平白掉点。
  • overlap 不是越大越好:冗余推高存储和拼接 token 成本;chunk 也不是越小越精准,切碎会让完整答案跨块丢失。

自测 1:把 chunk 切得非常大(比如整篇长文档当作一块),最可能带来的问题是?

A. 分块数量太多,索引构建会变得很慢相反,块越大数量越少,索引反而更小;这是块太小才有的问题。
B. 无法为这一块计算 embedding只要不超模型最大长度就能编码;真超了是截断问题,不是「无法计算」。
C. 一个向量要概括多个主题,语义被平均稀释,检索精度下降,且命中后塞进上下文的无关内容变多 ✅正确。这正是「块太大」的核心代价:向量表达不聚焦 + 上下文引入噪声、浪费预算。
D. 一定会超出所有 embedding 模型的最大输入长度「所有」「一定」过绝对——不同模型上限不同,大块未必都超限。

自测 2:某 embedding 模型按余弦相似度训练。检索时你直接用未归一化向量的内积来排序,可能出现什么?

A. 内积和余弦完全等价,没有任何影响只有在向量都已 L2 归一化时二者才相等;未归一化时不成立。
B. 排序会被向量模长干扰,模长大的向量被系统性地排前,偏离余弦想表达的方向相似度 ✅正确。内积 = 余弦 × 两者模长,模长把方向信号污染了;先归一化即可让内积回到余弦。
C. 检索速度会显著变慢内积本身就是快的算子,速度不是这里的问题,受影响的是排序正确性。
D. 召回率一定会掉到 0「一定为 0」过绝对——排序会失真、召回可能下降,但通常不会归零。

这节课的一手出处与深挖方向:

  • Sentence-BERT(Reimers & Gurevych, 2019)——用双塔结构 + 余弦目标训练句向量的奠基工作,解释了「为什么检索用余弦」。
  • C-Pack / BGE(Xiao et al., 2023)——BGE 系列中文/通用 embedding 的资源与训练方法,含 query 指令前缀的用法。
  • MTEB: Massive Text Embedding Benchmark(Muennighoff et al., 2022)——评测 embedding 模型的综合基准,选型时的公开参照。
  • HNSW(Malkov & Yashunin, 2018)与Product Quantization(Jégou, Douze & Schmid, 2011)——两类 ANN 索引的原始论文。
  • 下一步:光靠向量召回不够,如何叠加 BM25 稀疏检索做混合检索,再用 Cross-Encoder 重排(第 0023 课)。

一句话记忆:切得好、编得准、存得对,检索才有天花板——chunk 大小用 Recall@k 调,向量库先分清定位再选,embedding 准不准靠标注数据实测。
