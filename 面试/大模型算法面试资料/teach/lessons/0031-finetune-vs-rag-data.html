微调 vs RAG 抉择与数据工程

「这个业务需求,你打算微调还是上 RAG?」——这是大模型岗几乎必问的一道开放题。它考的不是你会不会跑 LoRA,而是你能不能把需求拆成「缺知识」还是「缺能力」,再算清成本、讲清数据从哪来、怎么清。这节课(也是本课程最后一课)把决策框架和数据工程一次讲透。

前面几课我们分别讲过:LoRA/PEFT 怎么用少量参数改模型,RAG 怎么把外部文档检索进上下文,还有评估怎么做。先别往下看,试着回答:如果老板要求「让模型能回答我们公司最新的内部规章」,你的第一反应是微调还是 RAG?为什么?

一、决策框架:先问「缺的是知识,还是能力」

面试官最想看到的,不是你背了一堆「RAG 优点」,而是你手里有一把能当场做判断的尺子。这把尺子只有一句话:

要改的是「模型知道什么」,用 RAG;要改的是「模型怎么做、什么风格、什么格式」,用微调。

为什么这么分?因为两者动的是模型的不同部位:

  • RAG 动的是「输入」——模型参数一个字节都不改,只是在推理时把相关文档塞进上下文,让模型「开卷考试」。所以它天生擅长处理时效性强、私域、需要溯源的知识:今天更新的政策、你司的内部 wiki、要求「答案必须给出处」的场景。文档一改,索引一更,模型立刻「知道」新事,不用重训。
  • 微调动的是「参数」——把某种行为模式烙进权重里:固定的输出格式(必须吐 JSON)、特定的语气人设(客服话术)、某类任务的推理能力(把一类题目做对)。这些是「怎么做」,靠往上下文塞文档是塞不出来的。

为什么「结合」才是常态

把两句合起来想就懂了:你希望客服机器人既用你司统一的话术和格式回答(能力/风格,微调),又能引用到今天刚更新的退款政策(知识,RAG)。单靠任何一个都缺一块。所以标准答法是:「我会先判断缺口在哪一侧,大多数生产系统两者都要——微调定人设与格式,RAG 供实时知识与出处。」

维度RAG微调(SFT/LoRA)
改的是输入(上下文),参数不动模型参数
擅长知识:时效、私域、可溯源能力、风格、输出格式
知识更新改文档/重建索引即可,近实时要重新准备数据 + 重训
可溯源天然能给出处(引用检索片段)难,知识揉进权重说不清来源
主要成本索引构建与维护、向量库、每次检索延迟标注数据 + 算力(训练一次性,推理更省)
典型风险检索不准 → 喂错料;上下文变长变贵数据少易过拟合、灾难性遗忘("SFT 后变傻")

二、成本对比:两种「贵」的方式不一样

面试官追问成本时,想听的是你知道钱花在不同的地方,而不是笼统说「RAG 便宜、微调贵」。

  • RAG 的成本是「持续的运维」:要搭并维护向量索引(见第 0028/0029 课的 ANN 索引选型),文档变了要重新分块、重新向量化、重建索引;每次请求都要跑一次检索,还会因为把检索片段拼进 prompt 而拉长上下文,推理 token 变多、延迟变高。
  • 微调的成本是「前期的数据 + 算力」:训练本身是一次性投入(数据准备往往比训练更费人力),但训练完之后推理时不需要额外检索、上下文更短。PEFT/LoRA 正是为了把这里的算力门槛压下来——只训练少量低秩参数,而不是全参数微调。

一句话记法:RAG 把成本摊到每一次调用和长期维护上,微调把成本压在训练前的数据与算力上。知识变得越频繁,RAG 的相对优势越大;行为要求越固定、调用量越大,微调摊薄后越划算。

三、数据工程:微调成败的地基

选了微调,真正的活儿才开始——大部分微调项目的瓶颈不在训练,在数据。源材料里那句「为什么 SFT 之后感觉 LLM 傻了」,根因通常就出在数据:分布偏移、数据太少导致过拟合。所以数据工程这一环,面试官会盯着问。

1）采集:数据从哪来

  • 私域已有数据:历史工单、客服对话、内部文档、日志——最贴合业务,但通常脏、格式乱。
  • 人工标注/编写:针对目标任务专门写「指令 → 期望回答」对,质量最高、最贵。
  • 合成/增强:用更强的模型或规则生成、对已有样本做同义替换/改写扩充(源材料提到的数据增强)。要小心合成数据的分布和质量。

2）规模与配比

SFT 不是越多越好。数据太少、模型容量又大,容易过拟合到这批样本、丢掉预训练学到的通用能力(灾难性遗忘,也就是「变傻」)。反过来,质量差的大批量数据比少量精标更糟。经验方向是:宁精勿滥,覆盖任务的各类情形,而不是盲目堆量。(具体数字随任务和模型而变,面试时讲权衡,不要背死数。)

3）清洗与去重(高频考点)

「你怎么给微调数据去重?」是很爱问的一问。要分两层答:

  • 精确/近似去重:完全相同或差几个字的样本,用哈希(如 MinHash)、编辑距离等快速去掉。
  • 语义去重:意思一样但措辞不同的样本(「怎么退款」vs「退款流程是什么」),精确匹配抓不到。做法是把样本过 embedding,算余弦相似度,超过阈值的判为重复,保留一条:
$$\operatorname{sim}(a,b)=\cos(\theta)=\frac{\mathbf{e}_a\cdot\mathbf{e}_b}{\lVert\mathbf{e}_a\rVert\,\lVert\mathbf{e}_b\rVert}$$

$\mathbf{e}_a,\mathbf{e}_b$ 是两条样本的句向量;$\operatorname{sim}$ 越接近 1 越像。设一个阈值(如 0.9 上下,具体要调)判重。

为什么非去重不可?重复样本会让模型在这些例子上过度加权,加剧过拟合、扭曲数据分布,还浪费算力。

4）标注质量:正负样本与「多师傅」经验统一

  • 正负样本:除了「好答案」(正样本),准备「坏答案」(负样本)对偏好类训练(如 DPO/RLHF 的偏好对)很关键——模型要学会「什么不该答」。
  • 多标注人一致性:多个「师傅」各写各的,风格、判断口径会打架。必须先立统一的标注规范,把多人的经验对齐成一套标准,否则模型学到的是相互矛盾的信号,越训越乱。这本质上和「Q、K 用不同权重」一样——信号不一致,学出来的就是噪声。

5）数据飞轮:让系统越用越好

数据工程不是一锤子买卖。上线后把线上真实反馈回流——用户点赞/点踩、人工纠正过的回答、被 RAG 检索命中的高频问题——清洗后补进训练集,再做下一轮微调。这个「上线→收集反馈→回流→再训」的闭环叫数据飞轮(Data Flywheel),是把 demo 熬成好产品的核心机制。

RAG(检索增强生成)
不改模型参数,推理时先检索相关文档、拼进上下文再生成。改的是「模型看到什么输入」,擅长时效/私域/可溯源的知识。
微调(Fine-tuning / SFT)
用任务数据继续训练、更新模型参数(全参数或 PEFT/LoRA)。改的是模型的行为:风格、格式、特定能力。
语义去重
用句向量余弦相似度 $\cos(\theta)=\dfrac{\mathbf{e}_a\cdot\mathbf{e}_b}{\lVert\mathbf{e}_a\rVert\lVert\mathbf{e}_b\rVert}$ 判定「意思重复」的样本并合并,抓精确匹配抓不到的换句话重复。
数据飞轮
「上线→收集真实反馈→清洗回流→再训练」的自增强闭环,让系统随使用不断变好。

语义去重的最小骨架(思路示意,阈值需按数据实测调):

import numpy as np

def dedup_by_semantics(texts, embed_fn, threshold=0.9):
    embs = embed_fn(texts)                       # [N, d]
    embs = embs / np.linalg.norm(embs, axis=1, keepdims=True)
    keep, kept_embs = [], []
    for i, e in enumerate(embs):
        # 与已保留样本的最大余弦相似度
        if kept_embs and max(k @ e for k in kept_embs) >= threshold:
            continue                             # 太像,视为重复,丢弃
        keep.append(texts[i]); kept_embs.append(e)
    return keep

注意:$N$ 大时两两比较是 $O(N^2)$,生产里会先用 ANN 索引(见第 0028 课)找近邻,再判阈值。

面试官会怎么问:

  • 「这个需求你微调还是 RAG?」——先拆「缺知识还是缺能力」;知识/时效/溯源→RAG,风格/格式/能力→微调,生产多为结合。别一上来就选边。
  • 「RAG 和微调各自成本花在哪?」——RAG 是索引维护 + 每次检索 + 长上下文;微调是前期数据 + 一次性算力(PEFT 压算力)。
  • 「微调数据从哪来?怎么保证质量?」——私域/标注/合成三路;立统一标注规范对齐多标注人,配正负样本。
  • 「怎么给数据去重?」——精确/近似(哈希、编辑距离)+ 语义去重(embedding 余弦相似度过阈值)。
  • 「上线后怎么持续变好?」——数据飞轮:线上反馈回流→清洗→再训。

易错点:

  • 把 RAG 和微调当成非此即彼的单选题——生产系统常常两者都用,答「结合」并说清各管一块才到位。
  • 指望「微调」来注入频繁变动的知识——知识一变就得重训,时效性场景应优先 RAG。
  • 去重只做精确匹配——换句话说的重复(语义重复)漏掉,仍会过拟合;必须补语义去重。
  • 盲目堆数据量——数据少 + 模型大易过拟合导致"变傻",但脏数据堆多更糟,质量优先于数量。
  • 忽视多标注人口径不一致——不统一规范,训练信号自相矛盾,越训越乱。

自测 1:业务要求「模型必须能回答每天更新的公司公告,并给出处链接」。最合适的首选方案是?

A. 全参数微调,把公告写进权重知识天天变,微调要反复重训,且难给出处,不合适。
B. RAG:把公告入库建索引,检索后拼上下文并附引用 ✅正确。时效强 + 需溯源正是 RAG 的主场,改文档即更新,还能天然给出处。
C. 只做 LoRA 微调,不用外部检索同样无法解决时效与溯源问题。
D. 增大上下文窗口,把所有公告全塞进 prompt公告量大且天天增,全塞不现实也贵,仍需检索筛选。

自测 2:下面哪种去重能抓到「怎么申请退款」和「退款要怎么操作」这类换句话说的重复?

A. 完全字符串相等去重两句字面不同,精确匹配抓不到。
B. MinHash / 编辑距离近似去重能抓字面接近的,但换了措辞、词序变化大时仍会漏。
C. 按样本长度分桶后去重长度相近不代表语义相同,无法判重。
D. 语义去重:句向量余弦相似度超阈值判重 ✅正确。embedding 表征语义,余弦相似度能识别措辞不同但意思一样的重复。

这节课的一手出处与深挖方向:

  • Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks(Lewis et al., 2020)——RAG 的原始论文,理解「为什么知识类任务靠检索」。
  • LoRA: Low-Rank Adaptation of Large Language Models(Hu et al., 2021)——PEFT 主流方法,微调侧的成本为何能压下来看这里。
  • 去重方法可顺着 MinHash / LSH(近似去重)与句向量检索(语义去重)两条线深挖,和第 0028 课 ANN 索引连起来看。
