双向链表:多一根指针换来什么

单链表只能一路向前,回头无门。双向链表给每个节点再加一根 prev 指针——看似只多存一个字段,却解锁了单链表办不到的两件事:双向遍历,以及「拿到一个节点就能 O(1) 删掉它自己」。这节课算清这笔「一根指针」的买卖,并看它如何撑起面试里的当红系统题——LRU 缓存。

先回忆:上一课单链表的自测里我们卡在一处——只给你指向中间某节点的指针,想删掉它却拿不到前驱,只能 O(n) 从 head 找回来。先想想:如果每个节点都随身记着自己的前驱,这个难题会怎样?

一、直觉:每颗珠子系了两根绳

双向链表的节点是 [prev | 数据 | next]:next 指后一个,prev 指前一个。第一个节点的 prev 和最后一个节点的 next 都是 NULL。付出的代价一目了然——每个节点多存一根指针(空间),而且每次插入删除要同时维护两组指针(更容易写错)。换来的红利有两条:任意节点都能往回走(双向遍历),以及下面这条杀手锏。

二、杀手锏:已知节点,O(1) 删除自己

在单链表里删一个节点,难点是找它的前驱(O(n))。双向链表里,前驱就存在节点自己的 prev 字段里——删除只需:node.prev.next = node.next;node.next.prev = node.prev。两句话搞定,O(1),和链表多长无关。这条性质看着不起眼,却是 LRU 缓存能做到 O(1) 的关键齿轮。

三、关键定义

双向链表(Doubly Linked List)
每个节点同时持有 next 与 prev 两根指针的链表,支持双向遍历;已知节点时插入/删除均 O(1)。避免:与单链表混称「链表」而不区分。
哨兵节点 / 哑节点(sentinel / dummy)
在头尾各放一个不存数据的占位节点,让「在头部插」「删末尾」也变成「在两个真实节点之间操作」,从而消除空表、首节点、尾节点的边界特判。避免:把哨兵当作真实数据参与计数。
LRU(Least Recently Used)
一种缓存淘汰策略:容量满时淘汰「最久未被访问」的项。经典实现 = 双向链表(记访问顺序) + 哈希表(O(1) 定位节点)。

四、复杂度:与单链表并排看

操作单链表双向链表
随机访问 value_at(i)O(n)O(n)
头部插入 / 删除O(1)O(1)
向前遍历(找前驱)O(n)O(1)
已知节点处删除该节点O(n) (需找前驱)O(1)
每节点额外空间1 指针2 指针

随机访问依然是 O(n)——多的那根指针只解决「方向」和「找前驱」,解决不了「没有连续内存」这个根子上的问题。所以双向链表和单链表一样,天生不擅长按下标读取。

面试怎么考。双向链表本身很少单独出题,它几乎总是作为更大结构的零件登场:

  • LRU 缓存(必考系统/数据结构题):双向链表按「最近使用」排序,访问过的节点 O(1) 摘下、挪到头部;容量满就 O(1) 删尾部。哈希表存 key → 节点指针,让 get/put 都 O(1)。这道题几乎是「双向链表 + 哈希表」组合的标准答卷。
  • 浏览器前进 / 后退、编辑器 undo-redo:天然的双向序列,当前位置一个指针,前后自由移动。
  • 被追问「怎么去掉边界特判」:答哨兵节点。加了 dummy head / tail 后,插入删除永远发生在两个节点之间,不必再单独判断空表和首尾——面试官很吃这一手。

指针更新顺序写错就断链。删除节点 x 时,必须先用 x.prev 和 x.next 把两侧接上,顺序要能自洽;插入时同理,新节点的 prev/next 与两侧邻居的指针要成对更新,漏掉任何一根都会让链表半路断掉或反向。养成习惯:改指针前先把要用到的邻居暂存到局部变量,再动手改。

另一个坑:别以为多了 prev 就能随机访问 O(1)。双向链表的随机访问仍是 O(n),它只是遍历方向多了一个,没有绕过「内存不连续」这个根本限制。

带走这一条:那根 prev 指针买到的,是「已知节点即可 O(1) 摘除/前移」的能力。正是这个能力,让双向链表成为 LRU 缓存的骨架——记住「双向链表管顺序、哈希表管定位」这对搭档,一道经典系统题就有了答案。

在单链表实现基础上升级为双向链表,重点体会两处差异:

① 给节点加 prev 字段,插入/删除时成对维护 next 与 prev;② 加一对哨兵 head/tail,重写 push_front / push_back / erase(node),验证空表、单元素等边界不再需要特判。

进阶:用「双向链表 + 哈希表」实现一个容量固定的 LRU 缓存,支持 O(1) 的 get(key) 与 put(key, value)。

五、自测题

Q1:LRU 缓存为什么要「双向链表 + 哈希表」两件套?只用其中一个不行吗?

两个各补对方的短板。只用双向链表:能 O(1) 维护访问顺序(最近用的挪到头、满了删尾),但要找「key 对应的节点」得 O(n) 遍历。只用哈希表:能 O(1) 按 key 定位,但哈希表不记顺序,没法知道谁「最久未用」。合起来:哈希表 key → 节点 负责 O(1) 定位,双向链表负责 O(1) 维护顺序与淘汰——正因为双向链表「已知节点就能 O(1) 摘除」,两者才能严丝合缝。

Q2:相比单链表,双向链表多付出的主要成本是什么?(不止一项)

两项:空间——每个节点多存一根 prev 指针;维护复杂度——每次插入/删除要同时更新两组指针,更容易写错、断链。它并没有改善随机访问(仍 O(n)),也没有降低时间量级——买到的只是「方向」和「已知节点 O(1) 删除」这两项能力。哨兵节点能缓解维护复杂度带来的边界 bug,但抵不掉那根多出来的指针。
