并发原语:锁、信号量与死锁

上一课留了个病:多个线程共享内存,同时改一份数据就会出错。这节课开药方——互斥锁、信号量、条件变量是并发编程的三味基础药材。但药也有副作用:用不好会得死锁。面试最爱考的两件事,就是「用这些原语实现生产者-消费者」和「说清死锁的四个条件、怎么破」。

先回忆 进程与线程的结论:同一进程的线程共享堆和全局数据,通信快是它的红利,但我们当时做过一个实验——两个线程各给同一个计数器自增一百万次,结果小于两百万。先自己说清:那一百万次自增里,到底哪一步「丢」了?为什么是「共享」导致的?这节就从治这个病开始。

一、病根:竞态条件与临界区

看似原子的 count++,其实是三步:读出 count → 加 1 → 写回。两个线程交错执行时,可能都读到同一个旧值 100,各自加到 101 写回——两次自增只涨了 1,另一次被覆盖丢失。这种「结果取决于线程执行的先后顺序」的 bug,叫竞态条件(race condition)。

出问题的那段「同一时刻最多只能有一个线程进入」的代码,叫临界区(critical section)。解法的核心思想只有一句:给临界区上一把锁,保证互斥(mutual exclusion)——同一时刻只放一个线程进去,其余的排队等。

二、三味基础药:锁、信号量、条件变量

原语解决什么一句话
互斥锁 mutex互斥只有 0/1 两态:一把钥匙,谁拿到谁进临界区,用完归还。
信号量 semaphore限量 / 计数一个计数器 + 一队等待者;可允许最多 N 个线程同时进(N=1 时退化成互斥锁)。
条件变量 condvar等待某条件成立让线程「睡下」直到被别人唤醒(如队列「非空」时才唤醒消费者),配合锁使用。
读写锁 rwlock读多写少允许多个读者并行,但写者独占。读远多于写时比互斥锁并发更高。

它们的关系值得记牢:互斥锁是信号量在 N=1 时的特例;信号量既能做互斥(N=1),又能做「限量」(如连接池最多 10 个,初值 10);条件变量不解决互斥,它解决等待——线程在条件不满足时高效睡眠,不空转烧 CPU(否则就是浪费的「忙等」busy-waiting)。

三、副作用:死锁与它的四个条件

加锁能治竞态,但用力过猛会得死锁(deadlock):两个及以上线程互相等着对方手里的锁,谁也不肯先松手,全体永久卡死。经典场景:线程 A 拿了锁 1 去抢锁 2,线程 B 恰好拿了锁 2 去抢锁 1。

死锁成立必须同时满足四个条件(Coffman 条件),缺一即不会死锁——所以破坏任意一条就能预防:

  1. 互斥:资源同一时刻只能被一个线程占用。(锁的本性,通常不好破)
  2. 持有并等待:线程持有一个资源的同时,又去等另一个。→ 破法:一次性申请全部所需锁,拿不齐就不拿。
  3. 不可抢占:资源不能被强行夺走,只能自愿释放。→ 破法:抢不到就主动放掉已持有的,回退重试。
  4. 循环等待:存在一个首尾相接的等待环。→ 破法(最常用):给所有锁定义全局顺序,永远按同一顺序加锁,环就无法形成。
竞态条件(Race Condition)
程序结果依赖于多个线程执行的相对时序,导致不确定的错误。根因是对共享数据的非原子并发访问。
临界区(Critical Section)
访问共享资源、同一时刻只允许一个线程执行的代码段。用互斥保护它。
互斥锁 / 信号量(Mutex / Semaphore)
互斥锁是 0/1 的独占锁;信号量是带计数的许可,允许最多 N 个线程进入,N=1 时即互斥锁。
条件变量(Condition Variable)
让线程在某条件不满足时睡眠、待他人改变条件后被唤醒的机制;必须与锁配合,避免忙等。
死锁(Deadlock)
多个线程互相等待对方持有的资源而永久阻塞;当且仅当同时满足互斥、持有并等待、不可抢占、循环等待四条件。避免把死锁与「活锁」(不停重试却都不进展)混为一谈。

面试怎么考。

  • 「什么是死锁,怎么避免?」——先说四个条件同时成立才死锁,再说「破坏其一即可,工程上最常用的是按固定全局顺序加锁破坏循环等待」。能说出四条件 + 至少一种破法,就是满分答法。
  • 用原语实现生产者-消费者:一个有界缓冲区,生产者满了要等、消费者空了要等。标准解是「互斥锁保护缓冲区 + 两个条件变量(非满/非空)」,或「两个信号量(空位数/产品数)+ 一个互斥锁」。手写时最容易错在唤醒和加锁的配合。
  • 进阶概念:原子操作、CAS(compare-and-swap)、无锁数据结构、乐观锁 vs 悲观锁——问你除了加锁还有没有别的路子。

死锁四条件是「必要条件的合取」——四条同时成立才死锁,破坏任意一条就不会死。常见错误是把它当成「充分条件」或漏掉「同时」,以及答不出具体破法。记住最实用的一招:所有线程按同一全局顺序加锁,循环等待就构造不出来。

另一个坑:锁粒度不是越细越好,也不是越粗越好。粗锁(一把大锁锁住一切)简单、不易死锁,但并发度低,线程都在排队;细锁并发高,却更容易出现「多把锁的加锁顺序」问题而死锁,也更难写对。这是个工程权衡,面试答「视竞争程度取舍」比一口咬定某种好更稳。还要能区分死锁(都卡住不动)和活锁(都在动、都在退让重试却没人前进)。

用锁 + 条件变量实现一个线程安全的有界阻塞队列(生产者-消费者的核心):

put(x) —— 加锁;当队列已满,在「非满」条件变量上等待(会自动放锁睡下);入队后唤醒「非空」;解锁。
take() —— 加锁;当队列为空,在「非空」条件变量上等待;出队后唤醒「非满」;解锁返回。

关键点:等待条件一定用 while 而非 if 复查(防止「虚假唤醒」和被唤醒后条件又被别人抢走)。写完开 3 个生产者 + 2 个消费者跑久一点,验证不丢数据、不越界、不死锁。有余力再用两个信号量重写一遍对比。

带走这一条:共享内存的病是竞态,药是互斥(锁/信号量);但药过量会死锁——四个条件同时成立才发病,按固定全局顺序加锁破坏「循环等待」是最实用的解。条件变量管的是「等待」,不是「互斥」,记牢它俩分工不同。

四、自测题

Q1:一个系统出现了死锁。下面哪种做法一定能预防这类死锁?
A. 把所有锁换成更快的自旋锁
B. 增大线程池,让线程更多
C. 规定所有线程都按同一个全局固定顺序申请锁
D. 给每把锁加更详细的日志

C。死锁需要四条件同时成立,破坏任意一条即可预防。C 破坏的是「循环等待」——所有线程按同一顺序加锁,等待关系就无法首尾相接成环,是工程上最常用、最可靠的一招。A(自旋锁)只改变等待方式,环照样成立,反而空转烧 CPU;B 加线程不减少锁的相互等待,可能更糟;D 只帮排查,不预防。

Q2:实现生产者-消费者时,消费者从空队列取数据要等待。为什么等待条件必须写成 while (队列为空) 等待 而不是 if (队列为空) 等待?

因为线程被唤醒后,条件不一定还成立。两种情况:一是虚假唤醒(spurious wakeup),线程可能在没人真正通知时被唤醒;二是竞争,即便被正确唤醒,重新拿到锁之前,可能有另一个消费者抢先把那个数据取走了,队列又空了。用 if 只判一次就往下走,会在空队列上取数据出错;用 while 被唤醒后重新复查条件,不满足就继续等,才安全。这是并发编程的铁律:等条件用 while 循环复查。

Q3:互斥锁和信号量是什么关系?一个初值为 3 的信号量,用来做什么最合适?

互斥锁是信号量在计数为 1 时的特例。信号量维护一个计数(可用许可数)和一个等待队列:申请时计数减 1、为 0 则阻塞,释放时计数加 1 并唤醒等待者。计数=1 时,同一刻只放一个线程进,就等价于互斥锁。初值 3 的信号量适合「限量」场景——比如一个最多允许 3 个并发的资源池(数据库连接、下载线程配额),允许最多 3 个线程同时进入,第 4 个必须等有人释放。这正是信号量比互斥锁更通用之处:它能表达「最多 N 个」,而不只是「最多 1 个」。
