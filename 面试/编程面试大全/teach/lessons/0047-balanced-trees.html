平衡查找树:对抗 BST 退化

普通二叉搜索树的复杂度全押在树高上。往一棵 BST 里按顺序插 1,2,3,4,5,它就退化成一条链表,查找变 O(n)——之前埋下的伏笔在这里爆雷。平衡查找树用旋转把树高强行压在 O(log n),让查找/插入/删除即便在最坏情况也有保证。这节课不要求你手写旋转,而要讲清「为什么需要它」和「库里到底用哪种」。

先回忆二叉搜索树那节留的一个坑:BST 的所有操作都是 O(树高),而树高在最好情况是 log n、最坏情况是 n。先自己说出来——什么样的插入顺序会把 BST 退化成一条链?退化之后,它和一个普通链表还有区别吗?

一、问题:BST 的复杂度是有条件的

BST 的美妙(左小右大、二分查找)只在树「够矮」时成立。可它对插入顺序毫无抵抗力:按有序序列插入,每个新节点都挂到最右下,树高一路涨到 n,查找退化成从头扫到尾的 O(n)。BST 教科书里写的 O(log n),其实是「平衡时」的复杂度,不是保证。

平衡查找树的目标就一句话:在每次插入/删除后做少量局部调整,把树高钉在 O(log n),从而让所有操作都拿到 O(log n) 的最坏保证。这个「局部调整」的基本动作叫旋转(rotation)。

二、旋转:一次 O(1) 的局部换根

旋转是在不破坏 BST「左小右大」序的前提下,把子树的父子关系重新挂一下,以降低高度。下图是最基础的一次左旋:右偏失衡的链,一步变成两边等高。

不同的平衡树,区别只在于「用什么规则判断失衡、失衡后转几下」。你不需要背旋转的每种情形,但要理解:平衡是靠旋转这种 O(1) 的局部修复持续维持的,不是一次性构造出来的。

三、AVL vs 红黑树:严格 vs 够用

AVL 树:严格平衡——任一节点的左右子树高度差不超过 1。树最矮,查找最快;代价是插入/删除时为维持严格平衡,旋转更频繁。适合「构建一次、之后大量只读查询」的场景(如字典)。

红黑树:近似平衡——用「红/黑」着色规则保证「最长路径不超过最短路径的两倍」。它没那么平衡,但换来的是插入/删除时旋转次数更少(平均 O(1) 次旋转)。工程库几乎都选它:C++ 的 std::map/std::set、Java 的 TreeMap/TreeSet、Java 8 HashMap 冲突链过长时的转化,以及 Linux 内核的完全公平调度器(CFS)。

再补一句 B / B+ 树:它不是二叉的,一个节点存多个键、有很多孩子(高扇出),树因此极矮。这正是磁盘/数据库索引要的——每读一个节点是一次昂贵的磁盘 IO,树矮就意味着 IO 少。MySQL 的 InnoDB 索引、文件系统都用它。

四、关键定义

自平衡二叉查找树(Self-balancing BST)
在插入/删除后通过旋转等局部调整,把树高维持在 O(log n) 的 BST,从而保证操作的最坏复杂度。避免把「平衡」误解成「完全平衡/满二叉树」。
旋转(rotation)
在保持 BST 大小序不变的前提下,重挂常数个指针以改变局部父子关系、降低高度的 O(1) 操作。分左旋、右旋。
AVL vs 红黑树
AVL 严格平衡、查找更快但旋转多;红黑树近似平衡、插删旋转少,是标准库(std::map、TreeMap)与 Linux CFS 的默认选择。

五、复杂度

操作平衡查找树普通 BST(退化)
查找 searchO(log n)O(n)
插入 insertO(log n)O(n)
删除 deleteO(log n)O(n)
有序遍历 / 前驱后继O(n) / O(log n)O(n) / O(n)

平衡查找树的三项核心操作都是 O(log n) 的最坏保证——这是它相对普通 BST 的全部价值。注意绿色写的是「最坏」,不是「平均」;普通 BST 只有「平均 O(log n)」,最坏会塌到 O(n)。空间都是 O(n)。

面试怎么考。这类题以概念题为主,几乎不会让你手写旋转:

  • 「std::map / TreeMap 底层是什么」:红黑树。能顺带说出「保证 O(log n) 最坏、有序、支持范围查询」就完整了。
  • 「为什么标准库用红黑树而不用 AVL」:红黑树平衡约束更松,插入/删除的旋转次数更少,通用容器写操作不少,综合更快;AVL 只在「几乎只读」时的查找上略占优。
  • 「哈希表 vs 平衡树,选哪个」:只要等值查找 → 哈希表(平均 O(1));要有序、范围查询、前驱后继、按序遍历 → 平衡树(O(log n) 但有序)。
  • 「数据库索引为什么用 B+ 树不用红黑树」:B+ 树扇出高、树矮,大幅减少磁盘 IO 次数;红黑树是二叉的,进磁盘会太高。

别把「平衡」理解成「完全平衡」。平衡查找树只保证树高是 O(log n) 量级,并不要求像满二叉树那样每层填满。红黑树甚至允许最长路径是最短路径的两倍——它「够平衡」就行,不追求极致。

「AVL 一定比红黑树好,因为更平衡」——错。更平衡=查找略快,但插入/删除旋转更多、维护更贵。写操作占比不低的通用场景,红黑树的更少旋转反而整体更优,这就是标准库偏爱它的原因。「读多写少用 AVL、读写混合用红黑树」才是准确的取舍。

这节以理解为主,动手核对即可(大纲也说面试基本不会要求手写平衡树):

1. 往一棵普通 BST 里按有序插入 1..8,画出结果——确认它退化成一条链、树高 8。

2. 手动对一个「右偏三节点」做一次左旋,验证左旋后 BST 的中序遍历不变(仍是升序)。

3. 查一下你常用语言的有序容器(std::map / TreeMap / C# SortedDictionary)文档,确认它承诺的是 O(log n) 且底层为红黑树。

带走这一条:平衡查找树用旋转把树高钉在 O(log n),给普通 BST 会退化的最坏情况上了保险。AVL 更平衡查找更快、红黑树少旋转写更快——标准库和 Linux CFS 都选红黑树;数据要进磁盘就换 B+ 树。

六、自测题

Q1:往一棵空的普通(非自平衡)BST 里依次插入 1,2,3,4,5。查找元素 5 的最坏时间复杂度是?

O(n)。有序插入使每个新节点都挂到最右下,树退化成一条 1→2→3→4→5 的链,查 5 要一路走到底,和遍历链表无异。这正是需要自平衡树的理由——换成 AVL 或红黑树,插入过程中会旋转,树高始终保持在 O(log n),查 5 就是 O(log n)。答 O(log n) 的人忘了「普通 BST 的 log n 只是平均、不是保证」。

Q2:C++ 的 std::map 和 Java 的 TreeMap 底层通常用哪种数据结构?为什么不用严格平衡的 AVL?

底层是红黑树。不用 AVL 的原因:红黑树的平衡约束更宽松,插入/删除时需要的旋转次数更少(平均常数次),对读写混合的通用容器整体更快;AVL 更严格的平衡只在「构建后几乎只读」的查找上略有优势,但要为此付出更频繁的旋转。所以「更平衡」不等于「更好」,取舍取决于读写比例。补充:哈希表(unordered_map/HashMap)平均 O(1) 但无序;map/TreeMap 选红黑树正是为了拿到有序 + O(log n) 保证。
