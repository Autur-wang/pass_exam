OOP 与常见设计模式

前 36 课都在攻数据结构与算法——那是砖。这节进入工程与设计部分,换个尺度:当代码规模变大、需求会变,怎么把砖砌得让人改得动、扩得开?面向对象(OOP)给了组织代码的四条地基,设计模式则是前人反复踩坑后沉淀下来的「砌法套路」。面试里它以两种形态出现:直接问「手写线程安全单例」,或在系统设计题里看你能不能点名用合适的模式解决问题。这节不背 23 个模式,只把面试真正在乎的那几个讲透。

回忆前一部分:我们花了很多篇幅在贪心 vs 动态规划上区分「什么问题该用什么解法」。设计模式是同一种思维在更大尺度上的复现——不是「什么算法」,而是「什么结构」:面对一类反复出现的设计问题,有没有一个被验证过的组织方式?数据结构是砖,设计模式是砌法。

一、OOP 的四条地基

设计模式全都建立在面向对象的四个特性上,先把它们分清——面试常让你「用自己的话解释封装和抽象的区别」。

特性一句话解决什么
封装 Encapsulation把数据和操作它的方法包在一起,只暴露必要接口隐藏内部状态,外部改不了、也不必知道细节
抽象 Abstraction只呈现「做什么」,隐藏「怎么做」调用者面向接口编程,不依赖具体实现
继承 Inheritance子类复用并特化父类共性上提、差异下沉,减少重复
多态 Polymorphism同一个调用,不同对象给出不同行为写一次逻辑,对未来新增的类型也成立

多态是设计模式的引擎。几乎所有模式的「可扩展」都来自这一句:调用方持有一个接口引用,运行时到底执行哪个实现,由对象自己决定。记住这条,后面每个模式你都能看穿它在利用什么。

二、设计模式是什么(和不是什么)

设计模式不是能直接 import 的库,也不是语法特性。它是针对一类反复出现的设计问题的、可复用的解决方案模板——是经验的名字。它的价值一半在「解决问题」,另一半在「命名」:当你和面试官都知道「这里用观察者」时,一个词就替代了半页解释。

经典按目的分三大类(源自 GoF《设计模式》):

Creational
创建型
怎么造对象
Structural
结构型
怎么拼对象
Behavioral
行为型
对象怎么协作

仓库大纲列了十几个模式,但面试高频的就下面这几个。逐类挑一两个讲透,胜过背全表。

类别模式一句话用途
创建型单例 Singleton全局只有一个实例(配置、连接池、日志器)
创建型工厂 / 抽象工厂 Factory把「new 哪个类」的决定从调用方挪出去
结构型适配器 Adapter把不兼容的接口包一层,让旧类接入新代码
结构型装饰器 Decorator不改原类,层层包裹动态加功能
行为型策略 Strategy把一族可互换的算法各封一个类,运行时切换
行为型观察者 Observer状态变了,自动通知所有订阅者

三、行为型代表:观察者与策略

观察者是「发布—订阅」的骨架:一个主体(Subject)维护一份观察者名单,状态一变就挨个 notify()。GUI 的事件监听、消息推送、MVC 里视图跟着模型刷新,全是它。

策略解决另一件事:同一个任务有多种算法(排序比较器、支付方式、压缩算法),想在运行时切换,又不想写一大坨 if/else。做法是把每种算法封成实现同一接口的类,让上下文持有一个接口引用。想换算法,换注入的对象即可——这正是「组合优于继承」的样板。

四、创建型代表:线程安全单例

单例是面试最爱手写的一个,因为它把「懒加载 + 线程安全」两个坑都塞进了十几行里。朴素写法在多线程下会造出两个实例:

// 反例:两个线程同时看到 instance == null,各 new 一个
if (instance == null) {
    instance = new Singleton();   // race！
}

面试想听的是双重检查锁(double-checked locking):先无锁检查一次(快路径),只有真为空时才加锁,锁内再检查一次。关键是 volatile——它禁止指令重排,防止别的线程拿到一个「已分配地址但还没构造完」的半成品对象。

class Singleton {
    private static volatile Singleton instance;   // volatile 必需
    private Singleton() {}
    static Singleton get() {
        if (instance == null) {                    // 1. 无锁快检查
            synchronized (Singleton.class) {
                if (instance == null) {            // 2. 锁内再检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

更省心的替代:Java 里用静态内部类(holder idiom)或 enum,靠类加载机制天然线程安全且懒加载;C++11 起局部 static 的初始化由标准保证线程安全。能说出「其实我更倾向 holder / enum,双检锁容易写错 volatile」是加分项。

五、关键定义

多态(Polymorphism)
同一接口调用作用于不同对象时产生不同行为,由对象的实际类型在运行时决定。它是几乎所有设计模式「可扩展」的来源。
设计模式(Design Pattern)
针对一类反复出现的设计问题的可复用解决方案模板,以及它的通用命名。避免把它当成能直接调用的库或语法特性。
SOLID 原则
五条面向对象设计准则(单一职责、开闭、里氏替换、接口隔离、依赖倒置)。模式是准则的具体落地,尤其常体现「对扩展开放、对修改关闭」的开闭原则。
组合优于继承(Composition over Inheritance)
用「持有一个对象并委托」而非「继承一个父类」来复用行为,更灵活、耦合更低。策略与装饰器都是它的样板。

面试怎么考。两条主线:

  • 手写题:「实现一个线程安全单例」是经典中的经典。追问会顺着 volatile 为什么必需、懒加载与饿汉式的取舍、有没有更好的写法一路深挖。
  • 系统设计题:描述一个场景让你设计。如果你能自然说出「这里日志接入用适配器」「通知机制用观察者」「支付方式用策略」,面试官立刻知道你有工程判断,而不只是会刷题。
  • SOLID 一句带过即可,不必背五条定义,但要能说出「开闭原则:加新功能靠加类而非改老代码」。

别背 23 个模式的定义。面试考的从来不是「说出享元模式的定义」,而是「能不能用合适的模式解决眼前的问题」。背了全表却在设计题里一个都用不上,反而暴露是死记。挑 5~6 个高频的讲到能手写、能说清适用场景,远胜过泛泛知道二十个名字。

单例的两个高频扣分点:① 说「加了 synchronized 就线程安全」却漏掉 volatile——没有它,双检锁在重排下仍会返回半成品对象;② 把单例当成「全局变量的美化」到处滥用,它其实引入全局状态、给单元测试和依赖注入添麻烦,该克制。

挑三个模式各写一个最小可运行例子,不看答案凭理解写:

① 策略:定义 SortStrategy 接口,写两个实现(升序 / 降序),一个 Sorter 上下文运行时切换比较器。② 观察者:一个 NewsAgency(Subject)+ 若干 Subscriber,publish() 时全部收到。③ 单例:把上面的双检锁版和 holder 版都写一遍,用两个线程并发调用 get() 打印对象哈希,验证只造了一个实例。

带走这一条:设计模式的本质是「用多态换可扩展」——调用方只依赖接口,新增行为靠加类而非改老代码。面试不考你背了几个模式,考你能不能在对的地方点名用对一个。

六、自测题

Q1:双重检查锁单例里,为什么 instance 必须声明为 volatile?去掉会怎样?

new Singleton() 在底层不是原子的,大致分三步:①分配内存 → ②调用构造函数初始化 → ③把引用指向该内存。②和③可能被指令重排成 ①→③→②。若重排发生,一个线程刚做完 ③(引用已非空)还没做 ②(还没构造完),另一个线程的无锁快检查看到 instance != null 就直接返回并使用这个半成品对象,导致难复现的崩溃。volatile 禁止这种重排、并保证写入对其他线程立即可见,所以必需。这也是为什么很多人转而用 holder idiom / enum——把线程安全交给类加载机制,避开这个坑。

Q2:面试官描述:「一个订单状态改变后,要同时刷新页面、写审计日志、清理缓存,而且以后可能还要加短信通知。」最贴切的模式是哪个?为什么?

观察者(Observer)。关键信号是「一变多」+「以后还要加更多接收方」:订单(Subject)状态一改,已注册的所有观察者自动收到通知;将来加短信通知,只需新增一个观察者、注册进去,订单本身的代码一行都不用改——这正是开闭原则。若硬写成订单里一长串「刷新、写日志、清缓存、发短信」的直接调用,每加一种就要改订单类,耦合越堆越死。(注意别选策略:策略是「多选一地替换算法」,这里是「同时通知多个」,方向不同。)

Q3:「继承」和「组合(委托)」都能复用代码,为什么现代设计普遍主张「组合优于继承」?

继承是编译期绑定的强耦合:子类被钉死在父类的实现细节上,父类一改子类可能崩,而且行为无法在运行时更换;深层继承树还容易催生「为了复用一个方法而背上一堆用不到的父类包袱」。组合则是运行时持有一个接口引用并委托——想换行为就换注入的对象(正是策略模式),耦合低、可测试、可动态切换。经验法则:表达「是一个(is-a)」用继承,表达「有一个 / 用一个(has-a / uses-a)」用组合;拿不准时优先组合。
