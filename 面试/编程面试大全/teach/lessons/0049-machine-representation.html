机器里的数与字符:浮点、Unicode、字节序

这节把三个「底层表示」的坑合成一课。它们表面无关,内核只有一句话:内存里存的从来不是「数」和「字符」本身,而是它们的一种约定编码。约定和你脑子里的直觉一旦错位,就出现「0.1 + 0.2 != 0.3」「一个 emoji 的长度是 4 不是 1」「换台机器读出来的整数变了样」这类让人抓狂的 bug。面试官爱考它们,正是因为它们暴露你有没有真的理解「二进制表示」。

先回忆:在位运算一课里,我们把整数彻底拆成一串二进制位,靠移位和掩码直接操纵它们。这节是同一个视角的延伸——浮点数、字符、多字节整数,在内存里同样只是一串按约定解释的位。先自己想一句:如果内存里只有 0 和 1,那么「小数点」和「负号」到底藏在哪?

一、浮点数:为什么 0.1 + 0.2 不等于 0.3

整数好办,一串位直接是它的二进制值。小数麻烦:计算机用 IEEE 754 标准,把一个浮点数拆成三段位——符号位(正负)、指数位(小数点浮动到哪)、尾数位(有效数字)。这就是「浮点(floating point)」名字的来历:小数点的位置是「浮动」的,由指数决定。

关键在于:尾数位数是有限的。十进制里干净利落的 0.1,换成二进制是无限循环小数 0.0001100110011…,像十进制写不尽 1/3 一样。有限的 23/52 位只能存一个最接近的近似值。于是 0.1、0.2 各自被舍入一点点,相加后的误差恰好让结果不等于同样被舍入的 0.3。这不是 bug,是有限精度的必然。

永远不要用 == 比较两个浮点数。 if (a == b) 在浮点上几乎总是错的写法。正确做法是判断差的绝对值是否小于一个足够小的容差 epsilon:if (abs(a - b) < 1e-9)。面试里写出 0.1 + 0.2 == 0.3 当真会被当作「没接触过浮点」的信号。

另一个坑:浮点不适合表示金额。钱要么用整数存「分」,要么用十进制类型(如 BigDecimal),否则累加久了会漂移出一分钱的误差。

二、Unicode vs UTF-8:码点和字节是两回事

很多人把「字符编码」当成一件事,面试里一追问就露馅。其实是两层:

  • Unicode 是一张字符集——给世界上每个字符分配一个唯一编号,叫码点(code point),写作 U+XXXX。它只回答「这个字是几号」,不管怎么存。
  • UTF-8 是一种编码方式——把码点落成实际的字节。它是变长的:ASCII 字符 1 字节,常见汉字 3 字节,emoji 常要 4 字节。

所以「字符串长度」这个词是有歧义的:按字节数、按码点数、还是按人眼看到的字符数(grapheme,一个 emoji 可能由多个码点组合而成),三者可以都不相等。面试官问「这个字符串多长」,聪明的回答是先反问「你要哪种长度」。

「一个字符一个字节」是 ASCII 时代的过时假设。 在 UTF-8 里按字节下标去切字符串,可能把一个汉字或 emoji 从中间劈开,得到乱码。截断用户昵称时最容易踩这个坑。也别以为「一个 emoji = 一个字符」:像肤色、旗帜类 emoji 由多个码点拼成,按码点数它也不是 1。

三、字节序:同一个整数,两种摆法

单机内自己读自己写,字节序你根本感觉不到。它一旦冒头就是在跨机器边界:网络传输、写二进制文件、读别人机器写的数据。两端字节序不一致,同一串字节就被解释成完全不同的数。因此 TCP/IP 规定了统一的网络字节序(network byte order)= 大端,程序发数据前用 htons/htonl 转成大端,收到再用 ntohs/ntohl 转回本机序——这条正好接上一课网络。

四、关键定义

IEEE 754 / 浮点(Floating Point)
用「符号 + 指数 + 尾数」三段位表示实数近似值的标准。尾数位有限,故大多数小数只能存最接近的近似值。避免把浮点当成精确值直接用 == 比较。
码点 vs 编码(Code Point vs Encoding)
Unicode 码点是字符的抽象编号(U+XXXX);UTF-8 是把码点落成字节的变长编码。避免把「Unicode」和「UTF-8」当同义词。
字节序(Endianness)
多字节数据在内存里字节的排列顺序。大端高位在前,小端低位在前;网络字节序是大端。避免假设「所有机器都一样」。

面试怎么考。 这三点很少单独出算法题,而是穿插在别处考你的严谨:

  • 「浮点为什么不精确?怎么比较?」——答:尾数位有限,小数存的是近似值;比较用 abs(a-b) < epsilon,金额用整数或十进制类型。
  • 「这个字符串多长?」——先分清按字节 / 码点 / 字符,再说 UTF-8 是变长编码,一个 emoji 可能占多字节甚至多码点。
  • 「把结构体写进文件/发到网络,换台机器读出来错了,为什么?」——字节序不一致;跨机器要统一成网络字节序(大端)或明确约定格式。

三个 5 分钟小实验,把抽象变成亲眼所见:

① 在任意语言的交互环境里敲 0.1 + 0.2,看它打印出 0.30000000000000004。② 取一个含中文和 emoji 的字符串,分别打印它的字节长度和码点长度,看两个数不相等。③ 写一个 4 字节整数到文件,用十六进制查看器(如 xxd)打开,确认你的机器是小端(78 56 34 12)。

带走这一条: 内存里没有「数」也没有「字符」,只有按约定解释的位。浮点是有限精度的近似、UTF-8 是变长字节、整数有字节序——只要跨越「你的直觉」和「机器的约定」这条缝,就要显式处理,别默认。

五、自测题

Q1:下面哪种做法能正确判断两个浮点结果「相等」?

正确做法是 abs(a - b) < epsilon(取一个足够小的容差,如 1e-9)。直接 a == b 会因舍入误差判为不等;四舍五入到固定小数位再比较也只是特例、不通用。根因是尾数位有限,浮点存的是近似值,几乎不该指望两条不同计算路径得到位级完全相同的结果。

Q2:一个字符串是 "a中😀"(1 个 ASCII 字母 + 1 个汉字 + 1 个 emoji)。它的 UTF-8 字节长度和 Unicode 码点长度分别是多少?

字节长度 = 1 + 3 + 4 = 8;码点长度 = 3。 UTF-8 里 a 占 1 字节、中 占 3 字节、😀 占 4 字节,合计 8;但按码点数,它就是 3 个字符。这正说明「字符串长度」必须先问清按哪种口径——按字节切下标会把汉字或 emoji 劈开成乱码。

Q3:把 4 字节整数 0x0A0B0C0D 存进一台小端序机器,内存最低地址处的那个字节是?

0x0D。小端序「低位在前」,最低有效字节 0D 放在最低地址,依次是 0C 0B 0A。若是大端序,则最低地址放最高位字节 0A。网络字节序采用大端,所以跨机传输前要做主机序↔网络序转换。
