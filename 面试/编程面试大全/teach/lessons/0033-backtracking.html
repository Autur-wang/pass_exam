回溯:在决策树上试错与剪枝

面试里只要出现「列出所有子集 / 排列 / 组合」「找出所有满足条件的解」,几乎就是在点名回溯。这节课把回溯拆成一句话——在一棵决策树上做 DFS,做了选择就递归下去,走不通就撤销选择再试别的——并把那个最容易漏、一漏就全错的动作「撤销选择」钉死。

先回忆:上一课递归我们说,写递归先问「base case 是什么、规模有没有变小」。再往前DFS那课,深度优先是「一条路探到底,到头再回退」。回溯 = 递归 + DFS + 一个新动作。试着先猜:这个新动作是什么?(提示:和「回退」有关。)

一、直觉:一棵「每一步都要做选择」的树

把求解过程想成走一棵决策树:树的每一层对应一个「要不要选它 / 选哪个」的决策,一条从根到叶的路径就是一个候选解。回溯就是系统地把这棵树走一遍——用 DFS 一条路探到底,收集到一个完整解就记下来,然后退回上一个岔口,撤销刚才的选择,换另一条分支。

二、通用模板:选择 → 递归 → 撤销

几乎所有回溯题都能套进同一个骨架,把它默写下来,现场只需要填三个空:

def backtrack(路径, 选择列表):
    if 满足结束条件:
        结果.append(路径的拷贝)      # 收集一个解(注意要拷贝!)
        return
    for 选择 in 选择列表:
        if 该选择不合法: continue    # ← 剪枝:提前砍掉走不通的分支
        路径.add(选择)               # ① 做选择
        backtrack(路径, 新的选择列表) # ② 递归进入下一层
        路径.remove(选择)            # ③ 撤销选择(回到做选择之前的状态)

③ 那行——撤销选择——就是「回溯」这个名字的来源,也是新手最爱漏的一行。它保证:当我从一条分支退回岔口时,状态被恢复得干干净净,不会把上一条路的痕迹带进下一条路。

三、回溯 ≠ 暴力:剪枝才是灵魂

有人说「回溯就是暴力枚举」,这话只对了一半。回溯确实系统地遍历决策树,但它的价值在剪枝(pruning):一旦发现当前部分解已经不可能通向合法答案(比如组合总和已经超了目标),就立刻砍掉整棵子树、不再往下走。剪掉的往往是指数级的搜索空间。没有剪枝的回溯才退化成纯暴力。

五、关键定义

回溯(Backtracking)
在决策树上系统地尝试,并在走不通时撤销选择(剪枝),用于组合/排列/子集类问题。避免说「回溯就是暴力」——回溯的关键是剪枝。
撤销选择 / 状态恢复(Undo)
递归返回后,把「做选择」时对路径/棋盘/访问标记做的修改原样还原,使兄弟分支从干净状态出发。漏写会污染其他分支。
剪枝(Pruning)
提前判定当前分支不可能产生合法解,直接跳过整棵子树。是回溯优于暴力的根本原因。

六、复杂度:天生指数级,靠剪枝压常数

问题解的个数时间(含拷贝每个解)
全部子集(幂集)2ⁿO(n · 2ⁿ)
全排列n!O(n · n!)
组合 C(n,k)C(n,k)O(k · C(n,k))
N 皇后—O(n!) 上界 (剪枝后实际远小于)

关键认知:回溯的时间下界就被输出规模卡死了——你要列出 2ⁿ 个子集,光是写出它们就得 2ⁿ 次。所以「回溯太慢」不是写法问题,是问题本身解就那么多。剪枝能把常数和实际运行时间压下来,但改不了这个量级。这也是它和动态规划的分水岭:DP 求「有多少个 / 最优那个」,回溯求「把它们全列出来」。

面试怎么考。回溯是「枚举型」题目的默认解法,信号词非常明显:

  • 看到「所有 / 全部 / 列举出每一个」就想回溯:所有子集(LeetCode 78)、全排列(46)、组合总和(39)、括号生成、划分回文串、N 皇后——全是一个模子。
  • 要求默写模板:面试官常让你先写出「选择→递归→撤销」的骨架,再往里填。README 给的「回溯蓝图」(见主推资源)就是这套模板的权威版,建议照着抄熟。
  • 追问剪枝:「怎么让它更快?」——答:在进入分支前判断可行性(如剩余和已超目标、列/对角线已被占),把不可能的子树剪掉。
  • 追问复杂度:别硬背公式,答「时间下界等于解的个数,因为要把每个解都构造出来」,再补一句「剪枝压实际耗时」。

坑一(最致命):撤销选择漏写。做了 路径.add(x) 递归完却忘了 路径.remove(x),下一条兄弟分支就带着上一条的残留,结果全乱。写模板时把「做选择」和「撤销选择」成对写好再填中间。

坑二:收集解时没拷贝。结果.append(路径) 存的是同一个列表的引用,后续 add/remove 会把已存进结果的解一起改掉,最后全变空。必须存快照:结果.append(路径[:]) / new ArrayList<>(路径)。

坑三:含重复元素时去重错。输入有重复(如 [1,1,2] 求子集/排列)会产生重复解。标准手法是先排序,再在同一层里「跳过与前一个相同且前一个未被使用」的元素。凭感觉去重几乎必错。

用同一套模板刷穿这五道,亲手体会「只改三处」:

子集(LeetCode 78)· 全排列(46,用 used[] 标记已选)· 组合总和(39,可重复取,靠传 start 下标避免重复组合)· 括号生成(22,剪枝:左括号用完前不能放右括号)· N 皇后(51,剪枝:列 / 两条对角线冲突检测)。

每道都特意注释出「做选择 / 递归 / 撤销选择」三行,并在收集解处确认自己写的是拷贝而不是引用。

带走这一条:回溯 = DFS 遍历决策树 + 成对的「做选择 / 撤销选择」 + 尽早剪枝。看到「列出所有…」就套模板,写完先自查两件事:撤销那行在不在?收集解是不是拷贝?

七、自测题

Q1:回溯模板里 路径.remove(选择)(撤销选择)这一行如果删掉,会发生什么?

兄弟分支会被上一条分支的残留状态污染,产出错误的解。因为从一条路径退回岔口时,路径里还留着刚才那条路加进去的元素,换分支时它们没被清掉,导致后面的解越滚越长、互相串味。撤销选择的唯一职责就是把状态恢复到「做这个选择之前」,让每条分支都从同一个干净起点出发。这是回溯最高频的 bug。

Q2:下面哪个说法不准确?

不准确的是:「回溯就是暴力枚举,和暴力没区别。」

回溯的关键增值是剪枝:一旦当前部分解不可能通向合法答案,就砍掉整棵子树,省下指数级的无用搜索。没有剪枝时它才退化为暴力。其余说法都成立:回溯本质是决策树上的 DFS;列出全部子集的时间下界确实是 O(2ⁿ)(受输出规模限制);含重复元素要靠「排序 + 跳过相邻相同」去重。

Q3:为什么求全排列是 O(n·n!) 而不是「多项式级」?能靠更聪明的写法把它降到多项式吗?

不能。n 个不同元素的排列共有 n! 个,你被要求全部列出,光是把这 n! 个排列(每个长度 n)写出来就需要 O(n·n!) 的时间——这是输出规模决定的硬下界,与算法聪明程度无关。剪枝/优化只能减少无效尝试、压低常数,改不了「结果就有这么多个」这个事实。凡是「枚举全部」的题,复杂度天花板都由解的个数封顶。
