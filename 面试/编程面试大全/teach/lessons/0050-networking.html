网络基础:TCP/IP、HTTP、DNS

「在浏览器地址栏输入一个网址,回车,到页面显示出来——中间发生了什么?」这是网络面试的第一名高频题,几乎每家都问。它不考你背协议号,考的是你能不能把 DNS → TCP → HTTP → 渲染这条链路完整、有层次地讲出来。这节课就把这条链路拆开,顺带把 TCP vs UDP、三次握手、HTTP 状态码这些必答点补齐。

先回忆:上一课结尾我们说,跨机器传数据要统一成网络字节序(大端)。这节就走进那个「网络」——数据离开你的机器后,是怎么被分层打包、可靠送达对面的。先自己想一句:两台从没见过面的机器,凭什么能确认「我们建立连接了」?

一、分层:每一层只操心自己那点事

网络的核心设计思想是分层:把「让两台机器通信」这个巨大问题切成几层,每层只解决一件事,并只依赖下一层提供的能力。上层不用管下层怎么实现的。这和写代码时的抽象封装是同一种智慧。

二、TCP vs UDP:可靠还是快,二选一

传输层有两个主角。它们的分歧只有一句话:要不要为「可靠」付出代价。

维度TCPUDP
连接面向连接(先握手)无连接(直接发)
可靠性可靠:确认、重传、去重不保证到达
顺序保证按序交付不保证顺序
开销 / 速度头部大、有拥塞控制,较慢头部小、无控制,更快
典型场景网页、文件、邮件直播、游戏、DNS 查询、音视频

选型的判据不是「哪个更好」,而是「你更怕丢包还是更怕延迟」。网页传文件宁可慢一点也不能错一个字节,用 TCP;直播丢一两帧无所谓、但卡顿不能忍,用 UDP。

三、三次握手:为什么非得是三次

TCP 通信前要先「握手」建立连接,确认双方的收发能力都正常、并同步各自的初始序号。经典追问是:为什么是三次,不是两次?

两次为什么不够?两次的话,服务端发完第二个包就以为连上了,但它无法确认客户端真的收到了自己的响应。更要命的是:一个在网络里滞留很久的历史重复 SYN可能突然到达服务端,若只需两次,服务端就会为这个早已作废的请求单方面建立连接、白白占用资源。第三次的 ACK 让客户端有机会说「这个连接我不认」,从而挡掉历史连接。三次是「双向确认」所需的最小次数。

四、HTTP 与 DNS:把这条链路走完

DNS 是互联网的「电话簿」:你只记得住 example.com 这样的域名,但机器之间靠 IP 地址找人。DNS 负责把域名解析成 IP,过程中层层缓存(浏览器 → 操作系统 → 本地 DNS → 权威 DNS)以省时间。

HTTP 是应用层的请求-响应协议:客户端发一个请求(方法 + URL + 头 + 体),服务端回一个响应(状态码 + 头 + 体)。它无状态——服务端默认不记得你上次是谁,靠 Cookie / Session / Token 才认得出会话。HTTPS = HTTP 跑在 TLS 加密通道上,防止中间人窃听篡改。状态码按首位分类:

状态码含义例子
2xx成功200 OK
3xx重定向301 永久 / 302 临时
4xx客户端错误404 找不到 / 401 未认证 / 403 禁止
5xx服务端错误500 内部错误 / 503 不可用

现在把整条链路串起来——这就是那道高频题的标准答法:

五、关键定义

TCP vs UDP
TCP 面向连接、可靠、有序,代价是开销与延迟;UDP 无连接、不保证到达、更快更轻。避免说「UDP 就是残缺版 TCP」——低延迟场景 UDP 是更优选择。
三次握手(Three-way Handshake)
SYN → SYN+ACK → ACK,建立 TCP 连接并同步双向序号。避免答成两次(无法双向确认,且挡不住历史重复连接)。
无状态(Stateless)
HTTP 每个请求相互独立,服务端默认不记忆上下文;会话靠 Cookie / Session / Token 维持。避免说「登录后服务器就一直记得我」。

面试怎么考。 网络这块的题高度套路化,备好这几条几乎覆盖八成:

  • 「输入 URL 到页面显示发生了什么?」——按 DNS → TCP → (TLS) → HTTP → 渲染五步讲,每步补一句作用。面试官会挑一步深挖。
  • 「TCP 和 UDP 怎么选?」——不比优劣,讲权衡:怕丢包用 TCP,怕延迟用 UDP,举直播/游戏的例子。
  • 「三次握手为什么三次?」——双向确认收发能力 + 防止历史重复连接建立,三次是最小次数。
  • 「HTTP 是无状态的,那登录怎么保持?」——靠 Cookie/Session/Token,把状态显式带在请求里。

三次握手别脱口而出「两次」。 两次无法让服务端确认客户端收到了响应,也挡不住滞留的历史 SYN 造成的假连接。

「TCP 保证送达」不等于「保证实时」。 TCP 靠重传保证最终到达,但重传会带来延迟抖动——这恰恰是实时音视频宁可用 UDP 的原因。把「可靠」误当成「又快又稳」是常见误解。

别把 HTTP 说成有状态。 HTTP 本身无状态,是 Cookie/Session 在上面「补」出了状态的错觉。

动手核对,把协议从文字变成可观察的现象:

① 命令行跑 nslookup example.com 或 dig example.com,亲眼看域名解析成 IP。② 用 curl -v https://example.com,在输出里找到 TCP 连接、TLS 握手、请求头、响应状态码。③ 打开浏览器开发者工具的 Network 面板,刷新一个页面,观察每个请求的状态码、耗时,以及 DNS/连接/等待各阶段的时间瀑布。

带走这一条: 网络的一切都建立在「分层 + 每层各管一件事」之上。答网络题时,先定位在哪一层(DNS/TCP/HTTP…),再讲这层解决什么问题、代价是什么——层次感本身就是高分信号。

六、自测题

Q1:一款实时多人对战游戏要同步玩家位置,偶尔丢一两个位置包可以接受,但绝不能卡顿。传输层该选谁?

选 UDP。游戏最怕延迟和卡顿,而位置数据下一帧就会刷新,偶尔丢包无伤大雅。TCP 的重传和拥塞控制会引入延迟抖动,反而害了实时性。判据始终是「更怕丢包(→TCP)还是更怕延迟(→UDP)」,这里显然是后者。

Q2:关于 TCP 三次握手,下面哪个说法正确?

正确的是:三次握手能防止已失效的历史重复连接请求被服务端误建立。若只用两次,服务端收到滞留的旧 SYN 就会单方面建连、浪费资源;第三次 ACK 给了客户端否认旧连接的机会。而「三次是为了传输数据」是错的(握手只建连不传业务数据);「握手越多越可靠」也错(三次已是双向确认的最小充分次数)。

Q3:用户访问一个页面,服务器返回了 301。这意味着什么,浏览器接下来会做什么?

3xx 是重定向,301 表示「永久移动」。浏览器会读取响应头里的 Location,自动向新地址再发一次请求。对比:404(4xx)是客户端要的资源不存在,500(5xx)是服务端自己出错。记住按首位分类:2 成功、3 重定向、4 客户端错、5 服务端错。
