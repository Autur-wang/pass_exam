字典树 Trie:前缀即路径

哈希表能 O(1) 判断「某个词在不在」,却答不出「有哪些词以 ca 开头」——因为它把键打散成了没有结构的指纹。字典树(Trie)反其道而行:让每个字符成为一层分叉,一个单词就是一条从根往下的路径。于是「前缀查询」变成「沿路径走几步」,这正是自动补全、拼写检查的底层引擎。

先回忆两件事。树那节:节点带若干孩子,从根到某节点的路径编码了一段信息。哈希表那节:平均 O(1) 存取,但键之间彼此无关。先想一个问题:如果要「找出所有以某前缀开头的单词」,哈希表能高效做到吗?为什么不能?

一、直觉:把字母摊在路径上

Trie 的每个节点代表「走到这里为止拼出的前缀」。从根出发,每条边对应一个字符;顺着 c → a → t 走三步,就拼出了 cat。共享前缀的单词共享前半段路径:cat 和 car 一起走到 ca,再分岔。

二、三种操作,代价都只看串长

插入 word:从根开始,对每个字符,若对应孩子不存在就新建,然后下移;走完在末节点打上词尾标记。查找完整词:沿字符走,任一步没有对应孩子就返回「不存在」,走到头再看末节点是否有词尾标记。前缀查询:同样沿字符走,能走完前缀就说明「存在以它开头的词」——不需要词尾标记。

关键观察:三种操作的代价都是 O(L),L 是被查串的长度,与 Trie 里存了多少个词(n)无关。哈希表查找是 O(L)(得先算整串的哈希),Trie 也是 O(L),但 Trie 额外白送了哈希表给不了的前缀能力——代价是更大的空间。

三、关键定义

字典树(Trie)
按字符逐层分叉的树,从根到节点的路径即一段前缀,用于字符串前缀检索。避免「前缀树」与「Trie」混用时不统一——本课统一叫 Trie。
词尾标记(end-of-word flag)
节点上的布尔位,标记「从根到此的路径正好是一个被收录的完整词」。区分「前缀存在」与「单词存在」的唯一凭据。
字母表大小 σ(alphabet size)
每个节点可能的分叉数(小写英文字母 σ=26)。若每节点用定长数组存孩子,空间与 σ 成正比;用哈希表/映射存孩子则省空间但常数更大。

四、复杂度

操作时间说明
插入 insert(word)O(L)L=词长,与词数 n 无关
查完整词 search(word)O(L)走完后需查词尾标记
前缀查询 startsWith(pre)O(L)能走完前缀即存在,不看标记
空间(定长数组孩子)O(N·σ)N=所有词总字符数,σ=字母表大小

时间栏全绿,是 Trie 的卖点:查询代价只跟当前串长挂钩,存一百万个词也不会让单次查询变慢。但空间栏是红的:稀疏数据下大量节点只有一两个孩子,却各占一个 σ 大小的数组,浪费惊人——这是 Trie 的主要代价,也是面试易错点。

面试怎么考。听到这些关键词就该条件反射想到 Trie:

  • 「自动补全 / 前缀匹配 / 输入联想」:走到前缀节点,再对其子树做一次 DFS 收集所有词。哈希表做不了这件事。
  • 「实现 Trie」(LeetCode 208 经典题):要求写 insert/search/startsWith,考点就是「search 要查词尾标记、startsWith 不查」。
  • 「单词搜索 II / 单词游戏」:把词典建成 Trie,再在字母网格上 DFS + Trie 同步下移,一次遍历同时匹配大量单词——这是 Trie + 回溯的高频组合。
  • 其它经典应用:拼写检查、IP 路由最长前缀匹配、词频统计。

最常见错误一:查完整词只看「路径能走通」。在存了 cat 的 Trie 里查 ca,路径能走通,但 ca 节点没有词尾标记,应返回「不存在」。search 必查标记,startsWith 才不查——把这两者答反是最典型的丢分点。

最常见错误二:低估空间。Trie 用空间换时间,稀疏或字母表大(如 Unicode)时空间开销可能非常大。别脱口而出「Trie 比哈希表好」——它在前缀查询上强,在纯粹的存在性判断上,哈希表往往更省内存。工程里常用压缩前缀树(Radix/Patricia Trie)来缓解。

动手清单(对应 LeetCode 208):

1. 定义节点:children(长度 26 的数组或哈希表)+ isEnd 布尔位。

2. 实现 insert(word) / search(word) / startsWith(prefix),务必让 search 收尾时检查 isEnd。

3. 加一个 collect(prefix):走到前缀节点后 DFS 子树,返回所有以它开头的词——这就是自动补全的核心。

4. 存入一小份词典,分别用哈希表和 Trie 实现「前缀有多少个词」,对比代码复杂度。

带走这一条:Trie 把「前缀」变成「路径」,让前缀查询降到 O(串长)、与词数无关;它用空间换来了哈希表给不了的前缀能力。查完整词别忘了检查词尾标记。

五、自测题

Q1:一个 Trie 里存了 {apple, app}。调用 search("app") 和 startsWith("app") 分别返回什么?

search("app") 返回 true,startsWith("app") 也返回 true。因为 app 本身被收录了(它的末节点有词尾标记),两者都成立。但如果 Trie 里只存了 apple(没存 app),那么 search("app") 应返回 false(路径走得通但无词尾标记),而 startsWith("app") 仍返回 true。这道题就是在逼你说清「查词要看标记、查前缀不看」。

Q2:在一个存了 n 个单词、被查串长为 L 的 Trie 上,单次 search 的时间复杂度是?

O(L),只跟被查串的长度有关,与已存单词数 n 无关。这正是 Trie 相对「遍历词典逐个比较(O(n·L))」的优势。干扰项 O(n·L)、O(log n)、O(n) 都错把词数 n 塞进了复杂度——Trie 的查询代价只由「走几步」决定。空间才是随词数增长的那一维。
