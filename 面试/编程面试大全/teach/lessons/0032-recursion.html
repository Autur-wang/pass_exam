递归:自我调用与 base case

递归是接下来一整个「算法范式」部分的地基——回溯、分治、动态规划都长在它上面。这节课只攻一件事:把一个函数调用自己为什么能算出答案讲清楚,以及面试官最爱盯的两个死穴——漏了 base case 会栈溢出、子问题重叠不做缓存会指数爆炸。

先回忆:在树的遍历那课,我们几乎每个遍历都写成「先处理自己,再对左右子树做同样的事」。那句「对子树做同样的事」就是递归。还有一个隐藏角色——每次函数调用自己,系统都往调用栈压一层栈帧。试着自己说出:如果一直压栈、永远不返回,会发生什么?

一、直觉:把问题缩小成同一个问题

递归的心法只有一句:假设「更小的那个问题」已经解决了,我只负责拼出当前这一层。求 n! 时,我不去想 5×4×3×2×1 怎么连乘,只想一件事:n! = n × (n-1)!——只要有人替我算出 (n-1)!,我乘个 n 就完事。那个「有人」就是递归调用它自己。

但光有「缩小」不够,必须有个地方停下来直接给答案,不再往下递,否则会无限递归。这个终点就是 base case(基准情形):0! = 1。于是递归的三要素浮现:

二、递归靠调用栈展开

递归不是魔法,它借的是调用栈:每进入一层函数,系统压入一个栈帧(保存参数、局部变量、返回地址);撞到 base case 后开始逐层返回,栈帧一个个弹出、把结果往上交。所以递归深度 = 栈的高度。深度太大(比如对 100 万个元素做线性递归),即使逻辑正确也会爆栈——这是递归相对循环最现实的代价。

三、危险案例:朴素斐波那契

把 fib(n) = fib(n-1) + fib(n-2) 直接写成递归,看起来干净,却慢得离谱。画出它的递归树就明白了:同一个子问题被反复重算。

树的节点总数随 n 近似翻倍,所以朴素斐波那契是 O(2ⁿ)(更精确是 O(φⁿ),φ≈1.618)。只要在算过的子问题上加一层缓存(记忆化),同一个 f(k) 只算一次,复杂度立刻塌到 O(n)——这就是下下节 DP 的核心动作。

四、尾递归:一个常被高估的优化

尾递归指递归调用是函数的最后一个动作,返回值直接就是那次调用的结果,当前栈帧没有任何后续计算要做。理论上编译器可以复用同一个栈帧(尾调用优化,TCO),把递归变成不增长栈的循环。但现实是——多数主流语言默认不做尾调用优化(如 CPython、大多数 JVM 实现),原因之一是会破坏调用栈信息、让异常堆栈不可读。所以别指望「写成尾递归就不会爆栈」;真要控制栈深,老老实实改写成迭代更可靠。

五、关键定义

递归(Recursion)
函数调用自身、把问题化为更小的同类子问题;必须有 base case 保证收敛。避免把递归和「循环」当作可无脑互换——递归多占栈空间。
base case(基准情形)
递归的终止条件:小到可以直接给出答案、不再往下递的情形。漏写或写错会导致无限递归。
重叠子问题(Overlapping Subproblems)
递归展开中同一个子问题被反复求解。是「递归 + 记忆化 = 动态规划」适用的前提;不重叠则属分治范畴。
尾递归(Tail Recursion)
递归调用是函数执行的最后一步。理论上可被优化成常数栈空间,但多数语言默认不优化。

六、复杂度:同是递归,天差地别

递归写法时间栈空间(深度)
阶乘 fact(n)(线性递归)O(n)O(n)
朴素斐波那契 fib(n)O(2ⁿ) (重叠子问题)O(n)
递归二分查找O(log n)O(log n)
归并排序(分治)O(n log n)O(log n) (递归) + O(n) 合并缓冲

要点:递归本身没有固定复杂度——时间由「子问题个数 × 每层工作量」决定,空间至少要算上调用栈的最大深度。面试里一句「这段递归空间是多少」,考的往往就是你有没有把栈深算进去。

面试怎么考。递归很少单独成题,但它是解题的默认工具,面试官会用它探你的基本功:

  • 套用「解决任何递归问题的 5 步」(见主推资源):① 找出最小子问题(base case);② 假设子问题已解决;③ 写出当前层如何用子问题的解拼出答案(递归式);④ 确认每次调用规模都在缩小;⑤ 估复杂度。能按这条流水线口述,面试官就知道你不是靠背模板。
  • 要求你现场估复杂度:画出递归树,数「节点数 × 每节点工作量」。斐波那契树能画出来,分数就到手一半。
  • 追问栈溢出风险:「输入 10⁶ 会怎样?」——线性递归深度 10⁶ 直接爆栈,这时要么改迭代、要么显式用栈模拟。

坑一:漏 base case 或 base case 覆盖不全。比如只处理了 n==0 却忘了 n==1,或者递归参数可能走到负数却没拦。结果是无限递归直到栈溢出。写递归先写 base case,是肌肉记忆。

坑二:明明有重叠子问题却裸递归。朴素斐波那契、裸递归的爬楼梯,面试官等的就是你说出「这里子问题重叠,加记忆化能从 O(2ⁿ) 降到 O(n)」。说不出这句,就暴露了没吃透递归树。

坑三:以为「写成尾递归就不爆栈」。多数语言不做尾调用优化,别把它当保命符。

徒手写并对照跑一遍,把「递归树」从抽象变具体:

fact(n) · 递归版 fib(n)(在函数里打印每次调用,数一数 fib(2) 被调用几次)· 加一个字典做记忆化的 fib_memo(n)(再数一次调用次数,对比)· 把 fib 改写成迭代版 · 用递归做二分查找和数组求和。

实验:让 fact 的 n 一路加大,亲眼看它在哪个深度抛出 RecursionError / StackOverflowError。

带走这一条:写任何递归先问三句——base case 是什么?每次调用规模有没有严格变小?子问题会不会重叠(重叠就该上记忆化)?这三问答完,递归的对与快都稳了。

七、自测题

Q1:下面哪一项最能解释「朴素递归斐波那契为什么是 O(2ⁿ)」?

因为存在重叠子问题,同一个 fib(k) 在递归树的不同分支里被反复重算,节点总数随 n 近似翻倍。

干扰项辨析:不是「因为递归比循环慢」(常数差异,不改变量级);也不是「因为要压很多栈帧」(栈深只有 O(n),那是空间不是时间)。慢的根源是重复计算——所以加记忆化(每个子问题只算一次)就能把时间降到 O(n),而这并不改变代码的递归形态。

Q2:一位同学说「我把递归改成尾递归了,所以再大的输入也不会栈溢出」。这话对吗?

不一定对,通常是错的。尾递归理论上可以被编译器优化成常数栈空间(TCO),但多数主流语言默认不做这个优化(如 CPython、常见 JVM 实现)。在这些语言里,尾递归照样一层层压栈,深度够大照样爆。真要保证不爆栈,应改写成显式迭代(循环)或用自己维护的栈。

Q3:递归二分查找的空间复杂度是多少?为什么不是 O(1)?

O(log n)。虽然二分查找不额外开数组,但每次递归都压一层栈帧,而递归深度等于对半砍的次数,即 O(log n)。所以尽管「没开新数据结构」,调用栈本身就占了 O(log n) 空间。若改写成迭代二分,才是真正的 O(1) 额外空间——这也是面试里区分「原地」与否的常见细节。
