缓存:局部性与命中率

缓存(cache)是整个计算机系统里最重要的一句谎言:让慢而大的存储「看起来」既快又大。这节课把两个东西讲透——为什么缓存有效(局部性),以及面试里最高频的一道设计题:怎么用哈希表 + 双向链表实现 O(1) 的 LRU 缓存。它同时会回收前面两处伏笔:数组为什么「缓存友好」,以及双向链表在这里到底救了什么。

先回忆两件旧事。数组那节我们说「连续内存带来一个表里看不见的红利——缓存友好」,当时先记了个账;这节要还。另外 哈希表让我们有了平均 O(1) 的按键存取——它是 LRU 缓存的一半骨架。先自己想想:为什么按顺序遍历数组,会比按指针跳着遍历链表快好几倍?明明都是读 n 个元素。

一、直觉:一座速度与容量成反比的金字塔

存储不是一层,而是一座层级金字塔。越靠顶,越快、越贵、容量越小;越往底,越慢、越便宜、容量越大。CPU 每次要数据,先问最快的一层,没有再往下问。缓存的全部工作,就是把「马上又要用」的数据尽量留在靠上的层。

二、缓存为什么有效:两种局部性

如果程序访问内存是纯随机的,缓存一点用都没有。缓存能生效,靠的是真实程序几乎都有局部性(locality):

  • 时间局部性:刚用过的数据,很可能马上又用(循环里的计数器、反复调用的函数)。→ 把它留在缓存里别急着赶走。
  • 空间局部性:用了某个地址,很可能接着用它旁边的地址(顺序遍历数组、连续的结构体字段)。→ 每次不只取一个字节,而是取一整条缓存行(cache line,通常 64 字节)一起搬上来。

这两条合起来,正好回答了开头那个问题。顺序遍历数组时,读第一个元素就顺手把它后面 63 字节(十几个 int)一起装进了缓存行,接下来十几次访问全是缓存命中,近乎免费。链表节点散落在内存各处,每跳一个指针就可能是一次全新的、慢几十倍的内存访问——这就是「数组缓存友好」的真正含义,也是它常常在实测中吊打链表的原因,哪怕两者大 O 相同。

三、命中、未命中与淘汰:LRU

缓存容量有限,装满后再来新数据,必须踢掉(evict)一个旧的。踢谁?最常用的策略是 LRU(Least Recently Used,最近最少使用):淘汰「最久没被碰过」的那个,赌它接下来也不会被用——这正是时间局部性的直接应用。

面试要你手写 get/put 都是 O(1) 的 LRU。难点在于:要 O(1) 按 key 找到值(哈希表擅长),又要 O(1) 地把某个节点「移到最近端」和「从最久端删除」(双向链表擅长)。两者合体,各补对方的短板:

缓存(Cache)
把慢速存储中「可能再次用到」的数据,临时存一份到更快存储里的机制。核心指标是命中率。
时间 / 空间局部性(Temporal / Spatial Locality)
时间:刚用的很可能再用;空间:用了某地址很可能用其邻居。缓存有效的两大前提。避免把两者混为一谈。
缓存行(Cache Line)
缓存与内存之间搬运的最小单位(常见 64 字节),而非单个字节。空间局部性的硬件兑现方式。
命中率(Hit Rate)
命中次数 ÷ 总访问次数。平均访问时间 ≈ 命中率 × 快层延迟 + 未命中率 × 慢层延迟。避免只谈缓存大小不谈访问模式。
LRU(Least Recently Used)
淘汰「最久未使用」项的缓存替换策略;用哈希表 + 双向链表可做到 get/put 均 O(1)。

四、复杂度:O(1) 从哪来

LRU 操作平均最坏
get(key)(查+移到头部)O(1)O(n) (哈希冲突退化)
put(key, val)(插入/更新+可能淘汰)O(1)O(n) (哈希冲突退化)
淘汰最久项(删链表尾)O(1)O(1)

空间 O(capacity):哈希表和链表各存一份指向同一批节点的引用,常数不影响量级。注意「平均 O(1)」里的「平均」来自哈希表——冲突严重时理论最坏是 O(n),说清楚这一点比死记「O(1)」更能体现你懂原理。

面试怎么考。缓存在面试里有两副面孔,都很高频:

  • 直接手写 LRU(LeetCode 146):几乎是数据结构综合题的「国民题」。考官看你能否想到「哈希表 + 双向链表」这对组合,并把移动/删除的指针操作写对不出错。进阶会问 LFU(按频率淘汰)怎么做。
  • 概念追问「数组遍历为什么比链表快」:标准答案不是大 O,而是局部性 + 缓存行——数组连续,一条缓存行命中一片;链表节点散,几乎每跳一次都未命中。能答到这一层,面试官立刻知道你理解硬件而不只是背复杂度。
  • 系统设计里:缓存无处不在(浏览器、CDN、Redis、数据库 buffer pool)。会被问缓存淘汰策略、缓存穿透/雪崩、写策略(write-through vs write-back)。

「缓存越大越好」是错的。缓存变大,命中率提升会边际递减,而每一层做大都要付出成本和延迟代价(更大的 SRAM 更慢也更贵)。真正决定命中率的往往不是容量,而是访问模式:一个反复顺序扫过超过缓存容量的大数组(cache thrashing),缓存基本帮不上忙——它每装满就被后面的数据整片冲刷掉。

另一个坑:别把「堆(数据结构)」和「缓存」混谈,也别以为 LRU 用单链表就行。单链表删任意节点要先 O(n) 找前驱,达不到 O(1);必须双向链表(或哨兵节点简化边界)。

手写一个 LRUCache,构造参数 capacity,实现两个方法都要 O(1):

get(key) —— 命中返回值并把该节点移到链表头(标记为最近);未命中返回 -1 / null。
put(key, val) —— 已存在则更新值并移到头;不存在则新建插到头,若超容则删链表尾节点、并从哈希表里同步删掉它的 key。

关键技巧:链表两端各放一个哨兵节点(dummy head / dummy tail),插入删除就不用处理「头尾为空」的边界。写完拿 capacity=2、序列 put(1,1) put(2,2) get(1) put(3,3) get(2) 手跑一遍,验证 get(2) 返回未命中。

带走这一条:缓存靠的不是「大」,而是局部性——把马上要用的留在快层。数组比链表快的深层原因是缓存行 + 空间局部性,而不是大 O;LRU 的 O(1) 来自「哈希表管定位、双向链表管顺序」这对黄金搭档。

五、自测题

Q1:两个程序都遍历一个含 100 万个 int 的容器各一遍,总大 O 都是 O(n)。为什么用数组的那个在实测中往往快数倍?

因为空间局部性 + 缓存行。数组元素在内存里连续,读一个就把相邻一整条缓存行(约 64 字节 ≈ 16 个 int)一起搬进 L1,接下来十几次访问几乎全命中。链表节点散落各处,每跳一次指针都可能触发一次比 L1 慢几十倍的内存访问。大 O 忽略了常数,而这里的常数差别正是缓存命中率带来的。这就是数组被称为「缓存友好」的原因。

Q2:实现 LRU 缓存,为什么是「哈希表 + 双向链表」,而不是「哈希表 + 单链表」或「只用哈希表」?

因为要同时满足两种 O(1)。只用哈希表能 O(1) 按 key 取值,但哈希表本身不记录「谁最近用过」的顺序,找不到该淘汰谁。链表能维护使用顺序(头=最近、尾=最久),但要在淘汰或命中时删掉/移动任意一个节点,必须知道它的前驱——单链表找前驱要 O(n),只有双向链表能 O(1) 摘除并重接。哈希表负责「O(1) 定位到节点」,双向链表负责「O(1) 调整顺序」,缺一不可。

Q3:下面关于缓存的说法,哪一个是正确的?
A. 缓存越大命中率一定越高,所以应尽量做大
B. 平均访问时间 ≈ 命中率×快层延迟 + 未命中率×慢层延迟
C. 只要程序对,缓存对性能没有影响
D. LRU 一定比其它策略命中率高

B 正确。这就是缓存性能的基本估算式,命中率是主角。A 错:命中率随容量边际递减,而更大缓存更慢更贵,且顺序扫过超容大数组时容量再大也救不了(thrashing)。C 错:局部性好坏能让同一份正确代码相差数倍。D 错:LRU 只是常用启发式,遇到「循环扫过略大于容量的数据」这类模式反而可能全未命中,此时其它策略更好——没有普适最优的淘汰策略。
