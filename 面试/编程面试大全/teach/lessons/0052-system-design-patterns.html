系统设计(下):缓存、分片、一致性哈希与作答框架

上一课打了地基(数字直觉 + CAP)。这节课发武器:缓存、分片与复制、一致性哈希、消息队列——这几件几乎是每道系统设计题都要用到的通用手段。最后把它们收进一套作答框架:一道 45 分钟的系统设计题到底该怎么组织,才能既有条理又能展示深度。这是整个精读课的收官课。

先回忆:上一课我们说「内存≪SSD≪磁盘≪网络」的延迟台阶,以及 CAP 的取舍;又在很早的哈希表里学过用哈希函数把键映射到桶。这节课的一致性哈希,正是把「哈希映射」和「分布式取舍」两个旧知识拼到一起。先自己想一句:如果你把数据按 hash(key) % N 分到 N 台机器上,某天要加第 N+1 台,会发生什么灾难?

一、缓存:最便宜的提速,和它的三个坑

缓存就是把慢速数据源(数据库、磁盘)的热点结果,暂存到快速层(内存)。呼应上一课的延迟表:内存比数据库快几个数量级,命中缓存就是白赚的速度。最常用的模式是缓存旁路(Cache-Aside):应用先查缓存,未命中再查库并回填缓存。

但缓存有三个经典的坑,面试官爱一次性追问:

问题是什么应对
缓存穿透大量查根本不存在的键,每次都绕过缓存打到库缓存空值;或用布隆过滤器先挡
缓存雪崩大量键同一时刻过期,请求瞬间全压到库过期时间加随机抖动,错开失效
缓存击穿某个热点键过期瞬间,海量请求同时穿透去重建加互斥锁,只让一个请求去重建

三个坑的共性:缓存没挡住,压力直达数据库。理解了「缓存是数据库的护盾」,应对办法自然就推得出来——要么让不存在的键也被挡下(穿透),要么别让护盾同时消失(雪崩/击穿)。

二、分片与复制:一台装不下、扛不住怎么办

数据大到一台机器装不下,就分片(sharding):按某个键把数据水平切到多台。读写压力大,就复制(replication):做主从多副本,主库写、从库分摊读。二者常一起用。

Sharding
分片
按键水平切分,扩容量
Replication
主从复制
多副本,扩读 + 容灾
Message Queue
消息队列
异步削峰 + 解耦

分片的天真做法是 hash(key) % N。它平时工作良好,但一旦机器数 N 变化(加机、宕机),几乎所有键的归属都会改变——因为取模的结果全变了。这意味着一次扩容要迁移几乎全部数据、缓存全部失效,系统直接雪崩。这正是上面 recall 里埋的灾难。

三、一致性哈希:让增删节点只动一小块

一致性哈希的巧思:不把键映射到「机器编号」,而是把机器和键都映射到同一个环(0 到 2³² 首尾相接)。每个键顺时针找到的第一个节点,就是它的归属。

妙在增删节点只影响环上相邻的一小段:新增 N5 落在 N1 和 N2 之间,只有那段弧上的键从 N2 挪到 N5,别的键完全不动。相比取模法「动一台迁全部」,一致性哈希把迁移量从 O(全部) 降到大约 O(数据量 / 节点数)。(工程上还会给每个物理节点分配多个虚拟节点,让键分布更均匀。)这就是分布式缓存、分布式存储普遍采用它的原因。

四、SQL vs NoSQL:又一个权衡题

维度SQL(关系型)NoSQL
结构固定表结构 (schema)灵活 / 无固定结构
事务强事务 (ACID)多为最终一致 (BASE)
扩展垂直为主,分片较难为水平扩展而生
擅长复杂查询、强关联、强一致海量数据、高吞吐、结构多变

又一次,没有「哪个更好」,只有「合不合适」:要复杂关联和强一致(如金融)选 SQL;要海量写入和灵活结构(如日志、feed)选 NoSQL。这与上一课 CAP 的取舍一脉相承。

五、作答框架:45 分钟怎么组织

把上面所有武器收进一条流水线。系统设计题的第一名大忌是一上来就画架构图——你连要解决什么都没问清,画的一定是错的。正确的顺序是:

第 ⑤ 步是拉开差距的地方:主动说「这里数据库会成瓶颈,我加读缓存 + 主从复制;写入峰值高,我前面加消息队列削峰」——把这节课的武器一件件挂上去,并说清每件的取舍。以「设计一个短链服务」为例:澄清(要不要自定义短码、多少读写)→ 估容量(读远多于写,重缓存)→ API(POST /shorten、GET /{code})→ 数据模型(短码↔原始 URL)→ 主干(负载均衡 + 应用 + 缓存 + 分片存储)→ 深挖(发号器怎么避免冲突、热点短码怎么缓存)。

六、关键定义

一致性哈希(Consistent Hashing)
把节点和键映射到同一个哈希环,增删节点时只有相邻区间的键需要迁移。避免与普通「取模哈希分片」混同——后者一变节点数几乎全部键都要迁。
分片 vs 复制(Sharding vs Replication)
分片按键把数据水平切到多机(扩容量);复制做多副本(扩读、容灾)。避免把「分片」等同于「加缓存」,二者解决的问题不同。
缓存三问(穿透 / 雪崩 / 击穿)
穿透=查不存在的键绕过缓存;雪崩=大量键同时过期;击穿=单个热点键过期瞬间被击穿。避免把三者混为一谈——应对手段各不相同。

面试怎么考。 这是系统设计的「实战」半区:

  • 45 分钟怎么组织?——照「澄清 → 估容量 → API/数据模型 → 画主干 → 深挖瓶颈」五步走,开场务必先问需求。
  • 能不能主动找瓶颈?——不等面试官问,自己指出「数据库读压力大 → 加缓存」「写峰值高 → 加消息队列」「单表装不下 → 分片 + 一致性哈希」,并讲清取舍。
  • 经典题套路:短链、feed 流、限流器、键值存储——都能套这套框架。缓存、分片、一致性哈希、消息队列是反复出现的积木。
  • 一致性哈希 vs 取模:能说清「取模一改节点数就全量迁移,一致性哈希只迁相邻段」就是加分项。

一上来就画架构、不问需求,是系统设计的头号大忌。 需求没澄清就动手,等于答一道你没读完的题。先花几分钟问清:功能范围、读写比例、规模量级、一致性要求。

别把一致性哈希和取模分片混为一谈。 取模 hash(key) % N 在 N 变化时几乎全部键重映射;一致性哈希只影响环上相邻的一小段。这个区别是高频追问。

缓存三个坑的应对不能张冠李戴。 穿透靠「缓存空值 / 布隆过滤器」,雪崩靠「过期时间加随机」,击穿靠「互斥锁重建」——答错对应关系会露怯。

动手核对,用一道真题把框架跑通:

挑「设计一个短链服务」或「设计一个限流器」,不看答案,自己按五步在纸上写一遍:先列你会向面试官澄清的 3~5 个问题,再估容量,定 API 和数据模型,画出高层架构主干,最后至少指出 2 个瓶颈并给出用到本课武器(缓存/分片/一致性哈希/队列)的解决方案。写完对照 System Design Primer 里的同类案例查漏。

带走这一条: 系统设计的高分不来自记住多少组件,而来自先问需求、再按框架推进、主动找瓶颈并讲清每一步的取舍。缓存、分片、一致性哈希、消息队列只是积木;真正被考察的,是你在约束下做权衡的思维方式。

七、自测题

Q1:一个用 hash(key) % N 分片的系统,从 4 台机器扩到 5 台。大约多少比例的键需要迁移?换成一致性哈希呢?

取模法:N 从 4 变 5,取模结果几乎全变,约 80% 甚至更多的键都要迁移,缓存大面积失效——这就是取模分片不能随意扩容的原因。一致性哈希:新节点只从环上相邻节点接管一小段,理想情况下只迁移约 1/5(新节点应承担的那一份)的键,其余不动。这个对比是面试高频追问点。

Q2:凌晨大量商品缓存被设置成「12:00 整点统一过期」,结果一到点数据库 QPS 瞬间飙升差点打挂。这属于哪个缓存问题,怎么解?

这是缓存雪崩——大量键在同一时刻集体失效,请求瞬间全压到数据库。解法是给过期时间加一个随机抖动(如 12:00 ± 随机几分钟),把失效时间打散错开。对比:如果是「某个爆款商品的热点键过期瞬间被海量请求击穿」那是缓存击穿(加互斥锁重建);「大量查询不存在的商品 ID」才是穿透(缓存空值 / 布隆过滤器)。

Q3:面试官刚说完「设计一个新闻 feed 系统」,最不该做的第一件事是下面哪个?

最不该做的是立刻开始画详细架构图 / 选数据库。需求还没澄清就动手,方向大概率错。正确的第一步是澄清需求:是拉模式还是推模式?日活多大?读写比例?要不要实时?把范围问清后再估容量、定 API、画主干、挖瓶颈。「先问后画」是这套框架的灵魂。
