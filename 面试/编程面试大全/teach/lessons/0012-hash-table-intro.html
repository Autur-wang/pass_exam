哈希表(上):O(1) 的魔法从哪来

前面几课的结构里,「按键查东西」要么 O(n)(链表逐个找),要么依赖有序(下一批的 BST)。哈希表却能平均 O(1) 地插入、查找、删除——它几乎是面试里把 O(n²) 降到 O(n) 的头号工具。这节课只回答一个问题:这个 O(1) 到底从哪来? 想清楚它就是「用哈希函数把键直接算成数组下标」,你就抓住了哈希表的灵魂(冲突与扩容留到下一课)。

先回忆:第一课数组里,只要知道下标 i,取第 i 个元素是 O(1)——一步跳到。先想一个问题:如果我想用「字符串 "apple"」当键去查一个值,数组能直接用字符串当下标吗?哈希表要做的,就是把任意键变成一个合法的数组下标。

一、直觉:把键「算」成一个下标

数组的 O(1) 靠的是「下标 → 位置」的直接计算。哈希表的野心是:让任意类型的键(字符串、对象……)也享受这份 O(1)。做法是加一道翻译——哈希函数(hash function):把键喂进去,吐出一个整数,再对桶数组的长度取模,得到一个桶下标(bucket index)。存值就存进那个桶,取值就再算一遍下标、直接去那个桶拿。整个过程和键的总数无关,所以平均是 O(1)。

桶数组本身就是一个普通数组(呼应第一课)——哈希表并不是全新的底层结构,而是「在数组前面接了一个哈希函数」。

二、什么样的哈希函数才算「好」

O(1) 是平均意义的,前提是键被均匀撒进各个桶。所以好的哈希函数有三条性质:确定(同一个键每次算出同一个下标,否则存进去就找不回来)、均匀(不同键尽量散开,避免都挤进同一个桶)、快(计算本身要 O(1) 级别,否则 O(1) 查找就名不副实)。当很多键算到同一个桶,就发生冲突(collision);冲突越多,那个桶越像一条要逐个找的链表,查找就越滑向 O(n)。冲突怎么处理、桶什么时候该扩容,是下一课的主题——这里先记住它们的存在。

三、关键定义

哈希表(Hash Table)
用哈希函数把键映射到桶来存取的结构,平均 O(1)、最坏 O(n)。避免:「哈希表查找总是 O(1)」;中文里「散列表」是同义词,本课统一叫哈希表。
哈希函数(Hash Function)
把键映射为一个整数(再取模得桶下标)的函数,需满足确定、均匀、快。避免:把「随机数」当哈希函数——它不确定,存了取不回。
桶 / 冲突(bucket / collision)
桶是数组中存放键值对的槽位;两个不同键落到同一桶即冲突。避免:以为「好哈希函数就不会冲突」——只要键比桶多,冲突必然发生(鸽笼原理)。
装载因子(Load Factor)
= 元素个数 / 桶数,衡量桶的拥挤程度。越接近或超过 1,冲突越频繁——它是「何时该扩容」的信号(细节见下一课)。

四、复杂度:平均很美,最坏要老实说

操作平均最坏
插入 add(key, value)O(1)O(n)
查找 get(key) / exists(key)O(1)O(n)
删除 remove(key)O(1)O(n)

最坏的 O(n) 从哪来?当所有键都因为糟糕的哈希函数(或被恶意构造)挤进同一个桶,那个桶退化成一条链表,查找得逐个比对——就成了 O(n)。空间复杂度 O(n)。所以正确的说法永远是「平均 O(1),最坏 O(n)」,不能省掉后半句。

面试怎么考。哈希表是面试的「万能加速器」,核心套路是用一次遍历 + 哈希表把嵌套查找的 O(n²) 压到 O(n):

  • 两数之和(Two Sum):暴力双重循环 O(n²);改用哈希表存「已见过的数 → 下标」,每个数只需 O(1) 查「target − 当前数」在不在——整体 O(n)。这是哈希表最标志性的登场。
  • 去重 / 计数 / 分组:「有没有重复」用哈希集合、「每个元素出现几次」用哈希表计数、「按某特征分组」(如字母异位词)用哈希表归类——都是 O(n) 一趟搞定。
  • 选型追问「用哈希表还是数组还是 BST?」:需要 O(1) 按键随机存取、不在乎顺序 → 哈希表;键是紧凑小整数、直接当下标 → 数组;需要有序(范围查询、找前驱后继、按序遍历)→ BST 或有序表。答题落到「要不要顺序」这个分水岭上,就显得专业。

「哈希表查找总是 O(1)」——漏掉最坏情况会被扣分。严谨说法是「平均 O(1),最坏 O(n)」。冲突严重时(坏哈希函数、或被精心构造的输入触发大量冲突)会退化到 O(n),这在关心最坏延迟或防 DoS 的场景里是真问题。

哈希表不保证任何顺序。遍历一个哈希表,元素出来的次序通常和插入顺序、大小顺序都无关(取决于哈希与桶布局)。需要「按键有序遍历 / 范围查询 / 找最接近的键」时,哈希表无能为力,该用 BST / 有序表。这是哈希表 vs 树的根本分界。

带走这一条:哈希表的 O(1) = 「哈希函数把键直接算成数组下标」。它拿走了「顺序」,换来了「按键的常数时间存取」。面试里凡是出现「快速查这个键在不在 / 对应什么值」,先想哈希表——它多半能把一层循环消掉。

照仓库大纲实现一个用数组 + 线性探测的哈希表(冲突处理下一课细讲,这里先把骨架搭起来):

hash(k, m)(键 → [0, m) 的下标)· add(key, value)(键已存在则更新)· exists(key) · get(key) · remove(key)。

做个实验:故意写一个坏哈希函数(比如永远返回 0),插入 1000 个键,测查找耗时;再换成正常哈希函数对比——亲眼看「平均 O(1)」如何退化成「最坏 O(n)」。

五、自测题

Q1:一个哈希表用了「随机数」当哈希函数——每次调用返回一个随机下标。它能正常工作吗?为什么?

不能。哈希函数必须确定:同一个键,存的时候算出下标 3,取的时候必须还算出 3,才找得回来。用随机数,存进桶 3、取时却算到桶 7,查找必然失败。这也说明「均匀」不是唯一要求——随机数虽然"均匀",却违反了更根本的「确定性」。好哈希函数三性质缺一不可:确定、均匀、快。

Q2:「两数之和」为什么用哈希表能从 O(n²) 降到 O(n)?哈希表在这里到底替换掉了什么?

暴力解是:对每个数,再用一层循环去找「有没有另一个数等于 target − 它」——这层内循环是 O(n),整体 O(n²)。哈希表把这层内循环的查找替换成 O(1):一边遍历,一边把见过的数存进哈希表(值 → 下标),对当前数只需 O(1) 查「target − 当前数」是否已在表中。于是每个数只花 O(1),整体降到 O(n)。本质是用 O(n) 的额外空间,换掉那层 O(n) 的查找循环——这正是哈希表在面试里最经典的用法。
