哈希表(下):冲突与扩容

上一课我们说哈希表平均 O(1),但那句「平均」是有代价换来的。这节课攻的窄主题就是那个代价:两个键算到同一个桶怎么办(冲突),桶快装满了怎么办(扩容)。面试里手写哈希表,考的几乎全是这两件事——尤其是开放寻址的删除,一个坑能筛掉一半人。

先回忆:哈希表(上)里我们把哈希表拆成「哈希函数 + 一排桶(桶数组)」,并说它平均 O(1)、最坏 O(n)。请你先自己回答一句:那个「最坏 O(n)」到底是怎么发生的? 这节课就是答案。

一、冲突不是意外,是必然

桶只有 m 个,而你可能往里塞 n > m 个键。鸽巢原理(pigeonhole:n 只鸽子进 m 个巢,n>m 时必有一个巢≥2 只)直接判了死刑:只要键比桶多,就一定有两个键落进同一个桶。就算 n≤m,好的哈希函数也只是让冲突「少」,不可能「无」。所以哈希表的设计不是「怎么避免冲突」,而是「冲突了怎么优雅地存下、还能查得回」。业界两条主线路:

二、链地址法:一个桶挂一条链

链地址法(separate chaining,又叫拉链法)让每个桶不再只存一个值,而是存一条链表(冲突多时可换成树)。算到同一个桶的键,就串在这条链上;查找时先定位桶,再在链上顺序比对。

三、开放寻址:不挂链,顺着往后找空位

开放寻址(open addressing)把所有键都存在桶数组本身里,不额外挂链表(README 里明确要你实现的正是「使用线性探测法的数组实现」)。冲突时按某种规则去探测(probe)下一个位置,最简单的是线性探测:占了就看下一格,直到找到空格。

两条路线的性格差异很直白:链地址法结构简单、装载因子可以略高、删除干净利落(从链上摘一个节点即可);开放寻址数据全在连续数组里、缓存更友好、不需要额外指针,但对装载因子敏感,且——删除很麻烦(下面易错点专门讲)。

四、装载因子与扩容:哈希表的「动态数组时刻」

装载因子(load factor)α = n / m,衡量桶被塞得多满。α 越大,链越长 / 探测越久,平均查找就从 O(1) 滑向 O(n)。所以哈希表设一个阈值(链地址法常用 0.75,开放寻址通常更低如 0.5):一旦 α 超过阈值,就申请一个更大的桶数组(通常翻倍),把所有键重新哈希(rehash)搬过去。

这一步和第 0007 课动态数组扩容是同一套逻辑:单次 rehash 是 O(n),但按倍数扩容让它摊还到 O(1)。所以哈希表的「平均 O(1)」其实是两层摊还叠加:哈希函数把键摊开到各桶,倍增扩容把重建代价摊到长序列上。补一句工程细节:Java 8 的 HashMap 在单桶链表过长(≥8)且表够大时,会把该桶从链表转成红黑树,把最坏情况从 O(n) 压到 O(log n),这是对恶意冲突的防御。

五、关键定义

冲突(Collision)
两个不同的键被哈希到同一个桶。由鸽巢原理,键多于桶时必然发生。避免说「好的哈希函数能消除冲突」——只能减少。
链地址法 / 开放寻址(Chaining / Open Addressing)
两种冲突解决法:前者每桶挂一条链表(或树);后者冲突时在数组内探测下一个空位(如线性探测)。
装载因子(Load Factor α)
α = 元素数 n / 桶数 m。α 越高冲突越多、性能越退化;超过阈值触发扩容重哈希。
墓碑(Tombstone)
开放寻址中删除元素时留下的「已删」标记,用来避免探测链被截断。避免删除时直接把槽位置空。

空间 O(n)(外加为把 α 压住而预留的常数倍空桶)。注意最坏列全是 O(n):当哈希函数极差或被攻击者构造出全冲突时,哈希表就退化成一条链/一次线性扫描——这正是上一课「最坏 O(n)」的来源,也是 Java 8 要把长链转树的原因。

面试怎么考。这个主题几乎总以「手写一个哈希表」出现,而且多半点名开放寻址 + 线性探测(README 要求实现 hash/add/exists/get/remove)。面试官会顺着追问三层:

  • 「装载因子设多少、什么时候扩容?」——答:超过阈值(如 0.75)翻倍重哈希,理由是把平均链长/探测长度压在常数,代价摊还 O(1)。
  • 「为什么容量常取 2 的幂?」——因为 hash % m 在 m 是 2 的幂时等价于 hash & (m - 1),位与比取模快得多。前提是哈希值本身分布要好,否则只用低位会更容易撞。
  • 「删除怎么做?」——这是筛人题,见下方易错点。

开放寻址的删除:直接置空会「断链」。假设 11 在桶 3、探测过来的 19 在桶 4。若你删掉 11 时把桶 3 直接清空,之后查找 19 会在桶 3 看到空格,误判「后面不可能有了」而提前放弃——19 明明还在桶 4,却查不到了。正确做法是给桶 3 打一个墓碑(tombstone)标记:查找遇到墓碑继续往后探,插入可以覆盖墓碑。墓碑攒多了也要靠重哈希清理。

另一个坑:装载因子放太高图省内存。α 逼近 1 时,链地址法链变长、开放寻址更是探测到「几乎扫全表」,平均 O(1) 名存实亡。省的那点内存,换来的是查询整体变慢。

照 README 大纲,徒手实现一个线性探测哈希表(定长数组起步,先不扩容也行,但要能说清怎么扩):

hash(k, m) · add(key, value)(键已存在则更新)· exists(key) · get(key) · remove(key)(用墓碑!)· 私有 resize()(α 超阈值时翻倍并重哈希)。

验证实验:故意用一个烂哈希函数(如 hash = 0 恒返回同一桶),打印一次查找要探测几格——你会亲眼看到它退化成 O(n)。再换成 2 的幂容量 + 掩码,对比平均探测次数。

带走这一条:哈希表的 O(1) 是「摊还 + 平均」——靠好的哈希函数把冲突压少、靠倍增重哈希把装载因子压住;一旦冲突失控或删除处理错(开放寻址不打墓碑),它就退化成 O(n)。

七、自测题

Q1:用线性探测实现的哈希表,删除一个键时,下面哪种做法是对的?

给该槽位打上「墓碑」标记,而不是直接置空。因为其他键可能是冲突后探测到当前键之后的位置的;若直接清空,查找那些键时会在这个空槽提前中止,导致它们「查不到」(探测链被截断)。墓碑让查找遇到它继续往后探,同时允许后续插入覆盖它。直接置空是最经典的错误答案。

Q2:哈希表容量常取 2 的幂(如 16、32),主要好处是下面哪一个?

可以用 hash & (m - 1) 代替 hash % m 来求桶下标,位与比取模快。当 m = 2^k 时,m - 1 的低 k 位全 1,位与恰好取出哈希值的低 k 位,等价于对 m 取模。干扰项要警惕:它不能「消除冲突」,也不会让最坏情况变成 O(1);它只是让「定位桶」这一步更快,且要求哈希值本身分布均匀,否则只看低位反而更易撞。

Q3:装载因子 α 从 0.5 升到 0.95,对一个线性探测哈希表意味着什么?

平均探测长度急剧变长,查找/插入从接近 O(1) 明显退化。开放寻址对 α 特别敏感:α 接近 1 时空位稀少,一次插入可能要探测很多格才找到空位,查找同理。这就是为什么开放寻址的扩容阈值通常比链地址法更低(约 0.5 vs 0.75)。省内存(让 α 更高)是用查询速度换的,不是免费的。
