# Patterns — 编程面试速查表技术模式

## 用哈希表换取 O(1) 查找
**When to use**: 需要频繁"某个值是否存在""按 key 查值",且不关心元素顺序时(如两数之和、去重、计数)。
**How**: 用 `dict`(Python)/`HashMap`(Java)/`unordered_map`(C++,注意本速查表因成书早未收录)/哈希表(通用)存储 key→value,平均 O(1) 存取。
**Trade-offs**: 最坏情况(大量哈希冲突)退化到 O(n);不保证遍历顺序(Python 3.7+ 的 dict 保证插入顺序是语言实现细节,不属于"哈希表"这个通用数据结构本身的保证)。

## 数组 vs 链表的选择
**When to use**: 需要按下标随机访问、且大小相对稳定 → 数组/`vector`;需要频繁在中间插入删除、且很少随机访问 → 链表/`list`。
**How**: 参照 Ch01 复杂度表——数组 Access O(1)/Insert O(n);链表 Access O(n)/头部 Insert O(1)。
**Trade-offs**: 数组连续内存,缓存局部性好,实际运行常比链表快,即使渐近复杂度更差;链表每个节点有额外指针开销。

## 排序算法选型
**When to use**: 数据量大、追求平均性能 → Quicksort;需要稳定排序或最坏情况保证 → Mergesort;内存受限(只需 O(1) 额外空间)且能接受不稳定 → Heapsort。
**How**: 三者平均都是 O(n log n)(见 Ch01 表),区别在最坏情况复杂度、额外空间、稳定性三个维度。
**Trade-offs**: Quicksort 最坏 O(n²)(已排序输入 + 差劲 pivot 选择时最明显);语言内置排序(Python `sorted`/Java `Collections.sort`)通常已选好稳定的 Timsort/Mergesort 变体,面试更多考"为什么选它"而非手写。

## 位运算代替算术运算/状态压缩
**When to use**: 需要判断奇偶(`n & 1`)、快速乘除 2 的幂(`<<`/`>>`)、用一个整数表示一组开关状态(位掩码)。
**How**: 参照 Ch02 位宽表确认不会溢出;用 `&`(取交集/判断某位)、`|`(置位)、`^`(翻转位/交换两数不用临时变量)、`~`(取反)组合。
**Trade-offs**: 位运算比取模/除法快,但可读性差,需要注释说明每个 bit 代表什么;不同语言"有符号右移"的行为需要提前确认(算术右移 vs 逻辑右移)。

## 用字典模拟 switch
**When to use**: Python 没有原生 `switch`,分支较多且每支逻辑简单(直接返回一个值)时。
**How**: `switcher = {0:"zero", 1:"one"}; return switcher.get(argument, default)`。
**Trade-offs**: 每支逻辑复杂(需要多条语句)时不如 `if/elif` 链清晰;`dict.get` 的第二参数就是默认分支,不要漏写。

## 自定义比较器 / 函数对象
**When to use**: 需要对自定义类型排序、或改变默认排序规则(如降序、按某个字段排序)。
**How**: C++ 传一个重载了 `operator()` 的类(Functor)作为 STL 算法/容器的 `Compare` 模板参数;Java 实现 `Comparable`/传 `Comparator`;Python 传 `key=` 函数给 `sorted()`。
**Trade-offs**: 三种语言实现机制不同(模板 vs 接口 vs 一等函数),但目的一致——把"怎么比较"这件事从算法本身剥离出来,可替换。

## 按引用传递避免复制大对象
**When to use**: C++ 中函数需要修改调用者的变量,或传递大对象/容器时避免整体复制的开销。
**How**: 参数声明为 `type &p1`(引用)而非 `type p1`(按值);只读大对象用 `const type &p1` 既避免复制又防止误改。
**Trade-offs**: C 没有引用语法,只能用指针(`type *p1`)模拟同样效果,但需要显式解引用 `*p1`,语法上更容易出错。

## 异常处理三段式(try/except-catch/finally)
**When to use**: 操作可能失败(文件 I/O、类型转换、网络请求)且失败后需要清理资源或给出明确提示。
**How**: Python/Java/C++ 都提供 `try + 一个或多个 catch/except(按异常类型从具体到通用排列) + finally`(清理代码,无论是否异常都执行)。
**Trade-offs**: 用异常控制正常业务逻辑(而非真正的异常情况)通常是反模式,异常应该保留给真正意外的失败路径。

## 容器适配器选择(stack/queue/priority_queue)
**When to use**: 只需要 LIFO → `stack`;只需要 FIFO → `queue`;需要每次取最大/最小值 → `priority_queue`。
**How**: 三者都是"包装现有容器、暴露受限接口"的适配器(见 Ch09),不需要自己实现底层数据结构。
**Trade-offs**: 适配器不支持遍历(没有 `begin()/end()`),如果既要"按优先级弹出"又要"遍历查看所有元素",适配器不够用,需要直接用底层容器 + 手动维护。

## Git 分支整合:rebase vs merge
**When to use**: 需要保持线性、干净的提交历史(如准备提 PR 前整理commit)→ `rebase`;需要保留真实的并行开发历史、且分支已经共享给他人 → `merge`。
**How**: `git rebase [branch]` 把当前分支提交重新应用到目标分支之后;`git merge [branch]` 产生一个额外的合并提交,保留两条历史线。
**Trade-offs**: **绝不要 rebase 已经推送到共享远程、其他人可能已基于其开发的提交**——这会改写提交历史,导致协作者的本地历史与远程产生冲突。

## 系统设计三步走
**When to use**: 系统设计面试开场,不确定该先做什么的时候。
**How**: (1) 和面试官对齐范围与用例,主动提议/砍需求;(2) 估算 QPS、读写比、存储量等约束;(3) 基于约束做分层抽象设计(服务层/数据层/缓存层/基础设施)。
**Trade-offs**: 跳过第 1、2 步直接画架构图是最常见的失分点——面试官更想看到"如何把模糊问题变具体"的过程,而不是背出来的架构图。
