# Cheatsheet — 面试速查决策表

## 数据结构选型决策树
```
需要按 key 快速查值,不关心顺序?
├─ 是 → Hash Table(平均 O(1),最坏 O(n))
└─ 否,需要保持有序?
    ├─ 是 → 平衡树(Red-Black/AVL/B-Tree,稳定 O(log n)) / STL 的 set/map
    └─ 否,主要按下标随机访问?
        ├─ 是,大小相对固定 → Array / vector
        ├─ 是,频繁在两端增删 → Deque
        └─ 否,频繁在中间插入删除、很少随机访问 → Linked List
```

## 排序算法选择矩阵
| 场景 | 选择 | 理由 |
|---|---|---|
| 追求平均最快、内存不敏感 | Quicksort | 平均 Θ(n log n),但要接受最坏 O(n²) 的风险 |
| 需要稳定排序(相等元素保持原相对顺序) | Mergesort / Timsort | 语言内置排序通常已是这两者之一(如 Python `sorted`、Java `Collections.sort`) |
| 内存极度受限,只要 O(1) 额外空间 | Heapsort | 唯一同时满足"最坏 O(n log n)"与"O(1) 空间"的选项 |
| 数据几乎已排序 | Insertion Sort / Timsort | 对近乎有序输入退化到接近 O(n) |
| key 范围小且已知(如 0–255) | Counting Sort | O(n+k),k 是 key 范围,不基于比较 |

## 整数位宽速记(阈值表)
| 位宽 | 无符号最大值 | 有符号范围 | 常见对应类型 |
|---|---|---|---|
| 8 | 255 | [-128, 127] | `byte`(Java)/`char`(C) |
| 16 | 65,535 | [-32768, 32767] | `short` |
| 32 | 4,294,967,295 | [-2,147,483,648, 2,147,483,647] | `int`(Java/C 通常) |

**判断溢出的规则**:操作数范围一旦可能超出目标类型的有符号区间(尤其是加法/左移),就要先转型为更宽类型或做溢出检查——Python 例外(整数无固定位宽,不会溢出)。

## C/C++/Java 三语言对照速查
| 概念 | C | C++ | Java |
|---|---|---|---|
| 引用传递 | 只能用指针 `type *p` 模拟 | 原生引用 `type &p` | 对象默认按引用语义,基本类型按值 |
| 内存管理 | `malloc/free` 手动 | `new/delete` 手动(必须配对,数组用 `[]` 版本) | 垃圾回收自动 |
| 字符串 | `char[]`,以 `\0` 结尾 | `std::string`(STL) | `String`(不可变对象) |
| switch 缺 break | 贯穿执行(fall-through) | 同 C | 同 C |
| 泛型 | 无(靠函数指针 `cmpf` 模拟) | 模板 `template<class T>` | 泛型 `<T>`(类型擦除) |

**规则**:换语言做同一道题时,先确认"这门语言的引用/内存管理模型",再翻译算法逻辑——语法差异远小于这两点带来的思维差异。

## Git 操作风险分级
| 操作 | 风险 | 使用前提 |
|---|---|---|
| `git add` / `git commit` | 低,本地可撤销 | 随时可用 |
| `git branch` / `git checkout` | 低 | 随时可用 |
| `git merge` | 中,产生额外合并提交但历史不丢失 | 分支已共享给他人时的默认选择 |
| `git rebase` | 中高,改写提交历史 | **仅用于尚未推送到共享远程的本地提交** |
| `git reset --hard` | 高,**不可逆**,清空工作区+暂存区 | 确认没有需要保留的改动后才用 |
| `git push --force` | 高,可能覆盖他人已推送的提交(本速查表未收录该命令,但属于同一风险等级,补充提醒) | 团队协作中原则上避免 |

## STL 容器选型速查(结合 Ch01+Ch09)
| 需求 | 选择 | 备注 |
|---|---|---|
| LIFO | `stack`(适配器) | 默认底层 `deque` |
| FIFO | `queue`(适配器) | 默认底层 `deque` |
| 每次取最大/最小 | `priority_queue`(适配器) | 默认底层 `vector`,本质是堆 |
| 有序去重集合 | `set` | 红黑树实现,O(log n) |
| 有序键值映射 | `map` | 同上 |
| 只需要遍历+尾部追加,不需要有序 | `vector` | 均摊 O(1) 尾插,随机访问 O(1) |
| 频繁头尾增删 | `deque` | 两端均 O(1) |
| 需要在已知位置频繁插入/删除、且已有迭代器指向该位置 | `list` | O(1) 插入/删除,但不支持随机访问、不能用 `std::sort` |

## Tells & Smells(面试中的信号)
- 面试官提到"频繁查找是否存在" → 大概率在暗示 Hash Table。
- 题目提到"保持插入顺序但要求 O(log n) 查找" → 暗示平衡树而非哈希表。
- 候选人直接开始画架构图、没有先问 QPS/读写比 → 系统设计面试中的典型减分项(见 Ch10 三步走)。
- 代码里出现 `switch` 却没写 `break` → 检查是否是有意的 fall-through,否则是 bug。
- Python 代码里 `[[0]*n]*n` 构造二维数组 → 几乎总是 bug(共享内部引用),应改用列表推导式。
