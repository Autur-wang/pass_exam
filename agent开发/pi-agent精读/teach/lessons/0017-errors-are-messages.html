Lesson 0017 · 第 5 章 工具系统

永不抛出
—— 工具出错,也只是一条消息

🎯 本课目标:上一课讲完调度器怎么并行/串行地把工具调用发出去, 这一课回答一个更扎心的问题——如果某个 tool.execute() 内部炸了(文件不存在、 权限拒绝、超时、JSON 解析失败),这颗雷会不会把整条 Agent Loop 一起炸掉? Pi 的答案是:不会。异常永远不会以「异常」的身份逃出工具执行这一步。
🔁 回忆上一课: 调度器决定「工具调用什么时候发、几个一起发」,但它没回答「工具发出去之后, 如果炸了怎么办」。这节课把镜头对准 tool.execute() 内部这一步——五步管道里最容易出错、 也最难防的一环。
这节课你将能做到一件事: 讲清楚 6 种错误 → 1 种产物 的统一出口规律,并说出 executePreparedToolCall 那段 try-catch-finally 做的三件事,以及为什么让模型自己决定下一步,比框架替它决定更聪明。
🎯 贯穿全课的类比:医院的分诊台。 不管你是感冒、骨折,还是一种叫不出名字的怪病,分诊台都不会把你直接轰出医院—— 而是统一登记成一张病历卡交给医生。病历卡上写得越具体(「腹痛 3 天,右下腹压痛」 远胜「不舒服」),医生(模型)就越知道下一步该怎么治。 Pi 对工具错误做的正是这件事:不管错误多稀奇,都统一「登记」成一条消息,交给模型这位「医生」。

1 · 6 种错误,1 种产物

五步管道(参数预处理 → Schema 验证 → 权限拦截 → 工具执行 → 结果后处理)里,每一步都可能出错。 但把六种出错场景摆在一起,你会看到一个惊人的规律——右列永远长一个样:

哪一步出错怎么处理最终产物
工具未找到直接返回错误结果,不进入管道isError:true,content:"Tool xxx not found"
prepareArguments 抛异常被 try-catch 捕获isError:true,content:异常信息
Schema 验证失败被 try-catch 捕获isError:true,content:验证错误描述
beforeToolCall 阻止返回阻止结果isError:true,content:阻止原因
tool.execute 抛异常被 executePreparedToolCall 的 try-catch 捕获isError:true,content:异常信息
afterToolCall 抛异常被 finalizeExecutedToolCall 的 try-catch 捕获isError:true,content:异常信息
为什么这张表值得多看一眼? 没有一种错误以「抛异常」的形式逃出管道——所有分诊结果都收敛成同一种 ToolResultMessage。这不是巧合,是设计:管道的每一环都自带 try-catch「兜底网」, 异常一进来就被网住,翻译成消息再放行。
🔎 出处:教程第 5 章 §四 / 错误的统一出口。

2 · 核心防线:executePreparedToolCall 的双重防护

六种错误里,最容易「防不住」的就是 tool.execute()——它是开发者写的业务代码, 什么姿势的异常都可能抛出来。包住它的就是这段代码: 

1// packages/agent/src/agent-loop.ts:628-669
2async function executePreparedToolCall(prepared, signal, emit) {
3    const updateEvents: Promise<void>[] = [];
4    let acceptingUpdates = true;          // 工具 Promise settle 后关闭
5
6    try {
7        const result = await prepared.tool.execute(
8            prepared.toolCall.id,
9            prepared.args,
10            signal,
11            (partialResult) => {
12                if (!acceptingUpdates) return;     // settle 后的孤儿回调直接忽略
13                updateEvents.push(/* ... 发 tool_execution_update ... */);
14            },
15        );
16        acceptingUpdates = false;
17        await Promise.all(updateEvents);
18        return { result, isError: false };
19
20    } catch (error) {
21        acceptingUpdates = false;
22        // 关键:先等所有进度事件发完,再把异常编码成消息
23        await Promise.all(updateEvents);
24        return {
25            result: createErrorToolResult(
26                error instanceof Error ? error.message : String(error)
27            ),
28            isError: true,
29        };
30    } finally {
31        acceptingUpdates = false;          // 兜底:无论如何都关闭闸门
32    }
33}

这段代码做了三件事,每一件都对应一个工程上的关键决策:

动作做了什么
① 异常被 catch,不穿透ENOENT/EACCES/TIMEOUT/SyntaxError——统统在这里止步,不再往外传
② 异常被「翻译」成正常结果createErrorToolResult(error.message) 把异常对象转成一个 AgentToolResult,长得跟正常结果一模一样,只是 content 里装的是错误文本
③ 进度事件先发完,再编码错误catch 里先 await Promise.all(updateEvents),确保已发出的 tool_execution_update 全部送达,才发出错消息
🔑 为什么③这一步不能省? 如果不先等进度事件发完就编码错误,UI 会看到工具「先报错、 再吐出最后一行进度」的诡异顺序——这和 0016 讲过的事件顺序正确性是同一类防御性细节。 finally 里再兜底关一次 acceptingUpdates 闸门,保证无论走哪条分支, settle 后的孤儿回调都不会再往外发事件。
🔎 出处:教程第 5 章 §四 / agent-loop.ts:628-669。

3 · 为什么「伪装成消息」是最佳处理方式

你可能会想:异常抛出去给外层统一处理不也行吗?为什么要费劲翻译成一条「长得像正常结果」的消息?

回到分诊台的类比:异常的接收者是调用栈(把你直接送进 ICU,打断一切正常流程); 消息的接收者是模型(病历卡交给医生,医生消化信息后继续问诊)。 异常和消息描述的是同一件事,区别只在于——谁来接收、接收之后能不能继续。
错误场景模型看到错误消息后的合理反应
read("/path/a.ts") 报"文件不存在"先 ls 看看目录里有什么,找到正确文件名再读
edit 报"oldText 找不到匹配"先 read 文件查看实际内容,调整 oldText 后重试
bash("npm run build") 报"模块未找到"npm install 后再 build
bash("rm -rf /") 被 beforeToolCall 阻止看到阻止原因,换一种安全的写法或向用户解释
为什么模型比框架更适合决定下一步? 框架不知道「文件不存在」是路径写错了还是该换个文件; 模型知道——它知道自己刚才想干什么,知道项目结构(前面 read/grep 的结果都在对话历史里), 知道用户的真实意图。如果框架直接抛异常打断循环,等于放弃了模型的自我纠错能力, 用户只能在 Agent 崩溃后手动重启。

一句话哲学: 错误信息是给模型的反馈,不是给框架的终止信号——这正是 Agent 比传统脚本 更「智能」的关键,错误成为下一步决策的输入,而不是流程的终点。
🔎 出处:教程第 5 章 §四 / 为什么"伪装成消息"是最佳处理方式。

4 · 错误描述越具体,模型纠错越强

到这里你可能会想:「反正框架会兜底,那我工具内部随便 throw new Error("failed") 不就行了?」——绝对不行。 错误消息的内容直接决定模型能不能纠错: 

1// 模糊错误(不可取)
2{
3  content: [{ text: "Read failed" }],
4  isError: true
5}
6
7// 具体 error.message(推荐)
8{
9  content: [{
10    text: "Offset 200 is beyond end of file (100 lines total)"
11  }],
12  isError: true
13}

模型看到 "Read failed",只能盲目重试或放弃;看到 "Offset 200 is beyond end of file (100 lines total)",能立刻明白「哦,文件只有 100 行, offset 给大了」,下次直接给 offset: 50 就成了。 具体的错误描述等于给模型一份「怎么改才对」的提示。

🔎 出处:教程第 5 章 §四 / 错误描述越具体那段。

5 · 两层错误处理,分层负责

Pi 自己的工具从不「靠框架兜底交差」,而是内部就把描述写得很具体。看 Bash 工具的 catch 块—— 一段教科书级别的「主动识别 + 重新包装」: 

1// bash.ts:390-407
2} catch (err) {
3    const snapshot = await finishOutput();              // 先把已经输出的内容固定下来
4    const { text } = formatOutput(snapshot, "");
5    if (err instanceof Error && err.message === "aborted") {
6        throw new Error(appendStatus(text, "Command aborted"));
7        // 重新包装:附上"中止前的输出" + "中止状态"
8    }
9    if (err instanceof Error && err.message.startsWith("timeout:")) {
10        const timeoutSecs = err.message.split(":")[1];
11        throw new Error(appendStatus(text, `Command timed out after ${timeoutSecs} seconds`));
12    }
13    if (exitCode !== 0 && exitCode !== null) {
14        throw new Error(appendStatus(outputText, `Command exited with code ${exitCode}`));
15    }
16    throw err;    // ← 关键:识别不了的异常,原样抛出,交给框架兜底
17}

注意 Bash 的策略——它主动识别已知的错误类型(中止、超时、非零退出码), 每种都用 appendStatus(text, ...) 把「已经输出的内容」和「具体原因」打包成新的 Error。 只有遇到实在识别不了的异常,才 throw err 原样抛出。

两层错误处理,分层负责 第一层(工具内部,主动):识别已知错误类型,包装成具体可读的描述 └── Read/Edit/Bash 都是这样——Bash 甚至把"已输出的内容"附在错误里 └── 目的:给模型提供"为什么失败、怎么改才对"的具体线索 第二层(框架兜底,被动):executePreparedToolCall 的 catch └── 只在工具没识别出来时生效 └── 不创造新的错误描述,只把 error.message 原样透传给模型 └── 目的:保证任何异常都不会穿透到 Agent Loop
🔑 写自定义工具的两个原则:
1. 能识别的错误一定要包装——附上「是什么错、为什么、怎么办」的线索。 "文件不存在"比"操作失败"强 10 倍;"文件 /a.ts 不存在,目录下有 [b.ts, c.ts]" 比"文件不存在"又强 10 倍。
2. 识别不了的不要硬编码描述——直接 throw err,让框架兜底 catch 把 err.message 透传出去。不要写 throw new Error("操作失败") 这种笼统描述——那等于把所有未知错误都涂成同一种颜色,模型无法区分。
🔎 出处:教程第 5 章 §四 / Pi 的真实做法:两层错误处理,分层负责;bash.ts:390-407。
