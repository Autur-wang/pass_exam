Lesson 0003 · 第 1 章 开篇总览

四种运行模式与 models.json 配置

🎯 本课目标:上一课我们摊开了三层堆栈的结构—— pi-ai → pi-agent-core → pi-coding-agent。这一课回答一个更实际的问题: 这套堆栈怎么被跑起来?本课只讲两件窄事——Pi 的四种运行模式, 以及如何用 models.json 把它接到国内的第三方模型上。
↩️ 回忆一下上一课: 三层堆栈里,pi-coding-agent 是顶层, 它既组装成一个完整的 CLI 产品,也暴露 SDK 接口供你嵌入自己的应用。 这节课要展开的「四种运行模式」,其实就是这同一套堆栈的四种不同穿法—— 同一个核心,不同的外壳。
这节课你将能做到一件事: 说清 Pi 的四种运行模式 各自解决什么场景,并且能亲手写一份 models.json,把智谱、DeepSeek 这类国内模型接进 Pi—— 不用再死等一个 ANTHROPIC_API_KEY 环境变量。
🎯 贯穿全课的类比:一台既能手动开、也能装上流水线的机床
把 Pi 想成一台机床。交互模式是你亲手扳动手柄操作它;print/JSON 模式 是把它接进自动化流水线,喂一个指令、吐一份结果就退出;RPC 模式是它旁边站着一个 不懂机床语言的机器人(比如 Python/Go 写的程序),两边靠标准化的纸条(JSON)递话; SDK 模式是干脆把整台机床嵌进你自己的工厂产线里,变成你产品的一部分。 而 models.json 就是这台机床的「刀具登记表」——你得写清每把刀(模型) 从哪进货(baseUrl)、用哪种接口卡口(api)、叫什么型号(id), 机床才认得怎么装上去用。

1 · 四种运行模式:同一套核心,四种穿法

Pi 不是只能在终端里手动敲命令的玩具——它把「跑起来」这件事拆成了四种模式, 覆盖从个人开发到生产系统的全部场景:

模式用途示例
交互模式日常编程的经典 TUIpi
print/JSON 模式脚本和 CI/CD 流水线pi -p "explain this code"
RPC 模式通过 stdin/stdout 交换 JSON,集成进非 Node.js 程序父进程写 JSON 到 stdin,读 stdout
SDK 模式嵌入自己的应用createAgentSession()

先看前两种模式在命令行上长什么样,建立最直观的感受:

1// 交互模式:日常手动敲,进入 TUI 界面
2$ pi
3
4// print/JSON 模式:一次性喂指令,吐结果就退出,适合塞进 CI 脚本
5$ pi -p "explain this code"
为什么要设计出四种模式,而不是一种「够用就行」? 因为项目会长大。 同一套框架要能覆盖「开发者手边随手一用」到「CI 脚本里跑一次」再到「生产系统里长期驻留」的全场景—— 这让 Pi 可以从「开发者手边的工具」无缝演进为「生产系统中的 Agent 能力提供者」, 项目长大后不需要中途换框架。

2 · SDK 模式实战:createAgentSession()

四种模式里,前两种(交互、print/JSON)是「用」,SDK 模式是「嵌」——把 Pi 整个 Agent 能力 当作一个库调用,塞进你自己的应用里。核心入口是 createAgentSession(): 

1import { createAgentSession } from '@earendil-works/pi-coding-agent';
2import { getModel } from '@earendil-works/pi-ai/compat';
3
4const session = await createAgentSession({
5  cwd: '/path/to/project',
6  model: getModel('anthropic', 'claude-sonnet-4-5'), // Model 对象,不是 {id, api}
7});
8
9// subscribe 接收一个监听器函数,事件类型是 AgentSessionEvent 联合类型
10session.subscribe((event) => {
11  if (event.type === 'turn_end') {
12    console.log('Agent 完成了一轮思考');
13  }
14});
15
16await session.prompt('Read the codebase and explain the architecture.');

注意第 4–7 行传的 cwd 与 model,以及第 10 行用 subscribe 订阅 turn_end 事件——这跟交互模式底下跑的是同一套引擎,只是外面不再套 TUI, 换成你自己的应用逻辑来接收事件、决定下一步。

🔎 出处:教程 §5.1 / pi-coding-agent(createAgentSession)。

3 · 一个环境变量搞不定第三方模型

官方教程默认让你设 ANTHROPIC_API_KEY,但真实项目里你大概率要接的是 国内的智谱、DeepSeek、Kimi、Qwen 之类。这些不可能靠一个环境变量搞定—— 你得同时告诉 Pi:baseUrl 在哪、用哪种 api 协议、模型 id 叫什么、 上下文窗口多大。一个字符串装不下这四件事。

Pi 的解法是本地 JSON 配置文件 ~/.pi/agent/models.json,由 ModelRegistry.create() 在启动时自动读取,不需要任何命令行参数。看一个真实例子 (zhipu 与 deepseek 两个 provider): 

1{
2  "providers": {
3    "zhipu": {
4      "baseUrl": "https://open.bigmodel.cn/api/paas/v4",
5      "api": "openai-completions",
6      "apiKey": "<your-zhipu-key>",
7      "models": [
8        { "id": "glm-4.5-air", "name": "GLM-4.5-Air" },
9        { "id": "glm-4-flash", "name": "GLM-4-Flash" }
10      ]
11    },
12    "deepseek": {
13      "baseUrl": "https://api.deepseek.com",
14      "api": "openai-completions",
15      "apiKey": "<your-deepseek-key>",
16      "models": [
17        { "id": "deepseek-v4-flash", "name": "DeepSeek V4 Flash" },
18        {
19          "id": "deepseek-v4-pro",
20          "name": "DeepSeek V4 Pro",
21          "contextWindow": 1000000,
22          "maxTokens": 384000
23        }
24      ]
25    }
26  }
27}
为什么用配置文件,而不是环境变量? 接入第三方模型需要一次性告知 baseUrl、api 协议、模型 id、上下文窗口等多个维度—— 一个环境变量根本表达不了这么多信息。文件形式还有个好处:能被 ModelRegistry.create() 在启动时自动读取,零命令行参数,配一次到处生效。
🔎 出处:教程 §3.7 / model-registry.ts:367(ModelRegistry.create)。

4 · 拆开关键字段:每一格「刀具登记表」记的是什么

对照上面的 JSON,逐字段拆解:

字段作用
providers顶层字典,键名(zhipu/deepseek)自己起,会作为 provider 显示名
api选协议:最常见 openai-completions(国内厂商几乎都支持),还有 anthropic-messages、openai-responses——它决定 Pi 用哪种请求格式去调
baseUrlprovider 的接口地址
apiKey明文存放
models该 provider 下的模型列表:id 是调 API 时传的真实模型名(机器用),name 是 TUI 里显示的友好名(人看)
contextWindow / maxTokens可选,影响上下文压缩策略
为什么 api 字段如此关键? 它决定 Pi 用哪种请求格式去调这个 provider—— 选错协议,请求格式就对不上,直接调不通。国内厂商几乎都支持 OpenAI 兼容接口, 所以多数场景填 openai-completions 就够。
🔑 为什么 apiKey 明文存放,还这样设计? 这是一次显式的安全权衡: 用换取本地配置的简单直接,代价是你必须自己把 .pi/ 加进 .gitignore—— 否则一个 git add . 就把 key 提交进版本库,直接泄露。Pi 没有替你兜底这一步, 这是留给你的责任。

另外注意 id 与 name 的区分:为什么要分开? id 是机器调用用的真实模型名, name 是给人看的友好显示名——职责分离,让「展示」和「调用」互不干扰, 改一个不用担心动到另一个。

5 · 配好之后怎么用

写完 models.json,有三种方式让这些模型真正派上用场:

1// 方式一:会话中临时切换 —— 按 /model 或 Ctrl+L,fuzzy 搜索选一个
2
3// 方式二:设为默认 —— 编辑 ~/.pi/agent/settings.json
4{
5  "defaultProvider": "deepseek",
6  "defaultModel": "deepseek-v4-pro"
7}
8
9// 方式三:命令行查列表 —— 解析错误会打在终端顶部,方便排查
10$ pi models
11$ pi models deepseek   // fuzzy 过滤
机床类比落地图 —— 四种模式 × models.json 交互模式 print/JSON RPC 模式 SDK 模式 (你亲手开) (接自动流水线) (递给别的机器人) (嵌进你的工厂) │ │ │ │ └────────┬───────┴────────┬────────┴────────┬────────┘ ▼ ▼ 同一套三层堆栈 models.json =「刀具登记表」 (pi-ai→agent-core→coding-agent) baseUrl / api / id / name (第三方模型 = 换一把刀)
