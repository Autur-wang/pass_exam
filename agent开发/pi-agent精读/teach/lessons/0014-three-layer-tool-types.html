Lesson 0014 · 第 5 章 · 工具系统

工具的三层类型
—— 名片、执行、展示

🎯 本课目标:第 3 章讲 Agent Loop 时,我们把"执行工具"当黑盒直接跳过了, 只说了"Loop 执行工具",没说具体怎么执行的。这一章开始打开这个黑盒——但在讲"怎么执行"之前, 得先搞清一个更基础的问题:工具到底是怎么定义的? 为什么 Pi 要把"一个工具"拆成三层类型来描述?
🔁 回忆上一课: 0013 讲的是 ThinkingLevel 枚举怎么用一张 Map 把"字符串档位"翻译成"模型能听懂的具体参数"—— 同一份配置,分发给不同的执行细节。这一课的三层工具类型,其实是同一种"分层不越界"的设计哲学, 只是这次分的不是配置档位,而是不同代码层各自该知道多少。
这节课你将能做到一件事: 画出 Tool → AgentTool → ToolDefinition 三层类型各自新增了哪些字段、为什么必须分层而不能塞进一个接口,并说清 wrapToolDefinition 这个十几行的包装器,是怎么让 Agent Loop 永远不知道 ExtensionContext 存在的。
🎯 贯穿全课的类比:名片 → 员工 → 会汇报的员工 想象同一个人在三个部门被逐层"加料"。人事部只需要一张名片——姓名、职位描述、能接的活; 用人部门要真正派活,得给这张名片配上工牌和干活的手(能被执行); 到了对外的产品部门,这个人还得能站到台前做汇报演示,面对客户展示成果。 三层加的是不同部门用得上的能力,人事部不该被要求懂 PPT 排版——这正是 Pi 不把这些字段都塞进一个接口的原因。

1 · 第一层 Tool:一张"名片"

打开 packages/ai/src/types.ts,你会看到工具的最底层定义——只有三个字段: 

1// packages/ai/src/types.ts:433-437
2export interface Tool<TParameters extends TSchema = TSchema> {
3    name: string;            // 工具名,如 "read"、"bash"
4    description: string;     // 给 LLM 看的工具描述
5    parameters: TParameters; // 参数的 JSON Schema(用 TypeBox 定义)
6}

三个字段。工具就是一个有名字、有描述、有参数 Schema 的东西。这个接口住在 pi-ai 层—— 纯模型适配层,它唯一关心的事情是:怎么把工具的信息告诉模型。 name 和 description 会出现在发给模型的 API 请求里, parameters 告诉模型"你可以传哪些参数"。在这个层面,工具只是一张名片—— 能描述自己,但不能执行任何操作。

🔎 出处:教程 §一 / packages/ai/src/types.ts:433-437。

2 · 第二层 AgentTool:加上"执行能力"

Agent Loop 要执行工具调用,光有名片不够——它需要知道怎么执行这个工具、 这个工具能不能并行执行、参数格式要不要预处理。 于是 pi-agent-core 层在 Tool 基础上扩展出 AgentTool: 

1// packages/agent/src/types.ts:371-394
2export interface AgentTool<TParameters, TDetails>
3    extends Tool<TParameters>          // 继承 Tool 的三个字段
4{
5    label: string;                     // 给人看的标签(不同于给 LLM 的 description)
6    prepareArguments?: (args: unknown) => Static<TParameters>;  // 兼容性垫片
7    execute: (                         // 执行函数
8        toolCallId: string,
9        params: Static<TParameters>,
10        signal?: AbortSignal,
11        onUpdate?: AgentToolUpdateCallback<TDetails>,
12    ) => Promise<AgentToolResult<TDetails>>;
13    executionMode?: "sequential" | "parallel";  // 执行模式
14}

从 Tool 到 AgentTool,新增了 4 个字段,每个都有明确用途:

新增字段用途
label模型看到的是 name("read"),UI 看到的是 label("读取文件")
prepareArguments兼容层,处理不同模型输出的参数怪癖
execute真正干活的函数——模型说"读文件",这个函数去读
executionMode标记这个工具能否和其他工具并行执行
为什么 label 要和 name/description 分开? 三者受众不同:name 是给模型看的标识 (进 API 请求),description 也是给 LLM 的描述,label 才是给人看的 UI 文案。 强行合并会让 UI 文案污染模型看到的工具名——这是 AgentTool 单独引入 label 的理由。
🔎 出处:教程 §一 / packages/agent/src/types.ts:371-394。

3 · 第三层 ToolDefinition:产品层再加东西

到了 pi-coding-agent 层(产品运行层),工具还需要更多能力:自定义渲染(read 工具在终端里怎么显示? edit 工具怎么展示 diff?)、提示词注入(有些工具需要在系统提示词里加一段使用指南)。 于是出现了第三层 ToolDefinition。它的 execute 函数比 AgentTool 多了一个参数—— ctx: ExtensionContext,让工具执行时可以访问当前会话状态: 

1AgentTool.execute:     (toolCallId, params, signal, onUpdate) => ...
2ToolDefinition.execute: (toolCallId, params, signal, onUpdate, ctx) => ...
3                                                                   ^^^
4                                                    多了 ExtensionContext(会话上下文)

ToolDefinition 还新增了 promptSnippet(系统提示词片段)、renderCall(调用时渲染)、 renderResult(结果时渲染)等 UI/扩展字段——管的是"能被展示和扩展"。

4 · 桥接两层:wrapToolDefinition

Agent Loop 只认识 AgentTool,但产品层的工具都是 ToolDefinition。 谁来把 ToolDefinition 变成 AgentTool?答案是一个只有十几行的包装器函数: 

1// packages/coding-agent/src/core/tools/tool-definition-wrapper.ts:5-18
2export function wrapToolDefinition(definition, ctxFactory?) {
3    return {
4        name: definition.name,
5        label: definition.label,
6        description: definition.description,
7        parameters: definition.parameters,
8        prepareArguments: definition.prepareArguments,
9        executionMode: definition.executionMode,
10        // 关键:重写 execute,通过闭包注入 ExtensionContext
11        execute: (toolCallId, params, signal, onUpdate) =>
12            definition.execute(toolCallId, params, signal, onUpdate, ctxFactory?.()),
13    };
14}

注意最后一行。AgentTool 的 execute 只有 4 个参数,但 ToolDefinition 的 execute 有 5 个。包装器通过闭包捕获了 ctxFactory,在调用时动态创建 ExtensionContext 并注入第 5 个参数。Agent Loop 永远不知道 ExtensionContext 的存在。

🔎 出处:教程 §一 / packages/coding-agent/src/core/tools/tool-definition-wrapper.ts:5-18。

5 · 为什么非要分三层?

把所有字段塞进一个 Tool 接口,加几个可选字段不就行了?不行。

🔑 原因是每层有独立的依赖范围。 pi-ai 层的 Tool 接口只依赖 TypeBox 的 TSchema。如果在这个接口里加了 renderCall(返回终端 UI 组件), pi-ai 就得依赖终端 UI 渲染库——但 pi-ai 是纯模型适配层,它的工作只是 "把工具信息格式化成 API 请求",不应该知道终端 UI 长什么样。 三层递进的本质是:每一层只加自己这个层级需要的能力,不越界。 Tool 管"我能描述自己",AgentTool 管"我能被执行",ToolDefinition 管"我能被展示和扩展"。 用包装器而不是让 Agent Loop 直接吃 ToolDefinition,则是为了让内核与产品层的 ExtensionContext 彻底解耦——靠闭包在边界处悄悄注入。
工具的三层类型 —— 每层只加自己层级需要的能力 Tool(pi-ai) AgentTool(pi-agent-core) ToolDefinition(pi-coding-agent) name ← 继承 Tool ← 继承/对应 AgentTool 字段 description + label + promptSnippet parameters + prepareArguments + renderCall 「一张名片」 + execute(4参数) + renderResult + executionMode + execute(5参数,多 ctx) 「能被执行」 「能被展示和扩展」 ▲ │ └──────── wrapToolDefinition ────┘ 闭包注入 ctxFactory?.() 作为第 5 个参数 Agent Loop 只认 AgentTool,永远不知道 ExtensionContext 存在
