Lesson 0005 · 第 2 章 三层架构

类型演进:从原子到分子到材料

🎯 本课目标:上一课我们看清了五个包的依赖方向——箭头全部单向向上,coding-agent 甚至会 跨层直接依赖 pi-ai。这节课回答遗留的问题:跨层依赖的到底是什么东西? 答案是类型——而且类型不是原地不动,它会随着层数往上递进扩展。
🔁 回忆上一课: pi-coding-agent 的 package.json 里同时依赖了 pi-agent-core 和 pi-ai——这不是打破分层,而是因为 Message、Model、 Tool 这些"原子类型"必须在一处统一定义,所有层都要引用它。这节课就来拆开: 原子怎么一路演进成 Agent 能用的"分子",再演进成业务能用的"材料"。
这节课你将能做到一件事: 看到任意一层的 interface, 能立刻说出它属于哪一层、相比下一层多加了什么字段、 以及为什么这些字段只该在这一层出现,而不是随手塞进底层。
🎯 贯穿全课的类比:原子 → 分子 → 材料 pi-ai 定义"原子"(Message / Model / Tool 这些最基础的类型)—— 就像化学元素,谁都要用,但只在一处定义。pi-agent-core 把原子拼成"分子" (AgentTool——多了"怎么执行"的字段)。pi-coding-agent 再把分子拼成"材料" (ToolDefinition——多了"怎么显示"的字段)。每往上一层,只在原有基础上添零件, 从不改动底层的原子。

1 · 第一层:pi-ai 定义原子

最底层的三个类型——Message、Model、Tool——就是整个 Pi 系统的"原子概念"。任何一个和 LLM 打交道的包,不管是 agent-core 还是 coding-agent,都必须引用它们: 

1// packages/ai/src/types.ts(节选)
2// 最基础的消息类型——所有 LLM 都认的格式
3type Message = UserMessage | AssistantMessage | ToolResultMessage
4
5// 模型定义——描述一个 LLM 的全部信息
6interface Model<TApi> {
7    id: string           // 如 "claude-sonnet-4-6"
8    name: string
9    api: TApi            // 如 "anthropic-messages"
10    contextWindow: number // 如 200000
11    // ... 更多字段
12}
13
14// 工具定义——描述一个工具的 schema
15interface Tool<TSchema> {
16    name: string
17    description: string
18    parameters: TSchema
19}

注意第 15–19 行的 Tool:它只描述工具长什么样——名字、说明、参数 schema。没有"怎么执行"的字段,因为 Tool 服务的是 LLM,而 LLM 只需要知道"有哪些工具可以调、 参数长什么样",不需要知道调用后台怎么跑代码。

为什么原子类型必须集中在 pi-ai 一处? 就像化学元素一样,如果 Message、 Model、Tool 在 agent-core 和 coding-agent 里各自定义一份, 两份定义只要有一点点不一致,跨层传值时就会"文字对得上但类型对不上"——一处定义、所有层引用, 才能保证跨层传递的是同一个概念。

2 · 第二层:pi-agent-core 把原子组合成分子

pi-agent-core 的 types.ts 顶部大量 import type 来自 pi-ai (Message、Model、Tool、ImageContent 等), 在此之上做两处关键扩展: 

1// packages/agent/src/types.ts(节选,types.ts:371-394)
2import type {
3    Message, Model, Tool, ImageContent, ...
4} from "@earendil-works/pi-ai";
5
6// 扩展消息:除了标准 LLM 消息,还可以有自定义消息
7type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]
8
9// 扩展工具:除了 schema,还有参数预处理、执行函数和执行模式
10interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any> extends Tool<TParameters> {
11    label: string                                    // 显示名称
12    prepareArguments?: (args: unknown) => Static<TParameters>   // 参数预处理
13    execute: (toolCallId: string, params, signal?: AbortSignal, onUpdate?: AgentToolUpdateCallback<TDetails>) => Promise<AgentToolResult<TDetails>>
14    executionMode?: ToolExecutionMode                 // "sequential" | "parallel"
15}

两件事值得盯住:第 7 行 AgentMessage 是 Message 的超集—— 用联合类型(|)把自定义消息加进去,原来的 Message 一个字段没改。 第 10 行 AgentTool extends Tool——底层的 Tool 只知道"叫什么、参数是什么" (LLM 需要的),这里加上了 label、execute、executionMode (Agent 循环需要的)。

为什么用联合类型和 extends 扩展,而不是直接改底层? 底层类型保持稳定,才能被独立发布——别人可以只引用你的原子类型 (比如只想调 LLM,不想要整个 Agent 框架),不必被迫吞下 execute、 executionMode 这些跟 Agent 循环绑死的字段。
为什么底层 Tool 里没有 execute 字段? 因为 LLM 只需要知道工具"长什么样",不需要知道"怎么执行"——那是 Agent 循环的职责。 每一层只承载自己关心的信息,职责不越界。

3 · 第三层:pi-coding-agent 把分子组合成材料

到了 coding-agent 层,类型变成了具体的业务定义——ToolDefinition 在 AgentTool 的基础上,再叠加"怎么显示"相关的属性: 

1// packages/coding-agent/src/core/extensions/types.ts:435-482(节选)
2// 注意:ToolDefinition 是独立 interface 重新声明,
3// 与 AgentTool 是"结构兼容"而非用 extends 继承
4interface ToolDefinition<TParams extends TSchema, TDetails = unknown, TState = any> {
5    name: string
6    label: string                         // UI 展示名
7    description: string
8    promptSnippet?: string                // 自动拼到 system prompt 的工具片段
9    parameters: TParams
10    renderShell?: "default" | "self"      // 渲染模式
11    prepareArguments?: (args: unknown) => Static<TParams>
12    executionMode?: ToolExecutionMode
13    execute: (toolCallId, params, signal, onUpdate, ctx: ExtensionContext) => Promise<AgentToolResult<TDetails>>  // 比 AgentTool.execute 多 ctx 参数
14    renderCall?: ...                      // 自定义调用渲染
15    // ... 还有渲染器、UI 组件等业务属性
16}

对比第 13 行的 execute:签名比 AgentTool.execute 多了一个 ctx: ExtensionContext 参数——这是 coding-agent 层才有的"扩展上下文"。 再加上 promptSnippet、renderShell 这些字段,清一色是"怎么显示、 怎么接入业务"的关切,跟底层的 LLM schema、中间层的执行调度完全不是一回事。

🔑 为什么 ToolDefinition 是结构兼容,而不是 extends AgentTool? coding-agent 层重新声明了一个独立 interface,用结构类型对齐 AgentTool——字段形状对得上就行,不需要真的写 extends。 这样既能自由加业务字段(比如 execute 多带一个 ctx), 又不会被继承链锁死(继承链一旦锁死,中间层的任何字段变化都会强制传导到这里, 灵活性反而变差)。
类型扩展的 Before → After 对照 Before(pi-ai 层):Tool 只知道"长什么样" ──────────────────────────────────────────── interface Tool<TSchema> { name: string description: string parameters: TSchema } ↓ agent-core 扩展 After(pi-agent-core 层):AgentTool 知道"怎么执行" ──────────────────────────────────────────── interface AgentTool<TSchema> extends Tool<TSchema> { label: string ← 新增 execute: (...) => Promise<AgentToolResult> ← 新增 executionMode?: "sequential" | "parallel" ← 新增 } ↓ coding-agent 扩展 After(pi-coding-agent 层):ToolDefinition 加上"怎么显示" ──────────────────────────────────────────── interface ToolDefinition { // 结构兼容 AgentTool 的全部字段 // + 渲染器、权限控制等业务属性 } 一图看清:Tool(长什么样) → AgentTool(怎么执行) → ToolDefinition(怎么显示) 每层只加自己该关心的字段,底层从不为上层的需求买单。
