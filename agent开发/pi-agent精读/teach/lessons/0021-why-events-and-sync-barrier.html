Lesson 0021 · 第 7 章 事件驱动

为什么要事件
—— emit 是同步屏障,不是通知

🎯 本课目标:上一课讲完消息怎么转成 LLM 能读的格式、又怎么在 UI 上保持可见性—— 但消息是怎么从 Agent 内部传到外面的?这节课打开 Agent 的「神经系统」: 事件系统。你会看到 Pi 最反直觉的一个设计——每次 emit 都要 await。
⏮ 回忆上一课: 我们讲过 convertToLlm 把内部消息结构转成 LLM 能吃的格式, 同时又要维护 UI 上的「可见性」——同一份数据,两种消费者看到不同的形状。 这背后其实一直藏着一个问题没答:Agent 内部发生的每一件事(消息开始了、更新了、工具跑起来了), 到底是怎么被 UI、日志、持久化这些外部消费者知道的?答案就是本课的主角——事件。
这节课你将能做到一件事: 解释清楚 Pi 为什么用发布-订阅 而不是直接函数调用,并说出 emit 里那个反常识的 await ——它换来的是状态一致性,而不是「异步提速」。
🎯 贯穿全课的类比:美团外卖的状态推送 你点了份外卖,App 推送一连串状态:「商家已接单 → 骑手已取餐 → 骑手距你 500 米 → 已送达」。 每个状态更新就是一个事件——它告诉你「发生了一件事」,你不用一直盯着骑手看, 收到事件时瞥一眼就够了。但 Pi 的 emit 更进一步:它发完一个状态后要 「站着等」你(监听器)看完、处理完,才肯发下一个状态。这就是本课要讲透的地方。

1 · 不用事件会怎样:一个 6 行的对比实验

假设你要给 Agent 加一个「工具调用日志」功能:每次调工具打印一行日志。 不用事件系统:你得改 Agent 源码,在 tool.execute() 前后加 console.log。Pi 一更新,你 merge 上游代码就冲突——你加的日志和上游新逻辑撞在一起, 下周更新又冲突。用事件系统,只需要: 

1session.subscribe((event) => {
2    if (event.type === "tool_execution_end") {
3        console.log(`[LOG] 调用了 ${event.toolName}，结果：${event.isError ? "失败" : "成功"}`);
4    }
5});

六行代码,不碰 Agent 一行源码。Agent 更新时你只需要 npm update, 日志逻辑不受影响,不会有任何 merge 冲突。

为什么这就是事件驱动最核心的价值? 它把「发生了什么」和「谁关心什么」彻底分离。 Agent 只管把快照推给所有关心它的人,它不知道也不关心谁在听。 这跟直接调用完全不同——直接调用是「我亲自找你」(Agent 要知道所有消费者才能一个个调用它们), 发布-订阅是「我对着空气喊一声,谁听到算谁的」。在 Pi 里,「喊」就是 emit(event),「听」就是 subscribe(listener)。 新增功能只需要 subscribe,内核代码里没有一行 updateTerminal() 或 appendToFile()——它甚至不知道 TUI 和文件存储的存在。

2 · emit 的类型签名:一个 Promise 藏着大秘密

事件是在 Agent Loop 里发出的,发出动作叫 emit。先看它的类型定义: 

1export type AgentEventSink = (event: AgentEvent) => Promise<void> | void;

注意返回值——Promise<void>。emit 可以是异步的。 如果你写过 Node.js 的 EventEmitter,你熟悉的 emit 是同步的、 fire-and-forget 的——发了就走,不管谁在听。但 Pi 的 Agent Loop 里, 每次调用 emit 都带着 await: 

1await emit({ type: "agent_start" });
2await emit({ type: "turn_start" });
3await emit({ type: "message_start", ... });
4await emit({ type: "message_update", ... });
5await emit({ type: "message_end", ... });

每一个 await 都在说:「等这个事件被完全处理完,再继续。」

🔎 出处:教程 §三 emit 不是"通知"，是"同步屏障"(agent-loop.ts:25)。

3 · processEvents:先更新状态,再逐一等监听器

emit 的实体是 Agent 类的 processEvents 方法,做三件事: 

1private async processEvents(event: AgentEvent): Promise<void> {
2    // 第一步：根据事件类型更新内部状态
3    switch (event.type) {
4        case "message_start":
5            this._state.streamingMessage = event.message;   // 开始追踪流式消息
6            break;
7        case "message_update":
8            this._state.streamingMessage = event.message;   // 更新流式消息内容
9            break;
10        case "message_end":
11            this._state.streamingMessage = undefined;       // 清空临时工位
12            this._state.messages.push(event.message);       // 搬入正式档案
13            break;
14        // ... tool_execution_start/end 更新 pendingToolCalls 等
15    }
16
17    // 第二步：拿 AbortSignal
18    const signal = this.activeRun?.abortController.signal;
19
20    // 第三步：同步等待所有监听器完成
21    for (const listener of this.listeners) {
22        await listener(event, signal);   // ← 一个一个等！
23    }
24}

关键在第三步(第 21–23 行):Agent 按订阅顺序,逐一 await 所有监听器。 this.listeners 是一个 Agent 并不知道内容的外部 Set—— 谁在 Set 里、谁不在,完全由外部通过 subscribe() 控制,Agent 只负责「遍历并等待」。

为什么先更新状态,再 await 监听器? 顺序不能反——监听器被唤起时, 读到的 streamingMessage 等状态必须已经是最新的。如果先通知再更新, 监听器读到的会是「上一刻」的状态,又制造了不一致。
🔎 出处:教程 §三 processEvents:先更新状态，再等监听器(agent.ts:509-556)。

4 · 为什么非要 await?——不 await 会发生什么

假设 emit 是 fire-and-forget（不等待）： Agent Loop: emit(start) emit(update) emit(end) ↓ ↓ ↓ TUI 监听器: [开始渲染...] [还没处理完 [三个事件堆在一起了] start...] 问题：TUI 还没处理完 message_start，message_update 就来了。 UI 可能显示空消息，也可能显示过时的内容——状态不一致。 ──────────────────────────────────────────────────── 实际设计（await，同步屏障）： Agent Loop: emit(start)──await──→ emit(update)──await──→ emit(end)──await──→ ↓ ↓ ↓ TUI 监听器: [处理完毕，返回] [处理完毕，返回] [处理完毕，返回] 保证：Agent 在监听器返回前不会发出下一个事件。
🔑 一句话总结: await 不是为了「通知」,而是为了「同步协商」 ——确保所有消费者都跟上了,Agent 才走下一步。这就是「同步屏障」的含义。 代价是性能(必须等最慢的消费者),换来的是正确性(状态永远一致)。

5 · 一个例外:tool_execution_update 的「先收集,后批量等」

同步屏障听起来很严格——那 tool_execution_update 呢?工具执行时可能疯狂输出进度 (比如 Bash 的每一行输出),每次都 await 会不会太慢?Pi 对这种高频事件做了特殊处理: 

1const updateEvents: Promise<void>[] = [];   // 收集箱
2let acceptingUpdates = true;
3
4const result = await tool.execute(id, args, signal, (partialResult) => {
5    if (!acceptingUpdates) return;   // 工具已结束，丢弃迟到 update
6    // 不 await！先把 emit 的 Promise 收集起来
7    updateEvents.push(emit({ type: "tool_execution_update", ... }));
8});
9
10acceptingUpdates = false;             // 关闭闸门
11await Promise.all(updateEvents);      // 一次性等所有 update 处理完
为什么这不矛盾? 同步屏障的规则不松,但对可合并的进度事件开了个口子。 进度更新是「高频、低价值、可合并」的——多发一条少发一条不影响最终状态; 而生命周期事件(start/end)是「低频、高价值」的——错过了 message_start 就没机会了。

acceptingUpdates 闸门是为了防什么? 工具的 execute 是 async 函数,它内部的进度回调可能在 Promise resolve 之后还异步触发(残留定时器/延迟回调)。 没有这道闸门,迟到的 partialResult 会在 tool_execution_end 之后 又发出 tool_execution_update,让监听器看到「工具已经结束了却还在更新」的错乱序列。
🔎 出处:教程 §三 一个例外：tool_execution_update 不等(agent-loop.ts:628-669)。

6 · 监听器循环没有 try-catch——像保险丝一样

再看一眼第 3 节的循环体:await listener(event, signal), 没有 try-catch 包裹它。如果某个监听器抛异常,异常会一路冒泡, 触发整个 Agent 运行失败——一个 UI 渲染的 bug 能把 Agent 干掉,听起来很危险。

为什么不包 try-catch? 因为 Pi 的设计哲学是:监听器出错,运行就停下来, 问题立刻可见。如果静默吞掉异常,Agent 看起来「正常」运行,但 UI 已经乱套了—— 你调试时根本找不到问题。这就像电路里的保险丝——烧断了,你立刻知道哪坏了; 如果每个元件都默默兜底从不报错,整个系统「看起来正常」但可能已经坏了一半。

但有一个例外:扩展系统。第三方扩展的回调由框架自己做 try-catch 隔离, 单个扩展崩溃不会拖垮整个 session。原则是:对内层受信任的代码(自己写的监听器), 让异常直接暴露;对外层不受信任的代码(第三方扩展),由框架做隔离。
