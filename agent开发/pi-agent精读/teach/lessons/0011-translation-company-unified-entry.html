Lesson 0011 · 第 4 章 模型调用

翻译公司:一个入口
消化 30 多家 Provider

🎯 本课目标:第 3 章我们拆过 Agent Loop,当时有一行代码被一笔带过—— streamSimple(model, context)。这节课我们回去补上这个悬念: 这行看似平平无奇的调用背后,是一整套三层抽象层,专门用来吞下 30 多家 Provider 的差异。 这节课先啃第一层——统一入口怎么用「查表派活」两步解决路由问题。
🔁 回忆一下:第 3 章讲 Agent Loop 时,我们说它调用模型只有一行代码, 拿到回复就根据 stopReason 决定继续还是停止——那时我们没深究「调用模型」这四个字底下发生了什么。 今天就打开这个黑盒。
这节课你将能做到一件事: 讲清楚为什么同一句纯文本消息 在 Anthropic / OpenAI / Google / Bedrock 下有四种不同写法,并说出 Pi 的第一层 stream() 函数为什么只做「查表 + 派活」两步,不掺一丝业务逻辑。
🎯 贯穿全课的类比:一家国际翻译公司 客户(Agent Loop)进门只跟前台打交道,前台问一句「你要翻译什么语言」, 查一下通讯录就找到对应语种的翻译员,把工作原样派给他。 客户不懂外语,翻译员不懂公司流程——两者靠一份标准报告模板解耦。 今天先看前台怎么工作。

1 · 问题:一句话,四种翻译

市面上几十家模型供应商——Anthropic、OpenAI、Google、AWS Bedrock……每家都有自己的 API 规范, 用不同字段名、不同数据结构描述同一件事。有多不一样?看一个最简单的例子:用户说了一句 「帮我读一下 main.ts」。这条消息在 Pi 内部统一存成: 

1// Pi 内部统一格式
2{ role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }

但要发给不同模型,就得翻译成各家要求的私有格式。同一句话,四种长相:

1// Anthropic —— content 必须是数组,每项带 type 字段
2{ role: "user", content: [{ type: "text", text: "帮我读一下 main.ts" }] }
3
4// OpenAI —— 字符串 content;若含工具结果需独立 role: "tool" 消息
5{ role: "user", content: "帮我读一下 main.ts" }
6
7// Google(Gemini)—— content 换成 parts,结构更扁平
8{ role: "user", parts: [{ text: "帮我读一下 main.ts" }] }
9
10// Bedrock(AWS)—— text 没有 type 字段,和 Anthropic 不一样
11{ role: "user", content: [{ text: "帮我读一下 main.ts" }] }

连最简单的纯文本消息都有四种写法。字段名不同(content vs parts), 结构不同(有的要 type,有的不要)。

🔎 出处:教程第4章 §一 / provider 消息格式四写法(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第4章-模型调用-一行代码驾驭多个模型.md)。

2 · 差异不止消息格式,是四个维度全都不同

消息格式只是冰山一角。Provider 之间的差异是全方位的,主要在四个维度上:

维度差在哪举个例子
消息格式同一条消息,字段名和结构不同Anthropic 用 content[],Google 用 parts[]
流式传输模型的「逐字返回」机制不同Anthropic 发原始 SSE 要自己解析,OpenAI SDK 直接返回结构化 chunk
思考模式「让模型深度思考」参数完全不同Anthropic 用 thinking.budget_tokens,OpenAI 用 reasoning_effort
缓存控制「标记不变内容」方式不同Anthropic 打 cache_control,Bedrock 插入 cachePoint 节点
为什么这值得单独强调? 每个维度单独看都不复杂,但四个维度 × 30 多个 Provider, 组合起来的差异量是巨大的。Agent Loop 只有一行 streamSimple(model, context), 它不可能为每个 Provider 写一套不同逻辑——这就是为什么 Pi 需要专门设计一层抽象来吸收这些差异。
🔎 出处:教程第4章 §一 / 四维度差异表。

3 · 解法:三层架构,各管一件事

直觉的答案是「给所有 Provider 封装一层,让它们看起来都一样」。Pi 正是这么做的, 具体拆成三层,每层职责单一:

第一层 · 统一入口 → "接收请求,查出该找谁处理" 第二层 · 事件协议 → "约定输出格式——不管谁处理,交回来的都是这个样子" 第三层 · 翻译器 → "真正干活的人——每个翻译器精通一种 Provider 的方言" 客户 前台 标准报告 翻译员们 Agent Loop ───────▶ stream() ───────▶ 12种统一事件 ◀─────── 4+个 Provider 客户永远只跟前台打交道,从不直接接触翻译员

回到翻译公司类比:前台(第一层)问「你要翻译什么语言」,查通讯录找到翻译员派活; 标准报告模板(第二层)规定不管翻译员翻的是法语还是日语,交出来的报告格式必须统一; 翻译员们(第三层)各自精通一种语言,内部怎么翻是他们的事。

🔑 为什么拆三层而不是一坨? 前台不需要懂外语,翻译员不需要懂公司流程—— 中间靠标准报告解耦,职责隔离让每层可以独立演化:新增一个 Provider 只需要加一个翻译员, 不动前台;修改报告格式(事件协议)所有翻译员一起遵守。今天这一课只展开第一层, 第二、三层留给下一课。
🔎 出处:教程第4章 §二 / 三层架构与翻译公司类比。

4 · 第一层拆开看:查表,派活

入口函数叫 stream(),代码极其简单——这正是它被设计成这样的核心目的: 

1// compat.ts
2export function stream(model, context, options?) {
3  const provider = resolveApiProvider(model.api);  // 查表:这个model该找谁?
4  return provider.stream(model, context, options);  // 把工作派给翻译器
5}

就两步:查表,派活。 model.api 是一个字符串(如 "anthropic-messages"), 系统启动时已经把所有翻译器注册进了一份「通讯录」。这份通讯录长这样: 

1const BUILTIN_APIS = [
2  ["anthropic-messages",       anthropicMessagesApi()],      // Claude 的翻译器
3  ["openai-completions",       openAICompletionsApi()],      // GPT 的翻译器
4  ["google-generative-ai",     googleGenerativeAIApi()],     // Gemini 的翻译器
5  ["bedrock-converse-stream",   bedrockConverseStreamApi()], // Bedrock 的翻译器
6  // ... 还有 5 个
7];

左边是 key(「工号」),右边是翻译器(「翻译员」)。model.api 的值就是 key—— 拿 key 查表,找到翻译器,调用它。整个入口层不处理任何业务逻辑,纯粹是一个路由器。

🔎 出处:教程第4章 §二 / compat.ts:237-247 与 compat.ts:172-206。基于 pi v0.80.2。
为什么第一层只做查表派活、不含任何业务逻辑? 入口保持极简才能让「新增一个 Provider」 不牵动路由代码,复杂度全部沉到翻译器里。

为什么用 model.api 字符串 key 查表,而不是硬编码一堆 if-else? 注册表模式让新翻译器「往通讯录加一条」即可被路由发现——这是开闭原则的体现: 对扩展开放(加条目),对修改关闭(不用改 stream() 本身)。

为什么 Agent Loop 被设计成永不直接接触翻译员? 客户只认标准报告, 底层换任何模型,上层代码一行不改。这也是为什么第 3 章里 Agent Loop 那一行 streamSimple(model, context) 能看起来如此云淡风轻——所有复杂度都被这一层挡住了。
