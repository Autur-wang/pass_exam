Lesson 0028 · 第 9 章 · 上下文压缩

在哪切:有效切点、向后遍历与 Turn 分割

🎯 本课目标:上一课讲清了「为什么要压缩、什么时候触发」——token 快超预算,或 API 已经报错。 这一课只回答下一步的问题:压缩决定已经做了,但具体从哪一条消息下刀? 刀口选错,模型会看到断裂的对话;刀口选对,才有后面第 0029 课的结构化摘要可讲。
↩️ 先回忆上一课: Pi 用「预防性压缩」(token 超阈值 183,616)和「应急性压缩」(API 报错兜底)两道防线决定要不要压缩。 这一课接着往下走:决定压缩之后,压缩函数拿到的是一整条 entries 数组,它不能随便挑一条切下去—— 切错位置,压缩出来的上下文会让模型confused。
这节课你将能做到一件事: 看到一段 entries 序列, 能自己指出哪些位置是合法切点、哪些不是,并说清 Pi 为什么宁可切断 Turn 也要保证压缩生效, 以及 turnPrefix 怎么把这笔账补回来。
🎯 贯穿全课的类比:剪一卷录像带 想象你在剪一卷会议录像。user 说话、assistant 回应的画面之间可以剪——观众看得懂; 但「我调用了 read 工具」和「工具返回的结果」这两帧必须连在一起—— 如果在中间剪断,观众看到的就是「他说要读文件……然后呢?」,一头雾水。 而且剪辑师不是从片头往后剪,而是从片尾往回量 20 分钟再下剪刀—— 因为最近发生的事,才是观众最需要记住的。

1 · 不是哪里都能切:有效切割点

LLM 的对话历史有一条硬性结构约束:ToolResult 消息必须紧跟在触发它的 AssistantMessage(含 ToolCall)之后。如果把 ToolCall 留在「保留区」、把它对应的 ToolResult 切进「压缩区」,模型会看到「我调用了 read 工具,但结果在哪?」——上下文彻底断裂。

所以能下刀的位置必须是有效切割点——源码里这套规则叫 findValidCutPoints:

1entry:  0     1     2      3       4     5      6       7      8
2       ┌─────┬─────┬──────┬───────┬─────┬──────┬───────┬──────┬─────┐
3       │ hdr │ usr │ ass  │ tool  │ usr │ ass  │ tool  │ ass  │tool │
4       └─────┴─────┴──────┴───────┴─────┴──────┴───────┴──────┴─────┘
5
6有效切割点 = [1(usr), 2(ass), 4(usr), 5(ass), 7(ass)]
7                                                       ↑
8                                          注意:3(tool)、6(tool)、8(tool) 全部被排除

user 和 assistant 都是合法切点,toolResult 不是。源码注释里的关键说明是:

"When we cut at an assistant message with tool calls, its tool results follow it and will be kept."

为什么这是硬约束,不是优化项? 这不是「压缩这条消息收益高不高」的权衡,而是 LLM 对话协议本身的正确性要求—— ToolCall 与 ToolResult 必须成对出现在模型看到的上下文里。排除 toolResult 作切点, 是为了不可能发生「调了工具却找不到结果」这种断裂,而不是为了效率。
🔎 出处:教程 §三「不是哪里都能切」/ findValidCutPoints:L305(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第9章-上下文压缩-当对话太长怎么办.md)。

2 · 切点的语义:它是「保留区的第一条」

理解切割点要先纠正一个直觉误区——切点不是「被切掉的最后一条」,而是「保留区的第一条」。 这个语义会澄清后面所有关于 Turn 分割的疑问。

切点选在 user 上,意味着什么?看这个例子:

1例子:切点选 entry 4 (usr)
2entry:  0     1     2      3       4     5      6       7      8
3       hdr   usr   ass   tool    [usr]  ass   tool    ass   tool
4       └──────── 压缩区 ────────┘  └────── 保留区 ──────────────┘
5                                   ↑
6                              切点 = 保留区第一条
7                              user + 后面的 ass + tool 全部保留
8                              → 这个 Turn 完整!

entry 4 这个 user 自己进保留区,它后面的 assistant 和 toolResult 也都跟着进保留区—— 这个 user 开头的完整 Turn 全部被保留,被压缩的只是 user 之前的消息。 所以在 user 后切是最安全的选择:天然保证 Turn 完整。

🔎 出处:教程 §三「切点的语义:保留区的起点」。

3 · 向后遍历:从最新消息往回累积

确定了合法切点集合后,具体切在哪个上?Pi 的策略是从后往前累积 token—— 这正是 findCutPoint 干的事: 

function findCutPoint(entries, keepRecentTokens) {
1    const cutPoints = findValidCutPoints(entries);  // 排除 toolResult
2
3    let accumulated = 0;
4    for (let i = entries.length - 1; i >= 0; i--) {
5        accumulated += estimateTokens(entries[i]);
6        if (accumulated >= keepRecentTokens) {
7            // 找到第一个 >= i 的有效切割点
8            return 第一个 >= i 的 cutPoint;
9        }
10    }
11    return 最早的 cutPoint;  // 全部需要压缩
12}

从 entries.length - 1 开始往回走,累积 token 数;一旦累积量 >= keepRecentTokens (默认 20,000),就停止,在停止位置之后找最近的有效切割点——那里就是切刀落下的地方。

为什么从后往前累积,而不是从前往后? 判断依据只有一条:最近的上下文最重要。 模型继续工作时,最需要知道的是「刚才做了什么」「刚才读了什么文件」「用户最新说了什么」, 而不是「10 轮前讨论过什么」。逆向遍历天然把近期消息保在保留区,把该压缩的旧消息留在前面。
🔎 出处:教程 §三「向后遍历:保护最重要的东西」/ findCutPoint:L392-454。

4 · 极端情况:Turn 分割与 turnPrefix 补丁

§一、§二 讲了 user 切点和 assistant 切点都合法,但两者性质不同:

切点类型Turn 是否完整原因
user 切点✅ 天然完整user 后面的 assistant + toolResult 都跟着进保留区
assistant 切点⚠️ 会切断它对应的 user 落在压缩区,自己却在保留区

源码里的判断逻辑很直白:

1const isUserMessage = cutEntry.message.role === "user";
2const turnStartIndex = isUserMessage ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);
3isSplitTurn: !isUserMessage && turnStartIndex !== -1,

切点是 user → 一定不是 split turn;切点是 assistant → 可能是 split turn。

为什么 Pi 不干脆只允许 user 切点,彻底避免这种麻烦? 看这个场景:向后累积到 entry 6 时预算刚好用完, 但最近的 user 是 entry 1。

🔑 只允许 user 切点 → 保留区被迫从 entry 1 开始,要保留 entry 1-8 共 8 条——token 预算可能只够装 2-3 条, 压缩失败,根本压不动。
🔑 允许 assistant 切点 → 直接选 entry 6,保留区只剩 entry 6-8 共 3 条,精确控制 token 量, 代价是切断了一个 Turn。
Pi 选择了后者——优先保证压缩能生效,再用轻量机制弥补 Turn 完整性的损失。

这个「轻量机制」就是 turnPrefixMessages:

1entry:  1     2      3      4      5      6       7      8     9
2       ┌─────┬──────┬──────┬──────┬──────┬───────┬──────┬─────┬──────┐
3       │ usr │ ass  │ tool │ ass  │ tool │ tool  │ ass  │tool │ ass │
4       └─────┴──────┴──────┴──────┴──────┴───────┴──────┴─────┴──────┘
5         ↑     └────────── turnPrefixMessages ──────────┘  └─ kept ─┘
6       turnStart=1            (entries 2-6)              entries 7-9
7
8       切点在 entry 7(assistant),但 entry 1(user)是它的 Turn 起点
9       → entry 1 在主摘要里压缩
10       → entry 2-6 是"被切断的 Turn 前缀",单独生成 turnPrefix 摘要

被切断 Turn 的前缀(user 起点到切点之间的 assistant + toolResult)用专门的 TURN_PREFIX_SUMMARIZATION_PROMPT 单独摘要——只用更轻量的 3 段格式 (Original Request / Early Progress / Context for Suffix),与主摘要并行生成 (Promise.all),最后合并成一份完整摘要。

为什么用 turnPrefix 弥补,而不是干脆禁止 split turn? 因为 Pi 的优先级排序很明确: 先保证压缩能跑通,完整性损失用一份轻量摘要打补丁,而不是牺牲压缩的有效性去死守完整性。 这是效率与完整性之间一个显式且可解释的权衡,不是妥协出来的 bug。
🔎 出处:教程 §五「极端情况:Turn 分割」/ findCutPoint:L444-453、turnPrefixMessages:L698-705。
