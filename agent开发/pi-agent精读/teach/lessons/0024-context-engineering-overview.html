Lesson 0024 · 第 8 章 上下文工程

上下文工程总览

🎯 本课目标:这一课不深入任何单一技巧的实现细节,只回答一个更根本的问题—— Pi 为什么需要"上下文工程",以及它在哪几个环节布防。 读完你会拿到一张两层防护地图,后面 §四、§五、§六(乃至独立成章的第 9 章 Compaction) 都是在这张地图上填细节。
🔁 先回忆上一课:第 6 章讲消息系统时说过——Agent 内部用 7 种 AgentMessage 自由表达,调用 LLM 之前会经过一道 convertToLlm 翻译边界,收窄成 3 种标准 Message。 第 7 章讲事件驱动时又提到:agent_end 事件之后会触发一次"上下文检查"。 这两件事当时都一带而过,但它们背后其实藏着同一个核心问题——这就是本课要打开的东西。
这节课你将能做到一件事: 说清 Pi 的两层防护地图 ——输入侧(工具输出截断 + 系统提示词组装)与历史侧(Compaction + 分支摘要)—— 并说出每一层的触发频率为什么天然不同。
🎯 贯穿全课的类比:行李箱与打包师 把 LLM 的上下文窗口想象成一个固定大小的行李箱,而 coding-agent 每一轮对话都在往里塞新衣服—— 系统提示词、工具输出、历史消息、项目规范——迟早塞爆。上下文工程就是那位"打包师"的多道整理工序: 该叠的叠(截断)、该压的压(摘要),该扔的先拍照存档(逃生通道),再放进去。 记住这个画面,后面每一层防护都能对号入座。

1 · 问题:窗口是固定的,对话是增长的

把一次 coding-agent 会话送进 LLM 的"信息源"摊开来看,你会立刻意识到问题有多严重—— 系统提示词、项目上下文文件(CLAUDE.md / AGENTS.md,可能多层嵌套)、 Skills 清单、工具定义、对话历史、当前轮新输入,随便挑一项都可能爆炸: 

1一次会话送进 LLM 的内容
2├── 系统提示词(工具说明、guidelines、pi 文档路径)
3├── 项目上下文文件(CLAUDE.md / AGENTS.md,可能多层嵌套)
4├── Skills 列表(每个 skill 一段描述)
5├── 工具定义(每个工具的 JSON schema)
6├── 对话历史(每一轮 user / assistant / toolResult)
7│   ├── 用户输入
8│   ├── LLM 回复(含 thinking、toolCall)
9│   └── 工具结果(read 文件、bash 输出、grep 命中……)
10└── 当前轮的新输入
🔎 出处:教程 §一 / 信息源树(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第8章-上下文工程-让有限窗口装下无限对话.md)。

这不是危言耸听。跑一次 npm install 的 stderr 可能十几 KB;read 一个 5000 行的 源文件,可能 80KB;grep 全仓库命中几百行;几十轮工具调用累积下来,轻松破 100K token。 而 LLM 的窗口是硬上限——超了直接报错 prompt is too long,对话中断, 不是"变慢",是"炸掉"。

上下文工程(Context Engineering)就是应对这个矛盾的工程 discipline: 在内容送入 LLM 之前,多层裁剪、过滤、压缩、组织,让有限的窗口装下 "对当前任务最有价值的信息"。Pi 在这个环节实现了 4 种互补的技巧。

2 · 地图:两层防护

为什么先给"地图",再讲细节? 因为没有任何单一机制能搞定所有上下文问题。 先建立这张全局漏斗的心智模型,才能避免新手"找到一招用到底"的错误—— 比如只指望 Compaction 把一切都压下去,结果单条 80KB 的 read 结果照样能撑爆一轮对话。

Pi 的上下文工程分布在两个环节,问题源头完全不同——所以必须分层各个击破:

1┌──────────────────────────────────────────────────────────────┐
2│                       输入侧(送进 LLM 之前)                 │
3│  ① 工具输出截断 — bash/read/grep 结果按行/字节裁剪            │
4│  ② 系统提示词组装 — 多层 CLAUDE.md 向上递归 + Skills 懒加载   │
5└──────────────────────────────────────────────────────────────┘
6                              │
7                              ▼
8┌──────────────────────────────────────────────────────────────┐
9│                  历史侧(长对话管理)                         │
10│  ③ Compaction —— 阈值触发,把旧消息变成结构化摘要             │
11│  ④ 分支摘要     —— 切换会话树分支时,给"被放弃的分支"做摘要   │
12└──────────────────────────────────────────────────────────────┘
🔎 出处:教程 §二 / 两层防护对照表(同上章节文件)。
为什么分"输入侧"和"历史侧"两层? 问题源头不同——输入侧是"单次内容太大" (一次 read、一次 bash 就可能撑爆),历史侧是"累积总量超窗口"(几十轮对话叠加)。 一个是"瞬时体积"问题,一个是"长期总量"问题,解法自然不同,分层才能各个击破。

把四层技巧连同触发频率列出来,会看到一个规律:

层解决的问题触发频率
① 工具输出截断单次工具结果太大每次工具调用
② 系统提示词组装项目规范要进上下文,又不能让用户每次说每轮 prompt
③ Compaction长对话累积超窗口阈值触发
④ 分支摘要会话树分支跳转,旧分支不能丢用户切换分支时
为什么要强调触发频率? 频率决定了每层的实现复杂度预算。 工具输出截断每次工具调用都要跑——高频,必须朴素可靠而快,容不得一次 LLM 调用的延迟。 Compaction 是阈值触发的低频操作,可以承担"再调一次 LLM 生成摘要"这种重开销。 分支摘要更是只在用户切换分支这个稀有事件里才触发。频率不同,该花多少工程力气,答案也不同。

3 · 承接前两章:同一个问题的两次伏笔

回头看第 6 章和第 7 章埋下的两个细节,现在能对上号了。第 6 章的 convertToLlm 翻译边界——把 Agent 内部 7 种表达力丰富的 AgentMessage,收窄翻译成 LLM 只认的 3 种 标准 Message——本质上已经是一次"为了让内容适配 LLM 的输入格式"而做的塑形。 第 7 章 agent_end 事件后触发的"上下文检查",指向的正是本课 §二地图里 ③ Compaction 那一层的阈值判定入口。

两处伏笔都指向同一个核心问题:LLM 的上下文窗口是固定的,但 coding-agent 的对话会无限增长。 第 6、7 章只是各自触及了这个问题的一角,本课才第一次把它摊开成完整的地图。

4 · 元原则:没有银弹,层层兜底

核心洞察: 每一层只解决自己擅长的问题,互不替代。 你可以把 Compaction 调得非常激进,但单条工具输出仍然需要截断——因为一次没截断的 80KB read 结果,连一轮对话都撑不过,根本轮不到 Compaction 出场。反过来,截断再彻底, 也挡不住几十轮对话的历史累积超窗口。四层组合成一道漏斗,层层过滤,才凑成完整防线。
上下文工程的漏斗 —— 四层互补,没有一层能单独扛下全部 输入侧 历史侧 ┌───────────────┬───────────────┐ ┌───────────────┬───────────────┐ │ ① 工具输出截断 │ ② 系统提示词组装 │ │ ③ Compaction │ ④ 分支摘要 │ │ 每次工具调用 │ 每轮 prompt │ │ 阈值触发 │ 切换分支时 │ └───────────────┴───────────────┘ └───────────────┴───────────────┘ 解决"单次内容太大" 解决"累积总量超窗口" │ │ └───────────────┬───────────────┘ ▼ 送进 LLM 的,是"对当前任务最有价值的信息"

这也是为什么本课刻意不深入任何一层的实现——先把这张地图焊进脑子, §四(下一课 0025)讲系统提示词组装、独立成章的第 9 章讲 Compaction 细节, 你才知道自己在漏斗的哪一层里挖。

5 · 立刻自测(答完即有反馈)

凭记忆作答——这种费力的回想,正是把地图焊进长期记忆的方式。

① 上下文工程要解决的根本矛盾是什么?

② Pi 把上下文工程的防线分成哪两层?

③ 下列哪个技巧的触发频率是"每次工具调用"?

💬 卡住就问我。 几个值得追问的好问题: 「为什么工具输出截断不能等 Compaction 来兜底,非要单独做一层?」 「如果只按"触发频率"给每层分配工程预算,那预算最紧张的是哪一层,为什么?」 「系统提示词组装既然每轮 prompt 都要跑,它是怎么在"高频"和"要塞进多层 CLAUDE.md" 之间找平衡的?」——最后这个问题,正好把我们带向下一课。
