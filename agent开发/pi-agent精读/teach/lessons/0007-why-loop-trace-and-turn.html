Lesson 0007 · 第 3 章 Agent Loop

为什么需要循环
—— 三种用法与 Trace / Turn 嵌套

🎯 本课目标:前面几课我们看的是分层架构——包与包之间谁依赖谁。 从这一课起,我们钻进「循环」本身。这是本章开篇课,只回答一个更根本的问题: 为什么 Agent 需要一个循环,而不是像普通调用那样一次搞定? 以及循环转起来时,内部到底在记录什么「节奏」。
📌 先回忆上一课:我们确认了依赖方向必须单向——底层包不知道上层包的存在。 但那只解决了「代码怎么分层」的问题。这一课要问的是另一件事:分好层之后, 运行时这些层之间的控制权到底怎么流转?谁来决定「下一步做什么」? 答案会把我们直接带到 Agent 和 Workflow 的分水岭。
这节课你将能做到一件事: 向别人讲清楚直接调用 / Workflow / Agent Loop 三种用法的本质区别只在「谁是决策者」,并且能画出一次完整运行(Trace) 如何由多个轮次(Turn)首尾相接、层层嵌套而成。
🎯 贯穿全课的类比:三种派活方式 把大模型想成一位专家。模式 1 是你问一句他答一句(直接调用); 模式 2 是你当项目经理、把活拆成几步逐步派给他(Workflow); 模式 3 是你只给他工具箱和目标、由他自己决定读哪个文件、改几处代码(Agent Loop)。 而一次「派活到彻底交付」是一个 Trace,他每一次「开口 + 动手」是一个 Turn。

1 · 是什么:三种用法的分水岭在「决策者是谁」

在聊 Agent Loop 之前,先退一步看「使用大模型」这件事本身有几种模式。 模式 1(直接调用):你构建提示词、调一次 API、拿到结果,完事,决策权在用户手里。 模式 2(Workflow):任务拆成几步,步骤之间由你的代码控制流转——你知道什么时候该进入下一步。 模式 3(Agent Loop):你把决策权交给了模型,步骤之间的流转不再由你写死, 而是由模型的输出内容驱动。 

1// 模式 3:Agent Loop 的流程全景(引子部分的示意)
2用户输入 → 调模型 → 模型说"我需要读文件" → 执行读文件 → 模型看结果
3         → 模型说"还需要搜索代码" → 执行搜索 → 模型看结果
4         → 模型说"我知道了,答案是..." → 输出 → 结束

三种模式的差异,教程里用一张表格摊开:

维度直接调用WorkflowAgent Loop
决策者用户你的代码模型
模型调用次数1 次N 次(由代码控制)不确定(由模型控制)
核心工作写提示词设计流程定义工具和循环
模型角色执行者流水线环节自主决策者
典型场景翻译、摘要文档流水线、RAG编程助手、自动化任务
为什么把决策权交给模型? 在 Agent 任务中你无法预知模型要读几个文件、 改几处代码——步骤数在运行前是未知的。如果硬要写死流转逻辑,代码要么覆盖不了所有分支, 要么退化成一个巨大的 if-else 迷宫。所以流转只能由模型输出驱动,这既是 Agent 的能力来源, 也是它与 Workflow 的本质分界。

那"该调什么工具、调几次"由谁定,"该什么时候停"又由谁定?这是本节最容易混淆的一点—— 你的代码在 Agent 模式下只做两件事:① 把输入和工具结果喂给模型; ② 模型输出里有工具调用就执行、没有就认为完成。调几次工具由模型定,何时停是人类定义的规则 ——不是模型在说"我完成了",而是我们在说"你没要工具,那就当你完成了"。

2 · 是什么 + 怎么做:Turn 的精确定义——一次模型调用的边界

弄清了「谁决策」,接下来要弄清「循环怎么转一圈」。Pi 的代码里,一圈内层循环有精确定义: Turn = 一次模型调用 + 这次调用触发的所有工具执行,由一对 turn_start / turn_end 事件包裹。 

1while (hasMoreToolCalls || ...) {
2    if (!firstTurn) emit(turn_start);    // ← 新 Turn 开始
3
4    处理 pendingMessages
5    streamAssistantResponse()             // ← 一次模型调用
6    检查 stopReason
7    executeToolCalls()                    // ← 执行这个 Turn 触发的一批工具
8    emit(turn_end);                       // ← 这个 Turn 结束
9
10    prepareNextTurn / shouldStopAfterTurn / 检查 steering
11}

关键点是一个 Turn 只有一次模型调用。如果模型在一次输出中一口气要求了 3 个工具(read + grep + find),这 3 个工具都在同一个 Turn 里执行——因为它们都是同一次模型调用的产物。只有把结果喂回去再调一次模型, 才算进入下一个 Turn。

为什么用「一次模型调用」来切分 Turn? 模型每次调用是一个原子的「思考 + 决策」单元—— 给定当前上下文,它一口气决定好这一步要做什么(可能是零个、一个或多个工具调用)。 以此为边界切分,能让 turn_start / turn_end 精确对应一次可观测的推理, UI 上就能画出「模型在想 → 工具在跑」这一条清晰的时间线,trace 追踪时也不会把多次工具执行 错误地拆成多个「决策」。

3 · 怎么做:Trace 包着 Turn——一次运行里的心跳节奏

把镜头拉远一点:一个 Trace 是从 agent_start 到 agent_end 的整个过程(一次完整运行),它包含一个或多个 Turn。 三种模式类比里,Trace 就是「一次派活到彻底交付」,Turn 就是「专家的每一次开口 + 动手」。 

1Trace(一次完整运行)
2│  agent_start
3│
4├── Turn 1
5│   │  turn_start
6│   ├── 调模型 → toolUse → 执行工具(read + grep)
7│   │  turn_end
8│   │
9├── Turn 2
10│   │  turn_start
11│   ├── 调模型 → toolUse → 执行工具(edit)
12│   │  turn_end
13│   │
14├── Turn 3
15│   │  turn_start
16│   ├── 调模型 → stop → 没有工具
17│   │  turn_end
18│   │
19│   agent_end

注意 Turn 3:模型返回 stop、没有工具调用,这个 Turn 一结束就触发整个循环退出—— 这正好呼应第 1 节讲过的「何时停是人类定义的规则」。

为什么首轮 turn_start 在入口就发、内层循环还要用 firstTurn 跳过? 入口函数 runAgentLoop() 需要在追加用户消息、发出 agent_start 的同时 同步开启第一个 Turn(否则 Turn 1 的开始时间点就无法与 Trace 的开始对齐)。 但内层循环本身每一圈开头都会尝试发 turn_start——如果不加 firstTurn 标志跳过首圈,第一个 Turn 就会收到两次 turn_start,破坏了「一个 turn_start 配一个 turn_end」的事件配对约定,下游做 trace 可视化时会以为多了一个空 Turn。
