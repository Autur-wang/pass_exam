Lesson 0009 · 第 3 章 · Agent Loop

内核 + 叠加的洋葱架构
—— 与流式「原地替换」

🎯 本课目标:上一课讲清了 stopReason 是驱动循环的唯一信号——但那只是循环里的 一个判断点。这一课把镜头拉远,看整个 runLoop() 的骨架:哪部分是所有 Agent 都要的内核, 哪部分是 coding-agent 按需叠加的产品外壳。再钻进内核最重的一步——调 LLM——看流式响应里 「先占位、逐 token 原地替换」这个精巧设计。
🔁 回忆上一课: stopReason 是模型返回后驱动循环走向的唯一信号—— "toolUse" 继续转,其他值("stop"/"length"/"error"/"aborted")让循环停下或善后。 这一课要问的是:这个"继续转"的循环,到底长什么样?它的骨架里,哪些是必须有的,哪些是可以拆掉的?
这节课你将能做到一件事: 画出「十几行最简 Loop → 叠加 steering → 再叠加 followUp」的 洋葱三层图,并说清 context.messages[last] = partialMessage 这行代码为什么不是 bug,而是刻意设计的流式渲染机制。
🎯 贯穿全课的类比:洋葱与正在画的画
洋葱:剥到最里层,是十几行的最简 Loop(调模型 → 执行工具 → 再调模型);外面一层层裹上 coding-agent 的产品特性(steering、followUp)。剥掉任何一层,里层仍能独立运转—— 这是判断「内核有没有被污染」的试金石。
正在画的画:调模型这一步的流式设计,像一幅正在画的画——先在墙上钉一张空画布(空壳消息), 画师一笔一笔往上添(text_delta/toolcall_delta),观众实时看着它长成完整作品(done)。 没人会等画完了才把画布挂上墙。

1 · 最简 Loop:所有 Agent 的最小公约数

剥掉所有产品特性,一个能用的 Agent Loop 只需要十几行:一个 while 循环, 调模型、判断 stopReason、执行工具、把结果喂回去,循环往复。 

1// 最简 Agent Loop(伪代码)
2async function simpleLoop(messages, model, tools) {
3    while (true) {
4        // ① 调模型
5        const response = await callModel(model, messages, tools);
6        messages.push(response);
7
8        // ② 没有工具调用 → 结束
9        if (response.stopReason !== "toolUse") {
10            return messages;
11        }
12
13        // ③ 有工具调用 → 执行,把结果喂回去
14        for (const toolCall of response.toolCalls) {
15            const result = await executeTool(toolCall);
16            messages.push(result);
17        }
18    }
19}
🔎 出处:教程 §四 / 最简 Agent Loop 伪代码。
为什么这十几行就是「内核」? 一个 while 循环,调模型、执行工具、再调模型, 直到模型不再要求工具——这就是上一课讲的那套 stopReason 逻辑的最小实现。 任何 Agent 都需要这个内核,无论它是一问一答的简单助手,还是交互式编程 Agent。

2 · coding-agent 叠加了两层外壳

Pi 的 coding-agent 是交互式编程助手,用户在终端里跟它对话,它可能要读好几个文件、改代码、跑测试。 这种产品场景比「最简 Loop」多出真实需求,于是在内核外面叠加了两层:

叠加 1 · steering:用户在 Agent 工作期间又输入了新指令——这些消息不能等当前任务跑完, 得在下一圈开头紧急插队。体现方式是内层循环条件从只看 hasMoreToolCalls, 多了一个 || pendingMessages.length > 0。

叠加 2 · 外层 followUp 循环:Agent 自然停了之后,系统可能还想追加任务 (比如「顺便跑个测试」)。while(true) 把整个内层循环包起来,内层停了外层可以重启它, 让追加任务在同一个 Trace 内继续跑。

🔑 关键认知: steering / followUp / 钩子都是 coding-agent 的功能选择, 不是 Agent 的通用法则。如果你做的是「一问一答带工具」的简单 Agent,这张表全是多余的—— 你只需要最简 Loop。这就是「从洋葱内核按需往外叠」的落地方式。

3 · 完整 runLoop 骨架:内核 + 两层叠加拼起来

把内核和两层叠加拼起来,才是完整的 runLoop() 骨架。下面代码里每一步都标注了 它属于「内核」还是「叠加」: 

1// runLoop() 骨架(内核 + 两层叠加)
2async function runLoop(currentContext, newMessages, config, signal, emit, streamFn) {
3
4    // ① 首次 steering 检查(在进入内层循环之前!)
5    let pendingMessages = (await config.getSteeringMessages?.()) || [];
6
7    // ========== 叠加2:外层循环(followUp 续命)==========
8    while (true) {
9        let hasMoreToolCalls = true;
10        let firstTurn = true;  // 首轮跳过 turn_start(入口已发)
11
12        // ========== 内核 + 叠加1:内层循环 ==========
13        while (hasMoreToolCalls || pendingMessages.length > 0) {
14            //                                    ↑ 叠加1:steering 消息也驱动循环
15
16            if (!firstTurn) {
17                emit({ type: "turn_start" });
18            }
19            firstTurn = false;
20
21            // 步骤 A:注入 pendingMessages(steering 消息) ← 叠加1
22            // 步骤 B:调 LLM → streamAssistantResponse()   ← 内核
23            // 步骤 C:检查 stopReason                       ← 内核
24            // 步骤 D:执行工具                               ← 内核
25            // 步骤 E:emit turn_end                          ← 内核
26            // 步骤 F:prepareNextTurn → shouldStopAfterTurn  ← 叠加(钩子)
27            //         → 再次检查 steering                     ← 叠加1
28        }
29
30        // ========== 内层循环结束 ==========
31        // 叠加2:检查 followUp 队列
32        const followUpMessages = (await config.getFollowUpMessages?.()) || [];
33        if (followUpMessages.length > 0) {
34            pendingMessages = followUpMessages;
35            continue;  // 回到外层循环顶部,内层循环重开
36        }
37
38        break;  // 两个队列都空,真正退出
39    }
40}
🔎 出处:教程 §4.2 / runLoop 内核+两层叠加骨架。

留意 第 5 行:首次 steering 检查在进入循环之前就做了——因为用户在等待 LLM 首次响应时 可能又输入了内容,循环还没开始就得先取一遍,否则这批消息会漏掉。而 第 13 行的循环条件正是「内核 hasMoreToolCalls + 叠加1 pendingMessages.length>0」 拼在一起的地方——两个条件任一为真都继续转。

从里到外的三层洋葱 ┌─────────────────────────────────┐ │ 叠加2:外层 while(true) followUp │ │ ┌───────────────────────────┐ │ │ │ 叠加1:内层循环条件 │ │ │ │ 多了 ||pendingMessages... │ │ │ │ ┌─────────────────────┐ │ │ │ │ │ 内核:simpleLoop │ │ │ │ │ │ 调模型→判断→执行工具 │ │ │ │ │ └─────────────────────┘ │ │ │ └───────────────────────────┘ │ └─────────────────────────────────┘ 剥掉外两层,内核十几行仍能独立运转——这是「内核未被污染」的试金石。

4 · 内核最重的一步:streamAssistantResponse() 调 LLM

调 LLM 是整个 Loop 最重的一步,分四阶段:A 上下文预处理(可选 transformContext)、 B convertToLlm 转换、C 构建全新 llmContext 并调用、D 流式处理响应。 这一节聚焦阶段 D——流式响应里最值得记住的设计。

streamFunction 返回的是一个异步迭代器。for await 逐个消费事件, 按事件类型做不同处理: 

1// 阶段 D:流式处理响应
2for await (const event of response) {
3    switch (event.type) {
4        case "start":
5            // 拿到一个"空壳"消息,直接 push 到 context
6            partialMessage = event.partial;
7            context.messages.push(partialMessage);
8            emit({ type: "message_start", ... });
9            break;
10
11        case "text_delta":       // 文本增量
12        case "toolcall_delta":   // 工具调用增量
13        case "thinking_delta":   // 思考增量
14            partialMessage = event.partial;            // 更新后的部分消息
15            context.messages[last] = partialMessage;    // ★ 原地替换!
16            emit({ type: "message_update", ... });      // UI 收到增量更新
17            break;
18
19        case "done":
20        case "error":
21            finalMessage = await response.result();
22            context.messages[last] = finalMessage;       // ★ 用最终完整消息替换
23            emit({ type: "message_end", ... });
24            return finalMessage;
25    }
26}
🔎 出处:教程 §4.4 / agent-loop.ts:313-357 流式原地替换。

数据在流式响应期间,context.messages[last] 的演变:

1start      → { role: "assistant", content: [] }                    // 空壳 push
2text_delta → { content: [{ type:"text", text:"好的..." }] }       // 文字在长
3toolcall   → { content: [{ text:"好的..." },                        // 工具调用出现
4                         { type:"toolCall", name:"read", arguments:{...} }] }
5done       → { content: [...], stopReason:"toolUse", usage:{...} } // 最终完整消息替换
为什么要先 push 空壳再原地替换? 目的是让 UI 实时展示。如果等全部响应完成才 push 到 context, 用户在 LLM 思考的几秒里会盯着空白屏幕。通过「先放空壳、逐 token 替换」,UI 通过 message_update 事件 拿到最新部分消息,能做到逐字渲染——这也解释了为什么「原地替换」的关键是覆盖最后一条 (context.messages[last]=...),而不是往数组末尾 push 新条目: 数量不变、内容在长大,才能让 UI 稳定地对着「同一条消息」持续刷新内容,而不是每来一个 delta 就多出一条消息。

5 · 顺带一提:convertToLlm 这个翻译官

阶段 B 的 convertToLlm(messages) 站在 Agent 内核与 LLM 之间的边界上。 Agent 内部维护的消息含自己的「内部语言」(如 CompactionSummary/BashExecution/BranchSummary), LLM 只认 user/assistant/toolResult 三种标准消息,默认实现就是一个 .filter(): 

1// 默认 convertToLlm:只保留三种标准消息
2function defaultConvertToLlm(messages) {
3    return messages.filter(
4        (message) => message.role === "user"
5                  || message.role === "assistant"
6                  || message.role === "toolResult",
7    );
8}
🔑 为什么每圈重建全新的 llmContext wrapper? 虽然 tools 和 systemPrompt 是引用赋值、字节稳定,但 prepareNextTurn 可能换模型/改 systemPrompt、 扩展系统可能动态注册工具——重建 wrapper 成本可忽略(一个 JS 对象),却能防止共享引用导致的状态污染。
