Lesson 0018 · 第 6 章 消息系统

第一层:LLM 只认三种消息

🎯 本课目标:上一课(0017)讲完"错误也是消息"——工具失败不抛异常,而是变成一条 isError: true 的 ToolResultMessage。这节课把镜头拉远一步:抛开 "错误"这个特例,LLM 能理解的消息,一共只有三种。我们要拆开这三种消息的字段, 搞清它们各自长什么样、为什么这么设计。
⏮ 回忆上一课:0017 说工具执行失败时,五步管道不抛异常,而是把错误包成一条 ToolResultMessage,靠 isError 字段告诉 LLM"这次没成功"。 可我们从没正面拆开过 ToolResultMessage 本身——它除了 isError 还有哪些字段?这正是今天要补的一课。
这节课你将能做到一件事: 画出 Message 联合类型的三个成员 ——UserMessage / AssistantMessage / ToolResultMessage——并说出每个字段的用途,以及 为什么 AssistantMessage 的 content 必须是数组而不是字符串。
🎯 贯穿全课的类比:信封的规格 上一章末尾,工具产出了一条 ToolResultMessage。可我们五章都在说"消息",却从没拆开看过它长什么样。 就像你天天寄信,却没看过信封到底有几种规格——LLM 这个"收件方"其实只认三种信封: 用户写的信(UserMessage)、AI 回的信(AssistantMessage)、快递员送回的回执(ToolResultMessage)。 信里能装什么、信封上有哪些必填栏,今天全部拆开看。

1 · Message 联合类型:封闭的三个成员

LLM 能理解的消息格式,在 Pi 里叫 Message 类型,定义在最底层的 packages/ai/src/types.ts——注意是最底层的包,连 Agent 概念都没有, 纯粹是"跟 LLM API 打交道"这一层的格式约定。它只有三个成员: 

1Message 联合类型(LLM 标准格式)
2│
3├── UserMessage        ← 用户说的话 / 发的图片
4├── AssistantMessage   ← LLM 的回复(含思考、工具调用)
5└── ToolResultMessage  ← 工具执行后的结果
为什么是"三种"而不是随便加? 因为这是 LLM Provider API 本身的约定——OpenAI、Anthropic 的对话接口只认 user / assistant / tool(-result) 这几个角色。Pi 的 Message 类型如实映射了这个约定,它是封闭的:不能随便往里加第四种成员。 这个"封闭性"很关键——下一节(0019)会讲 Agent 内部其实还有一堆自定义消息类型 (BashExecutionMessage、CompactionSummary 等),但它们都不属于 Message, 必须先翻译成这三种之一,LLM 才认得。

2 · UserMessage:最简单的一种

用户输入,字段最少:

1{
2    role: "user",
3    content: string | (TextContent | ImageContent)[],  // 纯文本或内容块数组
4    timestamp: number                                    // Unix 毫秒时间戳
5}

content 可以是一个纯字符串,也可以是一个内容块数组(TextContent 或 ImageContent)。这意味着用户消息既能发文字,也能发图片—— 两种表示法共存于同一个字段类型里,靠联合类型区分。

3 · AssistantMessage:字段最多的一种

LLM 的回复,字段最多,信息量也最大:

1{
2    role: "assistant",
3    content: (TextContent | ThinkingContent | ToolCall)[],  // 三种内容块
4    api: Api,                   // 使用的 API 类型(如 "anthropic-messages")
5    provider: ProviderId,       // 提供商(如 "anthropic")
6    model: string,              // 模型名(如 "claude-sonnet-4-6")
7    usage: Usage,               // token 用量统计
8    stopReason: StopReason,     // 停止原因(第3章讲过的5种值)
9    errorMessage?: string,      // 错误信息
10    timestamp: number
11}

最值得关注的是 content 字段——它不是字符串,而是一个内容块数组, 可以包含三种东西: 

1AssistantMessage 的 content 内容块
2│
3├── TextContent       ← 普通文本
4│     { type: "text", text: "..." }
5│
6├── ThinkingContent   ← 思考过程(第3章讲过,模型"在想"但不直接告诉用户的部分)
7│     { type: "thinking", thinking: "..." }
8│
9└── ToolCall          ← 工具调用(第5章讲过,触发五步管道的入口)
10      { type: "toolCall", id: "...", name: "read", arguments: { path: "..." } }

一条助手消息可能同时包含文本和工具调用。 比如 LLM 一边说"让我帮你看看这个文件", 一边发出一个 Read 工具调用——这两个内容会放在同一个 AssistantMessage 的 content 数组里。第 3 章讲的"模型回复中包含 ToolCall"就是这个结构。

为什么 content 设计成数组,而不是一个字符串? 因为一次回复要同时容纳 普通文本、思考过程、工具调用三类内容——三者的性质完全不同(说给用户听的、 模型自己的推理、发给执行系统的指令),但它们又需要共存于同一条消息里,保持时间顺序 (先说了什么、后调了什么工具)。只有数组才能让三种异质内容按发生顺序排在一起。 如果 content 是字符串,工具调用就得塞进别的字段,文本和工具调用的先后关系就丢了。

进阶细节 content 块里还有一些 *Signature 字段 (textSignature、thinkingSignature 等),是某些 Provider(OpenAI、Google) 要求的不透明签名 ID,下一轮请求必须原样回传。被安全过滤器编辑过的内容密文也存在这里。

为什么内容块里还有 *Signature 字段? 那是 OpenAI/Google 等 Provider 要求原样回传的 不透明签名 ID,是"Provider 之间的上下文连续性机制"。日常理解不必深究——知道它存在、 知道不能随便丢弃就够了。

4 · ToolResultMessage:精准关联回调用

工具执行的结果,是第 5 章五步管道的终点产物:

1{
2    role: "toolResult",
3    toolCallId: string,                             // 对应哪个 ToolCall
4    toolName: string,                               // 工具名
5    content: (TextContent | ImageContent)[],        // 结果内容
6    details?: TDetails,                             // 结构化详情(给 UI 看的)
7    isError: boolean,                               // 是否执行失败(第5章的"永不抛出"产物)
8    timestamp: number
9}

ToolResultMessage 通过 toolCallId 字段和 AssistantMessage 里的 ToolCall 对应起来。第 3 章提到的"工具结果必须精准关联回调用请求"就是靠这个字段。 details 字段携带结构化信息给 UI 渲染用,LLM 通常不需要看这个字段。

为什么 ToolResultMessage 要带 toolCallId? 因为一轮回复可能发出多个工具调用 (比如同时读三个文件),结果必须精准关联回是哪一个 ToolCall——靠这个 id 一一对应,不能靠顺序猜、 也不能靠工具名猜(同一个工具可能被调用多次)。
🔑 为什么 details 字段 LLM 通常不看? 它是给 UI 渲染用的结构化详情,LLM 只需要 content 里的文本就够理解结果。这是典型的职责分离: 同一条 ToolResultMessage 服务两个读者(LLM 和 UI),但各取所需——LLM 读 content, UI 读 details。这个"一条消息、两个读者"的矛盾,会在下一课(0019)进一步展开。

5 · 串成一个完整对话

把这三种消息串起来,一个典型的对话片段长这样:

1messages 数组:
2│
3├── [0] UserMessage
4│       role: "user"
5│       content: "帮我看看 auth.ts"
6│
7├── [1] AssistantMessage
8│       role: "assistant"
9│       content: [
10│           { type: "text", text: "让我帮你看看这个文件" },
11│           { type: "toolCall", id: "tc_001", name: "read", arguments: { path: "auth.ts" } }
12│       ]
13│       stopReason: "toolUse"     ← 第3章讲过:调了工具,循环继续
14│
15├── [2] ToolResultMessage
16│       role: "toolResult"
17│       toolCallId: "tc_001"      ← 和上面的 id 对应
18│       content: [{ type: "text", text: "import { auth } from '...' ..." }]
19│       isError: false            ← 第5章讲过:正常结果
20│
21└── [3] AssistantMessage
22        role: "assistant"
23        content: [{ type: "text", text: "auth.ts 是一个认证模块..." }]
24        stopReason: "stop"        ← 没调工具,循环结束

这就是 LLM 能理解的世界——用户说了什么、AI 回了什么、工具返回了什么,就这么三种。 stopReason 是驱动 Agent Loop 是否继续循环的开关:"toolUse" 意味着还有工具调用等着执行,循环继续;"stop" 意味着这轮回复没调工具,循环结束。

Message 联合类型 —— LLM 只认这三种信封 ┌──────────────┐ ┌──────────────────────┐ ┌──────────────────┐ │ UserMessage │ │ AssistantMessage │ │ ToolResultMessage│ │ role: user │ │ role: assistant │ │ role: toolResult │ │ content: │ │ content: [ │ │ toolCallId ──────┼──┐ │ string 或 │ │ text? / thinking? / │ │ content: [...] │ │ │ 内容块[] │ │ toolCall? ] │ │ isError: bool │ │ └──────────────┘ │ stopReason ──────────┼─┐ └──────────────────┘ │ └──────────────────────┘ │ │ "toolUse"→循环继续 ──────────┘ │ "stop" →循环结束 │ │ ToolCall.id === ToolResultMessage.toolCallId ◄────┘ (靠 id 一一对应,不靠顺序、不靠工具名)
