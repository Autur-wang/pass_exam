Lesson 0025 · 第 8 章 上下文工程

系统提示词组装与全景管道
—— 上下文工程的「加法」侧

🎯 本课目标:上一课我们建立了「上下文工程是两层防护」的地图—— 输入侧管窗口不被撑爆,历史侧管长对话不失控。这节课深入输入侧的加法问题: 怎么让 LLM 自动知道项目约定(比如「这个子项目用 pnpm 不用 npm」),而不用用户每轮重复说。 读完你会看到多层 CLAUDE.md 递归 + XML 包装 + Skills 懒加载三件事怎么拼成系统提示词, 以及它在「一次调用全景漏斗」里的位置。
↩️ 先回忆上一课: 上下文工程分两层防护——输入侧(单条工具输出别太大 / 提示词别太臃肿) 和历史侧(长对话要压缩 / 分支切换要摘要)。今天专注输入侧的第二件事:系统提示词怎么组装, 这是「加法」,和上节课讲的工具输出截断(「减法」)正好相对。
这节课你将能做到一件事: 说清系统提示词组装的三个动作 ——多层 CLAUDE.md 递归合并、XML 包装、 Skills 懒加载——各自解决什么问题、为什么这样设计, 并能把它嵌进「一次调用经过的全景漏斗」里,指出它是漏斗的第几层。
🎯 贯穿全课的类比:入职资料袋 想象你入职一家跨国公司分公司的一个项目组。桌上摆着一叠文件,从下到上分别是 公司总则(全局规范)、部门手册(祖先目录的规范)、项目须知(当前项目最具体的规范)—— 越往上越具体,遇到冲突以最上面那张为准。文件袋末尾还夹着一张技能目录卡: 列了公司有哪些操作手册(Skills),但手册全文不在袋子里,你需要用到时自己去档案室(read 工具)取。 这就是「不把整个档案室搬到你桌上,只给你一份目录 + 一条通往档案室的路」。

1 · 多层 CLAUDE.md 递归:从「满」变成「凑齐」

Pi 在每个目录下找 AGENTS.md 或 CLAUDE.md(大小写都试), 然后从 cwd 向上递归到根目录,把沿途所有目录的规范文件全部合并。 为什么要向上递归,而不是只读 cwd 这一份?因为现代项目常是 monorepo 嵌套结构—— 组织级、团队级、项目级规范分散在不同层的目录里,只读 cwd 会漏掉上层的通用约定, 向上递归才能凑齐一本完整的「分层规范手册」。完整的查找顺序(loadProjectContextFiles, resource-loader.ts:85-123): 

1┌──────────────────────────────────────────────────────┐
2│  系统提示词组装顺序                                   │
3├──────────────────────────────────────────────────────┤
4│  1. agentDir/CLAUDE.md   ← 全局(用户级)            │
5│  2. 祖先目录/CLAUDE.md   ← 从 / 到 cwd 上一层        │
6│  3. cwd/CLAUDE.md        ← 当前项目                  │
7└──────────────────────────────────────────────────────┘
为什么祖先在前、项目在后? 从外到内 = 从通用到具体。后出现的项目规范能覆盖前面的通用规范, 符合「细则优先于总则」的直觉——就像入职资料袋,项目须知永远压在最上面, 真出现冲突,你听最上面那张的。这让 LLM 读到的是一本有顺序的分层手册, 而不是一堆同等权重、互相打架的规则。
🔎 出处:教程 §四「多级上下文文件」/ loadProjectContextFiles,resource-loader.ts:85-123。

2 · XML 包装:给项目指令画一道清晰的边界

找到上下文文件后,buildSystemPrompt(system-prompt.ts:154-161) 用 <project_instructions path="..."> 包装,外层再套一个 <project_context>: 

1<project_context>
2
3Project-specific instructions and guidelines:
4
5<project_instructions path="/myorg/CLAUDE.md">
6全组织规范:所有项目使用 TypeScript strict 模式...
7</project_instructions>
8
9<project_instructions path="/myorg/teams/teamA/projects/app1/CLAUDE.md">
10本项目使用 pnpm,测试用 vitest...
11</project_instructions>
12
13</project_context>
🔑 为什么用 XML 而不是 Markdown? 两条理由—— ① 边界明确:</project_instructions> 是清晰的结束标记,LLM 不会把项目规范 和外部指令(比如用户临时插入的话)混淆;② 带 path 属性:LLM 看到内容来自哪个文件, 就能区分「这是全组织规范」还是「这是本项目规范」,进而判断优先级。 这是主流 LLM 都吃得准的标准 prompt 技巧,和体积、解析速度无关。
🔎 出处:教程 §四「XML 包装」/ buildSystemPrompt,system-prompt.ts:154-161。

3 · Skills 懒加载:清单进 prompt,全文按需 read

Skills(项目特定操作指南)每个是一份 SKILL.md,可能几千字。 如果把所有 skill 全文塞进系统提示词,token 开销巨大且大部分用不上。 Pi 的方案是 formatSkillsForPrompt(skills.ts:335-361)—— 只放轻量清单(name / description / location),全文由 LLM 自己主动 read: 

1<available_skills>
2  <skill>
3    <name>test-setup</name>
4    <description>How to run tests for this project</description>
5    <location>/path/to/skills/test-setup/SKILL.md</location>
6  </skill>
7</available_skills>

清单顶上还有一句契约:Use the read tool to load a skill's file when the task matches its description。对照两种方案的 token 开销:

方案Token 开销信息密度
推模式:全文塞10 个 skill × 2000 字 ≈ 50K token大部分无关
拉模式:懒加载10 个 skill × 4 行 ≈ 500 token精准命中才展开
为什么 Skills 用拉模式而非推模式? 大部分 skill 当前任务根本用不上,全文预付 token 是纯浪费。 Pi 把 LLM 的主动性(调 read 工具)纳入上下文工程设计——「用时才付,不用不付」。 这也揭示了更深一层的模式:工具调用本身就是一种按需上下文加载的载体。
🔎 出处:教程 §四「Skills 懒加载」/ formatSkillsForPrompt,skills.ts:335-361;Token 对照表。

4 · 骨架收尾:Current date / cwd 放在最后

把上面所有元素串起来,系统提示词骨架末尾才是 Current date 和 Current working directory——这两个看似简单的字段,其实是「基本元数据」: LLM 需要知道「今天是哪天」才能处理「昨天」「上周」这类相对时间, 需要知道「我在哪个目录」才能处理相对路径。放在骨架末尾,离 LLM 实际推理最近,便于随手解算。

5 · 全景漏斗:这一课的组装,嵌在链路的第几层?

第 24 课讲过「两层防护」的地图;把 §三(工具输出截断)到 §六(分支摘要)串起来, 就是一次工具调用经过的完整链路——本课讲的「系统提示词组装」正是这道漏斗的第 [1] 层:

一次工具调用经过的完整上下文工程链路 用户输入 "修复 auth.ts 的 bug" │ ▼ [1] 系统提示词组装(本课) buildSystemPrompt() ├─ 找 CLAUDE.md(向上递归 + agentDir) ├─ 加载 Skills 清单(懒加载) ├─ 拼接工具列表 + guidelines └─ 末尾加 Current date / cwd │ ▼ [2] 用户消息进入 context.messages ▼ [3] Agent Loop 开始 ▼ [4] LLM 返回 toolCall: read("auth.ts") ▼ [5] 执行工具 ▼ [6] ★ 工具输出截断(上一课讲的「减法」) ▼ [7] toolResult 进历史 ▼ ...循环... ▼ [8] agent_end 事件触发 ▼ [9] 检查 shouldCompact? ├── 否 → 等下一轮 └── 是 → 执行 Compaction(第9章)
🔑 四层组合成一道漏斗: §三控制单条工具结果的体积,§四(本课)控制 系统提示词的内容,§五控制长对话的总长度,§六控制多分支的信息保留。 没有哪一层单独就够——它们组合起来,才能让最终送进 LLM 的是「对当前任务最有价值的信息」。
🔎 出处:教程 §七「全景链路」/ ASCII 全景图。

💬 卡住就问我。 几个值得追问的好问题: 「如果两个不同层级的 CLAUDE.md 内容互相矛盾,LLM 真的会「以后者为准」吗,还是要靠 prompt 里的措辞去引导?」 「Skills 清单里的 description 写得不好,会不会导致 LLM 该 read 的时候没 read?」 「系统提示词组装(加法)和工具输出截断(减法)都在「输入侧」,它们会不会互相冲突——比如提示词本身也会被截断吗?」 ——最后这个问题,正好把我们带向下一课:工具输出截断的细节。
