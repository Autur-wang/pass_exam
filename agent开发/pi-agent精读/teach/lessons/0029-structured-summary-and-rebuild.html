Lesson 0029 · 第 9 章 上下文压缩

怎么压与如何生效
—— 结构化摘要 + 上下文重建

🎯 本课目标:上一课解决了「切哪里」——用向后遍历找到一个合法切割点, 把消息序列分成「被压缩」和「保留」两半。这一课接着讲被压缩的那一半去哪了: 它不是被扔掉,而是变成一段结构化摘要;以及这段摘要怎么在下一轮真正发挥作用。
🔁 先回忆上一课:切割点算法向后遍历、累积到 keepRecentTokens(20K)就停, 且只能切在 user 或 assistant 边界、绝不能切在 toolResult 后面——这是「切哪里」的答案。 但切完之后呢?切割点之前的那几十轮对话,总不能真的从内存里消失——LLM 还得知道「之前发生了什么」。 这节课就讲:那些消息被压成了什么,以及这个「压成的东西」怎么在下一轮对话里重新生效。
这节课你将能做到一件事: 说清 Pi 的摘要为什么是6 个固定 section 而不是「随便写一段总结」,理解增量更新和文件跟踪 怎么解决多次压缩的漂移问题,并画出 CompactionEntry 如何被 buildSessionContext() 重建成下一轮 LLM 能看懂的上下文。
🎯 贯穿全课的类比:填表 vs 凭记忆写会议纪要 让 LLM「随便写段总结」,就像让人凭记忆写会议纪要——它容易被某个有趣的技术细节吸引, 写了一大段却忘了记用户最核心的需求。Pi 的做法是给它一张固定表格 (Goal / 约束 / 进度 / 决策 / 下一步 / 关键上下文),像填病历一样每一栏都必须填—— 把「易遗漏」变成「必须填」。

1 · 摘要不是自由文本,是填表

Pi 不是让 LLM「随便写一段总结」,而是要求它填一个固定格式的表格—— SUMMARIZATION_PROMPT 强制 LLM 覆盖 6 个固定 section: 

1## Goal                    ← 用户最初要做什么
2## Constraints & Preferences  ← 有什么约束
3## Progress                ← 做了什么(Done / In Progress / Blocked)
4## Key Decisions           ← 关键决策
5## Next Steps              ← 下一步做什么
6## Critical Context        ← 不能忘记的关键信息
🔎 出处:教程第 9 章 §四「摘要的格式」/ SUMMARIZATION_PROMPT。代码为教程示意,基于 pi v0.80.2。

注意第 3 行 Progress 里专门拆了三个子项——Done / In Progress / Blocked。 Blocked 是最容易被自由文本摘要漏掉的一类信息:「卡住的事」往往不体面、不显眼, 但恰恰是新一轮 Agent 最该优先处理的。

为什么用 6 section 结构化模板,而不是「请总结对话」? 因为自由文本摘要有一个固定的失败模式:LLM 容易被「有趣的内容」吸引, 花大篇幅描述某个技术细节,却忘了记录用户的核心需求。固定 section 强制 LLM 在每个维度上至少扫一遍——这是用 prompt 设计对抗 LLM 认知偏差的一个范例。

2 · 生成流程:序列化 + 一次 LLM 调用

被压缩的那批 AgentMessage[],先被序列化成人类可读的文本 ([User] / [Assistant tool calls] / [Tool result] 这样的标注), 再调一次 LLM,用 SUMMARIZATION_PROMPT 让它生成结构化摘要: 

1原始消息(AgentMessage[])
2    │
3    ▼ 序列化
4"[User]: 帮我修 auth.ts
5 [Assistant tool calls]: read(path=\"auth.ts\")
6 [Tool result]: export function authenticate() {...}
7 [Assistant]: 找到问题了,缺少 salt..."
8    │
9    ▼ LLM 调用(用摘要 prompt)
10    │
11结构化摘要
12    ## Goal
13    Fix authentication bug in auth.ts
14    ## Progress
15    ### Done
16    - [x] Read auth.ts, identified missing salt
17    ...
🔎 出处:教程第 9 章 §四「摘要生成:一次 LLM 调用」。基于 pi v0.80.2。

3 · 增量更新:更新而非重写

一个长对话可能被压缩不止一次——比如第一次压缩第 1-30 轮, 第二次压缩第 31-50 轮。第二次压缩时,Pi 会把上一次的摘要作为 previousSummary 传进去: 

1第一次压缩:
2  输入:第1-30轮原始消息
3  输出:摘要 A
4
5第二次压缩:
6  输入:摘要 A + 第31-50轮原始消息
7  输出:摘要 B(在 A 的基础上合并新信息)
🔎 出处:教程第 9 章 §四「增量更新:不是每次从零开始」/ UPDATE_SUMMARIZATION_PROMPT。基于 pi v0.80.2。
🔑 为什么增量更新,而不是每次从零重写? 多次压缩若每次都从零写,摘要会一点点漂移、累积误差;在旧摘要基础上「更新而非重写」, 能让已有的 Goal / Constraints 稳定保留,新增的 Progress 只是追加——比每次从零开始写更稳定。

4 · 文件跟踪:编码 Agent 的领域特定知识

对编码 Agent 来说,「改了哪些文件」是至关重要的信息。Pi 在 6 section 摘要文字之外, 单独维护一份文件跟踪列表,用 extractFileOperations 从两处累积: 上一次压缩的 details.readFiles / modifiedFiles, 加上这次被压缩消息里工具调用涉及的文件。最终用 formatFileOperations 把它们附到摘要末尾: 

1<read-files>
2src/auth.ts
3src/utils/hash.ts
4</read-files>
5
6<modified-files>
7src/auth.ts
8</modified-files>
🔎 出处:教程第 9 章 §四「文件跟踪:压缩不只是摘要文字」/ formatFileOperations。基于 pi v0.80.2。
为什么单独跟踪文件,而不是写进 6 section 文字里? 「改过哪些文件」比「讨论过什么」更精确、可验证——这是把领域特定知识嵌入通用压缩机制: 压缩算法本身是通用的(适用于任何对话),而 details 字段承载了编码 Agent 特有的信息。这份列表跨压缩累积,即使经过多轮压缩,Agent 仍知道整个会话读过、改过哪些文件, 从而避免重复读、避免覆盖改动。

5 · 压缩结果的物理形态:CompactionEntry

摘要生成后要落地成一个具体的数据结构,存进 Session Tree(下一课的主题): 

1{
2    type: "compaction",
3    summary: "## Goal\nFix auth.ts...\n## Progress\n...",   // 摘要文本
4    tokensBefore: 185000,              // 压缩前 token 数(用于诊断和审计)
5    firstKeptEntryId: "e30",           // 保留的起始 entry id(重建上下文时从这开始)
6    details: {                         // 文件操作跟踪(来自 extractFileOperations)
7        readFiles: ["src/auth.ts", "src/utils/hash.ts"],
8        modifiedFiles: ["src/auth.ts"],
9    },
10    // ... 含 id/parentId/timestamp 等 SessionEntryBase 字段
11}
🔎 出处:教程第 9 章 §六「CompactionEntry:压缩结果的物理形态」/ session-manager.ts。基于 pi v0.80.2。
🔑 为什么用 CompactionEntry 存进 Session Tree,而不是直接替换消息数组? 压缩发生在两轮之间(上一课回忆过这个时序),结果需要一个能被下一轮 buildSessionContext() 读取、重建的持久物——直接改消息数组会丢失原始历史、 也没法审计。这也自然引出下一课的主题:历史为什么是树而不是线性数组。

6 · 如何生效:下一轮的上下文重建

下次 Agent 运行时,buildSessionContext() 会根据 CompactionEntry 重建上下文——摘要文本变成一条 CompactionSummaryMessage, 和 firstKeptEntryId 之后保留的原始消息拼在一起:

重建后的上下文 ├── CompactionSummaryMessage(role: "compactionSummary") │ content = 摘要文本 │ (convertToLlm 把它翻译成 <summary> 包裹的 UserMessage) │ ├── 保留的原始消息(entry 30 之后的消息) │ ├── UserMessage: "继续修复" │ ├── AssistantMessage: ... │ └── ... │ └── (新的消息会在运行中追加)
🔎 出处:教程第 9 章 §六「上下文重建」/ buildSessionContext。基于 pi v0.80.2。

CompactionSummaryMessage 是 coding-agent 的自定义消息类型, convertToLlm 会把它翻译成 <summary> 标签包裹的 UserMessage, LLM 看到的是:「The conversation history before this point was compacted into the following summary: ...」。 对 LLM 来说,之前的几十轮对话变成了一个摘要——它不知道原始消息的细节, 但它知道目标、进度、决策和文件操作记录,这对继续工作来说通常够用。

7 · 集成点:压缩嵌在哪、发什么事件

自动压缩嵌在 AgentSession 的 agent_end 事件处理里, 整个过程发出两种事件供 UI 显示进度: 

1Agent 运行结束(agent_end 事件)
2    │
3    ▼
4检查 shouldCompact()?
5    │
6    ├── 不需要 → 结束
7    │
8    └── 需要 → 执行压缩
9         ├── findCutPoint → 找切割点
10         ├── 序列化 + LLM 调用 → 生成摘要
11         ├── 追加 CompactionEntry 到 Session Tree
12         └── 下次运行时 buildSessionContext 使用压缩后的上下文

两种事件:compaction_start(reason: "manual" | "threshold" | "overflow") 和 compaction_end(携带压缩结果或错误信息)。

8 · 立刻自测(答完即有反馈)
