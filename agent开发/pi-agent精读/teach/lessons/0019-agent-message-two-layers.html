Lesson 0019 · 第 6 章 消息系统

第二层:AgentMessage
—— 内富外严的双层设计

🎯 本课目标:上一课讲了 LLM 只认识三种标准消息(User/Assistant/ToolResult)——那是「外层」。 这一课讲「内层」:Agent 内部为什么需要自己的一套消息类型,以及 AgentMessage 如何用联合类型 + 声明合并,把这些自定义消息安全地装进标准消息旁边。
⏮ 先回忆上一课:LLM API 只接受三种消息——UserMessage、 AssistantMessage、ToolResultMessage,这是协议强制的封闭集合,一个都不能多。 但 Agent 内部要处理的信息远不止「对话」——Bash 执行记录、上下文压缩摘要、Git 分支记录…… 这些东西塞进哪个标准消息都不合适。今天就来看 Pi 怎么解决这个「装不下」的问题。
这节课你将能做到一件事: 讲清楚 Pi 为什么不能把 Bash 执行结果直接拍扁存进 UserMessage,以及 AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages] 这行代码里,声明合并如何让核心包零依赖、应用层却全栈类型安全。
🎯 贯穿全课的类比:一份数据,两张嘴 你在终端敲下 !ls -la,这条命令的信息同时有两个「读者」要伺候: UI 想要 command/output/exitCode 分开渲染成漂亮终端, LLM 只想要一段扁平文本。一份数据,两张嘴,谁也不能得罪——这就是整章的矛盾核心。

1 · 是什么:功能性数据有两个互相打架的读者

Agent 内部除了「LLM 对话」之外,还有大量功能性数据要管理:Bash 命令的执行记录、 上下文被压缩后的摘要、Git 分支切换的记录、用户上传的附件元信息……这些数据有 两个独立的读者,而他们的需求是冲突的:

读者要什么举例(Bash 执行)
🖥️ UI 端结构化字段,才能分开渲染command、output、exitCode、cancelled、truncated 各占一行,命令高亮、输出等宽、退出码带颜色
🤖 LLM 端只要一段扁平文本"用户执行了 ls -la,输出是 file1.txt..."——塞进 UserMessage.content 就够
🔑 冲突点在哪? 如果为了迁就 LLM,提前把字段拍扁存进 UserMessage, UI 就再也拿不回结构化数据了——已经搅成一锅粥,退出码的颜色、命令的高亮全部消失。 反过来,如果只存结构化的自定义消息、不进 LLM 上下文,LLM 就会失忆——下一轮它根本不知道用户刚执行过什么。 二选一,两边都要付出代价。

2 · 怎么做:两边都不妥协——结构化存储 + 边界翻译

Pi 的解法是两层各管各的:以结构化形式存进 context.messages (满足 UI/持久化),在调用 LLM 的边界上做一次翻译(满足 LLM)。 这样 UI 永远有完整的结构化数据可用,LLM 也能看到它需要的扁平版本。

为什么翻译放在最后一刻、且是有损单向的? 因为损失掉的结构化字段(cancelled、 truncated 等)UI 早就用过了,进 LLM 时无所谓——单向拍扁最省心,没必要设计一套「反向还原」的机制。

但这里有个根本性的问题:LLM 认识的 Message 联合类型是封闭的—— 只有 UserMessage、AssistantMessage、ToolResultMessage 三种。 Bash 执行这类自定义消息根本不属于这三种中的任何一种。它们怎么被 Agent 系统接受的? 答案就是今天的主角——AgentMessage。

3 · AgentMessage 联合类型:LLM 标准消息 + 自定义消息

在 packages/agent/src/types.ts:314 有一行关键代码: 

1export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];

翻译成人话:AgentMessage = LLM 标准消息 + 自定义消息。 它是 Message(三种标准格式)和 CustomAgentMessages(自定义扩展)的联合类型。 

1AgentMessage(Agent 内部使用的消息格式)
2│
3├── Message(可直接发送给 LLM 的标准消息)
4│   │
5│   ├── UserMessage          ← role: "user"
6│   ├── AssistantMessage     ← role: "assistant"
7│   └── ToolResultMessage    ← role: "toolResult"
8│
9└── CustomAgentMessages(仅 Agent 内部使用的扩展消息)
10    │
11    ├── BashExecutionMessage      ← role: "bashExecution"
12    ├── CustomMessage             ← role: "custom"
13    ├── BranchSummaryMessage      ← role: "branchSummary"
14    └── CompactionSummaryMessage  ← role: "compactionSummary"

Agent 内部的 context.messages 数组里放的就是 AgentMessage[]—— 它可以混合存放标准和自定义消息。一条消息到底是标准还是自定义的,看 role 字段就能判断。

🔎 出处:教程第 6 章 §四「AgentMessage 联合类型」/ packages/agent/src/types.ts:314。

4 · CustomAgentMessages:核心包留的空插槽

关键在 CustomAgentMessages 这个接口——它在核心包 pi-agent-core 里是空的: 

1export interface CustomAgentMessages {
2    // Empty by default - apps extend via declaration merging
3    // 默认为空 - 应用通过声明合并扩展
4}

核心包完全不知道有什么 BashExecutionMessage、CompactionSummaryMessage 这些东西。它只提供了一个「插槽」,让应用层往里插。

应用层怎么「插」?靠 TypeScript 的声明合并(Declaration Merging)。 coding-agent 通过 declare module 语法把自己的 4 种消息类型注入进去: 

1declare module "@earendil-works/pi-agent-core" {
2    interface CustomAgentMessages {
3        bashExecution: BashExecutionMessage;
4        custom: CustomMessage;
5        branchSummary: BranchSummaryMessage;
6        compactionSummary: CompactionSummaryMessage;
7    }
8}

这段代码的效果是:编译器自动把这 4 种类型加入 AgentMessage 联合类型。 以后在 coding-agent 项目里,AgentMessage 就变成了 7 种消息的联合(3 种标准 + 4 种自定义), TypeScript 会帮你做完整的类型检查。

为什么用声明合并,而不用继承或泛型? 继承需要修改基类——你改不了 pi-agent-core 包; 泛型需要到处传参数——每个用到 AgentMessage 的函数签名都要加泛型参数。 声明合并的好处是:核心包完全不知道扩展的存在(零依赖),扩展包却能获得完整的类型安全。 不同应用还能注册各自不同的自定义消息——比如 Web UI 就注册了自己的 user-with-attachments、artifact, 每个应用只看到自己需要的类型。
🔎 出处:教程第 6 章 §四「默认为空的扩展点」「声明合并」/ packages/coding-agent/src/core/messages.ts:70-77。

5 · 具体长什么样:BashExecutionMessage

以开场的场景为例——你敲 !ls -la,Pi 内部生成的 BashExecutionMessage 结构如下: 

1{
2    role: "bashExecution",
3    command: string,          // 命令原文:"ls -la"
4    output: string,           // 输出内容:"file1.txt\nfile2.txt\n..."
5    exitCode: number | undefined,  // 退出码:0
6    cancelled: boolean,       // 是否被取消
7    truncated: boolean,       // 输出是否被截断
8    fullOutputPath?: string,  // 截断时的完整输出文件路径
9    timestamp: number,
10    excludeFromContext?: boolean  // 是否排除在 LLM 上下文之外
11}

结构化字段全保留下来了——这正是 UI 端要的东西。

🔎 出处:教程第 6 章 §三「BashExecutionMessage 结构」。

6 · 自定义消息不是麻烦,是能力

容易把自定义消息误解成「只是给 LLM 用的中间格式」,但它本身带来三个独立的能力:

能力标准消息做得到吗为什么自定义消息才行
UI 专用渲染做不到按 role 分派:bashExecution 用终端样式、compactionSummary 用摘要卡片,各占一行互不干扰
持久化恢复做不到session 存完整结构化数据,重启后 UI 能精确还原上次渲染状态
精细可见性控制做不到有自己的 role,可以在 convertToLlm 特殊处理——加 excludeFromContext 让某条消息对 LLM 隐身
🔑 为什么说这是「能力」而非「麻烦」? 没有独立的 role,就没有 UI 专用渲染、没有持久化精确还原、 也做不了「对 UI 可见对 LLM 不可见」——这三件事标准消息都办不到。下一课会展开 convertToLlm 翻译和 excludeFromContext 过滤具体怎么实现,记住: 那不是自定义消息的负担,而是它换来的好处。
两层消息 —— 内富外严 AgentMessage(内层,7 种,字段丰富) ├── Message(3 种标准)──────────┐ │ User / Assistant / ToolResult │ 直接透传给 LLM └── CustomAgentMessages(4 种) │ Bash / Custom / Branch / │ ← 核心包留空插槽 Compaction Summary │ 应用层用声明合并注入 │ │ └── 下一课:convertToLlm 翻译边界 ──→ Message[3] 发给 LLM
