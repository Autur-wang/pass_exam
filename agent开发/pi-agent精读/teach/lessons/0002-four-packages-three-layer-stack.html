Lesson 0002 · 第 1 章 开篇总览

四包三层
—— 堆栈与正交的 UI 库

🎯 本课目标:上一课我们只承认了「Pi 由 4 个包组成」这个事实,却没拆开它们的关系。 这一课只做一件事——把 pi-ai / pi-agent-core / pi-coding-agent / pi-tui 这四个包 之间「谁依赖谁、谁能单独拎出来用」讲清楚,不涉及任何一层内部的实现细节(那是后面每节课的任务)。
↩️ 接上一课: Lesson 0001 结尾留了个问题——「四个核心包到底怎么分工、谁依赖谁?」 当时我们只给了一句结论:「三层堆栈 + 一个正交 UI 库」。这节课把这句结论拆成看得懂的架构图和真代码。
这节课你将能做到一件事: 画出 Pi 的四包依赖图,并说清楚 pi-ai → pi-agent-core → pi-coding-agent 为什么是「堆栈」而 pi-tui 为什么是「正交」——这决定了你后面复用 Pi 时该拿哪一层。
🎯 贯穿全课的类比:三层货架 + 旁边的工具间 把 Pi 想成一栋三层楼货架:底层 pi-ai 管调模型(进货),中层 pi-agent-core 管跑循环(理货流程), 顶层 pi-coding-agent 是成品店面——每层都能单独拎出来用,想只进货就只租底层。 而 pi-tui 不是楼里的一层,它是货架旁边一个独立的工具间:谁都能借这套扳手螺丝刀, 它压根不知道货架在卖什么,却不属于这栋楼——反倒是店面(coding-agent)自己跑去工具间借了工具。

1 · 四个核心包,各司其职

先重温一句话定义:Pi 是极简、可扩展的终端编码 Agent 外壳(coding agent harness), 由 libGDX 作者 Mario Zechner 用 TypeScript 编写,MIT 开源。这个「外壳」由 4 个核心包拼成, 下面是教程原文的四层架构框图: 

1┌──────────────────────────────────────────┐
2│          pi-coding-agent                 │  ← 完整 CLI 产品 + SDK
3│  系统提示词 · 内置工具 · 会话管理 · 扩展  │
4├──────────────────────────────────────────┤
5│  pi-tui              │  pi-agent-core    │  ← 终端 UI + Agent 引擎
6│  差分渲染 · 组件系统  │  AgentLoop · 工具 │
7│                      │  系统 · 事件流    │
8├──────────────────────┴───────────────────┤
9│              pi-ai                       │  ← 多供应商 LLM 抽象
10│  统一 API · 上下文交接 · 流式 · Token 追踪│
11└──────────────────────────────────────────┘

注意中间那一行:pi-tui 和 pi-agent-core 是并排画的,不是叠在一条链上—— 这张图本身就在告诉你「四个包不是四层堆栈,而是三层堆栈 + 一根旁支」。

🔎 出处:教程第 1 章 §二「四个核心包,各司其职」ASCII 框图(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第1章-开篇-Pi-Agent框架总览.md)。基于 pi v0.80.2。

2 · 三层堆栈:自下而上,每层可独立用

把 pi-tui 挪开之后,剩下 pi-ai → pi-agent-core → pi-coding-agent 才是真正的堆栈, 依赖方向严格自下而上:

层包名只管一件事依赖谁
底层pi-ai调模型:统一 API、流式、跨供应商上下文交接、Token 追踪不依赖任何 Agent 概念
中层pi-agent-core跑 Agent Loop:AgentLoop · 工具系统 · 事件流依赖 pi-ai,不依赖上层
顶层pi-coding-agent组装成完整 CLI 产品 + SDK依赖 pi-ai 和 pi-agent-core

尝一口 Layer 1: pi-ai 的最小调用——它不依赖任何 Agent 概念, 可以在任何需要调 LLM 的项目里单独使用: 

1// 入口在 compat 子模块(不在主入口)
2import { getModel, stream } from '@earendil-works/pi-ai/compat';
3import type { Context } from '@earendil-works/pi-ai';
4
5const model = getModel('anthropic', 'claude-sonnet-4-5');
6// Context 是 interface(不是 class),用对象字面量构造
7const context: Context = {
8  systemPrompt: 'You are helpful.',
9  messages: [{ role: 'user', content: 'Hello!' }],
10};
11
12const eventStream = stream(model, context);
13for await (const event of eventStream) {
14  if (event.type === 'text_delta') process.stdout.write(event.delta);
15}

这段代码没有出现任何「Agent」「工具」「循环」——因为 pi-ai 压根不知道 Agent 是什么, 它只做一件事:把「给模型什么」变成「模型吐了什么」。这正是「底层」的含义。

为什么要求「每层可独立使用」? 这是 Pi 作为 SDK 的核心价值——聊天机器人只需要 pi-ai,数据分析 / 客服 Agent 只需要 pi-agent-core 在自己应用里跑循环, 完全不必碰 CLI。项目长大了也不用换框架,只是往上多接一层。
🔎 出处:教程第 1 章 §5.1 pi-ai(compat 子模块)独立使用示例(同上文件)。代码为教程示意,基于 pi v0.80.2。

3 · pi-tui:为什么画在堆栈旁边,而不是堆栈里

回到第 1 节的框图:pi-tui 和 pi-agent-core 并排,不在链条上。 原因不是「差不多重要就并排画」,而是一个可以验证的事实——

🔑 正交,是从依赖关系上验证出来的,不是画风偏好: pi-tui 的 package.json 只依赖 get-east-asian-width 和 marked 两个包,源码里零处 import 任何 @earendil-works/pi-* 兄弟包。反倒是 pi-coding-agent 单向依赖它(比如从 pi-tui 引入 fuzzyFilter)——依赖箭头永远只从堆栈指向工具间, 从没有反过来。谁调不调 LLM,pi-tui 都无所谓。

这也解释了为什么它「最容易脱离 Pi 单独复用」:任何需要终端交互界面的 Node.js 程序——CLI 工具、 交互式 dashboard、TUI 游戏、自定义 REPL——都能直接借走它,完全不必关心 Agent 体系。

4 · 极简是刻意设计,不是偷懒

四个包合起来有多「小」?下面是 v0.80.2 源码的实际数字:

指标数值含义
GitHub Stars64,000+十个月增长,社区验证了需求
内置工具4 核心 + 3 辅助核心 read / write / edit / bash;辅助 grep / find / ls
系统提示词静态模板 ~90 词运行时拼接后约 200–400 词
TUI 代码量~12000 行核心 tui.ts 单文件约 1700 行
支持供应商30+ 家KnownProvider 枚举实际 35 个(含区域变体),独立品牌约 27 个
核心包数量4 个pi-ai / pi-agent-core / pi-tui / pi-coding-agent
运行模式4 种交互 / print-JSON / RPC / SDK
为什么极简是刻意设计? 上下文窗口是 Agent 最稀缺的资源——固定指令(4 个核心工具、 ~90 词提示词)占得越少,留给你的代码和项目上下文的空间就越多。同理,Mario 不用 blessed/ink 而自己写 TUI:一旦选择了「终端外壳」这个形态,就必须自己解决终端渲染,他按游戏引擎的思路重写, 换来了差分渲染、保留模式声明式组件这些能力——这也是一种「极简」的延伸:自己掌控每一行代码的取舍。
🔎 出处:教程第 1 章 §二「关键数字」表(同上文件)。

5 · 刻意「不做」,本身也是分层的一部分

上一课已经列过「不做 MCP、不做子 Agent、不做权限弹窗」这份清单,这里只补一句和分层直接相关的: 这些缺失的功能不是靠某一层内部悄悄加代码补上的,而是统一靠 TypeScript 扩展、技能、 Pi Package 在堆栈之外补充——分层分得干净,才谈得上「按需插件」而不是「层层打补丁」。

为什么「不做」清单本身是设计? 看什么都做的框架只学到『他们做了什么』, 看刻意不做的框架才学到『做 Agent 到底需要什么』——而这份清单能存在,前提正是四包分层清楚, 「不做的东西」才有一个明确的、干净的地方可以插回来。
四包依赖关系 —— 三层堆栈 + 一根旁支 pi-coding-agent (顶层:完整 CLI + SDK) │ ▼ 依赖 pi-agent-core (中层:AgentLoop · 工具系统 · 事件流) │ ▼ 依赖 pi-ai (底层:多供应商 LLM 抽象) pi-tui ⇢ 单向被 coding-agent 依赖,自己零 import 任何 pi-* 包 (正交的终端 UI 库,与上面这条链完全解耦)
