Lesson 0031 · 第 10 章 会话管理

节点解剖与三个核心操作

🎯 本课目标:上一课我们看清了 Session Tree 这棵树为什么存在—— append-only、回退不删数据。这节课把镜头拉近,看树上一个节点到底长什么样, 以及树是靠哪三个操作长出来的。
⏮ 先回忆上一课:回退到 e2 时,branch() 的函数体只改了一行—— this.leafId = "e2",e3、e4、e5 一个都不删,完整保留在树和 .jsonl 里。 那这一行代码到底是怎么"追加"出 e3 这样的节点的?节点内部又存了什么,才能让别的节点找到它、 又不需要它自己知道谁是自己的孩子?这就是这节课要拆开看的东西。
这节课你将能做到一件事: 画出一个 MessageEntry 的 完整字段结构,说清楚 Pi 的 9 种 Entry 按对 LLM 的影响分哪三组,并解释追加(append)、回退(branch)、 分支(branch+append)这三个操作之间的组合关系——分支根本不是独立操作。
🎯 贯穿全课的类比:家谱只记父不记子 想象一本家谱。每个人的那一页只写"我爹是谁",从不写"我有哪些孩子"。 这样每添一个新丁,你只需要写新人的那一页——写上"某某之子"——永远不用翻回去改父辈的记录。 父辈的那一页,从落笔那一刻起就再也不会被改动。这就是 Session Tree 里节点"认父不认子" 的设计:parentId 单向指向过去,谁是自己的孩子,节点自己并不知道。

1 · 一个节点长什么样:MessageEntry 解剖

上一课第 3 步,Agent 调 read 工具生成的那个 AssistantMessage 节点, 在 .jsonl 文件里实际是这样一行 JSON: 

1{
2  "type": "message",
3  "id": "e3",
4  "parentId": "e2",
5  "timestamp": "2026-07-03T10:23:45.000Z",
6  "message": {
7    "role": "assistant",
8    "content": [
9      { "type": "text", "text": "让我读一下 auth.ts" },
10      { "type": "toolCall", "id": "call_001", "name": "read",
11        "arguments": { "path": "src/auth.ts" } }
12    ],
13    "model": "claude-sonnet-4-6",
14    "stopReason": "toolUse",
15    "usage": { "input": 1250, "output": 80 }
16  }
17}

注意第 8–12 行:文本 "让我读一下 auth.ts" 和工具调用 read(path: "src/auth.ts") 并列在同一个 content 数组里—— 这是同一个节点,不是两个。Pi 不会为"一段话"和"一次工具调用"各生成一个 Entry。

字段干什么设计动机
type: "message"区分节点类型树上不止消息,还有 model_change、compaction 等多种类型
id: "e3"节点唯一标识别的节点通过 parentId 指向它
parentId: "e2"指向父节点认父不认子——节点不知道自己有哪些子节点
timestamp创建时间排序、调试用
message真正的消息载荷role + content + model 等字段(第 6 章讲过)
为什么"认父不认子"是 append-only 的必要条件? 若父节点维护 children 列表,从 e2 长出新节点 e6 时,e2 的 children 就得从 [e3] 改成 [e3, e6]——这需要修改 e2,与"节点不可变" 直接矛盾。只有单向的 parentId,才能让追加操作永远不用碰任何一个旧节点。
🔎 出处:教程 第10章 §三(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第10章-会话管理-对话的存储恢复与分叉.md)。代码为教程示意,基于 pi v0.80.2。

2 · 9 种 Entry,按对 LLM 的影响分三组

上一课的例子里出现了 model_change、user、assistant、 toolResult 四种节点。其实 Pi 一共定义了 9 种 Entry 类型。 看起来多,但按"对 LLM 调用的影响"分三组就清晰了。

组别类型产生什么 / 改变什么
① 进 LLM 上下文(4 种)MessageEntryUserMessage / AssistantMessage / ToolResultMessage
CustomMessageEntryCustomMessage(第 6 章讲的自定义消息)
CompactionEntryCompactionSummaryMessage(第 9 章讲的压缩结果)
BranchSummaryEntryBranchSummaryMessage(被抛弃分支的摘要,本节 §4 讲)
② 影响后续 LLM 调用(2 种)ModelChangeEntry后续用哪个模型
ThinkingLevelChangeEntry后续的思考级别
③ 纯元数据,不影响 LLM(3 种)LabelEntry给节点贴书签
SessionInfoEntry会话元信息(名称、创建者等)
CustomEntry扩展自己存的元数据
为什么要分这么细? 下一课要讲的 buildSessionContext() 需要按类型分派处理—— 是消息就进 messages 数组、是状态变更就改状态变量、是元数据就跳过。如果只有一种类型, 处理逻辑就得塞满 if-else,可读性和扩展性都差。
🔎 出处:教程 第10章 §三 / types.ts SessionEntry 联合类型。

3 · 操作 1 与 2:追加(append)与回退(branch)

追加只有三步,而且是 O(1)、不改任何旧节点:

1appendEntry({ type: "message", id: "e3", parentId: "e2", message: ... });
2// 内部:
3//   byId.set("e3", newEntry);
4//   this.leafId = "e3";

没有修改 e2——只是创建 e3 时让它的 parentId 指向 e2。e2 完全不知道自己多了个孩子, 但通过全局 byId 表反查就能找到所有指向它的子节点——结构上单向,但通过全局表可以反向查询。

回退只移动 leafId(外加一个存在性检查):

1branch(branchFromId: "e2"): void {
2    if (!this.byId.has(branchFromId)) {
3        throw new Error(`Entry ${branchFromId} not found`);
4    }
5    this.leafId = "e2";   // 核心就是这一行
6}

没有删除 e3、e4、e5——它们还在 byId 里,还在 .jsonl 文件里。回退只是说 "以后追加新节点时,parentId 指向 e2,而不是当前最后那个节点"。

🔑 追加 vs 回退,共同点是什么? 两个操作都只碰 byId 表和 leafId 这一个指针,从不触碰任何已存在的旧节点。这正是 append-only 铁律在代码层面的体现——不是靠约定,而是操作本身根本没有"改旧节点"这一步。
🔎 出处:教程 第10章 §四 / session-manager.ts 的 appendEntry、branch。

4 · 操作 3:分支——不是独立操作,是组合效果

回退到 e2 后再追加 e6,e6 的 parentId 自动就是 e2——这就是分支。 分支不是独立的操作,是"回退 + 追加"的组合效果,没有任何额外机制。

为什么分支不设计成独立操作? 因为一旦有了"回退移指针"和"追加认父"这两个基础操作, 分支就是它们的自然结果——多设计一个"分支"函数只会是重复劳动,还多一条要维护的路径。

5 · 分支摘要:BranchSummaryEntry(可选项)

你从 e5 回退到 e2,旧分支(e3-e5)就成了"被抛弃的分支"。数据完整保留在树上, 但当前路径的 LLM 看不到它们(下一课讲的 buildSessionContext 只走当前路径)。

有时候你希望新分支的 Agent 大致知道之前试过什么——不用看完整对话, 知道个大概就行。这时用 branchWithSummary(): 

1branchWithSummary(fromId: "e5"): Promise<void> {
2    // 1. 把 e3-e5 这段被抛弃的分支喂给 LLM 生成一份结构化摘要
3    // 2. 创建一个新的 BranchSummaryEntry,其 parentId 指向 e2(与 e3-e5 同父)
4    // 3. 摘要内容是结构化的(Goal / Progress / Decisions 等,跟压缩摘要格式一样)
5}

挂上去后,e_BranchSummary 的 parentId 是 e2,与 e3(旧分支起点)、e6(新分支起点)同父—— 三者是并列的兄弟节点。

🔑 BranchSummaryEntry 是可选的,不是默认的。 如果旧分支完全不重要,直接 branch() 就够了。只有"想保留历史精华但不想保留完整对话" 时才需要它。而且它生成的 BranchSummaryMessage 和压缩产生的 CompactionSummaryMessage 是不同的消息类型——前者是被抛弃分支的"遗言", 后者是当前路径本身的压缩结果,两者语义完全不同。
🔎 出处:教程 第10章 §四 / session-manager.ts 的 branchWithSummary;摘要生成复用第 9 章的结构化 prompt。
回退 + 追加 = 分支,再挂一份可选摘要 e2 (user) ├── e3 (assistant: read auth.ts) │ └── e4 (toolResult) │ └── e5 (assistant: "问题在 23 行") ← 被抛弃的旧分支,数据仍在 │ ├── e_BranchSummary (可选:"之前试过 read auth.ts,发现 salt 编码问题但未解决根因") │ └── e6 (user: "先看 hash 函数") ← branch(e2) 后 append 的新分支 三者 parentId 都是 e2 —— 同父的兄弟节点
