Lesson 0015 · 第 5 章 工具系统

五步管道
—— 工具调用不是「调个函数就完了」

🎯 本课目标:上一课(0014)搞清了 Tool / AgentTool / ToolDefinition 三层类型定义—— 「一个工具长什么样」的问题解决了。这一课看它的实际执行过程——「一次工具调用具体怎么跑」。 读完你会明白:从模型吐出 ToolCall 到最终产出 ToolResultMessage 之间,中间站着五道关卡, 每一道都有独立职责和退出机制。
⬅️ 回忆 0014:AgentTool 的 execute 签名是 (toolCallId, params, signal, onUpdate) => Promise<AgentToolResult>—— 但光有这个函数签名,不代表「调用工具」就是直接调它。中间还差着好几步没讲。这节课把这几步补全。
这节课你将能做到一件事: 画出从 ToolCall 到 ToolResultMessage 的 五步管道,说清每一步挡住了什么、为什么prepareArguments 和 validateToolArguments 不能合并,以及 acceptingUpdates 标志位 防住的到底是什么问题。
🎯 贯穿全课的类比:机场安检流水线 想象你要登机:先整理行李(prepareArguments,把乱塞的东西归置整齐)→ 过安检机(validateToolArguments,类型不对直接卡住)→ 安检员可以拦下你(beforeToolCall,权限判断)→ 你真正登机(tool.execute,干活的那一步)→ 落地后的行李复检(afterToolCall,后处理)。 任何一关不过,你都上不了飞机——但机场不会因此「炸掉」,只是给你一张「未通过」的凭条。

1 · 为什么不能直接调函数?

最直觉的写法是:找到 read 工具 → 读文件 → 把内容塞进 ToolResultMessage → 完事。 一行函数调用,朴素又直接。但模型的输出并不总是规规矩矩的:

问题具体表现
参数格式不对Edit 工具期望 edits 是数组,但某些模型把它序列化成字符串 "[{...}]" 传过来
参数类型错误Read 工具的 path 应是 string,模型却传了个 number 12345
危险操作模型要求执行 rm -rf /,Agent 真的照做吗?

这些问题说明「直接调函数」不够——执行前必须加几道关卡。

2 · 五步管道全景图

LLM 输出 ToolCall │ ▼ ┌──────────────────────────────────────────────────┐ │ 第 1 步:prepareArguments(参数预处理) │ │ 处理 LLM 的参数怪癖 │ │ 如:把字符串化的数组解析回真正的数组 │ ├──────────────────────────────────────────────────┤ │ 第 2 步:validateToolArguments(Schema 验证) │ │ 用 TypeBox Schema 做运行时类型检查 │ │ 如:path 是 string,不是 number │ ├──────────────────────────────────────────────────┤ │ 第 3 步:beforeToolCall(前置钩子) │ │ 产品层的权限拦截,可以阻止执行 │ │ 返回 { block: true, reason: "危险命令" } │ ├──────────────────────────────────────────────────┤ │ 第 4 步:tool.execute(实际执行) │ │ 调用工具的 execute 函数 │ │ 支持 onUpdate 流式进度回调 │ ├──────────────────────────────────────────────────┤ │ 第 5 步:afterToolCall(后置钩子) │ │ 产品层的结果后处理,可以修改返回值 │ │ 可以替换 content、details、isError │ └──────────────────────────────────────────────────┘ │ ▼ ToolResultMessage

前 3 步是「准备工作」——任何一步失败都不会执行工具;第 4 步是「真正干活」;第 5 步是「收尾」。 逐步展开每一步。

🔎 出处:教程第 5 章 §二 · 五步管道方框图(agent-loop.ts:562-714)。

3 · 第 1 步 prepareArguments:兼容性垫片

不同模型的 API 在序列化工具参数时有微妙差异,prepareArguments 就是为这些差异准备的兼容层。 比如 Edit 工具期望 edits 是数组: 

1// 模型实际传来的(某些模型把 JSON 数组序列化成了字符串)
2{ edits: "[{\"oldText\":\"hello\",\"newText\":\"world\"}]" }
3
4// 经过 prepareArguments 处理后
5{ edits: [{ oldText: "hello", newText: "world" }] }

如果工具没定义 prepareArguments,参数直接透传——有就用,没有就跳过。

为什么不在 Schema 验证里一起处理? 因为两者关注的事情不同。prepareArguments 是 「我知道某个模型会犯什么错」的兼容层——只处理特定模型的已知问题;validateToolArguments 是「不管谁调我都得验」的安全层——保证参数类型正确。一个管兼容、一个管正确,混一起代码会难维护。
🔎 出处:教程第 5 章 §二·第 1 步。

4 · 第 2 步 validateToolArguments:Schema 验证

经过预处理后,参数还要过一道 TypeBox 的运行时类型检查:

1// Before
2{ path: 12345 }
3
4// After:验证失败 → 报错 → 不执行工具

验证错误会被 prepareToolCall 的 try-catch 捕获,生成一个错误 ToolResultMessage。 工具永远不会收到类型错误的参数。

5 · 第 3 步 beforeToolCall:前置钩子(可阻止执行)

参数验证通过后,在执行之前,产品层还有一次拦截机会——检查命令是否危险:

返回值效果
undefined放行,继续执行工具
{ block: true, reason: "危险命令" }阻止执行,生成错误 ToolResultMessage
🔑 关键权衡: 即使工具被阻止,结果仍然是一条正常的 ToolResultMessage, 只是 isError: true。模型会看到这条错误消息,知道命令被拒绝了, 然后决定下一步怎么做(换一个命令,或者跟用户解释为什么不能执行)。 整个过程不会抛异常,不会打断循环。
🔎 出处:教程第 5 章 §二·第 3 步。

6 · 第 4 步 tool.execute:实际执行

前 3 步都通过后,工具的 execute 函数被真正调用。回头看它的签名:

1execute: (toolCallId, params, signal, onUpdate) => Promise<AgentToolResult>

四个参数——toolCallId 是这次调用的 ID,params 是验证过的参数, signal 是用于取消的 AbortSignal(用户按 Ctrl+C 时触发)。第四个 onUpdate 呢?

它解决的是「长任务的进度感知」问题。 假设 Bash 工具要跑一个 30 秒的命令—— 如果只有「开始执行」和「执行完成」两个时刻能向外界报告,用户在这 30 秒里只能盯着加载动画。 onUpdate 让工具能边执行边向外推消息:Bash 工具每 100ms 推送一次 当前的终端输出,Grep 工具每找到一批匹配就推送一次,Read 工具读取大文件时可以分段报告进度。 这些推送被包装成 tool_execution_update 事件,最终流向 UI。

为什么要有 onUpdate,而不是只报「开始 / 结束」? 没有它,工具执行就是黑盒; 有了它,工具执行「可观察」,长任务能实时向用户汇报进度。

但有个边角问题:execute 是异步函数,它 return 之后, 内部可能还有没结束的异步操作——比如 Bash 工具的子进程在主命令返回后还在异步打印最后几行日志。 如果这些延迟回调还往 onUpdate 推数据,就会污染一个已经结束的工具调用, 让 UI 上下文错乱。Pi 用一个 acceptingUpdates 标志位解决: 

1// packages/agent/src/agent-loop.ts:628-669
2async function executePreparedToolCall(prepared, signal, emit) {
3    const updateEvents: Promise<void>[] = [];
4    let acceptingUpdates = true;          // 工具 Promise settle 后关闭
5
6    try {
7        const result = await prepared.tool.execute(
8            prepared.toolCall.id,
9            prepared.args,
10            signal,
11            (partialResult) => {
12                if (!acceptingUpdates) return;     // settle 后的孤儿回调直接忽略
13                updateEvents.push(/* ... 发 tool_execution_update ... */);
14            },
15        );
16        acceptingUpdates = false;
17        await Promise.all(updateEvents);
18        return { result, isError: false };
19
20    } catch (error) {
21        acceptingUpdates = false;
22        // 关键:先等所有进度事件发完,再把异常编码成消息
23        await Promise.all(updateEvents);
24        return {
25            result: createErrorToolResult(
26                error instanceof Error ? error.message : String(error)
27            ),
28            isError: true,
29        };
30    } finally {
31        acceptingUpdates = false;          // 兜底:无论如何都关闭闸门
32    }
33}
为什么需要 acceptingUpdates 标志位? execute return 后内部可能还有未结束的异步操作 (如 Bash 子进程还在打印),延迟回调会污染一个已结束的调用,让 UI 上下文错乱, 所以 settle 后必须静默丢弃——这是工程上的防御性细节,不复杂,但必须要有。
🔎 出处:教程第 5 章 §四·关键代码(agent-loop.ts:628-669)。

7 · 第 5 步 afterToolCall:后置钩子(可修改结果)

工具执行完毕后,产品层还有一次修改结果的机会:

场景做什么怎么做
脱敏把工具返回的敏感信息替换掉返回 { content: [{type:"text", text:"[已脱敏]"}] }
审计记录工具调用的详细信息读取 result,写日志,返回 undefined(不改结果)
修错把工具的错误结果修正为正常结果返回 { isError: false, content: [...] }
早停让 Agent 在当前批次后停止返回 { terminate: true }
为什么 afterToolCall 用字段级覆盖而非整体替换? 合并语义是「提供了就替换,没提供就保留原值」—— 让后处理只改自己关心的字段(如只改 content 做脱敏),其余原值保留,降低钩子的心智负担。

8 · 管道终点:ToolResultMessage

五步走完,不管中间出了什么状况,最终产物都是一条 ToolResultMessage:

1{
2    role: "toolResult",
3    toolCallId: "call_abc123",      // 关联到原始 ToolCall
4    toolName: "read",
5    content: [{ type: "text", text: "1│ import { Agent }..." }],
6    details: { language: "typescript" },  // 给 UI 的元数据
7    isError: false,                  // 是否为错误结果
8    timestamp: 1700000000000,
9}

这条消息会被追加到对话历史中,在下一轮循环里作为上下文发给模型。模型看到「文件内容是这样的」, 然后决定下一步——可能要编辑,可能要再读别的文件,可能直接回答用户。

🔎 出处:教程第 5 章 §二·管道终点。
