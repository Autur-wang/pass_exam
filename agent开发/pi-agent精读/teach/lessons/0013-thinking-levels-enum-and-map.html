Lesson 0013 · 第 4 章 模型调用

思考档位:统一枚举 + 各家映射表

🎯 本课目标:上一课我们拆开了翻译器的「五步流水线」和 12 种统一事件协议——那是处理响应的规则。 这一课回到发起请求这一侧,看 Pi 怎么把"让模型深度思考"这件事,从三种完全不同的 Provider 方言, 统一成一个上层只需说一句 reasoning: "high" 的干净接口。
🔁 先回忆上一课:翻译器把各家原始响应统一翻译成 12 种事件,上层永远只消费同一种格式——这是「响应方向」的统一。 这一课要看的是「请求方向」的对称问题:上层发指令时,又是怎么被统一的?
这节课你将能做到一件事: 说清楚 stream() 和 streamSimple() 的分工区别, 并用"统一枚举 + 各家映射表"这一套设计法,同时解释思考级别和缓存控制两个看似不相关的功能—— 它们其实是同一个设计模式的两次应用。
🎯 贯穿全课的类比:一个五级思考旋钮 想象一台万能遥控器,旋钮上刻着 off → minimal → low → medium → high → xhigh 六档。 你——上层调用者——只管把旋钮拧到 high,不用管你家到底是 Anthropic 电视、OpenAI 音响还是 Google 空调。 旋钮背后的翻译器自己查一张表,把"high"换成 Anthropic 要的 budget_tokens、 OpenAI 要的 reasoning_effort、Google 要的 thinkingConfig。 你只需要会拧旋钮,不需要会说三门外语。

1 · 为什么有 stream() 和 streamSimple() 两个版本?

Agent Loop 实际调用的不是 stream(),而是 streamSimple()。为什么要分两层?

版本定位做什么
stream()底层入口只做"查表 + 派活":根据 model.api 查到对应翻译器,把工作派下去,不管思考级别翻译
streamSimple()便捷层在 stream() 之上包一层语法糖:自动处理 reasoning 翻译、clamp 回退、自动调整 maxTokens,再调用底层 stream()

Agent Loop 使用 streamSimple() 的典型代码:

1const stream = streamSimple(model, context, { reasoning: "high" });
2// ↑ 告诉它"用高级别思考",streamSimple 会自动翻译成各 Provider 的具体参数
3
4for await (const event of stream) {
5  // 事件会按顺序到达:
6  // start → thinking_start/delta/end → text_start/delta/end → done
7  switch (event.type) {
8    case "text_delta":
9      // 文字增量,显示到终端
10      break;
11    case "toolcall_end":
12      // 模型要调工具,拿到完整的工具调用信息
13      break;
14    case "done":
15      // 本轮模型调用结束,看 stopReason 决定是否继续循环
16      break;
17    case "error":
18      // 出错了(网络超时、API错误等),errorReason 是 "error" 或 "aborted"
19      break;
20  }
21}
🔎 出处:教程第4章 §三 / compat.ts:258-268(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第4章-模型调用-一行代码驾驭多个模型.md)。
为什么要分两层? 底层 stream() 保持纯净,只做路由——这样它的行为始终可预测、可测试。 便捷层 streamSimple() 把"语法糖"(查表、clamp、调 maxTokens)集中在一处, 让最常见的调用场景一行代码搞定,又不会把这些"便利逻辑"污染进底层的核心派活逻辑。 实际开发中 streamSimple 是常用入口,直接用 stream 需要自己处理很多翻译细节。

2 · 三家方言:思考参数完全不同

不同 Provider 对"让模型深度思考"这件事,概念和参数完全不同:

1// Anthropic:给一个 token 预算,让模型在这个预算内思考
2params.thinking = { type: "enabled", budget_tokens: 16384 };
3
4// OpenAI:给一个努力程度(low/medium/high)
5params.reasoning_effort = "high";
6
7// Google:用 thinkingConfig 配置
8config.thinkingConfig = { includeThoughts: true, thinkingLevel: "high" };
🔎 出处:教程第4章 §四 / 思考参数三家方言。

甚至 Anthropic 自己都有两种模式——新版模型用"自适应思考"(模型自己决定思考多少), 旧版模型用"预算思考"(给固定 token 上限)。三家参数名不同、语义粒度不同,上层代码如果直接暴露这些原生参数, 每接一个新模型就要多学一门外语。

3 · Pi 怎么统一:ThinkingLevel 五级刻度 + 映射表

Pi 定义了一套统一的思考级别枚举,每一级都标注了 token 上限:

1  off    minimal    low    medium    high    xhigh
2  │        │         │       │        │        │
3 不思考  1024 tk   2048 tk  8192 tk  16384 tk  模型最大值
🔎 出处:教程第4章 §四 / ThinkingLevel 五级刻度。

上层代码只需说 reasoning: "high",翻译器自己查表翻译成各 Provider 的具体参数。 每个 Model 对象自带一个 thinkingLevelMap(翻译表), 声明"我这台模型,每个级别对应什么参数"——这就是旋钮背后的那张查表卡片。

如果请求的级别模型不支持(比如请求 xhigh 但只支持到 high), clampThinkingLevel() 函数做回退——先向上找,找不到再向下找。 streamSimple() 就是帮你自动完成这套翻译的便捷函数:查表 + clamp + 调整 maxTokens,然后调用底层 stream()。

为什么用"统一枚举 + 映射表",而不是"取所有 Provider 的交集"? 取交集的话,最终只能保留所有 Provider 都支持的档位——很可能只剩 off,太受限。 而"暴露每家原生参数"又会让上层代码记住 20 种参数名。 映射表两头讨好:每个 Model 自带 thinkingLevelMap,上层只说语义(high), 底层查表翻译成机制(budget_tokens: 16384 之类)——比交集灵活,比暴露原生参数简洁。
🔑 为什么 clamp 回退时先向上找? 思考更多通常比思考更少安全——请求高档位说明用户认为这个任务需要更深的推理, 模型不支持时,宁可给它一个更高的可用档位,也不要悄悄降级到一个"想得不够"的档位。找不到更高的,才退而求其次向下找。

4 · 同款套路的第二次应用:缓存控制

Pi 把缓存控制也抽象成三个语义级别:type CacheRetention = "none" | "short" | "long"。 上层只说"我要 long 缓存",翻译器自己翻译成各家的具体标记方式——这和 ThinkingLevel 是同一种"统一枚举 + 各家映射表"的套路, 但四家对"怎么标记不变内容"这件事,思路完全不同:

Providernoneshortlong打点位置
Anthropic不打标记cache_control: {type:"ephemeral"}(默认 5 分钟 TTL)加 ttl:"1h"system 末尾 + 最后一个 tool + 最后一条 user message
Bedrock不插节点插入独立对象 {cachePoint:{type:DEFAULT}}加 ttl:ONE_HOURsystem 块后面 + 最后一条消息后面
OpenAI Responses不发 cache key发送 prompt_cache_key: sessionId加 prompt_cache_retention:"24h"不打点——按 session key 自动匹配前缀
OpenAI 兼容(DeepSeek/Qwen 等)不打标记按 Anthropic 风格打 cache_control加 ttl:"1h"(如支持)复用 Anthropic 的三处策略
🔎 出处:教程第4章 §五 / 缓存控制四家对照表。

四家的思路可以对应成四种日常动作:Anthropic 像"贴便签"——在原内容上附加一个标签; Bedrock 像"插路标"——插入一个独立、不含业务数据的占位对象; OpenAI 原生像"按会员卡号查记录"——你不打标记,只报一个 key,后端自己按前缀匹配; OpenAI 兼容厂商则直接抄 Anthropic 的便签协议。

为什么缓存也要走"统一枚举 + 各家映射表"? 这是"语义统一,实现分散"的又一次应用: cacheRetention 描述"做什么"(要长期缓存),各家的映射表描述"怎么做"(贴便签/插路标/按卡号查)。 语义接口与机制接口分离,上层代码不用关心自己在跟哪家 Provider 打交道。
"统一枚举 + 各家映射表" —— 同一套设计法的两次应用 语义层(上层只说这个) 机制层(各家翻译表管这个) ┌─────────────────────┐ ┌─────────────────────────┐ │ reasoning: "high" │ ──▶ │ Anthropic: budget_tokens │ │ (ThinkingLevel 五级) │ │ OpenAI: reasoning_effort │ │ │ │ Google: thinkingConfig │ ├─────────────────────┤ ├─────────────────────────┤ │ cacheRetention:"long"│ ──▶ │ Anthropic: 贴 cache_control│ │ (none/short/long) │ │ Bedrock: 插 cachePoint │ │ │ │ OpenAI: 发 cache_key │ └─────────────────────┘ └─────────────────────────┘ clampThinkingLevel():请求档位不支持时,先向上找,找不到再向下
