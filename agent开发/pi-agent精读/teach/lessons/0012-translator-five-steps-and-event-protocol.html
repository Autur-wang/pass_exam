Lesson 0012 · 第 4 章 模型调用

翻译器内部
—— 五步骨架与事件协议宪法

🎯 本课目标:上一课我们啃了三层架构的第一层——「前台」怎么用「查表 + 派活」 两步把请求路由给对的翻译器。但前台自己不干活,真正的工作量在第二层(标准报告格式)和第三层(翻译员)。 这节课打开这两层:12 种统一事件长什么样、翻译器内部走的是哪 5 步、以及那份让所有翻译员都守规矩的 「入职宪法」——StreamFunction。
🔁 回忆一下:第 3 章讲翻译公司类比时说过,前台不需要懂外语,翻译员不需要懂公司流程—— 他们靠中间那份标准格式的报告连接。上一课我们只看到了前台怎么「查表 + 派活」, 还没打开翻译员真正在做的事,也没看过那份标准报告长什么样。今天就打开这两块。
这节课你将能做到一件事: 画出 AssistantMessageEvent 的 12 种事件是怎么从「文字 / 思考 / 工具调用」三类内容 + 「开始 / 结束」两个信号推导出来的, 并说清 StreamFunction 这个类型签名定的三条铁律,以及「协议优于继承」的设计理由。
🎯 贯穿全课的类比:翻译员的标准工作流程 一个称职的翻译员上岗,走的是固定流程:先确认自己带了字典(创建客户端), 再逐句翻译(把客户的话译成对方语言、发出去、再把对方的回话译回来), 最后必须交一份格式固定的标准报告(12 种统一事件)——不管这次翻的是法语还是日语, 报告的封面、正文结构、审签栏长相都完全一样。翻译员之间可能一句共同语言都没有, 但只要报告格式统一,前台就不用关心翻译员内部怎么工作。

1 · 第二层:12 种事件不用死记,抓一个模式

翻译器把请求发给模型后,模型是流式「一个字一个字」吐内容的。如果每个翻译员都按自己的方式吐, 前台就疯了——所以第二层约定了一套统一输出格式:不管底层是哪家模型, 翻译器都必须输出 12 种统一事件之一。 

1AssistantMessageEvent(12 种)
2│
3├── start                              ← 流开始了
4│
5├── text_start → text_delta → ... → text_end       ← 模型在输出文字
6├── thinking_start → thinking_delta → ... → thinking_end  ← 模型在思考
7├── toolcall_start → toolcall_delta → ... → toolcall_end  ← 模型要调工具
8│
9├── done   (reason: stop / length / toolUse)   ← 正常结束
10└── error  (reason: error / aborted)           ← 出错了

不用死记全部 12 种,只需抓模式:模型回复分三类内容——文字、思考、工具调用, 每类都有「开始→逐字增量→结束」三步,再加上流开始 start 和流结束 done / error 两个信号。

为什么每类内容都要拆成 start→delta→end 三步? 因为这是流式输出——翻译器先告诉你 「文字要开始了」,然后逐字推送 delta(可能有很多个),最后告诉你「结束了」。 这让 Agent Loop 能做到逐字渲染——你看到的 AI 回复一个字一个字蹦出来,就是这个机制在支撑。

还有一个容易被忽略但极关键的约定:每个事件都携带 partial(当前消息的完整快照)。 这正是「原地替换」的落地方式——每次收到事件,直接用 partial 覆盖 context 中最后一条消息, 不需要自己拼接增量。这把「维护状态」这件麻烦事从消费方(Agent Loop)身上卸掉了,交给了翻译器。

🔎 出处:教程第4章 §二 / types.ts:453-465。

2 · 第三层:翻译器都走同一套 5 步骨架

翻译器是真正干活的角色——每个翻译器对应一种 API(如 Anthropic、OpenAI), 负责把统一格式翻译成 Provider 的私有格式,再把响应翻译回统一事件。所有翻译器都遵循同一个流程: 

1翻译器(model, context, options)
2│
3├── 1. 创建客户端
4│      用 API Key 初始化连接。就像翻译员确认自己带了字典。
5│
6├── 2. 构建请求参数
7│      把统一格式的消息、工具定义、系统提示,翻译成 Provider 的私有格式。
8│      比如 Google 要 content → parts,这一步就做这个转换。
9│
10├── 3. 发送请求
11│      通过 SDK 或直接 HTTP 发给模型。等模型开始响应。
12│
13├── 4. 处理响应流
14│      模型流式返回内容。翻译器把 Provider 的私有事件格式,
15│      翻译成第二层要求的 12 种统一事件。
16│
17└── 5. 发送终止事件
18       成功 → push done;失败 → push error。流必须终止。
🔑 工作量藏在哪两步? 第 2 步(请求翻译)和第 4 步(响应翻译)是核心工作量所在—— 也是每个翻译器动辄上千行代码的主要原因。第 1、3、5 步大同小异,真正「翻译」这门语言的活儿 全压在 2 和 4 上。
🔎 出处:教程第4章 §二 / anthropic-messages.ts 5步骨架。

3 · 实例:Anthropic 第 4 步怎么翻译

抽象的「翻译响应」四个字,落到 Anthropic 身上具体长什么样?下面是它把私有事件名 映射成 Pi 统一事件名的对照表: 

1Anthropic 私有事件                     →  Pi 统一事件
2─────────────────                    ────────────
3content_block_start (type: "text")    →  text_start
4content_block_delta (text_delta)      →  text_delta
5content_block_start (type: "tool_use") →  toolcall_start
6content_block_delta (input_json)      →  toolcall_delta
7message_delta (stop_reason)           →  done(映射终止原因)

注意最后一行的「映射终止原因」——Anthropic 的 "end_turn" 要翻译成 Pi 的 "stop","tool_use" 要翻译成 "toolUse"。 每个 Provider 的命名都不一样,Pi 把它们统一成了自己的术语。第 3 章讲 Agent Loop 检查 stopReason 决定是否继续循环,那些值正是经过这层翻译之后的统一术语—— Agent Loop 从头到尾没见过 "end_turn" 这个词。

🔎 出处:教程第4章 §二 / Anthropic 第4步翻译规则。

4 · StreamFunction:翻译员的「入职宪法」

三层架构要运转起来,有一个前提:所有翻译器必须遵守同一套规则。 Pi 用一个 TypeScript 类型定义这套规则——它叫 StreamFunction,是整个抽象层的「宪法」: 

1export type StreamFunction<TApi extends Api, TOptions> = (
2  model: Model<TApi>,       // 用哪个模型
3  context: Context,         // 对话上下文(系统提示 + 消息 + 工具)
4  options?: TOptions,       // 可选配置(思考级别、缓存等)
5) => AssistantMessageEventStream;  // ← 必须返回统一事件流

这个签名定的三条规则:

规则具体内容
① 输入相同所有翻译器接受同样的三个参数(model、context、options)
② 输出相同必须返回 AssistantMessageEventStream——不管底层是原始 SSE 还是 SDK 流,对外都是这个类型
③ 错误不抛异常API 调用失败时,不 throw,而是 push 一个 { type: "error" } 事件
为什么用「协议 + 函数签名」而不是设计一个 BaseProvider 抽象类让翻译器继承? 因为翻译器之间几乎没有共同代码——继承需要找共同点,但 Anthropic 用 content[]、 Google 用 parts[],连「发消息」这件事的字段名都不一样,没什么可共享的实现。 协议只约定输入输出,不管中间实现——这是「协议 > 实现」的设计法。
🔑 第三条为什么这样设计? 这呼应了第 3 章的「永不抛出」原则。第 3 章说的 stopReason: "error" / "aborted" 不是模型返回的,而是翻译器的 catch 块在异常时注入的——把异常包装成一个 error 事件 push 进流, Agent Loop 用同一套机制处理成功和失败,for await 循环永远不会被异常打断。
🔎 出处:教程第4章 §二 / types.ts:304-308。
