Lesson 0027 · 第 9 章 上下文压缩

为什么要压:窗口红线与触发判断

🎯 本课目标:上一课讲的是单条工具输出太长时的局部截断; 这一课把视角拉高到整段对话——当 50 轮聊天把 200K 的窗口塞满,Pi 用什么信号判断 「该动手压缩了」、又为什么拒绝了最直觉的方案「删掉旧消息」。
⏪ 先回忆上一课:工具输出太长会被截断保留头尾,原始内容仍能找回——那是单条消息层面的体积控制。 但如果 50 轮对话里每一条消息都不算太长,整体加起来还是会逼近甚至冲破 200K 窗口。 这就是本课要处理的问题:不是某一条消息太大,而是历史的总和太大。
这节课你将能做到一件事: 手算出 Pi 的压缩红线 183,616 是怎么来的, 说清 chars/4 估算为什么故意「不精确」,并分清预防性压缩 和应急性压缩这两种触发场景各自兜底什么。
🎯 贯穿全课的类比:一卷快塞满的录像带 把 Agent 的记忆想成一卷录像带:50 轮对话是 150K token 的原始录像,快塞满 200K 的磁带盒了。 直接剪掉前 30 分钟(删旧消息)等于让它失忆——它忘了你最初让它做什么。 Pi 的选择是把旧录像转成一页「摘要笔记」,腾出空间又留住关键情节。

1 · 问题根源:对话是有状态的,窗口迟早装不下

Agent 和 LLM 的对话是有状态的——每一轮都要把之前的完整历史重新发给模型, 模型本身不记得上一次调用说了什么。你和 Agent 聊了 50 轮,每轮可能产生几千 token 的工具结果, 算一笔账:50 轮 × 平均 3000 token/轮 = 150,000 token。 Claude Sonnet 的上下文窗口是 200,000 token——快满了。

满了会怎样?API 直接报错:"prompt is too long",对话被迫中断。 这不是「体验变差」,是硬性失败——所以必须在撞墙之前处理。

2 · 为什么不能简单删旧消息

最直觉的方案是:把前 30 轮扔掉,只留最近 20 轮。但这样 Agent 就「失忆」了—— 它不记得你最初让它做什么、不记得之前做过哪些决策、不记得改过哪些文件。 删除是盲目且有损的:丢掉的信息完全随机,可能刚好把最关键的目标说明也删了。

为什么压缩而不是删旧: 删旧会造成 Agent 失忆(丢失目标/决策/文件记录), 压缩则用结构化摘要保留关键信息——记忆从「原始录像」降级为「摘要笔记」而非彻底消失。 两者都有损,但压缩有损地保留了「结构」,这正是它优于删旧的地方。
压缩前后对比 压缩前(185,000 token): ┌── 第1-30轮(135,000 token)──┬── 第31-50轮(50,000 token)──┐ │ 原始消息(大量工具结果) │ 原始消息(最近的上下文) │ └──────────────────────────┴──────────────────────────┘ 压缩后(约 60,000 token): ┌── 摘要(约 10,000 token)──┬── 第31-50轮(50,000 token)──┐ │ 结构化总结(目标、进度、 │ 原始消息(完整保留) │ │ 决策、文件跟踪……) │ │ └────────────────────────┴──────────────────────────┘

3 · 触发红线:shouldCompact 判断什么

压缩不是随便触发的,它有一条明确的「红线」——一个纯函数来判断要不要动手:

function shouldCompact(contextTokens, contextWindow, settings): boolean {
1    if (!settings.enabled) return false;
2    return contextTokens > contextWindow - settings.reserveTokens;
3}

代入具体数字:contextWindow = 200,000,reserveTokens = 16,384。

当 contextTokens > 200,000 - 16,384 = 183,616 时,触发压缩。 另外注意第一行:settings.enabled 关掉的话,不管 token 多少都永不压缩—— 这是一个显式的总开关,方便调试或者关掉自动压缩自己手动管理。

为什么保留 reserveTokens = 16,384? 上下文窗口是「输入 + 输出」共享的一块空间,必须给 LLM 的回复留出位置—— 如果把 183,616 之后的空间全塞满输入,模型连生成回复的余地都没有了。
🔎 出处:教程第 9 章 §二「触发条件」(compaction.ts:shouldCompact)。代码为教程示意,基于 pi v0.80.2。

4 · Token 怎么数:chars/4 的粗糙估算

一个关键前提问题:压缩判断需要知道「当前有多少 token」,怎么算? 精确计算要用 tokenizer,但不同模型 tokenizer 不同、且计算开销大。Pi 选了一个简单粗暴的办法: 

1// 实际签名(compaction.ts:256-296):estimateTokens(message: AgentMessage): number
2// 对每个 message 取其文本字符数 chars,然后 return Math.ceil(chars / 4)
3function estimateTokens(message: AgentMessage): number {
4    let chars = 0;
5    // ...按 message.role 分别累加 text/thinking/toolCall/command/output/summary 的字符数
6    return Math.ceil(chars / 4);  // chars / 4
7}

一个英文字符大约 0.25 token(4 个字符 ≈ 1 token),估算与实际接近。 但中文是反向偏差:1 个汉字实际大约 1-2 token,chars/4 却只算成 0.25 token—— 严重低估中文占比高的对话。纯中文场景下,Pi 可能觉得「还没到阈值」, 实际 token 已经接近甚至超过上限。

🔑 为什么用不精确的 chars/4 估算? 因为宁可高估、不可低估——高估最多多压缩一次(无害);低估会让 API 直接报错(有害)。 这是「用精度换安全」的保守策略,而且实现极简。

为什么接受中文低估这个缺陷? 这是已知的精度问题,但 Pi 的目标场景以英文编码为主, chars/4 在英文场景下够准。权衡下选择了简单实现,而不是引入精确但昂贵的 tokenizer。
🔎 出处:教程第 9 章 §二「Token 估算」(compaction.ts:256-296)。代码为教程示意,基于 pi v0.80.2。

5 · 两种触发场景:预防性 vs 应急性

知道了红线和估算方式,压缩实际发生时有两种不同的起因:

场景什么时候触发意味着什么
预防性压缩token 超过阈值(183,616)但还没报错提前压缩,避免 API 报错
应急性压缩API 返回上下文溢出错误补救措施,先压缩再重试

预防性压缩是常态——在问题发生之前就处理掉,这是 chars/4 估算准确工作时的正常路径。 应急性压缩是兜底——万一估算偏了(比如中文低估),API 真报错了,还有一道防线先压缩再重试。

6 · 核心时序:压缩发生在两轮之间

在往后学切割点算法、摘要生成之前,先把这条时序刻进脑子——这是理解整章的钥匙: 压缩不是在对话进行中触发的,而是在两轮对话之间发生的。

压缩时序 用户问 → Agent 回答 → (Agent 这一轮结束,发 agent_end 事件) │ ▼ 检查 token:超阈值了吗? │ ┌──────────┴──────────┐ ▼ ▼ 没超 → 等下一轮 超了 → 立刻压缩 ├─ 找切割点 ├─ 生成摘要 └─ 写进 Session Tree

换句话说,Agent 不会在生成回复途中被打断去压缩——那样会破坏正在进行的推理。 压缩总是等一轮彻底结束、发出 agent_end 之后才检查、才动手。 后面几课讲「在哪切」「怎么生成摘要」,都是这条主线上的具体环节。
