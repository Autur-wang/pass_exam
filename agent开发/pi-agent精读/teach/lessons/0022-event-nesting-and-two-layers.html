Lesson 0022 · 第 7 章 事件驱动

10 种事件的 4 层嵌套与两层事件

🎯 本课目标:上一课讲清了 emit 为什么是「同步屏障」而不是「通知」—— 每次发事件都 await 所有监听器处理完。这一课回到更基础的问题: Agent 内核到底定义了哪 10 种事件?它们为什么不是一个扁平列表, 而是4 层嵌套的生命周期?以及,为什么内核只放 10 种,Session 层还要再扩展 7 种?
📌 回忆上一课: 每次 emit(event) 都会 await 所有监听器处理完才继续—— 这保证了消费者永远看到一致的状态。但那一课没细讲:到底有哪些事件会被 emit? 今天就把这 10 种事件摊开看。
这节课你将能做到一件事: 画出 Agent→Turn→Message→Tool Execution 的 4 层嵌套图, 说清每层「开始→更新→结束」的配对规律,并能判断一个新事件(比如「上下文压缩开始了」) 该放内核层还是 Session 层。
🎯 贯穿全课的类比:内核里找不到「蓝牙已连接」 就像 Linux 内核里找不到「蓝牙已连接」这种通知——内核只管进程调度和内存管理, 蓝牙是上层的事,归蓝牙协议栈和桌面环境管。Agent 内核也一样:它只管生命周期的 10 种事件,至于上下文压缩、自动重试这些「产品级体验」,那是 Session 层的事, 内核压根不认识它们。

1 · 10 种事件 = 4 层嵌套的生命周期

Agent 内核层定义了 10 种 AgentEvent。乍一看是个不算短的列表, 但它们不是随手列出来的——是4 层嵌套的生命周期,从外到内依次是 Agent → Turn → Message → Tool Execution: 

export type AgentEvent =
  // 第1层:Agent 生命周期(整个运行)
  1| { type: "agent_start" }
  2| { type: "agent_end"; messages: AgentMessage[] }

  // 第2层:Turn 生命周期(一轮模型调用 + 工具执行)
  3| { type: "turn_start" }
  4| { type: "turn_end"; message: AgentMessage; toolResults: ToolResultMessage[] }

  // 第3层:Message 生命周期(一条消息)
  5| { type: "message_start"; message: AgentMessage }
  6| { type: "message_update"; message: AgentMessage; assistantMessageEvent: AssistantMessageEvent }
  7| { type: "message_end"; message: AgentMessage }

  // 第4层:Tool Execution 生命周期(一次工具执行)
  8| { type: "tool_execution_start"; toolCallId: string; toolName: string; args: any }
  9| { type: "tool_execution_update"; toolCallId: string; toolName: string; args: any; partialResult: any }
  10| { type: "tool_execution_end"; toolCallId: string; toolName: string; result: any; isError: boolean };

数一数每层几种:第1层(Agent)2 种、第2层(Turn)2 种、第3层(Message)3 种、 第4层(Tool Execution)3 种,加起来正好 2+2+3+3=10。 规律很清楚:每层都是「开始→更新(×N)→结束」的配对,只有第3、4层有 update—— 因为只有消息流式增量、工具执行进度这两件事需要「中途汇报」; 第1、2层(Agent、Turn)只有 start/end,没有中间态。

为什么每层统一「开始→更新→结束」配对? 这给出一个一致的心智模型: 10 种事件看着不少,但你只需要记住「4 层 × 配对规律」而不是死记 10 个名字。 只有需要流式渲染(逐 token)或进度汇报(如 Bash 输出)的层才有 update—— 这是根据「谁需要中间状态」反推出来的设计,不是凑数。
🔎 出处:教程 §二 / packages/agent/src/types.ts:413-428。

2 · 用一棵树看嵌套关系

把 10 种事件按发生顺序摆进一次真实的 Agent 运行里,就是一棵 4 层嵌套的树:

Agent 运行 ├── agent_start ───────────────────── Agent 开始 │ ├── Turn 1(回忆第3章:一次模型调用 + 它触发的工具执行) │ ├── turn_start ────────────────── Turn 开始 │ │ │ ├── Message(LLM 的响应) │ │ ├── message_start │ │ ├── message_update ×N ────── 流式增量(逐 token 更新) │ │ └── message_end │ │ │ ├── Tool Execution(工具执行) │ │ ├── tool_execution_start │ │ ├── tool_execution_update ×N 工具进度(如 Bash 的输出) │ │ └── tool_execution_end │ │ │ └── turn_end ──────────────────── Turn 结束 │ ├── Turn 2 ...(若无工具调用,就没有第4层嵌套) │ └── agent_end ──────────────────────── Agent 结束

留意两处细节:第一,turn_start 到 turn_end 之间,模型被调用了恰好一次—— 这正是第3章讲过的「一个 Turn」定义;第二,Turn 2 如果没有工具调用, 就完全没有第4层(tool_execution_*)那组嵌套——4 层是「最多 4 层」,不是「每次都 4 层」。

🔎 出处:教程 §二「10种事件4层嵌套」配图说明。

3 · 为什么要分 4 层,而不是拍平成 10 个同级事件?

这是理解本课的核心。答案不是「代码好看」,而是不同消费者关心不同粒度:

消费者关心的粒度订阅的事件
TUI(终端界面)逐 token 渲染文字message_update
Session 管理器这一轮对话结束了没有turn_end
日志 / 持久化扩展Agent 整体是否跑完agent_end
🔑 如果拍平成 10 个同级事件会怎样? 每个消费者都得从一堆同级事件里自己过滤出想要的那几种, 还得自己判断「这条 message_update 属于哪个 turn」。4 层嵌套把这层归属关系显式表达出来, 让每种消费者在刚刚好的粒度上响应,不多订阅、不用自己拼归属。

4 · 内核之外:Session 层再扩展 7 种

前 3 节讲的都是 Agent 内核的 10 种事件。但 Pi 不只有 Agent 层, 上面还有一层产品会话层 AgentSession,它要处理内核里完全不存在的概念: 上下文压缩、自动重试、队列状态管理…… 

AgentSessionEvent =
    // 基础 10 种(agent_end 被重载,增加 willRetry 字段)
  + // Session 新增 7 种:
      queue_update           // ← steering/followUp 队列变化
      compaction_start/end   // ← 上下文压缩(第9章详讲)
      auto_retry_start/end   // ← LLM 调用失败自动重试
      session_info_changed   // ← 会话名称变更
      thinking_level_changed // ← 思考深度切换

基础 10 种 + Session 新增 7 种 = 17 种。注意 agent_end 在 Session 层被重载,加了 willRetry 字段——因为「Agent 这一轮是否结束」 在 Session 层还要多回答一句「结束后会不会自动重试」。

🔎 出处:教程 §七 / packages/coding-agent/src/core/agent-session.ts:126-150。

5 · 判断标准:一个事件该放内核还是 Session?

这 7 种新事件(队列变化、压缩、自动重试、会话改名、思考深度)有一个共同点: 它们都只和「产品级体验」有关,和「Agent 内核逻辑」无关。判断标准非常直白:

去掉它之后,内核还能正常运行吗? 能,它就属于外层(Session);不能,它才属于内核。 compaction/retry/queue 通通去掉,Agent 的核心循环(读消息→调模型→执行工具→emit 事件) 照样能转——所以它们不进内核,而是靠联合类型扩展叠加在 Session 层。 这样内核保持纯粹,只定义 4 层生命周期;产品层按需扩展,内核不被上层需求污染。

回到开头的类比:Linux 内核里找不到「蓝牙已连接」——去掉蓝牙通知,内核的调度和内存管理 一点不受影响,所以蓝牙协议栈理所当然长在内核之上。Agent 内核和 Session 层的分野, 是同一套逻辑。
