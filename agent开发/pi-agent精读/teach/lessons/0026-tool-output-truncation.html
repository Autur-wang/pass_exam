Lesson 0026 · 第 8 章 上下文工程

工具输出截断策略
—— 剪报的艺术:双重限制、双向策略与不切坏一个字

🎯 本课目标:上一课讲了系统提示词怎么"组装"进上下文——那是加法。 这一课换个方向,讲上下文工程的减法:单次工具调用(bash 跑出 8000 行日志、 read 读一个 3000 行源文件)动辄几十 KB,不加控制几轮就把窗口塞满。 读完你会明白 Pi 用一套双重限制 + 双向策略 + 边界安全 + 兜底逃生的四件套解决这个问题, 而且每一处设计都有清晰的失败模式对照。
⏪ 回忆上一课:0025 讲的是系统提示词怎么把 CLAUDE.md 层层递归、用 XML 包装塞进上下文—— 这解决的是"怎么让该进来的信息进来"。今天反过来问:工具**执行后**产出的信息,怎么让它不把窗口撑爆? 这是同一个上下文工程主题下的两侧问题:一侧管"进什么",一侧管"进多少"。
这节课你将能做到一件事: 说清 truncateHead 与 truncateTail 除了遍历方向外别无二致,并说出 Pi 为什么用 行数 + 字节双重限制而不是单一限制,以及截断为什么必须"逐字符"而不能直接按字节切。
🎯 贯穿全课的类比:剪报 一篇 8000 行的报纸没法整版贴进笔记本。读文件像只剪保留"开头的标题导语"(truncateHead)—— 文件头部的 import、类定义信息密度最高;看报错像只剪保留"末尾的结论"(truncateTail)—— bash 的错误堆栈永远压轴出场。而且这把剪刀有原则:不能把一个汉字或 emoji 剪成半个, UTF-8 边界必须完整跨过,剪坏了就是一堆乱码 �。

1 · 问题:单次工具调用就能撑爆窗口

想象你让 Agent 跑 npm test,输出 8000 行日志;或者让它 read 一个 3000 行的源文件。 单次工具调用就可能产生几十 KB 的输出。如果不加控制,几轮下来上下文窗口就被工具结果塞满了。

最朴素的解法是"按字符数截断"。但这会立刻撞到三个新问题:截断位置不对(报错在末尾却截了头)、 切断多字节字符(emoji 变乱码)、单行就超限(grep 命中一行 100KB 的压缩 JS 怎么切)。 Pi 用一套算法同时解决这三个问题,实现全在 truncate.ts。

2 · 双重限制:行数 + 字节,先触者胜

Pi 给所有工具输出默认定义了两个上限常量(源码在 truncate.ts:11-13): DEFAULT_MAX_LINES = 2000 行,DEFAULT_MAX_BYTES = 50 * 1024(50KB)。 任何工具输出都按"最多 2000 行"或"最多 50KB"裁剪——哪个先触发就用哪个。

只用哪个限制失败模式
只限行数压缩 JS / minified CSS 单行极长,3 行就撑爆字节
只限字节200 行的大文件按字节切,可能把某一行硬生生切一半
为什么用双重限制而非单一限制? 行数管"展示可读性",字节管"硬性体积"——两者各有失败模式, 互为兜底。这不是过度设计,是因为现实输入的形状本来就有两种极端(超长单行 vs 超多短行), 一把尺子量不完两种极端。

3 · 两种策略:truncateHead vs truncateTail

同样的双重限制,从哪头裁是另一个问题。Pi 提供两个函数,核心差异只是遍历方向:

函数保留哪一段用在哪为什么
truncateHead开头read 文件文件头部通常是 import / 类定义 / 接口签名,最有信息密度
truncateTail末尾bash 输出bash 的错误堆栈、最终结果都在末尾,末尾最有信号

bash 工具的描述在源码里写得很清楚(bash.ts:284),"last" 这个词很关键—— bash 工具的契约就是"保留末尾": 

1// bash.ts:284 —— 工具描述里的截断契约
2"Output is truncated to last 2000 lines or 50KB"
3+ " (whichever is hit first). If truncated, full output"
4+ " is saved to a temp file."
🔎 出处:教程 §三 / bash.ts:284。

truncateTail 的核心逻辑是从末尾往回选保留行(truncate.ts:247-266),简化后是这样:

1// 伪代码:truncateTail 的核心思路
2function truncateTail(content, maxLines, maxBytes) {
3    const lines = content.split("\n");
4    const kept = [];           // 从末尾往回收集的行
5    let bytes = 0;
6
7    for (let i = lines.length - 1; i >= 0; i--) {
8        const lineBytes = byteLength(lines[i]) + 1;  // +1 是换行符
9        if (kept.length >= maxLines) break;          // 行数到了,停
10        if (bytes + lineBytes > maxBytes) break;     // 字节到了,停
11        kept.unshift(lines[i]);                      // 插到头部,保持原顺序
12        bytes += lineBytes;
13    }
14    return kept.join("\n");
15}
🔎 出处:教程 §三 / truncate.ts:247-266(伪代码简化)。

truncateHead 完全一样,只是把 for 改成"从前往后"、unshift 改成 push。

🔑 为什么 read 截头、bash 截尾? 信息密度分布不同——文件头部是 import / 接口最有信息, bash 末尾是错误堆栈 / 最终结果最有信号。截断要保留"最有价值"的那一段,而不是机械地留前 N 行。 同一套算法两个方向复用,是很干净的设计:改一个参数(方向),不用重写逻辑。

4 · 边界安全:不能把一个字切成半个

字节级截断最阴险的 bug 是切坏多字节字符。一个 emoji 😀 在 UTF-8 里是 4 个字节, 如果在第 2 个字节切一刀,剩下两个字节会变成无效字符 �。 Pi 用 truncateStringToBytesFromEnd(truncate.ts:295)解决—— 逐字符地累加字节数,遇到"加这一个字符就超字节预算"就停; 遇到 4 字节 emoji 这类代理对(surrogate pair)字符,就把它当成不可分割的整体—— 要么完整保留,要么完全不要。

为什么逐字符处理而非直接 slice? 直接按字节切会把 emoji 切成无效 �, 污染后续编码——下游任何再次编解码、展示、比较都可能因此出错。 把多字节字符当成不可分割的整体,是用一点点计算成本换取"永不产出坏字符"的保证。

5 · 单行就超限:部分行兜底

truncateTail 还有一个边角逻辑(truncate.ts:255-260):如果第一行(最长的那行)单独就超过 maxBytes, 不能什么都不返回——那样工具结果就成空了。它会取该行末尾 maxBytes 字节, 并设置 lastLinePartial: true 标志位。下游 bash 工具会渲染专门的提示(bash.ts:366-368): 

1// 单行超限时 bash 工具追加的提示(示意)
2"[Showing last 49.5KB of line 1 (line is 92.3KB)."
3+ " Full output: /tmp/pi-bash-xxx.log]"
🔎 出处:教程 §三 / bash.ts:362-374。

另外 grep 工具有独立的单行限长:truncateLine 默认 GREP_MAX_LINE_LENGTH = 500, 把超长行截到 500 字符并加 ... [truncated] 后缀——grep 经常命中压缩文件,一行几万字符, 这一步避免一行就吃掉几千 token。

为什么单行超限要"部分行兜底"而非返回空? 返回空等于工具结果丢失——LLM 会误以为命令没有输出。 取末尾 maxBytes 字节 + lastLinePartial 标志,至少让 LLM 看到有信号的一段, 并且知道完整输出在哪、可以主动去取。

6 · 截断后的提示:逃生通道

截断本身是有损的,但 Pi 不会偷偷干。TruncationResult 结构(truncate.ts:15-38)记录了完整的元信息—— 是否截断(truncated)、被什么限制触发(truncatedBy: "lines" | "bytes" | null)、 原始行数 / 字节数、输出行数 / 字节数、最后一行是否部分截断(lastLinePartial)等等。 bash 工具据此在输出末尾追加一行提示(bash.ts:362-374): 

1// bash.ts:362-374 —— 截断后追加的逃生通道提示
2"[Showing lines 6501-8500 of 8500."
3+ " Full output: /tmp/pi-bash-xxx.log]"
🔎 出处:教程 §三 / bash.ts:362-374。

这行字也会进 LLM 上下文——告诉模型"如果你想看完整输出,去 read 这个文件"。

🔑 为什么截断要留"逃生通道"提示? 截断是有损的,默认省 token,但把主动权还给 LLM—— 需要时它自己 read 完整文件,兼顾省钱与不丢信息。而且 Pi 不偷偷干,元信息全记在 TruncationResult 里,不是"静默丢弃"。
工具输出截断的四件套 —— 一次工具调用的减法流水线 原始输出(8000 行日志 / 3000 行源文件) │ ▼ ① 双重限制:maxLines=2000 / maxBytes=50KB,先触者胜 │ ┌────────┴────────┐ ▼ ▼ truncateHead truncateTail (留开头,read 用) (留末尾,bash 用) │ │ └────────┬────────┘ ▼ ② 边界安全:逐字符累加字节,4 字节字符不可分割 │ ▼ ③ 单行超限兜底:取末尾 maxBytes + lastLinePartial 标志 │ ▼ ④ 逃生通道:追加 [Full output: /tmp/...] 提示进上下文
