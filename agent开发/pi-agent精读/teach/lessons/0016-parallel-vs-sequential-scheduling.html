Lesson 0016 · 第 5 章 · 工具系统

并行 vs 串行
—— 一批工具不是「一起跑就完了」

🎯 本课目标:上一课我们拆完了单个 ToolCall 的五步流水线 (prepareArguments→validate→beforeToolCall→execute→afterToolCall)。 但模型的一次回复经常不止一个 ToolCall——这节课回答: 一批工具该怎么调度?全部并行省时间,还是有时必须排队?Pi 怎么判断、怎么执行?
↩️ 先回忆上一课: 单个 ToolCall 走五步管道,任何一步出错都被兜成 isError: true 的消息,不会打断循环。今天要处理的是更上一层的问题—— 当一次回复里同时冒出好几个 ToolCall,循环该怎么安排它们的执行顺序?
这节课你将能做到一件事: 说清 Pi 的一票否决调度策略 ——为什么只要一个工具声明 sequential,整批就得排队;以及并行执行时那套 「准备顺序、执行并行、事件有序」的三阶段设计,和它背后的分层防御逻辑。
🎯 贯穿全课的类比:独木桥 vs 大草坪 一队人要过河:如果都是空手的人(只读工具),大草坪可以并排一起走,谁也不挡谁; 但只要队里有一个人推着会占满桥面的独轮车(sequential 工具), 那整队就都得排成一列走独木桥——不是独轮车的人本身危险,是只要有它在,谁也没法确定安全并排。 Pi 的调度策略,就是「宁可让所有人多等一列,也不去赌谁和独轮车能擦肩而过」。

1 · 问题:模型一次回复常常不止一个 ToolCall

Agent Loop 的内层循环里,模型的一次回复经常同时列出好几个 ToolCall。比如同时要 read、grep、find 三个只读操作: 

1assistantMessage.content = [
2    { type: "text", text: "我来查一下文件" },
3    { type: "toolCall", id: "call_1", name: "read", arguments: {path: "a.ts"} },
4    { type: "toolCall", id: "call_2", name: "grep", arguments: {pattern: "TODO"} },
5    { type: "toolCall", id: "call_3", name: "find", arguments: {pattern: "*.test.ts"} },
6]

三个都是只读操作,直觉告诉我们该并行——用 Promise.all 一起跑,省时间。 但「并行」这件事没那么简单。

2 · 但并行不是无脑 Promise.all

如果这一批里有两个 edit,而且都改同一个文件,并行执行就会互相覆盖: 

1ToolCall 1: edit { path: "app.ts", oldText: "v1", newText: "v2" }
2ToolCall 2: edit { path: "app.ts", oldText: "v3", newText: "v4" }
3                     ^^^^^^^^
4                     同一个文件!并行执行 → ToolCall 1 的修改被 ToolCall 2 覆盖

所以 Pi 需要一种机制,判断「这一批里哪些工具能并行,哪些必须串行」。

🔎 出处:教程 §三 / 并行冲突示例(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第5章-工具系统-Agent的手脚是怎么被管住的.md)。

3 · Pi 的调度策略:一票否决

Pi 的策略很简单:只要有一个工具标记为 sequential,整个批次都串行执行。 用 toolCalls.some(...) 扫一遍这一批,命中一个就够了: 

1// 检查是否有串行工具
2const hasSequentialToolCall = toolCalls.some(
3    (tc) => tools?.find((t) => t.name === tc.name)?.executionMode === "sequential",
4);
5
6// 有串行工具 → 整批串行;没有 → 并行
7if (config.toolExecution === "sequential" || hasSequentialToolCall) {
8    return executeToolCallsSequential(...);
9}
10return executeToolCallsParallel(...);
🔎 出处:教程 §三 / agent-loop.ts:382。
为什么是「一票否决」,而不是「只串行冲突的那几个」? 因为「哪些工具会冲突」很难精确判断——两个 edit 操作不同文件是不是就能并行? 万一它们编辑的文件之间有隐藏的依赖关系呢?Pi 选择了保守策略: 宁可多等,不可出错。 判断冲突的成本和风险,都比「多等一会儿」贵。

4 · 并行执行的三阶段设计

就算判定「可以并行」,Pi 也不是简单地把整批扔进 Promise.all 跑完就完事—— 它把执行拆成三个各有各的顺序约束的阶段:

并行执行的三阶段 —— 各阶段的「顺序」要求各不相同 阶段 1 - 准备(顺序执行): ToolCall 1: emit_start → prepareArguments → validate → beforeToolCall ToolCall 2: emit_start → prepareArguments → validate → beforeToolCall ToolCall 3: emit_start → prepareArguments → validate → beforeToolCall // 准备阶段必须顺序,因为 beforeToolCall 可能有副作用(如修改全局状态) 阶段 2 - 执行(并行): ToolCall 1: execute ────────────────┐ ToolCall 2: execute ───────────────┤ Promise.all ToolCall 3: execute ───────────────┘ // 只有 tool.execute() 并行 阶段 3 - 事件发送(有序): ToolCall 2: emit_end ← 先完成的先发 tool_execution_end ToolCall 1: emit_end ToolCall 3: emit_end ToolCall 1: emit_result ← 但 ToolResultMessage 按调用顺序发 ToolCall 2: emit_result ToolCall 3: emit_result
🔎 出处:教程 §三 / 三阶段设计。
为什么准备阶段必须顺序? beforeToolCall 可能有副作用(比如修改全局/共享状态), 并行准备会让这些副作用彼此干扰、结果不可预测,所以逐个做——这里没有性能诉求,只有正确性诉求。
🔑 为什么 ToolResultMessage 必须按调用顺序发,而 emit_end 不用? 模型是依赖调用顺序理解结果的——它先要求 read 再要求 grep,消息就得照这个序排给它看, 乱序会误导模型对因果关系的理解;而 emit_end 只是一个「执行结束了」的观测事件, 谁先跑完就先发,不影响模型的推理链条。同一批操作里,不同种类的顺序约束可以并存。

5 · 内置工具默认 parallel,靠什么兜底文件安全?

这里有个容易被忽略的细节:v0.80.2 的 7 个内置工具 (read/write/edit/bash/grep/find/ls)都没有显式声明 executionMode,默认全部是 "parallel"。运行时只在 agent-loop.ts:382 判断是否 "sequential",未声明就按并行处理。

那两个 edit 并行改同一个文件时,怎么保证不互相覆盖?答案不在外层调度, 而在工具内部——edit.ts:312 调用了 withFileMutationQueue(file-mutation-queue.ts:32-61), 对同一个文件的编辑操作做串行化排队。扩展工具如果自己需要串行,可以显式声明 executionMode: "sequential"。

🔎 出处:教程 §三 脚注(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第5章-工具系统-Agent的手脚是怎么被管住的.md)。
🔑 分层防御: 外层调度选择保守(一票否决,宁可多等);工具内部再做精细兜底 (只对真正冲突的同一文件排队)。前者保安全底线,后者保性能——两层配合, 才做到「内置工具默认并行却依然安全」,而不必把整批都拖成串行。
