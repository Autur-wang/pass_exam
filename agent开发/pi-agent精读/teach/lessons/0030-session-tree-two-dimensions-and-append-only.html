Lesson 0030 · 第 10 章 会话管理

会话为什么是一棵树

🎯 本课目标:第 9 章讲压缩时反复提到「Session Tree」,当时我们只是假设它存在。 这节课回答一个更基础的问题——会话数据到底怎么存?你会看到这个问题其实是两个正交的子问题, 以及 Pi 为什么在「长什么样」这一维选了树而不是数组。
🔁 先回忆上一课:0029 讲 StructuredSummary 怎么把旧对话压成结构化摘要、 再靠 rebuildContext() 拼回 LLM 能用的 messages 数组——但那时我们跳过了一个前提: 压缩结果到底存在哪、存成什么形状?这节课把这个地基补上。
这节课你将能做到一件事: 把「会话怎么存」拆成存哪里和 长什么样两个独立问题,并说清楚 Pi 为什么在结构这一维放弃线性数组、 改用 append-only 的 Session Tree——回退时只移一个指针,不删一个字节。
🎯 贯穿全课的类比:走迷宫,退回岔路口 走迷宫遇到死路时,你不会拿橡皮擦掉已经走过的路线——你只是退回岔路口, 把「我在哪」这个指针移回去。走错的那条死路仍然留在地图上,以后想回去看一眼,随时能找到。 Session Tree 的回退就是这个动作:移指针,不删地图。

1 · 两个正交维度:存哪里 / 长什么样

前 8 章我们一直在跟 context.messages 打交道——它是个数组。但 Agent 重启后这个数组从哪来? 关闭后到哪去?这就是「会话数据怎么存」。这个问题其实包含两个独立的子问题:

维度回答什么一般做法Pi 的选择
子问题 A · 存哪里存储介质mysql / postgres 等数据库本地 JSONL 文件(接口允许换数据库)
子问题 B · 长什么样数据结构线性数组树(Session Tree)

两个维度是正交的——你可以"用 mysql 存线性数组",也可以"用 JSONL 文件存一棵树"。 混淆它们会让讨论糊成一团:别把"用了文件"和"必须 append-only"粘成一团,它们是两次独立的选择。

Pi 的 coding-agent 选本地 JSONL 文件,不是数据库,理由跟它的产品定位有关:

  • 单用户、本地运行:CLI 工具跑在自己机器上,没有"多用户并发""跨机器查询"的需求
  • 会话跟项目走:每个项目的 .pi/sessions/ 就是那个项目的对话档案
  • 零依赖、零运维:不用装数据库、不用起服务
  • 可读、可调试:纯文本,可以 cat / grep 直接看
1// .jsonl 文件第一行是 Session Header,不是树节点,是文件元信息
2{"type":"session","version":3,"id":"UUIDv7","cwd":"/project","timestamp":"2026-07-03T10:00:00Z"}
3// 后续每行是一个 Entry,一行一个,append-only
4{"type":"model_change","id":"e1","parentId":null,...}
为什么拆成两个维度? 因为混在一起会压缩选择空间,让人误以为"用了文件就必须 append-only"。 实际上 agent-core 层还提供了一个 SessionStorage 接口,允许别的应用换成数据库版本—— 但 coding-agent 自己的 SessionManager 是独立实现,直接读写 JSONL, 并未走这层抽象。「介质」和「结构」互不绑定,才是这一节真正的收获。

2 · 跟着一次真实会话,看树怎么长出来

抽象讲"append-only 的树"没人能看懂。用一个具体场景:调试一个认证 bug,8 步操作。 前 5 步很朴素——切模型、提问、读文件、拿结果、给分析——全部挂在一条直线上: 

1e1: ModelChangeEntry
2    parentId: null  // 根节点
3    payload: { model: "claude-sonnet-4-6" }
4
5e2: MessageEntry
6    parentId: "e1"
7    message: { role: "user", content: [..."salt 验证为什么失败?"] }

树形长这样(第 5 步为止,5 个节点,一条直线,这是"主分支"):

e1 (model_change) └── e2 (user: "salt 验证为什么失败?") └── e3 (assistant: read auth.ts) └── e4 (toolResult: auth.ts 内容) └── e5 (assistant: "问题在 23 行") ↑ leafId

每一步只做两件事:创建新节点(带 parentId)+ 移动 leafId。没有任何旧节点被修改—— 这就是"追加操作"的直觉。

3 · 第 6 步的转折:回退不是删数据,是移指针

你对"问题在 23 行"不满意,想换个思路。这时你执行回退——但没有删除任何节点: 

1branch(branchFromId: "e2"): void {
2    this.leafId = "e2";   // 只改这一行
3}

操作只有一行。回退后树变成:

e1 (model_change) └── e2 (user: "salt 验证为什么失败?") ├── e3 (assistant: read auth.ts) ← 旧分支还在 │ └── e4 (toolResult) 数据完整保留 │ └── e5 (assistant: "问题在 23 行") │ ↑ leafId 现在指回 e2

e3、e4、e5 一个都没删——它们还在树上,只是不在"当前路径"上。 这就是 append-only 的核心:回退不是删数据,是移动指针,O(1)。

为什么要保留旧分支? 因为你不知道以后会不会想回到它。新思路也许走半天没结果, 你想退回去看原来"问题在 23 行"的分析——如果回退时删了,就再也找不回来了。

第 7 步,你从 e2 这个岔路口换了一个问题,产生新节点:

1e6: MessageEntry
2    parentId: "e2"   // 跟 e3 共享同一个父!
3    message: { role: "user", content: [..."先看 hash 函数的实现"] }

e6 的 parentId 也是 e2,跟 e3 一样——分支的本质就在这一行:

e1 (model_change) └── e2 (user: "salt 验证为什么失败?") ├── e3 (assistant: read auth.ts) │ └── e4 (toolResult) │ └── e5 (assistant: "问题在 23 行") │ └── e6 (user: "先看 hash 函数") ← 新分支起点,与 e3 同父 ↑ leafId
🔑 为什么选树而不是线性数组: 对话不总是线性的——重试、分支、回退都会发生。 如果用线性数组,这些操作意味着"删掉后面的消息再重写"。删了就没了—— 如果你想留着两条分支对比(先试方案 A 走到底,再回头试方案 B,A 的记录还想留着), 数组做不到"分叉不丢数据"。两个节点共享同一个 parent,就是树上的两个分支—— 这是 e6 和 e3 教给我们的全部道理。
