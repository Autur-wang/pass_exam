Lesson 0032 · 第 10 章 会话管理

从树到 LLM 上下文
—— buildSessionContext 与 JSONL 落盘

🎯 本课目标:上一课我们搞清了树上每个节点长什么样、以及追加/回退/分支这三个核心操作。 但树本身不能直接喂给 LLM——这节课要拆开两件事:树怎么被buildSessionContext 「压扁」成 LLM 要的线性 messages 数组,以及这棵树最终怎么落盘成 JSONL 文件。这是本章(也是整门课主线)的最后一课。
⏮ 回忆一下上一课: 我们说过树是append-only的——节点只认父不认子,回退只是移动 leafId指针,旧节点原地不动。今天要接上这句话继续问:既然树上可能有好几条分支, 那调用 LLM 时,到底该把哪一条发过去?又是谁负责把树形数据变成 LLM 认识的样子?
这节课你将能做到一件事: 讲清 buildSessionContext 的两步走 (路径遍历 + 按类型分派)、说出为什么节点化状态让回退天然正确、 以及 JSONL 为什么要「延迟写入」到首个 assistant 消息到达之后。
🎯 贯穿全课的类比:只会读单行清单的读者 LLM 像一个只会读单行清单的读者:你内部存的是一棵族谱树,枝繁叶茂、记录着每一次 回退与分叉,但递给它之前,必须沿一条血脉从祖到孙抄成一张单行纸条——旁支不抄。 而且不是抄一次就完事:每次开口前都要现抄一遍,这就是 buildSessionContext。

1 · 为什么必须有这一步「压扁」

想象 LLM 的视角:你给它发一个 HTTP 请求,body 里是 messages: [...]——一个数组。 它根本不知道你内部的会话历史是树形还是别的什么形状,它只认线性数组。

所以无论内部数据结构多复杂,到 LLM 边界都必须变成线性的。树是存储形态,线性 messages 数组是「出口」形态——每次调用 LLM 之前,都要把树重新压扁一遍,而不是压扁一次存起来复用 (因为 leafId随时可能因回退/分支而改变,压扁的结果每次都可能不一样)。

2 · 第一步:路径遍历——从 leaf 走到 root

假设当前 leafId 是 e9,buildSessionContext 先从 e9 沿 parentId 一路往回走到根,收集路径上的所有 entry: 

const path: SessionEntry[] = [];
2let current = byId.get(leafId);   // e9
3while (current) {
4    path.push(current);   // 先按 leaf → root 顺序收集
5    current = current.parentId ? byId.get(current.parentId) : undefined;
6}
7path.reverse();           // 反转为 root → leaf 顺序

走完之后,path(root→leaf 顺序)是:

1[e1, e2, e6, e7, e8, e9]

注意 e3、e4、e5 不在 path 里——它们不在当前分支上。这就是「当前路径」的含义: 只看 leaf 到 root 这一条血脉,其他旁支的数据不会发给 LLM。

为什么必须这样做? LLM 的 API 只接受一个线性 messages 数组,无论内部结构多复杂, 到 LLM 边界都必须变线性——树是存储形态,线性是出口形态,两者不能混为一谈。

3 · 第二步:按类型分派——消息进数组,状态类改变量

路径上的每个 entry,按类型决定怎么处理:

1e1 (model_change)         → 更新状态变量 model = "claude-sonnet-4-6",不进 messages
2e2 (user message)         → 推入 messages 数组
3e6 (user message)         → 推入 messages 数组
4e7 (assistant + ToolCall) → 推入 messages 数组
5e8 (toolResult)           → 推入 messages 数组
6e9 (assistant)            → 推入 messages 数组

最后构建出来的 messages 数组:

1[
2  { role: "user", content: "auth.ts 里 salt 验证为什么失败?" },        // e2
3  { role: "user", content: "先看 hash 函数的实现" },                    // e6
4  { role: "assistant", content: [{ text: ... }, { toolCall: grep ...}] }, // e7
5  { role: "toolResult", toolCallId: "call_002", content: ... },        // e8
6  { role: "assistant", content: [{ text: "新分析..." }] }              // e9
7]
🔎 出处:教程 第10章 §五 / session-manager.ts buildSessionContext。

4 · 状态变量:覆盖式提取,让回退天然正确

model_change、thinkingLevel_change 不进 messages 数组,但它们影响 「用什么参数调用 LLM」。提取方式是覆盖式——沿路径从 root 走到 leaf,遇到变更就覆盖: 如果路径上有多条 model_change(先切到 4.6、又切到 4.5、再切回 4.6), 最后一次覆盖生效。若路径上没有任何 model_change 节点,函数返回 model: null,由调用方兜底使用 session 启动时配置的初始 model。

🔑 为什么把「切换模型」也存成节点,而不是塞进一个全局状态对象? 节点能完整记录「什么时候切的、在哪个位置切的」,状态变量只能存最后值。如果你回退到切换模型之前的 节点,buildSessionContext 走的路径就不包含那条 model_change, model 会自动回到切换前的值——节点化的状态让回退天然正确。

5 · CompactionEntry 的特殊处理:选择性收集,不是真删

假设路径上有一个 CompactionEntry(记录了 firstKeptEntryId = "e3"):

1e1 (user)              ← 这之前是早期对话(已被压缩)
2e2 (assistant)         ← 被压缩
3e3 (assistant)         ← 被压缩
4e4 (compaction)        ← 压缩节点,记录了 firstKeptEntryId = "e3"
5e5 (user)              ← 压缩后保留的近期消息
6e6 (assistant)

buildSessionContext 遍历到 e4 时,按 firstKeptEntryId 选择性收集,分三步:

11. 先生成一条 CompactionSummaryMessage(来自 e4 的 summary 字段),推入 messages 数组开头
22. e4之前的 entry 中,只收集 firstKeptEntryId(e3)及之后的——e1、e2 被丢弃,e3 保留
33. e4之后的所有 entry 正常收集

最终的 messages 数组:

1[
2  CompactionSummaryMessage (从 e4 生成),   // 替换了 e1、e2
3  { role: "assistant", ... },              // e3(保留区第一个)
4  { role: "user", ... },                    // e5
5  { role: "assistant", ... },              // e6
6]
为什么用「选择性收集」而不是真删旧消息? append-only 不允许删,压缩只是「当前路径上」的一种视图。 如果下次你回退到 e4 之前的位置,路径不再包含 e4,e1-e3 又会作为正常消息重新出现—— 压缩不是破坏性的,只是当前路径上的一种展示选择。
🔎 出处:教程 第10章 §五。

6 · JSONL 持久化:一行一个 Entry

树长好了要落盘。磁盘上的 .jsonl 文件长这样(每行一个 entry):

1{"type":"session","version":3,"id":"UUIDv7","cwd":"/project","timestamp":"2026-07-03T10:00:00Z"}
2{"type":"model_change","id":"e1","parentId":null,"provider":"anthropic","modelId":"claude-sonnet-4-6",...}
3{"type":"message","id":"e2","parentId":"e1","message":{"role":"user",...},...}
4{"type":"message","id":"e6","parentId":"e2",...}   // ← parentId 是 e2,标记出这里有分支

第一行是 Session Header(type: "session"),记录会话元信息(cwd、版本号等)。 e6 的 parentId 是 e2——通过这个字段就能在文件里直接看出「这里有个分支」, grep '"parentId":"e2"' 就能找到所有从 e2 长出来的子节点。

为什么用 JSONL 而不是单个大 JSON 文件? JSONL 是行级追加的——新 Entry 直接 appendFileSync 到文件末尾,不需要读入-修改-重写整个文件。这和 append-only 树的 设计完美契合:树只追加不修改,文件也只追加不重写。
🔎 出处:教程 第10章 §六 / session-manager.ts _appendEntry(约 L941),用 appendFileSync。

7 · 延迟写入:避免「有问无答」的半截对话

有一个写入策略细节:首次 assistant 消息到达前,写入会延迟。具体规则分四种情况:

已有 assistant?已 flushed?行为
没有已 flushed立即 append 当前 entry
没有未 flushed标记为「未 flushed」,不写盘——等 assistant 到来
有未 flushed重写整个文件(header + 所有积压 entry),用 openSync("wx") + writeFileSync 保原子性,标记为已 flushed
有已 flushed立即 append 当前 entry
🔑 为什么要延迟写入到首个 assistant 到来? 为了避免「有问无答」的半截对话残留—— 用户问了一句但 Agent 没回(网络断了、API 报错了),如果立即把每条用户消息都写盘, 下次打开会话就会看到一条孤零零悬着的用户消息,没有对应回复。延迟到首次 assistant 消息到达 再批量写入,保证落盘的对话至少有一对完整的 user-assistant 往返。 之后每条 entry 都立即 append——首次 flush 后这套机制就不再起作用,因为已经「上了轨道」。

另外还有两种情况会触发全文件重写(而非日常的 appendFileSync): 创建分支副本(克隆会话到新 .jsonl 文件,复制当前路径上的所有 entry)、以及 修复损坏的会话文件。重写不破坏 append-only 原则——产生的是新文件或新格式, 原历史数据完整保留在重写后的内容里。

🔎 出处:教程 第10章 §六 / session-manager.ts _rewriteFile(约 L876)。

8 · 两层实现:接口存在,但不强制统一继承

agent-core 层coding-agent 层
API 风格异步同步
Entry 类型11 种9 种
存储SessionStorage 接口(可插拔)独立实现,直接操作 JSONL

agent-core 提供了可插拔的 SessionStorage 接口,但 coding-agent 的 SessionManager 并未实现这个接口——它是一套完全独立的实现,直接操作自己的 JSONL 文件, 只复用了 agent-core 的类型定义(如 SessionEntry),没复用其存储抽象。两套实现平行存在。

为什么接口存在却不强制 coding-agent 复用? 松耦合让 Web 版 Pi 可以自己用 mysql 实现 SessionStorage 而不改 agent-core 的其他逻辑;但代价是你不能直接拿 coding-agent 的 SessionManager 去套该接口——它们签名不兼容。这是「接口允许换数据库」的具体落地,但落地路径是 各自实现而非统一继承。
🔎 出处:教程 第10章 §七 / SessionStorage 接口在 packages/agent/src/harness/types.ts:440;coding-agent 独立实现在 session-manager.ts:758。
