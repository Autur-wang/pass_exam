Lesson 0020 · 第 6 章 消息系统

转换边界:convertToLlm 与可见性

🎯 本课目标:上一课讲清了 AgentMessage 的「7 种类型、两层结构」——Agent 内部可以自由表达, 但 LLM 只认 3 种标准格式。这节课回答最后一个问题:这场「内部丰富 → 外部精简」的翻译到底在哪一步发生、 怎么发生?读完你会知道 convertToLlm 这个翻译器长什么样,以及它顺手解决的另一个问题—— 怎么让某条消息「UI 能看、LLM 看不到」。
⏮ 回忆上一课: AgentMessage 联合类型一分为二——左支 Message(user/assistant/toolResult 三种标准)、 右支 CustomAgentMessages(bashExecution 等四种扩展),核心包完全不知道扩展消息的存在, 只留了一个「插槽」。但留了插槽只解决了「Agent 内部怎么表达」,没解决「LLM 调用前怎么办」—— 这正是今天要拆的那道翻译边界。
这节课你将能做到一件事: 画出 context.messages 从 AgentMessage[] 到 Message[] 的完整两段管道,说清 transformContext 和 convertToLlm 为什么必须分开写,并解释 excludeFromContext 如何让一条消息「对 UI 可见、对 LLM 隐身」。
🎯 贯穿全课的类比:出海关的通行章 跟着开头那条 BashExecutionMessage 走完最后一程:它从 role: "bashExecution" 出发, 带着 command/output/exitCode 这些「本国身份证件」, 在调用 LLM 前的最后一道关卡被翻译成一条普通的 user 消息—— 就像出海关时,各国护照不管原本什么样式,最终都要盖上同一种通行章,LLM 才放行。

1 · 翻译发生在哪一刻?——两阶段管道

Agent 内部用最多 7 种消息类型自由表达,但每次调用 LLM 时,LLM 只接受 3 种标准格式。 翻译不是随时发生的,而是在 streamAssistantResponse(第 3 章讲过的「调用模型」那一步)里, 调用 LLM 之前的最后一刻精确发生:

每次 LLM 调用前的消息处理管道 context.messages: AgentMessage[] ← Agent 内部消息(最多 7 种类型) │ ▼ [1] transformContext (可选) ← AgentMessage[] → AgentMessage[] │ 同层变换:裁剪旧消息、注入外部上下文、触发压缩 ▼ [2] convertToLlm (必须) ← AgentMessage[] → Message[] │ 跨层翻译:自定义消息 → 标准格式 ▼ llmContext.messages: Message[] ← LLM 看到的消息(只有 3 种类型) │ ▼ streamFunction(model, llmContext, ...) ← 调用 LLM(第 4 章讲过)

注意顺序:先 transformContext(同层变换),再 convertToLlm(跨层翻译)。 这个顺序不是随意的——第 3 节会讲为什么必须这样分两步。

2 · 转换规则:所有自定义消息都变成 User

coding-agent 的 convertToLlm 核心逻辑是一个按 role 字段分派的 switch:

role怎么处理
"user"直接透传,不做任何修改
"assistant"直接透传
"toolResult"直接透传
"bashExecution"excludeFromContext=true → 过滤掉;否则 → 转换成 UserMessage
"custom"转换成 UserMessage
"branchSummary"转换成 UserMessage(加 XML 标签包裹)
"compactionSummary"转换成 UserMessage(加 XML 标签包裹)
为什么都变成 user? 因为 LLM API 对角色顺序有严格要求——对话格式是 user → assistant → user → ... 交替的,不能连续出现两个 assistant。 自定义消息本质上是「系统注入的信息」(Bash 执行结果、压缩摘要、分支摘要),放在 user 角色中最安全——这是「关键洞察」:所有自定义消息都被转换成了 user 角色的消息。

3 · 具体例子:BashExecutionMessage 的转换

回到开头的场景。一条 BashExecutionMessage 从创建到被 LLM 看到,数据结构发生了这样的变化:

Before —— BashExecutionMessage(Agent 内部格式):

1{
2    role: "bashExecution",
3    command: "ls -la",
4    output: "total 32\ndrwxr-xr-x  5 user  staff  160 May 30 10:00 .\n...",
5    exitCode: 0,
6    cancelled: false,
7    truncated: false,
8    timestamp: 1748568000000
9}

After —— UserMessage(LLM 看到的格式):

1{
2    role: "user",
3    content: [{
4        type: "text",
5        text: "Ran `ls -la`\n```\ntotal 32\ndrwxr-xr-x  5 user  staff  160 May 30 10:00 .\n...\n```"
6    }],
7    timestamp: 1748568000000
8}

变化总结:

字段变化
role"bashExecution" → "user"
command/output/exitCode结构化字段 → 被格式化成一段文本
cancelled/truncated丢失的信息:融合进文本描述里,不再是独立字段

其他自定义消息(CompactionSummary、BranchSummary)转换模式完全一样——把摘要文本用 <summary> 标签包裹,前面加一句说明,变成 UserMessage 的 content。

🔎 出处:教程 §五「转换规则」表格 / §五「具体例子:BashExecutionMessage 的转换」 (packages/coding-agent/src/core/messages.ts:82-195)。

4 · 为什么分两步,而不是一步到位?

回到管道图,有一个设计细节值得追问:transformContext 和 convertToLlm 为什么分开写?

  • transformContext 处理的是 AgentMessage 级别的操作:裁剪太旧的消息、 注入外部上下文、触发压缩算法。处理前后都是 AgentMessage[],类型不变。
  • convertToLlm 处理的是 跨类型翻译:把 AgentMessage 翻译成 Message。 处理前是 AgentMessage[],处理后是 Message[],类型变了。
🔑 分开的好处:你可以只替换其中一个,互不影响。 换了上下文管理策略(比如从「删最旧消息」改成「压缩成摘要」),只需要改 transformContext——convertToLlm 不需要动。 换了应用类型(比如把 coding-agent 改造成 Web 客服 Agent,自定义消息从 BashExecution/CompactionSummary 变成 TicketEvent/OrderNote 这类业务消息),只需要改 convertToLlm——transformContext 不需要动。
那换 LLM 提供商(Claude → GPT)呢?convertToLlm 也不需要动。 因为 convertToLlm 的输出已经是统一的 Message[](3 种标准消息)—— 「自定义消息 → 标准消息」这件事已经做完了。再往下,把 Message 翻译成各家 Provider 的私有格式 是 pi-ai 层(第 4 章讲过)的工作,那一层有自己的翻译器(anthropic-messages、openai-completions 等), 跟 convertToLlm 是完全独立的两层。Pi 把「消息类型翻译」和「Provider 协议翻译」放在了两层不同的抽象里, 互不干扰。

5 · 过滤机制:excludeFromContext 的可见性控制

到目前为止,所有自定义消息最终都变成了 UserMessage 被 LLM 看到。但有些情况下,消息应该只给 UI 看、 不给 LLM 看——比如 Pi 的 Bash 工具有个功能:用 !! 前缀执行命令时(比如 !!secret_cmd), 这条命令的执行结果对 LLM 不可见。

实现方式非常简单——BashExecutionMessage 有一个 excludeFromContext 字段,在 convertToLlm 里检查它:

1case "bashExecution":
2    if (m.excludeFromContext) {
3        return undefined;   // 直接返回 undefined,后续被 filter 掉
4    }
5    // ... 否则正常转换
🔎 出处:教程 §七 excludeFromContext 段落(packages/coding-agent/src/core/messages.ts:38-39)。
注意: excludeFromContext = true 的消息仍然存在于 context.messages 中。 UI 仍然可以看到它、渲染它。只是在调用 LLM 的那一刻,这条消息被「隐身」了—— 这就是「UI 能看、LLM 不能看」的机制:一个布尔字段,在翻译边界做过滤,数据本身不需要删除。

6 · 三种消息可见性级别

综合以上分析,Pi 的消息系统其实有三种可见性级别:

可见性级别LLM 是否看到UI 是否看到实现方式典型消息
全可见是是convertToLlm 正常转换普通的 BashExecution、User、Assistant
LLM 不可见否是excludeFromContext = true!! 前缀的 Bash 执行
仅持久化否否UI 渲染时跳过,convertToLlm 也过滤掉Web UI 的 ArtifactMessage

第三级「仅持久化」和第二级不是同一回事:第二级是「翻译边界隐身」,第三级是两端都刻意跳过—— 数据仍在,但既不进 UI 渲染逻辑,也不进 convertToLlm 的转换分支。
