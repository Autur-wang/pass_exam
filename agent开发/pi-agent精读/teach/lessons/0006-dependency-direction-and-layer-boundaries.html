Lesson 0006 · 第 2 章 三层架构

层边界与依赖
—— 方向单向向上

🎯 本课目标:上一课我们看清了类型如何从 pi-ai 的「原子」一路扩展到 pi-coding-agent 的「材料」。 这节课要拆穿一个几乎所有人都会踩的误解——分层不等于「隔一层调一层」。 读完你会知道分层真正守的是什么规则,以及这条规则为什么能让你把任意一层整个换掉。
🔁 回忆一下: 上一课你看到 Tool → AgentTool → ToolDefinition 一路继承扩展, 每一层只加自己关心的字段,底层类型从不被修改。今天我们要问一个更底层的问题: 这些「层」之间,到底谁能引用谁?
这节课你将能做到一件事: 看到任意一个 monorepo 的 package.json dependencies 字段,你能立刻判断它的分层是「健康的」 还是「已经破坏了」——依据不是「有没有跨层引用」,而是「箭头有没有反向」。
🎯 贯穿全课的类比:你以为分层像协议栈,直到你打开 package.json 你以为分层就像网络协议栈——「隔一层调一层」,应用层不能直接碰物理层。 于是你打开 pi 的 packages/coding-agent/package.json,却发现它的 dependencies 里直接列了 pi-ai——跳过了中间的 pi-agent-core。 你愣了一下:这不是破坏分层了吗?这个「意外」正是理解真正规则的入口。

1 · 意外:顶层直接依赖了底层

如果你的分层理解是「上层只能依赖相邻的下层」,那打开 packages/coding-agent/package.json 的 dependencies 字段, 会看到一个意料之外的细节: 

1// packages/coding-agent/package.json
2"dependencies": {
3    "@earendil-works/pi-agent-core": "^0.80.2",   // ← 依赖中间层,合理
4    "@earendil-works/pi-ai": "^0.80.2",            // ← 也直接依赖底层?
5    "@earendil-works/pi-tui": "^0.80.2",
6    // ... 其他依赖
7}

coding-agent 直接依赖了 pi-ai,而不是只通过 pi-agent-core 间接使用它。 如果你之前认为分层就是「隔一层调一层」(就像网络协议栈那样),这个发现会让你愣一下: 这不是打破分层了吗?为什么顶层要跨层直接引用底层的东西?

🔎 出处:教程 §4 / packages/coding-agent/package.json。

2 · 答案藏在类型系统里:跨层引用是必然

打开 packages/agent/src/types.ts 的开头,你会看到 pi-agent-core 大量的基础类型 (Message、Model、ImageContent、Tool……) 都是从 pi-ai 直接导入的。这些是整个系统的「原子概念」——就像化学元素, 不管你在哪一层,都需要用到「原子」的定义。

同样,coding-agent 也需要直接用到 pi-ai 的类型:比如用户往聊天里贴了一张截图, coding-agent 需要知道图片数据用什么格式表示——这个 ImageContent 类型就定义在 pi-ai 里, 而不是在中间层 pi-agent-core 重新定义一份。

为什么跨层依赖不是设计失误? 因为 ImageContent 等原子类型只在 pi-ai 定义, 上层要用就必须直接引用它——这是「集中定义原子」的必然结果。如果强行禁止跨层, coding-agent 要么被迫复制一份 ImageContent 的定义(两份定义迟早会漂移), 要么加一层纯转发的「传声筒」模块(只为了合规,没有任何实际作用)。两条路都更差。

3 · 真正的规则:依赖方向必须单向向上

关键不在于「能不能跨层引用」,而在于依赖方向是不是单向的。 验证方法很直接——看每个包的 dependencies 里有没有反向依赖:

包依赖了谁有没有反向依赖?
pi-ai@anthropic-ai/sdk, openai, @google/genai 等 SDK没有,它不依赖任何 pi-xxx 包
pi-agent-core@earendil-works/pi-ai, typebox, yaml只向上依赖 pi-ai,不依赖 coding-agent
pi-coding-agent@earendil-works/pi-ai, @earendil-works/pi-agent-core, @earendil-works/pi-tui只向上依赖,不反向依赖
所有箭头都朝上 pi-ai(底层) ↑ ↑ │ │ │ pi-agent-core(中间层) │ ↑ │ │ └─── pi-coding-agent(顶层) 底层永远不知道上层的存在 ——pi-ai 的代码里没有任何一个 import 指向 pi-agent-core 或 pi-coding-agent
🔑 规则是控制方向,而非限制层级: 限制跨层会逼你复制类型或加转发层——两者都是纯负担; 而「单向向上」既允许跨层复用原子类型,又天然杜绝了循环依赖。 这就是分层的真正规则:不是限制引用层级,而是控制依赖方向必须单向向上。
🔎 出处:教程 §4 反向依赖对照表。

4 · 三层不是教条,层数取决于复杂度

理解了「方向」之后,一个自然的问题是:如果我只想写一个简单的 Agent,真的需要三层全用吗? 教程给出三个场景的对照:

场景适合什么你自己做什么
只用 pi-ai只需要调 LLM、不需要 Agent 循环自己管状态、自己写循环(如果需要)
pi-ai + pi-agent-core需要完整 Agent 能力、但有自己独特的业务场景写自己的工具、自己的入口
全部三层做 Pi 同类的编程助手直接用,或写扩展

比如场景 C,只用 pi-ai:

1// 只用底层
2import { streamSimple } from "@earendil-works/pi-ai";
3
4const stream = streamSimple(model, context);
5for await (const event of stream) {
6  console.log(event);
7}

完全可行——但你就得自己写循环、自己管理消息状态、自己处理工具调用。 这正是 pi-agent-core 存在的意义:它帮你做了 Agent 最难的那部分(循环、状态、事件、压缩), 你只需要告诉它用什么工具。

为什么三层可以裁剪,但铁律不能裁剪? Agent 最难的是循环/状态/事件/压缩, agent-core 已经包办了这部分;你的复杂度决定要用几层。但不管你选场景 A、B 还是 C, 依赖方向的铁律与层数无关——它是所有场景都必须遵守的底线。
🔎 出处:教程 §6 场景对照表。

5 · 唯一不可违反的铁律 + 三个可带走的方法

三层不是教条,但有一条规则不能违反:底层的代码里不能出现任何对上层的引用。 pi-ai 不能 import pi-agent-core 的任何东西,pi-agent-core 不能 import pi-coding-agent 的任何东西。 这条规则保证了:你可以把任何一层换成自己的实现,而不影响其他层——比如把 pi-ai 整个换成自己的模型调用层, pi-agent-core 和 pi-coding-agent 都不需要改。

方法是什么怎么验证
依赖漏斗分层法先画依赖箭头:底层不知道外面世界,中间层知道底层但不知道业务,顶层知道一切检查有没有高层的东西被底层 import
类型递进扩展模式底层定义最小接口,上层用联合类型 / extends 扩展,不修改底层类型底层能否独立发布,不引入整个 Agent 框架
可独立使用测试去掉上层这一层,底层还能不能正常工作暂时移除上层依赖,看底层编译 / 测试还能不能过
🔑 核心承诺: 只有底层对上层一无所知,你才能把 pi-ai 整个换成自己的模型层而不动上面两层—— 这就是分层架构真正要兑现的承诺,也是本节唯一不可违反的铁律。
