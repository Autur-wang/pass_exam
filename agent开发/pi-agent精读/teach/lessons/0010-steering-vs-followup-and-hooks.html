Lesson 0010 · 第 3 章 Agent Loop

两种干预:
steering vs followUp 与 Turn 钩子

🎯 本课目标:上一课我们剥完了「内核 + 叠加」的洋葱图,知道内核只有十几行, 叠加是产品功能。这节课把两块最容易混淆的叠加拆清楚:steering 和 followUp 这两种「外部消息注入」机制到底谁管什么、什么时候被检查, 以及 turn_end 之后挂的两个扩展钩子 prepareNextTurn 与 shouldStopAfterTurn 各自解决什么问题。
⏮️ 回忆上一课: 洋葱图从里到外是——最内核的最简 Loop(~10 行通用法则), 外层依次叠加 steering(紧急插队)、followUp(任务追加)、钩子(切模型/安全阀)。 剥掉任何一层,里层仍能跑。这节课就是把外面这几层挨个打开看。
这节课你将能做到一件事: 给定一个「用户中途插话」或「系统想追加任务」的场景, 你能立刻判断该走 steering 还是 followUp, 并说清 prepareNextTurn 和 shouldStopAfterTurn 各自的职责边界。
🎯 贯穿全课的类比:开会递纸条 vs 翻信箱 steering 是你正在开会,有人敲门递张纸条说"紧急,先看这个"——它在会议进行的间隙插队; followUp 是开完会翻信箱,"不急,但需要处理"——等当前任务全部完成后才叫号。 而 prepareNextTurn 像每讲完一段就问一句"下一段要不要换个更资深的人来讲", shouldStopAfterTurn 像会议室的安全阀"时间/空间快满了,该收尾了"。

1 · steering(叠加1):紧急插队,在工具执行间隙生效

想象你让 Agent 帮你修一个 bug,Agent 正在读文件、分析代码。这时候你突然想到一个补充: "也检查一下测试文件"——你希望这条指令能插队,而不是等 Agent 把当前任务做完再说。 这就是 steering:用户在 Agent 工作期间输入的新指令,会被放进 steering 队列。

它的检查时机不是一处,而是两处——runLoop 一进来的首次检查, 以及内层循环每圈结尾的二次检查: 

1// ① 首次 steering 检查(在进入内层循环之前!)
2let pendingMessages = (await config.getSteeringMessages?.()) || [];
3
4// … 内层循环开头:把紧急消息注入到上下文
5if (pendingMessages.length > 0) {
6    for (const message of pendingMessages) {
7        await emit({ type: "message_start", message });
8        await emit({ type: "message_end", message });
9        currentContext.messages.push(message);
10        newMessages.push(message);
11    }
12    pendingMessages = [];  // 消费完毕,清空
13}
为什么首次 steering 检查放在进入内层循环之前? 用户在等待 LLM 首次响应时可能又输入了内容——这时候消息已经从外部排队了,但循环还没开始, 如果不提前取出来,这批消息就漏掉了。所以 pendingMessages 的初始化不是空数组,而是先问一遍 getSteeringMessages。
🔎 出处:教程 §4.3 / agent-loop.ts:167 steering 首次检查(../../原始资料/dg-ai-notes/pi-agent/docs/typescript/第3章-Agent-Loop-让模型转动起来的引擎.md)。代码为教程示意,基于 pi v0.80.2。

2 · turn_end 收尾四步:钩子在哪里插进来

一个 Turn 的核心工作(调模型 + 执行工具)做完后,收尾分四步——前两步是内核, 后两步是 coding-agent 叠加的扩展点: 

1// ① emit turn_end —— 通知外部"这一轮结束了"(内核)
2await emit({ type: "turn_end", message, toolResults });
3
4// ② prepareNextTurn —— 给外部一个机会"改装"下一轮(叠加)
5// 返回值可包含 context / model / thinkingLevel 三者之一的覆盖
6const nextTurnSnapshot = await config.prepareNextTurn?.({...});
7if (nextTurnSnapshot) {
8    currentContext = nextTurnSnapshot.context ?? currentContext;
9    config.model = nextTurnSnapshot.model ?? config.model;
10}
11
12// ③ shouldStopAfterTurn —— 外部判断是否该停了(叠加)
13if (await config.shouldStopAfterTurn?.({...})) {
14    await emit({ type: "agent_end", messages: newMessages });
15    return;
16}
17
18// ④ 再次检查 steering —— 有没有新的紧急消息?(叠加1)
19pendingMessages = (await config.getSteeringMessages?.()) || [];

prepareNextTurn 在每个 turn_end 之后、下一轮开始前被调用, 可以覆盖 context / model / thinkingLevel 三者之一。 例子:Turn 1 用 Haiku 开始读文件,turn_end 时发现要改的文件很多、任务变复杂了, 返回 {model: opus},下一轮自动切到更强的 Opus。返回 undefined 表示"什么都不换,按原配置继续"。

shouldStopAfterTurn 是产品层的"安全阀":外部判断上下文窗口是否快满了 (快满就停下来触发压缩),或者是否达到了最大 Turn 数限制。返回 true 就 emit agent_end 并 return——最简 Loop 不需要它。

🔑 为什么把这两个钩子做成函数而不是数据? Loop 在运行时调用它们"拉取"最新状态与决策, 把切模型、压缩、限流等产品策略与 Loop 内核彻底解耦——简单 Agent 不传这些钩子即可, 内核完全不受影响。这正是上一课「洋葱图」的落地:剥掉这层叠加,里层照样能跑。
🔎 出处:教程 §4.7 / agent-loop.ts:218-253 turn_end+钩子(同上文件)。代码为教程示意,基于 pi v0.80.2。

3 · followUp(叠加2):内层结束后才检查,靠外层循环续命

内层循环退出了——没有工具要执行,也没有紧急消息。但 coding-agent 的设计是: 此时检查一下 getFollowUpMessages(),看看系统有没有追加任务 (比如"顺便跑个测试"): 

1const followUpMessages = (await config.getFollowUpMessages?.()) || [];
2if (followUpMessages.length > 0) {
3    pendingMessages = followUpMessages;   // 塞进 pending,触发新 Turn
4    continue;                              // 回到外层循环顶部
5}
6break;  // 两个队列都空了,真正退出

如果有 followUp 消息,它们被塞进 pendingMessages,continue 回到外层循环顶部,内层循环检测到 pendingMessages 不为空, 在同一个 Trace 内继续跑。

为什么用外层循环续命,而不是重启新的 runAgentLoop()? 连续性——复用同一个 newMessages 数组和同一条事件序列, 在同一个 Trace 内继续,不需要额外合并两次运行的结果。如果重启一个全新的 Loop, 就得自己把两段独立的消息历史、事件流拼接起来,这正是"续命"比"重启"更省心的地方。
🔎 出处:教程 §4.9 / 外层 followUp 循环(同上文件)。代码为教程示意,基于 pi v0.80.2。

4 · 一张表看清两种干预

本章出现了两种"外部消息注入"机制,放在一起对比才能看清差异:

维度steering(叠加1)followUp(叠加2)
检查时机runLoop 开始前 + 内层循环每圈结尾内层循环全部结束后
语义"紧急插队"——在工具执行间隙中插入"排队等叫号"——等当前任务全部完成
典型场景用户在 Agent 工作时输入了新指令系统在 Agent 完成后追加"顺便跑个测试"
为什么检查时机差这么多? 两者语义不同——steering 是"紧急插队",必须尽快在工具执行间隙生效; followUp 是"排队等叫号",不急、要等当前任务干净收尾。时机差异直接对应语义差异, 这不是随意的工程选择,而是需求本身决定了它该被安插在哪个位置。
🔎 出处:教程 §4.10 steering vs followUp 对比表(同上文件)。
