Lesson 0008 · 第 3 章 Agent Loop

stopReason
—— 驱动循环的唯一信号灯

🎯 本课目标:上一课你认识了 Trace / Turn 这两层容器,知道一个 Turn 是「模型调用 + 工具执行」的闭环。 这节课只回答一个更具体的问题——Turn 之间到底靠什么决定「继续转」还是「停下来」? 答案挂在一个叫 stopReason 的字段上,但它没你想的那么单纯。
⏪ 先回忆上一课:一个 Turn 只有一次模型调用,模型返回后要么带着 toolCall(去执行工具、开下一个 Turn), 要么不带(准备结束这个 Trace)。上一课我们只说了「有没有 toolCall」,这节课要拆开: 这个「有没有」到底是谁在判断、判断的依据叫什么、又为什么不能完全信任它字面的值。
这节课你将能做到一件事: 说清 stopReason 的五种取值分别来自哪里、 各自什么含义,并且能反驳一个常见的误解——「循环是靠 stopReason === "toolUse" 驱动的」。
🎯 贯穿全课的类比:十字路口的信号灯,和交警的应急手势 把 stopReason 想成十字路口的信号灯——但这盏灯有个秘密:它显示的颜色一半来自真实路况 (模型 API 的 stop / toolUse / length,是路口探测器测出来的), 另一半是交警在灯坏时手动打出的应急手势(框架注入的 error / aborted, 是路况探测器本身罢工了,交警不得不出来指挥)。而司机(Loop)真正看的其实不是灯色本身, 而是「前面路上还有没有要执行的工具」——灯只是参考,不是唯一依据。

1 · 关键认知:模型不会说「我要停了」

模型只是一个 token 预测器——给定上下文,猜下一个 token,如此反复。它不「知道」任务做完了没有。 stopReason 这个字段虽然挂在模型每次返回的 AssistantMessage 上, 但它的值来自两个不同的地方:一部分是模型 API 自己上报的,另一部分是框架事后「兜底」贴上去的。

2 · 模型 API 真正返回的三种

stopReason含义
"toolUse"模型输出了工具调用 JSON,API 检测到后返回
"stop"生成自然终止(遇到了结束标记),没有工具调用
"length"token 数达到 maxTokens 上限,被截断

3 · 框架流式层注入的两种

下面两种模型 API 本身不会返回——它们发生在框架层,模型根本感知不到:

stopReason含义谁注入的
"error"调用过程异常(网络断了、API 报错等)流式层的 catch 块:output.stopReason = "error"
"aborted"用户主动中止(AbortSignal 触发)流式层的 catch 块:output.stopReason = "aborted"
 
1// packages/ai/src/ —— streamSimple 内部调用抛异常时的 catch 块
2catch (err) {
3  output.stopReason = options?.signal?.aborted ? "aborted" : "error";
4  // ↑ 这不是模型说的,是框架替它"兜底"的
5}
为什么要区分 stopReason 的两个来源? 模型 API 只能报告它自己知道的三种终止; 网络异常和用户中止发生在框架层、模型根本感知不到,所以流式层的 catch 块必须替它「兜底」注入 error / aborted,否则 Loop 无法得知这次调用其实已经失败了。

4 · 真正驱动循环的不是 stopReason 本身

这是本课最容易被误解的一点。Loop 实际上只看一件事——模型输出里有没有工具调用(且未全部 terminate)。 背后是一条人类定义的工程约定:如果模型一次输出中没有工具调用,就认为本轮不需要更多操作,循环可以停了。 换句话说:不是模型在说「我完成了」,而是我们在说「你没要工具,那就当你完成了」。 

1// 简化逻辑(实际见 agent-loop.ts:202-216)
2const toolCalls = message.content.filter(c => c.type === "toolCall");
3hasMoreToolCalls = false;
4if (toolCalls.length > 0) {
5  const executedToolBatch = await executeToolCalls(...);
6  hasMoreToolCalls = !executedToolBatch.terminate;  // 任何一个工具 terminate 则停止
7}
🔑 注意:实际驱动循环的不是 stopReason === "toolUse",而是 toolCalls 数组长度 > 0 && !terminate。这意味着:即使 stopReason === "length"(被截断),只要 content 里有 toolCall 块,循环仍会执行工具; 反之,即使 stopReason === "toolUse",如果所有工具结果都设置 terminate: true,循环也会停。 为什么用「有没有 toolCall」而不是 stopReason 本身? stopReason 是描述性的元信息,可能与实际内容脱节; 以 content 里真实的 toolCall 块为准更鲁棒,不会因元信息偏差误判。
为什么不让代码更聪明地判断「任务完成没」? 这正是 Agent 与 Workflow 的分界——Agent 模式下你无法预知步数, 唯一能稳定依赖的信号就是「输出里有没有工具调用」,用最简单的判断换取通用性,是局限也是优雅。

5 · 循环的所有退出路径

把上面两件事(stopReason 的来源、toolCall 驱动)拼起来,循环一共有四条退出路径:

退出路径触发条件原因
正常退出stop / length + 无 followUp + 无 pendingMessages最常见。模型没要工具,也没追加任务
硬停止error / aborted模型调用本身出了问题,继续跑没意义,不检查 followUp
外部钩子停shouldStopAfterTurn() 返回 true上下文快满了、达到最大 Turn 数等
工具终止一批工具的执行结果全部 terminate: true所有工具都同意停止(是 every 不是 some)
为什么工具终止用 every 而非 some? 只要有一个工具还在正常工作就不该中断,必须整批全部 terminate 才停——这是保守策略,避免单个工具的意见误杀整个循环。
stopReason 的两个来源 vs 真正驱动循环的信号 模型 API 真实路况 框架层应急手势(catch 块注入) toolUse / stop / length error / aborted │ │ └──────────┬───────────────────┘ ▼ stopReason(信号灯,仅供参考) │ │ 司机真正看的不是灯色,而是—— ▼ content 里有没有 toolCall 块 && !terminate │ ┌───────────┴───────────┐ ▼ ▼ 有 → 继续转下一个 Turn 无/全 terminate → 准备停 / 硬停止
